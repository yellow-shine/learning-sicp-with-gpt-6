## 1. 问题不是怎样存两个整数，而是谁可以知道存法

如果每个业务过程都直接用 `car` 当分子、`cdr` 当分母，那么“改用另一种表示”就是全程序搜索替换。数据抽象让上层依赖**数学约定**而不是偶然的内存布局。

```text
使用有理数的程序
    add-rat / sub-rat / mul-rat / div-rat / equal-rat?
---------------- 算术接口 ----------------
    make-rat / numer / denom
---------------- 表示接口 ----------------
    cons / car / cdr，或一组过程
```

每道横线都是约束依赖的屏障，不是运行时自动执行的隔离墙。Go 中“不导出 struct 字段，只导出构造器和方法”有相似目的；这里先用编程纪律实现，不需要造一个类层次。

给定整数 `n` 和非零整数 `d`，若 `r = (make-rat n d)`，必须满足：

```text
numer(r) / denom(r) = n / d
```

并不要求 `numer(r)=n`：`2/4` 完全可以存成 `1/2`。数据由**构造器、选择器和它们必须满足的关系**共同定义，只有名字没有关系还不够。

## 2. 先写使用者，再决定表示

依靠尚未实现的接口，已经能写加法：

```scheme
(define (add-rat x y)
  (make-rat (+ (* (numer x) (denom y))
               (* (numer y) (denom x)))
            (* (denom x) (denom y))))
```

同理，减法把交叉乘积相减；乘法分别乘分子、分母；除法把第二个数倒过来乘。相等判断用交叉乘积，不能用 pair 身份 `eq?`。

```text
1/2 + 1/3
→ make-rat(1×3 + 1×2, 2×3)
→ make-rat(5, 6)
→ 表示为 (5 . 6)
```

算法知道有分子与分母，但不知道它们由哪个槽保存。`print-rat` 这样的展示过程也应调用选择器，而不是为了方便越过屏障。

## 3. 习题 2.1：规范化正负号

**题意概述**：改进 `make-rat`，正数的分子分母都为正，负数只让分子为负。

完整策略：

1. 要求 `n,d` 为精确整数且 `d≠0`。
2. `g = gcd(|n|, |d|)`，所以 `g>0`。
3. 令 `s` 为分母的符号：`d<0` 时 `s=-1`，否则 `s=1`。
4. 保存 `(s×n/g, |d|/g)`。

```scheme
(let ((g (gcd (abs n) (abs d)))
      (sign (if (< d 0) -1 1)))
  (cons (* sign (/ n g)) (/ (abs d) g)))
```

前置检查在文件中的 `make-rat` 内，不能省略后让 `(0,0)` 落入 `gcd=0`。四个符号组合的结果是：

| 输入 | 保存结果 |
| --- | --- |
| `2,4` | `(1 . 2)` |
| `-2,4` | `(-1 . 2)` |
| `2,-4` | `(-1 . 2)` |
| `-2,-4` | `(1 . 2)` |
| `0,-7` | `(0 . 1)` |

分母始终正且既约，因此零也唯一化为 `0/1`。`div-rat` 除以一个零有理数时，会把零送到结果构造器的分母位置；同一边界检查拒绝它，不必让每个调用者各自修补。

这里的“有理数包”与 Racket 原生精确数 `1/2` 不同：我们的值是自定义 pair，用于学习表示屏障。拒绝 `1.0`、`1/2` 作为分子，是为了保持此包的**精确整数分子/分母**约定，不是否认它们有数值意义。

### 在哪里约分，是成本决策

- 构造时约分：每次构造做一次 GCD，选择器很便宜。
- 选择时约分：构造便宜，但反复选分子、分母会反复求 GCD。

两者都能满足抽象关系。上层算术不应因这个决定而变化。规范化更方便比较和展示，但它不是数据抽象的定义本身。

## 4. 习题 2.4：pair 可以是一个等待选择规则的过程

**题意概述**：已知下面的过程表示，证明 `car(cons(x,y))=x`，并补全 `cdr`。

文件使用 `proc-` 前缀，避免遮盖语言原生 pair 操作：

```scheme
(define (proc-cons x y) (lambda (m) (m x y)))
(define (proc-car z) (z (lambda (p q) p)))
(define (proc-cdr z) (z (lambda (p q) q)))
```

代换证明把“选择器本身是过程”看清楚：

```text
(proc-car (proc-cons x y))
→ ((lambda (m) (m x y)) (lambda (p q) p))
→ ((lambda (p q) p) x y)
→ x

(proc-cdr (proc-cons x y))
→ ((lambda (m) (m x y)) (lambda (p q) q))
→ ((lambda (p q) q) x y)
→ y
```

`x,y` 可以是任意对象，包括列表和过程，不限于整数。构造出来的 `z` 是保留 `x,y` 绑定的词法闭包，参数 `m` 告诉它如何使用这两个值。这里不声称 Scheme 的原生 pair 真用这种方式实现；我们证明的是**只经这三个接口观察时**，它满足 pair 的约定。若客户调用原生 `pair?` 或依赖打印布局，已经越过屏障，不能再保证表示不可区分。

文件中的 `procedural-rat-example` 在局部换掉构造和选择表示，保留同一段加法过程体，实际得到 `(5 6)`。这不是拿预设的 `5/6` 当结果，而是用过程 pair 完成选择、交叉相乘与重建。

- **抽象屏障保护什么？** 保护上层免于依赖表示，不自动保证所有代码都守纪律。
- **pair 一定是两个槽吗？** 不一定；上述构造选择关系比槽的具体形状更根本。
- **规范化会改数学值吗？** 不会，只改变等价值的存法和操作成本。
