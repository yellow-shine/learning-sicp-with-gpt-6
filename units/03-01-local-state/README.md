## 从“计算一个值”到“响应一次事件”

纯过程 `(+ 10 5)` 的答案只依赖输入。账户的 `(withdraw 10)` 却依赖之前存取过多少钱。可以每次显式传入余额并返回新余额，也可以让对象保存余额：

```scheme
(define (make-accumulator sum)
  (lambda (amount)
    (set! sum (+ sum amount))
    sum))
```

`define` 建立绑定；`set!` 修改已有绑定的值，不建立新的局部变量。最后单独写 `sum` 是必要的：不依赖 `set!` 的返回值。返回的过程携带对那个绑定的访问能力，创建过程的调用虽然结束，绑定仍然活着。Go 的捕获变量闭包可作类比，但这里先用 Scheme 的环境规则解释。

封装状态有实际好处：用户只说“加入 10”，不用在每一层传递累加结果。账户、随机数生成器、仿真导线都能用相同的模块化办法。但这样的调用不再是“随时可用其结果替换”的表达式。

## 3.1：独立的累加器

**题意**：构造一个接受初值的工厂，每次调用产物时把输入加入总和，返回新总和；多个产物互不影响。上面的过程就是解答。

```text
A = make-accumulator(5) ──→ 槽 sum_A = 5
B = make-accumulator(5) ──→ 槽 sum_B = 5
A(10): sum_A ← 15，返回 15
A(10): sum_A ← 25，返回 25
B(0):  sum_B 仍为 5，返回 5
A(-30): sum_A ← -5
```

每次调用工厂才分配独立状态；`(define alias A)` 只给同一个过程另取名字，不再调用工厂。代码还用两个独立账户和一个别名验证这个区别。账户例子限制提款非负且不超余额，失败不会改变余额；累加器允许负数，因为“累加”没有提款的业务约束。

**值相等不是身份相同**：两个余额都是 100 的账户可能相互独立；两个名字也可能指向同一个账户。过程的 `equal?` 不是业务身份协议；我们通过一个引用写入、另一个引用读出来观察共享状态。

## 3.8：参数顺序变成可观察行为

**题意**：设计 `f`，使 `(+ (f 0) (f 1))` 在左先求值时得 0，右先时得 1。

```scheme
(define (make-f)
  (let ((state 1))
    (lambda (x)
      (set! state (* state x))
      state)))
(define f (make-f))
```

| 顺序（各从新的 state=1 开始） | 第一次调用 | 第二次调用 | 和 |
| --- | --- | --- | --- |
| 左→右 | `f(0)`：state=0，返回0 | `f(1)`：state=0，返回0 | 0 |
| 右→左 | `f(1)`：state=1，返回1 | `f(0)`：state=0，返回0 | 1 |

不能先跑左序，再在同一个 `f` 上跑右序：此时初值已经变了。自检用新工厂产物和 `let*` 显式固定两个次序，不把 Racket 恰好采用的操作数顺序说成所有 Scheme 的保证。普通调用“先算参数”没有规定参数之间的统一左右顺序。

## 为什么随机过程也适合局部状态

代码的小生成器采用 `x_next = (5x+1) mod 16`，从 1 开始输出 `6,15,12,…`。这是确定的状态转移，不是物理随机，更不用于密码学。工厂把种子隐藏起来；同种子的两个对象能重复同样的序列，互不推进对方。

也可直接调用纯函数 `rand-update`，由调用者传递种子。隐式状态简化接口，显式状态方便复现和组合；蒙特卡洛把大量试验的命中比例作为估计时，仍需讨论样本、误差和生成器质量，不能因“有 random 接口”就断言试验独立。

## 代价：代换不再足够

把 `(A 10)` 一律替换成第一次的结果 15，会抹去更新以及第二次得到 25 的事实。这就是失去引用透明性。两个程序是否“相同”必须考虑调用历史、别名和观察方式。赋值还引入时间顺序，随后第三章的共享结构、并发与流都会受其影响。

不要把所有问题都改成对象：不需要历史的数学变换继续用纯过程最简单。反过来，也不必为了纯粹而让每个调用层手动搬运一个真正属于对象的局部状态。
