## 1. 问题：不是一串答案，而是产生答案的机制

如果先算完全部证明再返回一个列表，就无法从无限答案中取有限前缀；若盲目递归，甚至一个已知事实也可能被其他无限分支挡住。查询系统因此返回**延迟的框架流**。

本单元复用 04.05 的真实查询核心，不另造一组手写答案。核心将宿主 cons-stream 用作结果流；它不同于 04.03 对象语言中的过程表示惰性表，也不同于 04.04 的 success/failure 接口。它们保存的延后工作相关，但具体表示不同。

## 2. 实现的逐层接口

```text
被引用的查询 S 表达式
  → qeval(query, frame-stream, ancestor-history)
       ├─ and：把前一子查询的框架流交给后一子查询
       ├─ or：从同一输入流分别求解，再交错结果
       ├─ not / lisp-value：逐框架筛选
       └─ simple：逐框架处理
             ├─ pattern-match 所有候选事实
             └─ 延迟应用规则：freshen → unify → qeval(rule-body)
  → instantiate 原查询
  → 有限 stream-take
```

`singleton '()` 是一个“尚无绑定”的成功状态；空流才是没有证明。匹配失败用独立符号 `failed` 表示，再转成空流，避免把合法的空框架误判为失败。

与 textbook 相比有几个刻意简化：

- 变量保留 `?` 开头的符号，不做 reader 后的 `(? name)` 表示转换；重命名用宿主 gensym，保证两次规则应用不撞名。
- qeval 使用显式 cond 分派，没有额外数据导向表；要增加特殊查询形式需修改这一处。
- 事实和规则保存在流中，**线性扫描而不建索引**。小型教学库足够；数据库变大时可按关系名建索引，规则结论首项为变量的通配规则也必须纳入候选，不能被索引漏掉。
- 每个查询捕获当前事实/规则流头作为快照，后续添加不改变已经启动的查询。这是本实现的明确约定，教材原始各次 fetch 读取全局库的做法不自动提供相同快照保证。
- 查询携带独立步骤预算，预算耗尽抛出异常，不当成逻辑失败。合法查询仍可超过预算；可在构造器调高数值，不声称预算是终止判定。

没有宿主 eval。有限的宿主谓词白名单负责 lisp-value，详见上一单元。

## 3. 一个亲属查询从空框架走到答案

事实：Ada→Bob、Bob→Cora、Ada→Dan。规则：

```scheme
(rule (ancestor ?x ?y)
      (or (parent ?x ?y)
          (and (parent ?x ?z)
               (ancestor ?z ?y))))
```

查询 `(ancestor Ada ?child)`：

1. 初始框架 F0={}。
2. 本次规则变量变成 ?x₁/?y₁/?z₁；与查询合一得到 ?x₁→Ada，?child→?y₁。
3. 直接 parent 分支可生成 ?y₁→Dan、?y₁→Bob。
4. 递归分支某个框架有 ?z₁→Bob；再次应用 ancestor 时产生独立 ?x₂/?y₂/?z₂，与 `(ancestor Bob ?y₁)` 合一，不能复用第一次的 ?x₁。
5. `(parent Bob Cora)` 得 ?y₂→Cora，沿别名链使原 ?child 实例化为 Cora。

```text
F0 {}
 ├─ 直接事实 → {child=Dan}
 ├─ 直接事实 → {child=Bob}
 └─ parent(Ada,Bob) → ancestor(Bob,child) → {child=Cora}
```

这是逻辑树，不规定打印顺序。由于头插事实与交错分支，实际输出顺序为 **Dan、Cora、Bob**。反向查询 `(ancestor ?who Cora)` 得 Bob、Ada，也实际运行验证。

### 为什么重命名必须发生在每次规则应用？

若第二次直接沿用 ?x₁，第一层已把它绑定成 Ada，第二层又要求它是 Bob，就会错误失败。简单地“先清空框架”更不行，那会丢掉原查询的已有约束。freshen 保持一次应用内部的同名变量一致，同时隔离不同应用的局部变量。

实现还运行两个 append-to-form 规则：

```scheme
(rule (append-to-form () ?y ?y))
(rule (append-to-form (?u . ?v) ?y (?u . ?z))
      (append-to-form ?v ?y ?z))
```

查询 `(append-to-form ?left ?right (a b))` 得三种分割：`()/ (a b)`、`(a)/(b)`、`(a b)/()`。本实现实际顺序为第三种、第一种、第二种，来自规则头插及交错，不能把答案顺序当作关系本身的一部分。

## 4. 为什么 delay 要包住“整个分支”

`append-delayed(fact-answers, delay(rule-answers))` 先返回已找到的事实，等事实流耗尽才求规则部分。如果仅仅使用一个内部延迟尾部的流构造器，但在调用 append 之前就先执行 `apply-rules`，构造规则流头时仍可能陷入递归，连现成事实也看不到。

or 与 stream-flatmap 使用 interleave-delayed：每输出一个答案，交换两边的角色。若左侧是能持续产出自然数的无限流，右侧只有 `(marker done)`，简单 append 永远到不了右侧；交错则让 marker 成为第二条答案，自检验证这一点。

然而这种公平性有条件：被强迫的一方必须在有限时间内返回流头或空流。若求一个流头本身不终止，宿主不会抢占它去跑另一分支。交错不是线程调度器，更不是对任意无限搜索树的完备公平搜索。

`stream-take` 在取得第 n 项后**不再强迫第 n+1 项**，否则“只要一个已知答案”也可能因为多取一项而卡住。流中的重复证明不会被自动去重，memoization 缓存的是尾部计算，不是答案集合。

## 5. 习题 4.67：可执行的祖先目标去环启发式

**题意概述**：保存当前推导链的历史，避免开始处理已经在处理的查询；说明需要什么模式/框架信息以及如何比较。

### 不能只比较源码名字

规则每次 freshen 后变量名不同，`(same ?x₁ ?y₁)` 与 `(same ?x₂ ?y₂)` 可能是同一类未推进目标。如果只比较名字，就漏掉最简单循环。反之若只记关系名 ancestor，就会把 `(ancestor Ada ?y)` 与 `(ancestor Bob ?y)` 混同，剪掉真正有进展的递归。

本实现的历史键是 **当前目标在当前框架下实例化后，未绑定变量按首次出现顺序规范化的结构**：

```text
p(?x, ?x, ?y) → p(V0, V0, V1)
p(?a, ?a, ?b) → p(V0, V0, V1)  相同
p(?a, ?b, ?b) → p(V0, V1, V1)  不同
p(?x), x=a   → p(a)
p(?x), x=b   → p(b)              不同
```

先沿框架追别名，再规范化，所以间接绑定也参与比较。内部 V 标记带不可由普通 reader 数据伪造的 gensym 标签。名字编号使用显式先 car 后 cdr 的顺序，避免宿主参数顺序影响历史键。

历史不保存整个可变环境或全局“访问过”集合，而是不可变的**当前祖先链**。应用规则体时把当前简单目标的 key 压入历史；同层其他独立分支仍用原历史。若 key 已在这条链上，剪掉这个重复目标。本实现对普通正关系的相关绑定作键，没有把整条剩余合取和所有外部约束都作为状态，因此刻意称为启发式。

### 可以挡住什么？

- `(same a b)` → `(same b a)` → `(same a b)` 的互换循环。
- 4.64 错误规则中反复出现的、变量仅重命名的 outranked-by 目标。

开启检测后，4.64 查询返回 Warbucks 后可以结束。自检实际对比未检测版本的预算耗尽和检测版本的有限结果。

### 不能保证什么？给出真正的反例

规则：

```scheme
(nat z)
(rule (nat (s ?n)) (nat ?n))
```

对 `(nat ?n)`，不剪枝的流会产生 `z、(s z)、(s (s z))…`；递归分支虽再次遇到“nat 加一个未绑定变量”的变体，但调用者已经在构造更大的输出。祖先变体剪枝会把这种**有产出的递归**也剪掉，检测版本只返回 z。

代码同时运行这两个版本，断言检测版本损失答案。这不是一个留在文字里的免责声明：我们明确展示它不完备。

另外，结构不断增长的目标可能永不重复，因此本启发式也会漏检循环；步骤预算只把运行截断成错误。若需要更强的正逻辑递归处理，应考虑 tabling/固定点答案传播，而不是把历史集合扩大后宣称解决停机问题。not 加上不完备剪枝还可能把“被剪掉的证明”当成“找不到证明”，所以不把检测模式下含否定的结果宣传为完整逻辑推论。

## 6. 习题 4.70：let 保存旧流，防止尾部追着新全局变量走

**题意概述**：为什么 add-assertion! 与 add-rule! 先 let 绑定旧流？直接在 cons-stream 尾部引用被 set! 的全局变量有什么错？

正确形式：

```scheme
(let ((old-assertions THE-ASSERTIONS))
  (set! THE-ASSERTIONS
        (cons-stream assertion old-assertions)))
```

let 的初始化立即取到**旧流对象**；延迟尾部闭包以后读取的是不会再赋值的局部 old-assertions。它没有复制整张数据库，只是保存原流头引用。

错误形式：

```scheme
(set! THE-ASSERTIONS
      (cons-stream assertion THE-ASSERTIONS))
```

其时间顺序是：

```text
原 THE-ASSERTIONS → old-stream
建立 N = (assertion . promise(读取 THE-ASSERTIONS))
set! THE-ASSERTIONS → N
稍后 force N.tail → 读取当前 THE-ASSERTIONS → N
```

在期间没有再次添加的通常场景中，结果是 assertion 无限重复，旧库从这条链上不可达；不是“新事实没添加”，也不是普通的“读到了旧快照”。若旧流仍被其他变量引用，它并没有从内存世界中消失，只是新全局链不再连接它。

**细节不能省略**：如果 N 的尾还没强迫，就又把全局变量改成另一个新头 M，那么强迫 N.tail 会读到 M，而不一定是 N。自检先加 a、保存 a 头，再加 b、才强迫旧头，得到 `(a b b b)`。这取决于首次强迫时变量指向哪里；尾 promise 一旦记忆化，就保留那次读出的对象，以后的全局赋值不会自动改写已缓存尾。

程序运行三个有限前缀作为证据：

| 方式 | 取得的前缀 |
| --- | --- |
| 错误插入 new 后立即遍历 | `(new new new new)` |
| 错误插入 a，插入 b 后才遍历旧 a | `(a b b b)` |
| let 保存旧 `(old)`，正确插入 new | `(new old)` |

规则流完全同理。索引桶如果也用延迟尾连接原桶，就同样需要捕获旧桶引用；不能只修全局流而保留有自引用问题的索引。
