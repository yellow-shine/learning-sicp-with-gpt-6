## 1. 为什么看到自调用还不能判断空间复杂度？

源代码中的**递归过程定义**，指过程直接或间接调用自身；运行中的**递归计算过程**，指不断积累等待子计算结束后才能完成的工作。这两个“递归”说的是不同层次。

以 `4!` 为例，第一种写法返回 `(* n (fact (- n 1)))`：

```text
fact(4)
→ 4 × fact(3)
→ 4 × (3 × fact(2))
→ 4 × (3 × (2 × fact(1)))
→ 4 × (3 × (2 × (1 × fact(0))))
→ 4 × (3 × (2 × (1 × 1)))
→ 4 × (3 × (2 × 1)) → 4 × (3 × 2) → 4 × 6 → 24
```

展开时保存“还要乘 4、乘 3、乘 2……”，收缩时完成乘法。文件中的版本把 `0!=1` 也纳入基例。

另一种写法只保存 `(product,counter,n)`：

```text
(1,1,4) → (1,2,4) → (2,3,4) → (6,4,4) → (24,5,4) → 24
```

不变量是进入状态时 `product=(counter-1)!`。每一步只更新有限个状态变量；最后一次调用的返回值就是整个过程的返回值，调用后没有待完成的乘法。这是**尾调用**，产生线性迭代过程。

Scheme 保证正确的尾调用空间行为：这种控制状态不随调用次数增长。Go 的自调用写法不能直接获得同一保证；Go 中通常要用循环表达这种常量控制空间。也不要把“尾调用优化”解释成仅某个编译器碰巧做的可选技巧。

## 2. 习题 1.9：同一个加法，两种形状

**题意概述**：原题用 `inc` 和 `dec` 定义两种加法；按代换模型展开 `(+ 4 5)`，判断计算过程类别。代码改名为 `add-recursive` 和 `add-iterative`，不覆盖内建 `+`。

### 第一种：回来以后还要 inc

```scheme
(if (= a 0) b (inc (add (dec a) b)))
```

```text
add(4,5)
→ inc(add(3,5))
→ inc(inc(add(2,5)))
→ inc(inc(inc(add(1,5))))
→ inc(inc(inc(inc(add(0,5)))))
→ inc(inc(inc(inc(5))))
→ inc(inc(inc(6))) → inc(inc(7)) → inc(8) → 9
```

`dec` 在下降时执行；`inc` 被推迟到递归调用返回之后。时间 Θ(a)，待完成工作空间 Θ(a)。这不是因为名字里有 recursive，而是因为存在那串 `inc`。

### 第二种：把工作写进状态

```scheme
(if (= a 0) b (iter (dec a) (inc b)))
```

```text
(4,5) → (3,6) → (2,7) → (1,8) → (0,9) → 9
```

每步的 `a+b` 不变，每步 `a` 减一，直到变为零，所以最终 `b` 就是初始和。时间 Θ(a)，控制空间 Θ(1)。两段代码都自调用，但只有第一段生成线性递归计算过程。

本题原域是正整数；实现自然扩展到非负整数，`a=0` 立即返回 `b`。负 `a` 会越减越远，故入口拒绝；这不是用“尾调用所以没问题”掩盖不终止。

## 3. 树形递归：节点数不是树高

朴素 Fibonacci 的式子 `fib(n)=fib(n-1)+fib(n-2)` 直接产生计算树：

```text
                 fib(5)
              /          \
           fib(4)        fib(3)
          /      \       /    \
       fib(3)  fib(2)  fib(2) fib(1)
       /   \    /  \    /  \
    fib(2) ... 1    0   1    0
```

相同下标的子问题反复出现，但普通递归不会自动记忆结果。时间看总节点数，Θ(φⁿ)，`φ≈1.618`；深度优先运行时并不同时保存整棵树，只保存当前路径的待完成工作，空间 Θ(n)。说“二叉树所以 Θ(2ⁿ)”只给了较松上界，不是紧确增长阶。

把状态改为 `(a,b)=(Fib(k+1),Fib(k))`，同时更新为 `(a+b,a)`，就能线性时间、常量个数值寄存器地计算。这里“同时”指新值都由旧值算出，不是先赋 `a=a+b` 再用新 `a` 赋给 `b`。

树形递归不是坏东西。零钱计数把解分成两个互斥且完备的集合：不用当前面额；至少用一枚当前面额（扣除一枚后还可继续用）。所以

```text
cc(amount,coins)
 = cc(amount,rest-coins)
 + cc(amount-first-coin,coins)
```

`amount=0` 有一种办法，即不再取硬币；负金额或没有硬币且金额非零为零种。自检对美国五种面额算出 `count-change(100)=292`。这种树形结构让“没有漏算/重算排列”的理由直接写在程序里；是否值得改成记忆化或动态规划，要看需求，不以“树形递归必然指数级”代替分析。

## 4. 习题 1.11：从三项递推到状态机器

**题意概述**：整数 `n<3` 时 `f(n)=n`，`n≥3` 时

```text
f(n)=f(n-1)+2f(n-2)+3f(n-3)。
```

分别给出递归计算过程和迭代计算过程。原版 HTML 的 `≥` 用带下划线的 `>` 表示，不能把纯文本抽取后的 `n>3` 当成遗漏 `n=3` 的定义。

### 递归答案

直接把分段定义写成 `if`，非基例发起三次递归调用：

```scheme
(define (f n)
  (if (< n 3)
      n
      (+ (f (- n 1))
         (* 2 (f (- n 2)))
         (* 3 (f (- n 3))))))
```

例如：

```text
f(4) = f(3) + 2f(2) + 3f(1)
     = [f(2)+2f(1)+3f(0)] + 2×2 + 3×1
     = [2+2+0] + 4 + 3 = 11。
```

### 迭代答案与不变量证明

当前最高下标是 `k`，保存 `a=f(k), b=f(k-1), c=f(k-2)`：

```scheme
(define (iter a b c k)
  (if (= k n)
      a
      (iter (+ a (* 2 b) (* 3 c)) a b (+ k 1))))
```

`n<3` 直接返回 `n`；否则从 `(2,1,0,2)` 开始。

| k | a=f(k) | b=f(k-1) | c=f(k-2) |
| --- | --- | --- | --- |
| 2 | 2 | 1 | 0 |
| 3 | 4 | 2 | 1 |
| 4 | 11 | 4 | 2 |
| 5 | 25 | 11 | 4 |
| 6 | 59 | 25 | 11 |

初始三个基例满足不变量；递推公式算出 `f(k+1)`，其余两个值右移，故更新保持不变量；到 `k=n` 返回 `a` 就正确。下降到基例和上升到目标是两种不同执行方向，不意味着两套数学定义。

### 正确的成本结论

- 递归版的**调用次数**满足 `T(n)=T(n-1)+T(n-2)+T(n-3)+Θ(1)`。系数 2、3 只是乘法，不代表把第二、第三项调用两次、三次。因此时间 Θ(αⁿ)，其中 `α≈1.839286` 是 `α³=α²+α+1` 的正实根；空间 Θ(n)。`O(3ⁿ)` 可以作上界，但不能写成紧确 `Θ(3ⁿ)`。
- 迭代版每个下标只计算一次，时间 Θ(n)，常量个状态变量、Θ(1) 控制空间。
- `f(n)` 的数值增长满足另一条带 2、3 系数的方程；不要把**答案增长**与**调用次数增长**混为一谈。

## 5. 增长阶的模型边界

Θ(g(n)) 表示充分大的 n 上，资源数同时被 g(n) 的正常数倍上下夹住；O 只要求上界，Ω 只要求下界。必须先说明 n 是什么。本节 n 是数值输入/递推下标，不是它的二进制位数。

| 过程 | 单位成本时间 | 控制/数值寄存器个数的空间 |
| --- | --- | --- |
| 递归阶乘 | Θ(n) | Θ(n) |
| 迭代阶乘 | Θ(n) | Θ(1) |
| 树形 Fibonacci | Θ(φⁿ) | Θ(n) |
| 迭代 Fibonacci | Θ(n) | Θ(1) |
| 1.11 递归版 | Θ(αⁿ) | Θ(n) |
| 1.11 迭代版 | Θ(n) | Θ(1) |

这里把一次算术当作单位成本。Racket 精确整数会增长，例如 `n!` 本身需要 Θ(n log n) 位，所以“常量空间”不是宣称任意大的答案都放得进固定字节。大整数乘加的位成本也没有包含在此表中。实测耗时还包含解释/编译、运行时与硬件因素，不能由一个小例子的秒数证明渐近界。
