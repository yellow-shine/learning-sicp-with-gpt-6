## 1. 问题：未使用的参数为什么要计算？

对象程序 `((lambda (x y) x) 7 (/ 1 0))` 在应用序求值器中先算参数，因此报除零。在本单元惰性求值器中得到 7，y 始终没有被需要。

这不是把宿主 Racket 切换成惰性模式。宿主仍用应用序执行 `lazy-evaluator.rkt`；对象程序只是传给它的引用数据：

```scheme
(define need (make-lazy-evaluator #t))
(need 'actual '((lambda (x y) x) 7 (/ 1 0))) ; 7
```

`#t` 表示缓存 thunk；`#f` 表示不缓存。'actual/'eval 是宿主侧访问接口，不是新增的对象语言语法。

## 2. 三个名字不能混叫

- **应用序**：先取得实参值再进复合过程体。
- **按名调用**：保存实参表达式，需要时重算，重复需要可能重复副作用。
- **按需调用**：也是延迟，但同一个 thunk 的所有使用共享第一次算出的值。

第一章的正则序代换模型强调先展开、再归约；这里给出具体环境式延迟机制。它们相关，但不要拿“不提前求值”一句话抹平表达式共享、变量位置和副作用的区别。

## 3. 哪一层需要改？

`lazy-eval` 对应用不再调用 `list-of-values`，而是把**原操作数表达式及调用者环境**交给 `lazy-apply`：

```text
应用 (f argument)
  actual-value(f, caller-env) → 取得真正过程，不能拿 thunk 当过程
  ├─ primitive：actual-value(argument, caller-env) → 宿主 primitive
  └─ compound：构造 thunk(argument, caller-env)
                → 绑定到形参
                → 在闭包环境扩展出的新框架中运行过程体
```

必须区分两个环境：thunk 保存 **实参出现处的环境**，复合过程本体使用 **闭包定义时的环境**。保存源码却漏掉环境，会让自由变量错绑到强迫发生的位置。

`actual-value` 的定义是 `force-it(lazy-eval(...))`。强迫点包括 primitive 的参数、if 的谓词、应用的操作符，以及驱动接口要显示最终答案的位置。define 和 set! 的右侧仍使用 lazy-eval，可能把 thunk 存入变量；变量查找也可能只返回 thunk。

序列沿用教材原版规则：非最后一项只调用 lazy-eval，不一律强迫。显式执行 set! 仍有副作用，但若某项只返回一个被丢弃的 thunk，其内部副作用可能永远不发生。这不是承诺所有命令式程序在惰性模式下保持原行为。

## 4. thunk 的状态转换

```text
未强迫：(thunk 表达式 环境)
               │ force-it → actual-value（递归追到底）
               ▼
已强迫：(evaluated-thunk 值)
```

按需版本原地改标签与内容，并删除不再需要的环境引用；所有别名仍指向同一个 pair，因而都看到缓存值。按名版本不修改 thunk，下一次强迫重新解释保存的表达式。

这使用宿主可变 pair 实现，但 **不是**靠宿主 `delay` 偷代所有对象语言语义：什么地方构造 thunk、保存哪个环境、什么地方强迫，都是我们写的对象求值规则。环境是引用而不是值快照；若强迫前环境内变量改变，thunk 会读到那时的值。记忆化又会把第一次成功强迫的结果固定下来。

本实现没有黑洞检测；自我强迫而无法产出值的递归仍可能不终止。自检不启动这样的程序。按需也可能因为仍可达的闭包、thunk 或惰性表前缀保留大量内存，不能笼统声称它总比应用序省空间。

## 5. 习题 4.27：为什么 count 先是 1，后来是 2？

**题意概述**：在教材的缓存惰性求值器中，id 每次进入过程体时把 count 加一，之后返回 x；定义 w 为嵌套 id 调用，再依次读取 count、w、count。

对象定义：

```scheme
(define count 0)
(define (id x) (set! count (+ count 1)) x)
(define w (id (id 10)))
```

完整轨迹：

1. 定义 w 的右侧调用**外层 id**。进入其过程体，count 从 0 到 1。
2. 形参 x 的值是 T1=`thunk((id 10), 全局环境)`。过程体返回 x，lazy-eval 不强迫 T1，w 存入 T1。
3. 读取 count：它是普通数字，输出 **1**。
4. 要显示 w，actual-value 强迫 T1，执行**内层 id**，count 从 1 到 2。
5. 内层返回 T2=`thunk(10, 全局环境)`；actual-value 继续强迫成 10。T2、T1 都记住 10。
6. w 输出 **10**；再读 count 输出 **2**。

| 输入 | 输出 |
| --- | ---: |
| count（定义 w 后） | 1 |
| w | 10 |
| count | 2 |

重复读 w 不会第三次进入 id。不能说“define 都不求右侧”，也不能说“define 会强迫整个右侧到最终值”：教材这里恰好在两者之间，调用外层过程但返回内部 thunk。

## 6. 习题 4.29：缓存既影响成本，也影响副作用

**题意概述**：给出没有记忆化会慢很多的程序；分别说明 `(square (id 10))` 在缓存/不缓存模式下的返回值和 count。

```scheme
(define (square x) (* x x))
```

count 重新从 0 开始：

| 策略 | square 的结果 | count | 理由 |
| --- | ---: | ---: | --- |
| 按需 | 100 | 1 | 第一个 x 强迫 id；第二个 x 复用同一 thunk 的值 |
| 按名 | 100 | 2 | primitive `*` 的两个参数分别强迫同一未缓存 thunk |

更显著的差距不需要依赖墙钟噪声：

```scheme
(define (twice x) (+ x x))
(define (grow n)
  (if (= n 0)
      (id 1)
      (twice (grow (- n 1)))))
```

求 `(grow 10)`，两者结果均为 1024。按名时一个递归结果被需要两次，又各自需要下层两次，产生 `2^10=1024` 次叶子 id；按需时每层参数结果共享，叶子 id 只执行 **1** 次。自检运行真实求值器并读取 count，绝非用预计常量替换 grow。这个计数证明了叶子工作量指数差距；它不是所有宿主操作的精确总计，按名还会重复强迫 n 的表达式链。

因此纯表达式时缓存常常保留值而节约工作，副作用存在时却会改变行为。不能把缓存当成对任何语言程序都不可观察的优化。

## 7. 惰性表：连表头也可以不计算

在对象语言中覆盖 cons/car/cdr：

```scheme
(define (cons x y) (lambda (m) (m x y)))
(define (car z) (z (lambda (p q) p)))
(define (cdr z) (z (lambda (p q) q)))
```

它们都是对象语言复合过程，所以 x、y 都延迟。`(cons (/ 1 0) (cons 8 '()))` 可以形成一个闭包而不除零；取它的 cdr，再取该尾部的 car，只需要 8，最初表头仍未计算。第三章 cons-stream 通常立即计算头、延迟尾；本节两边都延迟。

运行中的无限整数表由 `(integers-from 1)` 递归构造；`(list-ref integers 17)` 只走有限前缀，输出 18。代码也检验 `(car (cons 7 (/ 1 0)))` 返回 7，说明无用的尾部不计算。

**表示陷阱**：quote 返回的 `'(a b)` 仍是宿主 reader 的 pair，不是上述过程 pair。对象 car 试图把它当过程调用，会报错，自检明确捕获。我们没有选做把 quote 改造为惰性表的 4.33；所以示例只以 cons 建立非空惰性表，以空引用表作为结束标记。不提供无限表的通用打印器，接口只取有限位置或有限值。
