# 05.04 显式控制求值器：尾递归由谁保证

[返回全书路线](../../README.md) · [可运行题解](solutions.rkt) · [控制器](evaluator.rkt) · [语法与环境操作](runtime.rkt)

- **教材**：[§5.4.1–5.4.4][source]，习题 **5.26(a)(b)、5.27**。
- **前置**：05.02 的模拟器、04.01 的 eval/apply 与词法环境。
- **问题**：元循环求值器借宿主递归保存待完成工作，也借宿主获得尾调用性质。把这些隐含动作写成机器指令，才能确切说明“为什么栈不会一直长”。

## 1. 求值器是一段控制器，不是一条巨大的 eval 原语

`evaluator.rkt` 的 `eval-dispatch` 按表达式种类跳转。每个分支只做有限的语法选择、寄存器赋值和后续跳转。递归求值子表达式通过 `goto eval-dispatch` 实现；`runtime.rkt` 没有递归解释复合表达式的宿主 eval。

| 寄存器 | 当前职责 |
| --- | --- |
| exp | 要求值的表达式，已经由 Scheme reader 读成数据 |
| env | 当前词法环境（框架链） |
| val | 子表达式的结果 |
| continue | val 算好后应跳到的位置 |
| proc | 已经求出的操作符过程对象 |
| argl | 已求值的实际参数表 |
| unev | 尚未求值的操作数/过程体等语法片段 |

核心约定是：进入 eval-dispatch 时给定 exp、env、continue，离开时 val 为结果并跳到 continue。原子、变量、quote 和 lambda 不需递归求子表达式。lambda 建立 `(参数,过程体,定义环境)` 的闭包；应用时扩展的是**定义环境**，不是调用者碰巧所在的环境。

例如 `(((lambda (x) (lambda (y) (+ x y))) 8) 3)` 得 11。返回的内层过程仍指向保存 x=8 的框架，即使外层调用已经结束。机器显式处理的是控制栈，词法闭包的存活则由堆上的环境对象决定，不可混称为同一种“栈帧”。

## 2. 一次应用怎样拆成微小步骤

以 `(f (+ 1 2) 4)` 为例：

```text
ev-application:
  save continue, env, unev（原操作数表）
  exp←f；continue←ev-appl-did-operator；goto eval-dispatch
返回：proc←f的过程值，argl←()
  save proc
求第一个参数 (+ 1 2)：save argl, env, unev，再进入 eval-dispatch
返回：恢复参数处理状态，argl←(3)
求最后参数4：只save argl；返回后argl←(3 4)，restore proc
apply-dispatch：原语直接应用；复合过程则扩展词法环境，跳 ev-sequence
```

本控制器明确从左到右求参数，因为 first-operand=car、rest-operands=cdr。不是所有 Scheme 实现都必须用这个顺序。宿主 `apply` 只用于 `+` 等受信任原语；复合过程的 body 由机器再次进入 ev-sequence/eval-dispatch 执行。

为什么最后一个参数不用保存 env、unev？参数都求完了，应用过程只需要 proc、argl、返回位置；旧操作数遍历状态不再有用途。不是最后一个参数“不会修改环境”，而是**没有后续读取旧 env 的工作**。

## 3. 条件、定义和赋值

`if` 先保存 exp、env、continue，求谓词；返回后恢复它们，再把 exp 改成选中的分支并跳回 dispatch。不选中的分支从未求值。运行时仅 #f 为假，0 为真。

`define` / `set!` 先提取变量名，保存名字与环境，求右侧，再写入目标框架。两者不同：define 在当前框架新增或更新，set! 沿框架链查找已有绑定，找不到报错。定义过程简写在语法接口中转成 lambda；并没有把过程体提前执行。

脚本的框架是可变的 `(名字表 . 值表)`。新增定义追加到框架末尾，为下一单元的词法地址保留参数偏移；与教材前插名字的具体表示不同，但按名查找的语义相同。

## 4. 尾调用的关键不是“有递归优化开关”

过程体可以有多条表达式。非最后一条要保存 unev/env，因为还要回来处理后面的表达式。最后一条则：

```scheme
 ev-sequence-last-exp
   (restore continue)
   (goto (label eval-dispatch))
```

这里先取出调用者的返回位置，随后直接让最后表达式对调用者负责。没有留下“先回到本过程、再弹出 continue、再返回”的空工作。因此尾位置的应用可以无限次复用同一控制状态，虽然每一轮内部仍会临时 push/pop。

若改成“每一条表达式都保存 unev/env 并在返回后继续循环”，结果数值可以不变，但每次尾调用都会保留两格无用状态，迭代就退化为线性空间。Scheme 的尾递归语义约束的是这种空间行为，不是禁止出现 `save`。

## 5. 5.26(a)(b)：迭代阶乘的实测与推导

**题意**：在带栈监测的显式控制求值器里定义教材的内部 iter 阶乘，测最大深度与累计 push；回答固定深度是多少、push 关于 n 的公式是什么。

测量先执行定义，再分别求 `(factorial n)`，每次调用从清零的监测栈开始。不能把定义阶段的保存操作混入调用数据。这里保留教材的应用/序列/条件保存策略，仅把交互 REPL 改成有限 CLI 入口。

| n | n! | 累计 push | 最大深度 |
| ---: | ---: | ---: | ---: |
| 2 | 2 | 99 | 10 |
| 3 | 6 | 134 | 10 |
| 4 | 24 | 169 | 10 |
| 5 | 120 | 204 | 10 |
| 8 | 40320 | 309 | 10 |

**(a) 最大深度为 10，与 n 无关。** 不同轮 iter 不叠加返回工作，峰值来自一轮内的条件和参数求值。

**(b) P(n)=35n+29，n>1。** 相邻输入多执行一轮 iter，差为 35。可从控制器逐段核算该增量：if 保存3格，`(> counter n)` 应用保存8格；尾调用 iter 的操作符与两个参数循环保存8格，其内部两次二元原语调用各8格，共 `3+8+8+8+8=35`。固定入口、内部定义、初始调用和最后一次条件贡献剩余常数29。用 n=2 求出截距 `99−35×2=29`，再以多个 n 验证，而非用两点拟合代替解释。

## 6. 5.27：递归阶乘的两条线性公式

**题意**：测 `(* (factorial (- n 1)) n)` 版本，给出累计 push 和最大深度，并与迭代版本填表比较。基例 n=1，输入范围正整数。

| n | 累计 push | 最大深度 |
| ---: | ---: | ---: |
| 2 | 48 | 13 |
| 3 | 80 | 18 |
| 4 | 112 | 23 |
| 5 | 144 | 28 |
| 8 | 240 | 43 |

每增一层，新增 if 的3次保存、相等测试的8次、外乘法应用的8次、一元递归应用的5次、减法的8次，合计32次。基例调用共16次，故 `P(n)=16+32(n−1)=32n−16`。

在真正进入递归阶乘的 body 时，外层乘法保留了5格待恢复状态：continue、proc、argl、env、unev。每层新增5格，基例自身峰值8，因此 `D(n)=8+5(n−1)=5n+3`。

| 过程形状 | 最大深度 D(n) | 累计 push P(n) |
| --- | --- | --- |
| 递归阶乘 | 5n+3 | 32n−16 |
| 迭代阶乘 | 10 | 35n+29 |

迭代版不一定累计 push 更少；它省的是随 n 增长的**峰值空间**，而不是自动消除一般求值器的控制开销。所有常数属于这里复现的教材保存策略，不能当作 Racket 自身或所有 Scheme 实现的普遍计数。
