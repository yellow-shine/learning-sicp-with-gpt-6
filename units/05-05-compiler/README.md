# 05.05 编译与指令组合：只保存确实需要的旧值

[返回全书路线](../../README.md) · [可运行题解](solutions.rkt) · [编译器](compiler.rkt)

- **教材**：[§5.5.1–5.5.5][source]，习题 **5.31 四个表达式、5.33**。
- **前置**：05.04 的显式控制求值器、02.04 的序列组合。
- **问题**：求值器每次都重新辨认语法、准备最坏情况下的保存。表达式已经知道时，哪些工作可以提前做，哪些保存根本不需要？

## 1. 编译不是把源表达式包装成宿主过程

本单元的实际路径为：

```text
Scheme表达式（列表数据）
  → compile(exp,target,linkage)
  → (needs modifies statements)
  → statements 交给05.02汇编器
  → 指令执行闭包向量
  → PC逐条执行 → val/其他目标寄存器得到结果
```

编译器运行于宿主 Scheme，但只**生成**指令；不运行被编译过程的 body。执行阶段仍是同一个寄存器模拟器，没有 `eval` 后门。

`target` 指定结果寄存器，`linkage` 指定完成之后怎么走：`next` 顺序执行，`return` 跳到 continue，其他符号跳到相应标签。例如把 5 编译到 val/return：

```scheme
(assign val (const 5))
(goto (reg continue))
```

target 与 linkage 是独立维度。表达式作为操作符时通常编译到 proc；作为操作数时编译到 val，再加入 argl；过程体返回值使用 val。若要求过程调用“return 但结果在非 val 寄存器”，违反本调用约定，编译器明确报错。

## 2. 指令序列的 needs/modifies 是数据流摘要

一个序列包含三部分：执行前必须已有效的寄存器 N、执行可能修改的寄存器 M、实际指令。注意 N 不等于“所有被读的寄存器”：若先写 r 再读 r，就无需调用者提供旧 r。

先执行 S1 再执行 S2：

```text
N(S1;S2) = N1 ∪ (N2 − M1)
M(S1;S2) = M1 ∪ M2
```

S1 已经产生的值不需要由外界再初始化。互斥分支则取 N、M 各自的并集，不能把一个分支的写入误当成另一个分支的前置初始化。lambda 的 body 是跳过后才可能进入的代码，用 `tack-on-instruction-sequence` 接在后面时，不让 body 的寄存器使用污染“创建闭包”本身的摘要。

`preserving '(r ...) S1 S2` 只在 `r∈M1 且 r∈N2` 时包裹 S1：

```text
save r
S1
restore r
S2
```

包裹后，r 加入该序列的 needs，从 modifies 移除。这保证 S2 读到的是 S1 开始前的 r，而不是被 S1 改掉的值。若 S2 不需要旧 r，保存就是浪费；若 S1 不修改 r，保存也是浪费。

脚本用真正的序列验证：S1 改 env，S2 从 env 取结果，则插入 env 的 save/restore；要求保留一个从未被 S1 修改的 proc，不插入任何东西。metadata 写错会生成数值错误的程序，不能把它当纯注释。

## 3. 如何编译条件、lambda 和调用

- **if**：编译谓词，再 test/branch；两分支有独立标签，target 相同，linkage 确保不会从真分支落进假分支。
- **lambda**：生成 `make-compiled-procedure(entry,env)`，随后跳过 body。对象保存的是入口地址和定义环境，不再保存待解释的源 body。
- **应用**：编译操作符到 proc，编译参数，再构造 argl，按 primitive/非 primitive 分派。非原语调用设 continue、取入口、`goto`；尾调用继承 continue。

教材编译器将参数从右到左求值，以便直接 cons 建立正确顺序的 argl。运行时参数表仍按源码从左到右排列，不是把参数值交换了。例如 `(- 10 3)` 先求3，再求10，最后 argl=(10 3)，结果7。与前一单元解释器从左到右的参数求值次序不同；本章比较使用无参数顺序依赖的程序。

## 4. 5.31：四个应用中哪些保存可以删

**题意**：教材求值器会在操作符外保存 env，在非末参数外保存 env，在每个参数外保存 argl，在整个参数序列外保存 proc。分析哪些是多余的。

先按题目列出的求值器左到右路径说明保留理由：

| 表达式 | 操作符外 env | 第一个参数外 env | 参数外 argl | 参数序列外 proc |
| --- | --- | --- | --- | --- |
| `(f 'x 'y)` | 删：变量引用不改 env | 删：quote 不改 env | 两个都删：quote 不改 argl | 删：参数不改 proc |
| `((f) 'x 'y)` | 删：虽调用可改 env，但后面只有常量，不再需要旧 env | 删 | 两个都删 | 删：得到操作符之后，两参数不改 proc |
| `(f (g 'x) y)` | 删：查 f 不改 env | 保留：g 的应用可改 env，后面查 y 需要旧 env | g 外需保护；y 外删 | 保留：求 g 的应用会改 proc |
| `(f (g 'x) 'y)` | 删 | 删：后面的 quote 不读 env | g 外需保护；quote 外删 | 保留 |

这里按通用调用的保守 modifies 集分析 f、g，没有假定它们的实际函数体是什么。尤其 `((f) 'x 'y)` 中“调用修改 env”本身不足以证明要保存 env；必须还有后续需求。

再看**实际编译器的右到左参数次序**：第三行先取得 y 放进 argl，再调用 g；此后不再查 y，所以也不需要跨 g 保存 env。但已有的 `(y的值)` 要留在 argl，且外层 f 要留在 proc。第四行同样保留 proc、argl。脚本从实际编译产物提取 save，四行结果是：

```text
()、()、(proc argl)、(proc argl)
```

这同时解释了为何不能机械把求值器的左到右位置表当成编译代码的位置表。若再进行常量传播，左到右版本第一次求参数前的空 argl 可能重新建立，而不必压栈；那是更强的优化，不是本节单靠 needs/modifies 的 preserving。

## 5. 5.33：交换乘法参数是否改善阶乘

**题意**：编译比较原版本 `(* (factorial (- n 1)) n)` 与替代版本 `(* n (factorial-alt (- n 1)))`，解释代码差异和效率。本脚本在两个独立全局环境都使用名字 factorial，以排除名字长度差异；递归绑定关系分别完整成立。

右到左编译导致两种累积顺序：

```text
原版：读 n → argl←(n)
      save argl → 算递归结果 → restore argl
      argl←cons(递归结果,argl)      ; 得 ((n−1)! n)

替代版：save env → 算递归结果
        argl←(递归结果) → restore env → 读 n
        argl←cons(n,argl)          ; 得 (n (n−1)!)
```

原版保护的是已求出的参数表，替代版保护的是之后读 n 所需的环境。两边都还需要为递归调用保护外层乘法过程与返回位置；换顺序并没有消除未完成的乘法。

把**定义编译**后，用同一显式控制入口解释 `(factorial n)` 调用它。定义阶段的计数不算入调用。实际运行结果：

| n | 两版结果 | 两版 push | 两版峰值 | 两版执行指令数 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 1 | 7 | 3 | 79 |
| 2 | 2 | 13 | 5 | 126 |
| 3 | 6 | 19 | 8 | 173 |
| 5 | 120 | 31 | 14 | 267 |
| 8 | 40320 | 49 | 23 | 408 |

两份定义编译后均有62条静态指令、6条静态 save。对正整数 n，动态数为 `6n+1` 次 push、`max(3,3n−1)` 峰值、`47n+32` 条指令。仅在 n>1 时峰值简化为 `3n−1`；n=1 的实测峰值为3，来自最外解释入口，不能把直线外推成2（05.06 进一步拆解这一边界）。**在本教材式编译器与计数单位下，没有一版更高效。** 乘法交换律使结果相同，但它并不能一般保证带副作用的操作数换序无害，也不能推出所有编译器运行时间相同。

## 6. 运行、边界与已回答回顾

```sh
racket units/05-05-compiler/solutions.rkt
```

脚本断言 needs/modifies、是否插入保护、5.31 的实际 save 集、5.33 两版本的值/栈/指令数，以及非 val target。最后为 `05.05: all checks passed`。静态指令计数包括不会在同一次运行中全部经过的不同分支，动态计数则来自实际 PC 执行。

编译器主体按 Abelson、Sussman、Sussman 的 SICP §5.5.1–5.5.4 改编，保留目标/连接、右到左参数构造与 preserving 算法；语法接口复用本章 runtime。为下一单元增加了词法查找和解释过程入口桥；尚未做内联原语、跨过程寄存器分配、死代码消除、机器码生成。支持的源语法与05.04核心子集相同，不接受完整 Scheme。编译上下文用受 dynamic-wind 保护的模块状态，适用于本章单线程 CLI，不声称可并发重入服务。

**已回答回顾**：编译提前完成的是语法判别与控制安排，不是提前知道所有运行值；needs 表达外部依赖，modifies 表达旧值可能被破坏；只改了参数次序可能仅仅把“保护参数表”换成“保护环境”。下一单元继续把变量名查找提前成地址，并让两类过程真正互调。
