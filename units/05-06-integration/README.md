- **问题**：变量的值运行时才知道，但它在哪一层框架是否早就知道？两种不同表示的过程，能否在同一个环境中互相调用？

## 1. 编译时环境不是运行时环境

在下面的嵌套词法位置，编译器看到的环境是：

```text
((y z) (a b c d e) (x y))
   ↑最近框架              ↑最外框架
```

它只有**名字和位置**，没有运行值。运行时对应框架可能是 `((y=12,z=8),(a=1,b=2,c=3,d=4,e=5),(x=3,y=4))`，也可能是另一组值。词法结构使“跨几层、取第几格”在不同调用中保持一致。

词法地址 `(depth displacement)` 从0计数：depth 跨过框架数，displacement 在选中框架里跨过绑定数。它不是裸内存地址，也不是把闭包环境丢弃；运行时仍需以当前 env 为基准解析。

## 2. 5.41：find-variable 的完整答案

**题意**：在编译时环境中查变量，返回地址；找不到返回 `not-found`。

实现位于共用 `compiler.rkt`，分两层扫描：内层从 displacement=0 扫名字，外层从 depth=0 扫框架；找到立即返回，保证内层同名绑定遮蔽外层。

```text
查 c：第0层(y z)不含c；第1层跳过a、b → (1 2)
查 x：第0、1层都不含x；第2层第一格 → (2 0)
查 w：所有层都失败 → not-found
查 y：第0层第一格就找到 → (0 0)，不是最外层的y
查 x 于 (() (x))：空框架也占一层 → (1 0)
```

注意 Scheme 的0为真，内层返回 offset=0 不能按某些语言的“假值”约定误判为没找到。没有框架或所有框架为空时同样返回 not-found；不要用地址 `(0 0)` 作为失败哨兵。

设总共扫描 B 个绑定、F 个框架，查找是 O(B+F)；但这是**编译时**一次性工作。运行时按地址跳框架并取槽，不再比较符号。当前 runtime 仍用列表，所以访问成本 O(depth+displacement)，不是声称裸指针 O(1)；若框架改用向量，可以直接按槽索引访问。

## 3. 地址真的进入指令并执行

`compile-lexically` 在编译 lambda body 时扩展编译时框架，退出时恢复外层。普通局部变量读取生成：

```scheme
(assign val (op lexical-address-lookup) (const (1 0)) (reg env))
```

全局名字不在编译时环境里，继续用 `lookup-variable-value`，所以后来定义或重新定义全局过程仍可见。没有把全局环境快照冻结进代码。

例如 `(((lambda (x) (lambda (y) (+ x y))) 10) 7)`：

1. 编译内层 body 时，名字框架为 `((y) (x))`，x→(1 0)、y→(0 0)，+ 按名查找。
2. 外层执行建立 x=10 的框架，返回闭包，闭包捕获这一框架。
3. 应用内层时建立 y=7 框架，父链指向捕获的 x 框架。
4. 地址指令实际取出10和7，机器走原语应用，val=17。

自检不仅检查 find-variable，也检查编译文本确有 `lexical-address-lookup`，再汇编运行，检查遮蔽、赋值、嵌套闭包和内部定义。运行时地址越界或值为 `*unassigned*` 会报错。当前 `set!` 仍生成按名赋值；运行时也提供了地址赋值操作，但本单元不冒充完成未选的5.42全部改写。

内部定义支持过程体顶层、按顺序建立的 define：名字按 runtime 的追加顺序列入编译时框架，参数偏移不变；重复定义同名变量更新原格。没有支持嵌套 begin 中任意位置的内部定义，也没有实现完整 letrec/scan-out 初始化语义；共同支持的内部定义子集要求初始化期间不读取尚未建立的内部绑定（lambda 只捕获、不立即读取，所以允许教材 iter 的自引用）。例如内部 `define x` 的初始化式企图读取同名外层 x，会碰到两种实现初始化策略的差异，不属于本章解释/编译等价声明。全局定义、教材阶乘、内部 iter、直接内部遮蔽都在已测试范围内。词法编译出错时 dynamic-wind 恢复编译上下文，避免下一次编译沿用半截环境。

## 4. 两种过程对象，共用一套调用约定

```text
解释过程：(procedure 参数 源body 定义环境)
编译过程：(compiled-procedure 入口PC 定义环境)
共同入口输入：proc=过程对象，argl=参数值表
共同出口：val=结果，返回到continue
```

**解释器调用编译过程**：在 apply-dispatch 分辨 compiled-procedure，先弹出解释器应用时压入的 continue，再取编译入口并跳转。编译过程入口提取定义环境、扩展参数框架，执行 body 指令。

**编译过程调用解释过程**：编译器对一般非原语应用发出 `procedure-call-entry` 操作。这只分辨过程种类并返回地址，绝不求值 body。若目标是解释过程，地址指向 `compound-call-bridge`：

```scheme
(save continue)
(goto (label compound-apply))
```

为何要补一次 save？解释器的 compound-apply / ev-sequence 约定最终 continuation 已在栈上；编译代码通常把它放在寄存器。桥接修正的是约定，不是绕开显式控制。返回时双方仍共用 val。

脚本把以下编译定义放进同一个汇编镜像，再用解释器定义 interpreted-step：

```scheme
;; 编译的两个过程
(define (compiled-double x) (+ x x))
(define (compiled-caller x) (+ (interpreted-step x) 100))
;; 解释过程，源body留在过程对象中
(define (interpreted-step x) (+ (compiled-double x) 1))
```

`(interpreted-step 7)` 得15；`(compiled-caller 7)` 经 **解释入口→编译caller→解释step→编译double** 得115，最终栈深0。这个测试不能由两个隔离的宿主函数互调替代，它们的来回跳转都发生在同一机器上。

所有代码一次汇编进镜像，入口 PC 才有共同地址空间。运行时全局环境共享，编译 caller 时 interpreted-step 尚未定义也无妨，因为那是运行时全局查找。这里不实现交互式动态追加/重定位代码、持久化机器码或真实链接器。

## 5. 5.45(a)：比较三种实际执行方式

**题意**：给出递归阶乘的解释、编译、专用机器的 push/深度公式，求相对解释器的渐近比例，再评价编译质量。

计数协议沿用教材 §5.5.7：先安装定义、清零统计，再由显式控制入口求 `(factorial n)`。解释组装入解释过程；编译组装入编译过程。专用组直接执行图5.11控制器。n>1，所有结果互相比对，而不是用预先写好的统计数字冒充执行。

| n | 解释 push / 深度 | 编译 push / 深度 | 专用 push / 深度 |
| ---: | --- | --- | --- |
| 2 | 48 / 13 | 13 / 5 | 2 / 2 |
| 3 | 80 / 18 | 19 / 8 | 4 / 4 |
| 5 | 144 / 28 | 31 / 14 | 8 / 8 |
| 8 | 240 / 43 | 49 / 23 | 14 / 14 |
| 12 | 368 / 63 | 73 / 35 | 22 / 22 |

公式及其理由：

- **解释**：P=32n−16，D=5n+3；05.04 已逐层核算。
- **编译**：P=6n+1，D=3n−1（n>1）。每多一层递归增加6次 push（谓词前 env/continue，以及递归路径上的保护），未完成层净保留3格；P(1)=7，故 `P(n)=P(n−1)+6`。深度由3(n−1)格未完成工作加最深编译 body 的2格局部峰值得到，但最外解释入口自身还有3格峰值，所以完整式为 `D(n)=max(3,3n−1)`。特别地 n=1 时实测 D=3，不能把 n>1 的直线外推成2。词法地址替换一次查名操作，不改变 save/restore 布局。
- **专用**：每个非基例仅保存 n、continue，基例不保存，P=D=2(n−1)。

因此当 n→∞：

| 比较 | push 比 | 最大深度比 |
| --- | --- | --- |
| 编译 / 解释 | 6/32 = **3/16** | 3/5 |
| 专用 / 解释 | 2/32 = **1/16** | 2/5 |

专用机器相对编译机器只需约1/3的 push、2/3的峰值深度。编译器已去掉大量一般求值器开销，但仍为参数表、通用环境与动态过程分派付费。

这些是**栈操作/栈空间比例**，不是实测墙钟时间比。一个模拟指令内部的按名查找、乘大整数、分配列表成本并不相同。脚本还打印指令数，但不能把3/16直接宣称为编译后用时18.75%。若把最外层调用也编译，固定项可能变化；这里为与教材比较，故意保留同一解释入口。

## 6. 5.45(b)：怎样更接近专用控制器

最直接的改进是内联确定绑定的 `= - *` 等原语，用寄存器操作代替查过程、造 argl 和通用 apply；给简单参数专用寄存器，再按活跃性只保留 n 和返回位置。已知目标的直接调用也能去掉过程类型分派；跨过程分析若能证明哪些寄存器不变，可以缩小保守 modifies 集。

但是不能仅看到符号 `*` 就当成机器乘法：Scheme 允许局部遮蔽或重新绑定全局名字。要有绑定不变证明、限制语言，或添加守卫与回退。词法地址只消除查名，不会自动消除参数表和保存，因此它本身不能把本题的6n+1变成2n−2。这里给出完整的改进理由，不额外实现未选的开放编码习题或生产级优化器。
