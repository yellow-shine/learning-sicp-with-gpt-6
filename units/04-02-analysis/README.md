## 1. 两种重复工作，两个不同问题

第一种问题是语义：局部名字的作用域从哪里开始？第二种是效率：每次调用阶乘，是否都要重新识别过程体是 if，再重新提取三个分支？

它们都能通过处理程序数据改善，但不能混为一谈。`scan-out-defines` 改善内部定义的绑定语义；`analyze` 则把语法工作提早做，不应该把动态变量查找提早成常量。

```text
源 S 表达式
   → scan-out-defines / let、cond 等派生变换
   → analyze：得到 (lambda (运行环境) ...)
   → 多次调用执行过程：查找、计算、选择分支、赋值
```

输入经 reader 已是数据。`(cons '* (list 5 5))` 和 `'(* 5 5)` 可以生成同一个待解释程序；但分析结果是**宿主闭包**，对象语言过程又是带标签的数据，两者不再等于那张源码列表。

## 2. 习题 4.16：同时作用域不等于同时有值

**题意概述**：a. 读取 `*unassigned*` 时出错；b. 写 scan-out-defines 将内部定义改为预分配加赋值；c. 接入求值器并比较安装位置。

考虑：

```scheme
(lambda (x)
  (define u <e1>)
  (define (v y) (+ u y))
  (v x))
```

变换结果是一个只含一条 let 的过程体：

```scheme
(lambda (x)
  (let ((u '*unassigned*) (v '*unassigned*))
    (set! u <e1>)
    (set! v (lambda (y) (+ u y)))
    (v x)))
```

### a. 查找必须区分两种错误

- 链中根本没有名字：unbound。
- 找到了位置，但位置还含 `*unassigned*`：unassigned，**不能继续向外查找同名变量**。

共享 `lookup` 先取得最近绑定单元，再比较其值。`'*unassigned*` 是对象程序中的引用符号，不是查找一个名为 `*unassigned*` 的全局变量。这里沿用教材保留符号方案，不把这个符号作为普通可用的绑定值；更完整的实现可以改用不可伪造哨兵。

下面的程序会报 unassigned，而不是返回 16 或 20：

```scheme
(let ((a 1))
  ((lambda ()
     (define b (+ a 10))
     (define a 5)
     (+ a b))))
```

创建局部 a 的位置时就遮蔽了外部 a；初始化 b 时局部 a 尚未赋值。先分配名字不是按依赖关系自动重排计算，更不是并发初始化。

### b. scan-out-defines 的完整算法

实现位于 [共享 evaluator.rkt](../04-01-metacircular/evaluator.rkt)：

1. 只扫描当前过程体的直接元素，把 define 与其他表达式分别收集。
2. 用 `def-name`、`def-value` 统一处理变量定义和过程定义简写。
3. 为所有定义生成 let 绑定，初值都是引用的哨兵。
4. 按定义原顺序生成 set!，随后接上原顺序的非定义表达式。
5. 如果没有内部定义，原样返回过程体，避免额外框架。

不递归钻进 quote：引用数据中的 define 不是定义；不提前扫描嵌套 lambda 的局部作用域，它在建立自己的过程时处理。实现按教材的过程体级定义规则工作，不扩展为任意嵌套 begin 中的定义提升。正常对象程序把内部定义放在体首；算法即使收集到混排定义也会把初始化移到其他表达式前，因此不承诺保留非法混排程序的副作用顺序。

### c. 安装位置与环境轨迹

我们在 `make-procedure` 中调用变换，而不是每次取 `procedure-body` 时重做。一个闭包构造一次，可能调用很多次；变换结果存进闭包，执行时直接使用。

```text
G: 外部绑定
 ↑
Ecall: x=20          （调用参数框架）
 ↑
Elocal: even?=<闭包>，odd?=<闭包>
            │               │
            └── 两者都捕获 Elocal ──┘
```

let 先创建 even?/odd? 两个位置；初始化 even? 只创建闭包，不调用 odd?，因此合法。初始化 odd? 后执行 `(even? 20)`，它们在同一局部框架互相查找，最终得到 `#t`。如果初始化式实际读取另一个尚未赋值的位置，就报错。这区分了“保存一段将来要执行的代码”与“现在执行该代码”。

代价是含内部定义的体多出一个 let 调用框架。没有环境反射的正确程序不能仅凭多出的空层区分语义；更低层的实现可以在调用框架预留局部槽，避免额外层。此处不为省一个教学框架改造所有环境接口。

## 3. analyze 如何真的只分析一次

`analyzer.rkt` 不用 `lambda` 包住一次完整 `mc-eval` 来冒充分析。每个语法类别都递归产生专门的执行过程：

| 源类别 | 分析时 | 执行时 |
| --- | --- | --- |
| 字面量/quote | 取出常量 | 返回它 |
| 变量 | 记住符号 | 在传入环境 lookup |
| if | 分析谓词及两分支 | 求谓词，只执行一分支 |
| lambda | 扫出定义、分析整个体 | 构造捕获当前环境的对象闭包 |
| set!/define | 取名字，分析右侧 | 求右侧，修改对应位置 |
| 普通调用 | 分析操作符及操作数 | 取得过程与实参，然后应用 |
| 序列 | 组合执行过程 | 按组合顺序执行，返回最后值 |

例如 `(+ x 1)` 分析后仍在每次运行查 x。自检在同一 code 上先让 x=3，后让 x=9，得到 4 和 10。若“优化”时直接查出 x=3，就把分析和执行的分界画错了。

单项序列直接返回这一项的执行过程；多项序列构成组合闭包，不在每次执行时重新扫描表达式列表。`analyzed-apply` 对复合过程直接调用已经分析好的体，不再返回 `mc-eval`。对象过程标记为 `analyzed`，与直接解释器的 `compound` 不混用；两条路径有各自的环境，但复用同样的环境操作与 primitive 表。

## 4. 习题 4.24：实际测量，谨慎估计

**题意概述**：比较直接解释与分析式解释的速度，对不同程序估计分析与执行的时间占比。

`solutions.rkt` 用宿主单调性并无严格保证的墙钟 `current-inexact-milliseconds` 读取本地经过时间；短程实验中它足够作粗测量，不用于语义断言。先验证两个解释器答案相同，再预热，批量测三个量：

- D：直接解释整条程序 N 次。
- E：对同一分析产物执行 N 次，不计初始分析。
- A：仅分析源程序 N 次，不执行。

三类工作负载是小算术式、递归 factorial(12)、迭代求和 loop(100)。设置环境和打印不在计时区间；程序内的 define 如果是工作负载的一部分，则两条执行路径都要执行它。

本次实际执行的一组结果（毫秒，机器与进程状态会改变结果）：

| 工作负载 / 次数 | D | E | A | `(D-E)/D` |
| --- | ---: | ---: | ---: | ---: |
| 小算术 / 15000 | 7.749 | 5.440 | 9.201 | 29.8% |
| factorial / 2000 | 14.258 | 12.392 | 0.794 | 13.1% |
| tail-loop / 400 | 25.879 | 22.958 | 0.152 | 11.3% |

这些是实验数据，不是固定预期输出或普适加速比。题目要求的一个粗估计是：把 E 当作运行期开销近似，则直接解释器中“可通过分析消除的开销”比例约为 `(D-E)/D`，相应执行比例约为 `E/D`。上表约对应 70.2%、86.9%、88.7% 的执行部分。

但这**不是精确剖析**：两个解释器有不同分派和闭包调用成本，GC、JIT、计时噪声也在内。若差值为负，应该原样报告本轮未测到优势，而不是硬裁成一个正分析占比。A 是分析器创建执行闭包的成本，不等于直接解释器每次做语法判断的成本；小算术中 A>D 并不矛盾。

把批量测量换成单次成本：`a=A/N` 是一次分析，`e=E/N` 是一次已分析执行。一次分析后执行 N 次的总成本约为 `a + N·e`，摊销每次为 `a/N + e`。仅运行一次的小程序不一定值得分析；循环过程体反复运行时更能摊薄分析成本。

## 5. 程序数据化的能力与限制

数据化使转换、解释、分析成为普通过程可以处理的对象，不等于可以自动回答所有程序问题。设想一个总能正确判断任意过程是否终止的 halts?，再构造“预测自己会停就永远跑，预测不停就返回”的程序，自应用就产生矛盾。这个思想也约束 04.06 的循环检测：有限历史启发式不是普遍终止判定器。

分析不是执行，也不等于生成机器码；这里输出宿主执行闭包，第五章才把类似分阶段思想落实到指令序列。完整 Scheme 的宏展开、模块、异常、控制操作不在本核心子集内。
