## 一行 set! 不等于一个原子事件

`(set! balance (+ balance 10))` 至少需要读余额、计算、写余额。如果两人都读到100，再分别写110、80，后一次写会覆盖前一次更新。并发无需真的在两颗 CPU 上同时运行；一个执行器在读写之间切换任务，已经足以造成这个问题。

所以不能靠“代码只有一行”判断原子性。必须给出模型中哪些动作不可分割。以下把单次共享余额的读/写视作原子，局部算术不共享；机器级实现可以更复杂。

## 3.38(a)：先完整列出串行结果

**题意**：余额100，Peter存10，Paul取20，Mary取当前余额的一半。先要求三项操作各自完整、按某个顺序串行执行。以下 P=Peter，U=Paul，M=Mary。

| 顺序 | 余额轨迹 | 最终 |
| --- | --- | --- |
| P U M | 100→110→90→45 | 45 |
| P M U | 100→110→55→35 | 35 |
| U P M | 100→80→90→45 | 45 |
| U M P | 100→80→40→50 | 50 |
| M P U | 100→50→60→40 | 40 |
| M U P | 100→50→30→40 | 40 |

不同最终值是 **{35,40,45,50}**。串行化不规定哪个顺序，所以不保证只有一个答案。代码对六个顺序执行真实更新函数并断言上表，不只返回这个集合常量。

## 3.38(b)：交错可以超出串行集合

Mary 的原式是 `(- balance (/ balance 2))`，包含**两次**余额读取。不能不加说明就把它变成读一次再除二。代码模型固定先读减法左操作数 `Ml`，再读除法中的 `Mr`，最后 `Mw` 写 `Ml-Mr/2`。这是明确选择的一种求值顺序，并不声称所有 Scheme 都规定左先。

第一条时序让三人的更新几乎都丢失：

| 步 | Peter | Paul | Mary | 共享余额 |
| --- | --- | --- | --- | --- |
| 1 | Pr：读100 | | | 100 |
| 2 | | Ur：读100 | | 100 |
| 3 | | | Ml：读100 | 100 |
| 4 | | | Mr：读100 | 100 |
| 5 | | | Mw：写50 | 50 |
| 6 | | Uw：写80 | | 80 |
| 7 | Pw：写110 | | | **110** |

第二条把后半段改为 `Pw,Mw,Uw`，最终 **80**。这些不在串行集合里。

第三条展示 Mary 两次读取不一致，不只是一般的“最后写覆盖”：

```text
Ml：Mary 先保存左操作数 100
Pr,Pw：Peter 完成存款，余额 110
Ur,Uw：Paul 完成提款，余额 90
Mr：Mary 再读取右操作数 90
Mw：写 100 - 90/2 = 55
```

最终 **55** 也不在串行集合里。无论是否列出全部机器可能性，以上已完整回答题目要求的“一些额外值及其时间图”。

代码还递归枚举保持 P两步、U两步、M三步各自先后关系的全部 `7!/(2!2!3!)=210` 个交错，逐条执行，得到本模型的集合 `{25,30,35,40,45,50,55,60,65,70,80,90,110}`。这不是所有编译器、内存模型、Mary 另一种读取顺序的通用全集。没有用随机线程运行次数来冒充穷举证明。

## 互斥与串行化分别做什么

mutex 提供独占 acquire/release；serializer 接受过程 p，返回“取得该 mutex→执行 p→释放”的包装过程。同一 serializer 生成的过程彼此互斥；不同账户的 serializer 可以并行。

教材用单槽 `test-and-set!` 解释锁，但**检查是否空闲并标成占用必须原子完成**。普通 Scheme 的 `if` 加 `set-car!` 并不自动具备这个保证。本单元使用宿主 Racket 的计数1信号量作为真正的互斥原语，Scheme 层实现包装与账户协议。`call-with-semaphore` 负责异常时释放，`dynamic-wind` 维护对应的观测日志。错误自检之后再次取得锁，验证不会留下永久占用。

只锁单次存款/提款不够保护“交换两个余额”：差额的读取和两个修改必须处在**两个账户共同保护**的临界区里。已在外层取得锁时，内层原始调整过程不再重复取得同一非重入锁。

## 3.48：把加锁顺序落实到账户 ID

**题意**：账户有唯一编号，交换时总先锁编号小的账户，解释避免死锁的原因并改写构造器及交换过程。

工厂实际分配单调递增的 ID，`(account 'id)` 可读；分配本身也用一个互斥原语保护，避免并发创建出重复编号。两个账户都有自己的 serializer。关键代码是：

```scheme
(let* ((low (if (< (a 'id) (b 'id)) a b))
       (high (if (< (a 'id) (b 'id)) b a))
       (outer (low 'serializer))
       (inner (high 'serializer)))
  ((outer (inner exchange)) a b))
```

**外层包装先执行**：即使实参是 `(b,a)`，且 b.id 大于 a.id，也先取得 a 锁，然后 b。不是按参数位置或当前余额排序；余额会变化，ID 不变。相同账户直接返回 `same-account`，否则重入同一锁会挂起。

```text
账户 A.id=1，B.id=2，原余额100/40
exchange(B,A)：acquire1 → acquire2 → 交换 → release2 → release1
exchange(A,B)：acquire1 → acquire2 → 交换 → release2 → release1
```

两种参数顺序都在可运行代码中核对 ID 日志及真实余额变化。余额相等仍应按 ID 排序，与差额是否为0无关。

**证明**：若一个任务持有编号 i 的锁、等待编号 j，则 i<j。假如存在死锁环，沿等待关系走一圈会推出 `i1<i2<…<ik<i1`，矛盾。因此统一严格递增顺序排除了循环等待。这里假定参与者都遵守协议，所需两个账户预先已知，不在锁内动态发现更小编号的额外资源。

不统一顺序时，T1先拿A再等B，T2先拿B再等A，就满足循环等待。本文件不真的启动这个无限等待，只用上述资源图说明。统一顺序解决本交换协议的死锁，不保证调度公平、不保证无饥饿，也不替无关资源协议兜底。

## 与事务、线性一致性的边界

串行化机制约束临界区重叠，不自动提供持久化或失败回滚；取款成功而后续过程抛错时，余额不会自动恢复。线性一致性还要求每个操作可解释为调用到返回之间的某个瞬间生效，并遵守真实时间先后。若所有观察和修改都纳入正确锁范围，可以据此证明一个具体对象的线性化性质；仅看见一个 serializer 不能跳过证明。

代码的原始余额读取/有符号调整端口是为教材交换机制开放的，必须按协议使用；不是可直接暴露给不可信客户的银行 API。锁日志只服务单线程确定性验证，没有宣称是一套并发审计系统。
