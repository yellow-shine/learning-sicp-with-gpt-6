## 变量不是值

到上一章为止，`eval` 只看树。表达式里没有名字，所以不需要“现在哪些名字有值”。

真实语言有变量，作业语言也有。求值一个表达式，必须带着当前环境（environment）。

```text
Environment:  variable → value
```

例如：

```text
x → (const 10)
y → (const 20)
```

**【课程】** 环境就是课程从 ML 第一周起使用的那个东西：变量到值的映射。现在要把它做成解释器的参数。作业里的表示可以自选；讲师建议的简单表示是 Racket 的 list，元素是 pair：

```text
(list (cons "x" (const 10))
      (cons "y" (const 20)))
```

左边是 Racket 字符串，不是对象语言的值。右边必须是对象语言的 value：`const`、布尔、pair 的值、闭包，而不是还没算完的 `add`。

```text
eval(Var "x", env) =
    在 env 里找 "x"
    找到 → 那个 value
    找不到 → 对象语言的错误：未绑定的变量
```

没有魔法。解释器收到环境，变量情形做查找。

**【讲解】** 这就是 “Variable ≠ Value”。变量是树上的一个节点，或环境里的一个键。值是查找的结果，或别的表达式求值的结果。把变量节点直接返回，等于没求值。把 Racket 的字符串 `"x"` 返回给对象语言的调用者，等于又一次越过宿主语言的边界。

### 子表达式用哪一个环境

多数构造把同一个环境传下去。加法不绑定名字：

```text
eval(Add e1 e2, env) =
    eval(e1, env) + eval(e2, env)
    （仍要检查两边都是数，再包回 const）
```

`x + y` 的两支查找用的是同一次调用收到的那张表。缺了 `x` 或 `y`，在变量那一支报错，不在加法那一支猜测。

有的构造必须换环境。最明显的是 `let`：求值体时，表里要多一对，体才能使用 `let` 绑定的那个变量。

```text
eval(Let x e1 e2, env) =
    let v = eval(e1, env) in          ; 初始化表达式用旧环境
    eval(e2, extend(env, x, v))       ; 体用扩展后的环境
```

**【课程】** 这和从课程开头讲的 `let` 语义是同一句话。现在它是你要写的递归调用，不是口头规则。

初始化表达式用旧环境，是教学语言里对应 ML / Racket `let*` 的单绑定情形。作业若有同时绑定多个变量的形式，每个初始化看见哪些名字，要以作业说明为准。视频只把“体需要更大的环境”讲死了。

### 两个函数，空环境起步

**【课程】** 真正干活的是辅助函数，例如 `eval-under-env`。它接收表达式和环境，大 `cond` 每种表达式一支。变量支用环境。有的递归调用原样传递环境，有的传递稍作扩展的环境。

对外的 `eval-exp` 只做一件事：用空环境调用 `eval-under-env`。程序开始时没有任何变量。

```text
eval-exp(program) = eval-under-env(program, empty)
empty = 空 list，没有任何 string–value pair
```

空环境不是 `null` 这个对象语言的值。它是宿主语言里表示“没有绑定”的表。

**【课程】** `eval-under-env` 确实只是 `eval-exp` 的辅助函数。一般风格会把它定义在局部。作业不要这么做。评分脚本要能直接用特定环境调用 `eval-under-env`。你若把环境处理写错一点，局部定义会让所有测试都叫不到它，于是全部失败。请把它留在文件顶层。这是评分约定，不是更优美的语义。

顶层的一个例子：环境里可以有 `"x"` 映射到作业语言的 `(int 17)`。视频把常数构造器在作业里的名字说成 `int`。教学笔记里仍写 `const`，以免和上一章的树打架。交作业时用作业给的名字。

## 闭包要解决的问题

函数体里的自由变量（free variable）不在参数列表里，也不在函数内部的局部绑定里。它的值从哪来？

```text
let x = 10
function f(y):
    x + y
```

若函数值只保存体，调用 `f(3)` 时解释器只拿到当前环境。当前环境可能已经没有 `x`，或者 `x` 是别的绑定。词法作用域要求：体使用函数定义时的环境，再扩展成参数到实参的映射。

解释器的参数只有当前环境。定义时的环境不会在调用时魔法般再传进来。

**【课程】** 没有魔法的做法是：定义函数时，把当时的环境放进闭包。以后使用这个闭包，环境就在里面。

```text
Closure = 函数代码 + 定义时的环境
```

这是本章的核心定义。Part A 用它解释程序为什么这样算。Part B 要求你在解释器里把它造出来。

```text
Closure
├── code: λy. x + y
└── env
    └── x → 10
```

即便后来在另一个环境里调用 `f`，加的仍是这个 `10`，加上这次的参数。调用处的环境不负责提供 `x`。

## 词法作用域，以及闭包为什么是它的实现

同一段程序，两种作用域规则，结果可以不同。

```text
let x = 10
let f = λy. x + y
let x = 20
f(3)
```

| 规则 | `f` 的体里的 `x` 找谁 | 结果 |
| --- | --- | --- |
| 词法作用域（lexical scope） | 定义 `f` 时看得见的那个 `x`，即 10 | 13 |
| 动态作用域（dynamic scope） | 调用 `f` 时当前环境里的 `x`，即 20 | 23 |

**【课程】** 作业语言实现词法作用域，因为那是适当的语义。闭包是它的自然实现：定义时把环境存下来，调用时只用存下来的那一份，不用调用者的环境。动态作用域反而不需要把环境放进函数值，调用时直接用当前环境即可。那更简单，也不是我们要的语言。

**【讲解】** “闭包 = 函数指针”错在这里。函数指针只有代码。代码不足以决定自由变量。没有环境的函数值，要么禁止自由变量，要么被迫使用动态作用域。Part A 允许自由变量又坚持词法作用域，所以函数值必须是一对，不能是一段代码。

## 解释器里的函数与调用

语言的源程序里有函数构造，例如 `function`，里面是参数名和体。另有一个 `closure` struct，两字段：函数（参数和体），以及环境。

**【课程】** `closure` 不是给源程序用的。测试时可以用。程序员写的树里应该出现 `function`，不应出现 `closure`。解释器在求值 `function` 时才把闭包造出来。

### 求值一个函数定义

```text
eval(Function(arg, body), env) = Closure(Function(arg, body), env)
```

不返回函数 AST 本身。函数还不是值。闭包才是值。和其他值一样，解释器见到已经是闭包的东西，就把它返回。

当时的 `env` 整个放进去。里面有什么自由变量以后用得着，调用时不再回来问。

### 求值一次调用

```text
eval(Call(e1, e2), env):
    1. 用当前 env 求值 e1，得到闭包。不是闭包 → 错误
       （把数当函数，和上一章把布尔当数是同一类检查）
    2. 用当前 env 求值 e2，得到参数值
    3. 取出闭包里的环境，不是调用者的 env
    4. 扩展它：参数名 → 第 2 步的值
    5. 再扩展：函数名 → 整个闭包          （作业的递归办法，见下）
    6. 用这个环境求值闭包里的函数体
```

```text
调用处环境 env_caller
        │
        ├─ eval e1 ─► Closure
        │               ├── code: 函数名、参数名、体
        │               └── env_def
        │
        └─ eval e2 ─► v

然后丢掉 env_caller，至少不再用它求值体

env_body = env_def
         + 参数名 ↦ v
         + 函数名 ↦ 整个 Closure

eval(body, env_body) → 值
```

**【课程】** 给定一个闭包，求值它的体时只用它存着的那一个环境（再加参数和递归绑定）。不会有时用定义环境、有时用调用环境。但是每次求值一个函数定义，都会用当时的当前环境新建一个闭包。循环里两次求值同一个 `function` 节点，若环境已经不同，得到的是两个闭包。

这就是高阶函数的实现。做完之后，对象语言里可以写 `map` 和 `filter`，可以把闭包当参数传递，函数体也可以使用定义在函数外面的变量。

### 递归：把函数名映射到整个闭包

**【课程】** 作业里的函数可以递归。做法是在求值体之前，再把函数名映射到整个闭包，不是只映射到函数 AST。

只映射到函数 AST 不够：递归调用会再次求值这个函数，又造一个闭包；更糟的是，若体里需要的是一个可以调用的值，函数 AST 按上面的规则还不是值。映射到整个闭包，递归调用得到的就是原来那个值，它带着原来的定义环境。

```text
Closure c
├── code: function f(y) = ... f(...) ...
└── env_def: x → 10

求值体的环境：
    env_def
    + y → 实参
    + f → c          ; 整个闭包，不是 function 节点
```

视频把这称为递归的一点变通（workaround）。它不是另一套作用域。它是在闭包环境上再加一个绑定，使函数体能通过自己的名字找到自己。

**【讲解】** 因此有三条不变量。违反任一条，词法作用域就会算错：

```text
1. 变量查找必须使用这次求值传入的那个环境，不能去找“全局表”或调用者随手传来的表。
2. 函数值必须携带定义时的环境。只保存 AST 就丢了自由变量。
3. 函数调用必须在闭包的环境上扩展，而不是在 caller environment 上扩展。
```

一个常见的解释器 bug：`Call` 的分支正确地从 `e1` 得到了闭包，然后用 `env`——函数的当前参数，也就是调用者的环境——去求值体，只把参数名加进去。自由变量会找到调用处的绑定，或根本找不到。这违反第 3 条。表现出来就是动态作用域，或无端的未绑定变量。

另一常见 bug：`Function` 分支返回函数 AST，不包环境。调用时没有定义环境可用，只能用当前环境。这违反第 2 条，并迫使你违反第 3 条。

## 一个完整的小例子

教学语言，只为跟踪。`extend` 把一对放在表头；查找从头部开始，所以内层绑定遮蔽外层。

```racket
(struct const (n) #:transparent)
(struct var (s) #:transparent)
(struct add (e1 e2) #:transparent)
(struct fun (name arg body) #:transparent)
(struct call (f e) #:transparent)
(struct closure (fn env) #:transparent)

(define (extend env name value)
  (cons (cons name value) env))

(define (lookup env name)
  (cond [(null? env) (error "unbound variable")]
        [(equal? name (car (car env))) (cdr (car env))]
        [else (lookup (cdr env) name)]))

(define (eval-under-env e env)
  (cond
    [(const? e) e]
    [(var? e) (lookup env (var-s e))]
    [(add? e)
     (let ([v1 (eval-under-env (add-e1 e) env)]
           [v2 (eval-under-env (add-e2 e) env)])
       (if (and (const? v1) (const? v2))
           (const (+ (const-n v1) (const-n v2)))
           (error "add applied to non-number")))]
    [(fun? e) (closure e env)]
    [(closure? e) e]
    [(call? e)
     (let ([c (eval-under-env (call-f e) env)]
           [v (eval-under-env (call-e e) env)])
       (if (closure? c)
           (eval-under-env
            (fun-body (closure-fn c))
            (extend
             (extend (closure-env c)
                     (fun-arg (closure-fn c))
                     v)
             (fun-name (closure-fn c))
             c))
           (error "call applied to non-closure")))]
    [else (error "not an expression")]))
```

程序：定义 `f` 时 `x` 是 10；调用 `f` 时外面的 `x` 若已是 20，结果仍是 13。

```text
env0 = { x → const 10 }

eval( fun f(y) = x + y , env0 )
  → c = Closure( that function , env0 )

; 假设调用发生在 env1 = { x → const 20 }，f 已经作为值传了进来
eval( call c  3 , env1 )
  1. c 已是 closure
  2. 参数求值得 const 3，用的是 env1，但参数表达式是常数，环境不影响
  3. 体的环境从 env0 开始，不是 env1
  4. y → const 3
  5. f → c
  6. eval( x + y , { f→c, y→3, x→10 } )
       x 找到 10，y 找到 3
       → const 13
```

若第 3 步误用 `env1`，`x` 找到 20，得到 23。那就是动态作用域，是 bug，不是语言的另一种合法模式。作业语言没有动态作用域开关。

`x` 不在 `env0` 里时，错误应在求值体、查找 `x` 的时候发生，并且是“未绑定变量”。不应在创建闭包时就预知体里会用哪些名字。课程的简单实现不在创建闭包时扫描自由变量。可选讲才讨论提前算自由变量，那是为了空间，不是为了改变何时报错。

## 可选：闭包不必慢，也不必记下整个环境

**【课程】** 前面的实现时间上不贵。造闭包只是构造器填两个字段。调用时只是把正确的环境传给解释器。贵的是空间：每个闭包保存定义点的整个环境。

用 list 表示环境时，表头扩展会和旧表共享尾部，所以不是每次都复制全部绑定。即便如此，这不是更现实的实现会满意的结构：沿 list 查找变量太慢。共享在更现实的表示里也更难做对。

更严重的是，闭包会把环境里以后用不到的数据留活。任何闭包都可能在将来被调用，于是它保存的全部绑定都不能回收。

实践中的替代：创建闭包时不必保存整个环境，只保存一个更小的环境，其中只有函数代码可能用到的变量。这些变量叫自由变量。Free 不是“免费”，是“不被绑定”：出现在函数体里，又不是参数，也不是函数内部的局部变量。

只保存自由变量的绑定就够了。函数体不可能查找别的名字，因为那些名字不出现。

```text
λ(). x + y + z           自由变量 {x, y, z}
λx. x + y + z            自由变量 {y, z}      x 是参数
λx. if ... then y else z 自由变量 {y, z}      每次调用只用一个，但两个都可能被用
λx. let y = ... in y+z   自由变量 {z}         y 是局部的
λx. x + x                自由变量空           这就是“函数不是闭包”的那种旧语言能表达的全部
最后一例：参数 x 不算；前面一次使用的 y 算；
          后面被局部 y 遮蔽的 y 不算；外面的 z 算
```

**【课程】** 自由变量可以用对函数体的简单递归算出来，并且要考虑遮蔽。解释器不应在每次创建闭包时都跑一遍这个递归。大函数的话，那是在运行时反复扫描语法。应有一个求值开始前的预遍，可以想成编译的一步：对程序里每个函数算一次自由变量，存在函数上，或存在旁边的表里。创建闭包时只在当前环境查找那几个名字，用它们做一个小环境放进闭包。

这比“整个环境塞进去”多花一点时间，换来空间。值得。

环境本身也不该用 list。要更快的查找，就用平衡树或哈希表。那只是把表示换掉，规则不变。作业仍可用 list。

### 再可选：编译到没有闭包的语言

**【课程】** 若根本没有解释器，目标语言的函数也不接收环境参数，就要改翻译。

- 每个函数多一个参数。原来 n 个参数，翻译后是 n+1 个。多出来的那个是环境。
- 每个调用多传一个参数，把环境传下去。
- 整个程序一致地这么做，环境就由程序自己带着走，不再由解释器参数带着走。
- 变量的使用也要改：自由变量不再是“直接的 x”，而是“在那个额外参数里查找 x”。
- 函数值仍要做成闭包：当前环境（现在是本函数收到的额外参数）加上函数，组成一对。这一部分没变。

这是翻译策略，不是作业要写的解释器。它说明闭包不是解释器专有的低效技巧。

## 宿主语言的函数，作为对象语言的 macro

本节把解释器和 Section 5 的 macro 想法接上。机制不同，不要并成 `define-syntax`。

**【课程】** 我们已经会：用 A 的构造器写 B 的 AST，用 A 的递归函数解释它。Macro 则是：定义一种重写，使用处在程序运行前按定义展开。

两者合在一起的惯用法是：写普通的 Racket 函数，输入是语言 B 的语法，输出也是语言 B 的语法。在写 B 程序时调用这些函数，它们的输出会在你调用 `eval-exp` 之前就进到树里。

```text
Racket 函数（所谓 macro）
    语言 B 的语法  →  语言 B 的语法
        │
        ▼
这棵更大的树
        │
        ▼
eval-exp          解释器不需要新 struct，也不需要知道这些函数的名字
```

这发生在调用解释器之前。它是源到源的变换，更准确说是 AST 构造，不是对象语言运行时的函数调用。

```racket
(define (andalso e1 e2)
  (if-then-else e1 e2 (bool #f)))

(define (double e)
  (multiply e (const 2)))

(define (list-product es)
  (if (null? es)
      (const 1)
      (multiply (car es) (list-product (cdr es)))))
```

```racket
(define y
  (andalso (bool #t)
           (eq-num (const 3) (const 4))))
; y 已经是 if-then-else 树，不是 “andalso 节点”
; eval-exp(y) → bool #f，因为 3 不等于 4
```

`list-product` 接收的是 Racket 的 list，元素是对象语言表达式。它不把那些表达式求值，也不把数乘出来。它造一棵嵌套的 `multiply` 树。空 list 变成 `(const 1)`，那是以后求值才是一的程序。

这些函数可以用在程序的内部，不必在最外层。一个使用了 `andalso`、`double` 和 `list-product` 的测试，在解释之前已经是一棵很大的 `if-then-else` 和 `multiply` 树。解释器只认识那些 struct。

**【课程】** 为什么不在“macro”里就把乘法算掉？第一，macro 不是这么工作的：它们产生展开后的语法。第二，语言若有变量或函数，现在还不能乘。某个表达式里可能有变量。要点是产生表示展开结果的语法，然后再求值。

### 这种 macro 不卫生

**【课程】** Section 5 夸过 Racket 的 hygienic macro。用 Racket 函数给被解释语言做 macro，不是那种好系统。它不按你期望的方式处理变量遮蔽。

若对象语言有变量，而你在这种“macro 函数”里生成了局部变量，就要自己避免和调用者的名字相撞，例如使用奇怪的变量名。尽管如此，总的想法仍成立：一个产生本语言语法的 Racket 函数，可以当作这个语言的 macro。

**【讲解】** 它不卫生，是因为它就是在构造树。它不会给生成的绑定改名，也不会把生成的自由变量绑回“macro 定义处的对象语言环境”。定义处的 Racket 环境与对象语言环境是两个世界。Hygiene 需要的是对象语言作用域的信息，普通 Racket 函数在构造 struct 时并不拥有那套信息。

所以：

| | `define-syntax` | 解释器旁的 Racket 函数 |
| --- | --- | --- |
| 发生时机 | 求值前展开 | 也在 `eval-exp` 之前，但是普通 Racket 求值 |
| 输入输出 | 语法树到语法树 | 对象语言 AST 到对象语言 AST |
| 解释器是否看见 macro 名 | 看不见，已经展开 | 看不见，树里没有这个函数的节点 |
| Hygiene | 有 | 没有。有变量时要自己起不会撞的名字 |
| 能否推迟对象语言的求值 | 能，把语法放进函数体 | 能，只要你生成的是 `fun` 或 thunk 式的 AST，而不是先调用 `eval-exp` |

最后一行是和 `my-delay` 相同的教训：若 Racket 函数里不小心先 `eval-exp`，那就不再是 macro，而是宿主语言在建树期间就把对象程序跑了。

## 逐讲笔记

### 06 Implementing Variables and Environments

1. **问题：** 表达式里出现名字时，解释器到哪里去找它的值？
2. **动机：** 没有变量的解释器还不是一门能写程序的语言。作业语言有变量。
3. **概念：** 环境是变量到值的映射；list of pairs；`eval-under-env`；空环境；顶层定义是为了评分。
4. **机制：** 变量支查找，没有则报错。加法传递同一环境。`let` 的体传递多了一对的环境。`eval-exp` 从空表开始。
5. **代码：** 视频故意不给 Racket。上面的 `lookup` / `extend` 是教学重建。
6. **执行：** `x + y` 两次查找用同一张表。`let` 的初始化用旧表，体用新表。
7. **PL：** 环境从“语义讲话里的词”变成了数据。作用域规则就是“哪一次递归把哪张表传下去”。
8. **误区：** 变量节点本身就是值。环境是调用栈。把 `eval-under-env` 藏进局部，以为这只是风格，不影响评分。
9. **联系：** Part A 从第一周就在用环境。上一章的 `eval(e)` 少了一个参数，因为那时没有名字。
10. **一句：** `eval(x, env)` 就是在 `env` 里查找 `x`；谁造出这张表，谁就决定了作用域。

### 07 Implementing Closures

1. **问题：** 函数体要使用定义时的环境，可解释器调用时只有当前环境。环境从哪来？
2. **动机：** 这是作业最难、也是这一部分最值得想通的地方。语言要有一等闭包，才能写 `map` 和 `filter`。
3. **概念：** 闭包 = 代码 + 定义环境；函数 AST 不是值；调用的七步；递归时函数名映射到整个闭包。
4. **机制：** 求值 `function` 时打包当前环境。求值 `call` 时检查 `e1` 是闭包，在闭包环境上绑定参数和函数名，再求值体。
5. **代码：** 教学语言的 `fun` / `call` / `closure` 分支。作业要用自己的 struct 名。
6. **执行：** `x = 10` 时定义的 `λy. x + y`，在 `x = 20` 的环境里调用，结果是 13，不是 23。
7. **PL：** 词法作用域不是附加检查，而是“体的环境从闭包里取”这条实现规则。动态作用域是用错环境时你会不小心实现出来的东西。
8. **误区：** 闭包是函数指针。调用时把参数加进调用者环境即可。递归绑定只要指向函数 AST。源程序里应该写 `closure` 构造器。
9. **联系：** Part A：闭包是一对。上一章：使用值之前要检查种类。这里要检查的种类是闭包。
10. **一句：** 定义时把环境放进值里，调用时从值里取出来，词法作用域就实现了。

### 08 Are Closures Efficient?（可选）

1. **问题：** 每个闭包保存整个环境，会在时间和空间上付出什么？实践里保存什么就够了？
2. **动机：** 否则会留下“闭包必然低效”的印象。课程要说明低效的是这一种表示，不是这个语义。
3. **概念：** 自由变量；预遍；更快的环境表示；编译时给每个函数加一个环境参数。
4. **机制：** 创建闭包前已经知道自由变量集合，只查找那些名字，做成小环境。编译方案里，环境变成显式参数，自由变量的使用变成对这个参数的查找。
5. **代码：** 视频是例子和注释，不是另一份解释器。五个函数的自由变量集合见上文。
6. **执行：** 没有新的求值例子。预遍发生在解释开始之前，所以运行时不再扫描函数体。
7. **PL：** 语义要的是“自由变量的绑定在”，不是“整个定义环境的对象身份在”。更小的环境可以保持语义，并让用不到的数据被回收。
8. **误区：** 闭包慢是因为调用时要构造。每次调用都应该重算自由变量。没有自由变量的函数才叫闭包。编译之后就不需要闭包这个值了。
9. **联系：** 上一讲的简单实现是正确的，只是空间上粗糙。List 环境解释了为什么作业可以先求正确，再谈查找速度。
10. **一句：** 闭包必须保存的是自由变量的绑定；保存整个环境是正确的粗实现，不是语义的一部分。

### 09 Racket Functions as Macros

1. **问题：** 怎样给对象语言加 `andalso` 这样的形式，而不改解释器、不加 struct？
2. **动机：** 作业要写类似的辅助函数。它也把 macro 从“Racket 的 `define-syntax`”推广成“任何在求值前把语法变成语法的东西”。
3. **概念：** 宿主函数生成 AST；展开发生在 `eval-exp` 之前；解释器只看见生成结果；这种做法不卫生。
4. **机制：** `andalso` 返回 `if-then-else` 树。`list-product` 返回嵌套 `multiply`，空列表返回 `(const 1)`，不在这时做乘法。
5. **代码：** `andalso`、`double`、`list-product`。视频里的语言没有变量；有变量时名字要自己避开。
6. **执行：** `y` 在调用 `eval-exp` 之前已经是条件树。解释得到 `bool` 假，因为 3 不等于 4。大例子展开成一长串乘法，然后求值得真。
7. **PL：** 这是源到源变换。它看起来像语言的一部分，只是因为造树的函数在宿主语言里先跑完了。它没有 Racket macro 的词法作用域保证。
8. **误区：** 这些函数是对象语言的函数，所以会在解释器里被调用。它们和 `define-syntax` 一样卫生。应该在生成函数里把能算的子树先 `eval-exp` 掉。
9. **联系：** Section 5：macro 在求值前重写语法，函数做不到不求值参数。这里参数是已经建好的树，重写的是树，所以普通函数够用。Hygiene 的缺失，正是因为没有用那套会改名的展开器。
10. **一句：** 宿主语言函数若把对象语言的树变成树，它就是对象语言的 macro；解释器不应该知道它的名字。

## 本范围小结

### 核心问题

名字的值不在树上，在环境里。函数若能使用定义处的名字，函数值就必须把那张环境带走。调用时用错那张表，得到的就是另一种语言。

### 知识地图

```text
eval(expr, env) → value
      │
      ├── Var：lookup(env)
      ├── Let：初始化用旧 env，体用 extend 后的 env
      ├── Fun：不返回 AST，返回 Closure(fun, env)
      └── Call：
            eval 函数 → 必须是 closure
            eval 参数 → value
            体的 env = closure.env + 参数 + 函数名↦整个 closure
```

可选优化把 `closure.env` 收成自由变量的小表。可选的编译把这张表变成目标语言的额外参数。旁边的 Racket 函数可以在进 `eval` 之前把树变大，那是 macro，不是这条 `eval` 的新分支。

### 最重要的代码模式

```text
eval(fn, env) → closure(fn, env)

eval(call(fn, arg), env) →
    c = eval(fn, env)
    v = eval(arg, env)
    eval(c.body, extend(extend(c.env, c.arg, v), c.name, c))
```

### 容易混淆

| 混淆 | 分辨 |
| --- | --- |
| 环境与调用栈 | 环境是变量到值的表。调用栈是解释器自己的 Racket 调用。对象语言的调用不一定对应你想象的那层栈帧；它对应一次以新环境进行的递归 `eval` |
| 闭包与函数 AST | AST 是源程序节点。闭包是值，多了一个环境 |
| 闭包与函数指针 | 指针没有自由变量的绑定 |
| 调用者环境与闭包环境 | 参数表达式在调用者环境里求值。函数体在闭包环境里求值 |
| 函数名绑定到 AST 或绑定到闭包 | 必须是整个闭包，递归才仍带着定义环境 |
| 宿主函数 macro 与 `define-syntax` | 都在解释前产生语法。只有后者卫生 |

### 和上一范围的关系

上一章的 `eval` 少了环境，因为算术树里没有名字。值的种类检查仍在：调用前要确认得到的是闭包，加法前要确认得到的是数。非法 AST 仍可崩溃。闭包 struct 可以由解释器构造，即使源程序不该写它；这和“合法 AST 是子集”不冲突，因为闭包是求值过程中的值，不是源程序语法的一种。

### 为下一 Section 准备了什么

你现在有两门语言的体验：ML 在运行前拒绝一大类程序；Racket 和你写的解释器在运行时检查值的种类。Section 7 不再写解释器。它问：这种检查放到运行前，到底保证了什么，又必须拒绝哪些其实不会出错的程序。你的解释器就是“动态检查”的一个具体样本。类型检查器是试图在跑之前证明某些样本永远不会走到 `error` 的那个程序。

## Engineering Connection

**【课程】** 闭包的简单实现并不因此就不能用。空间问题来自保留了用不到的绑定；自由变量分析和换一种环境表示是实践中的修法。编译到没有闭包的语言时，环境变成额外参数，函数值仍是闭包。Part C 会说方法查找比这套规则更复杂，并把闭包和 Ruby 的 block 放在一起看。

**【扩展，类比】**

- JavaScript 的回调、Go 的闭包、Rust 的闭包，都是“代码加上它要的外层绑定”。Rust 还会问这些绑定是借还是搬走，那是课程没有的所有权层。不要用本课证明 Rust 闭包没有环境。
- 动态作用域仍出现在一些特殊机制里（某些 shell 变量、Emacs Lisp 的可选动态绑定）。它们是另一条规则，不是闭包实现写错时的“差不多”。
- 配置语言和模板语言里的“宏函数”，常常就是宿主语言在求值模板前拼 AST。它们通常也不卫生。撞名是这类设计的真实 bug，课程已经让你在 MUPL macro 里提前看到了。

## 检查题

1. 为什么 `eval` 在有变量之后必须多一个环境参数？只在变量那一支去读一个全局表，会破坏什么？
2. `let` 的初始化表达式和体，各使用什么环境？若初始化也使用扩展后的环境，哪个绑定会和课程讲的 ML 式 `let` 不同？
3. 为什么 `eval-under-env` 要留在顶层？这是语义要求还是评分要求？
4. 函数值为什么不能只保存体？自由变量在定义时和调用时可能有什么不同？
5. 画出 `λy. x + y` 在 `x → 10` 时变成的闭包。若在 `x → 20` 的环境里用参数 3 调用它，词法作用域的结果是什么？动态作用域呢？
6. 求值 `function` 节点时为什么返回 `Closure(function, env)`，而不是返回 function AST？
7. 写出 `call` 的步骤。哪一步开始必须停止使用调用者的环境？
8. 递归时为什么要把函数名映射到整个闭包，而不是映射到函数 AST？
9. “用调用者环境扩展参数绑定，然后求值体”违反了哪条不变量？用户会观察到什么？
10. 自由变量和参数有何不同？为什么 `if` 的两个分支各用一个不同的外层变量时，两个都要放进闭包？
11. 为什么不在每次创建闭包时扫描函数体来算自由变量？预遍把结果放在哪里？
12. `andalso` 作为 Racket 函数，为什么解释器里可以没有 `andalso` 这种 struct？它和 hygienic macro 相比缺了什么？

## Answers

1. 因为变量的值不在树上，而在“当前哪些绑定有效”这张表里。不同子表达式可能要不同的表。全局表无法表达 `let` 的局部绑定，也会让一次调用看见不该看见的名字。
2. 初始化用 `let` 之外的环境，体用加上新绑定的环境。若初始化用新环境，初始化表达式会看见正在定义的名字，那是另一条规则，不是视频描述的 `let`。
3. 评分要求。语义上它只是 `eval-exp` 的辅助函数，局部定义也可以。脚本要直接用给定环境调用它，所以必须是顶层绑定。
4. 体里的自由变量要按定义时的环境解释。调用时的环境可能没有那些名字，或有同名的别的绑定。只保存体会把词法作用域变成“到时候再看当前环境”。
5. 闭包的代码是 `λy. x + y`，环境是 `x → 10`。词法结果是 13。动态作用域会在调用环境里找 `x`，得到 23。
6. 函数 AST 没有定义环境，还不是值。返回闭包，才把当时的环境冻结进一个可以传来传去的值。以后调用不再依赖当时的调用栈还在不在。
7. 用当前环境求值函数表达式，得到闭包，否则报错；用当前环境求值参数；从闭包取出环境；扩展参数绑定；为递归再绑定函数名到整个闭包；用这个环境求值体。从取闭包环境那一步起，体的求值不再用调用者环境。
8. 函数 AST 不是可调用的值，也不携带环境。递归调用需要同一个闭包，这样再次进入体时仍用原来的定义环境。
9. 违反“调用必须基于闭包环境，而不是 caller environment”。自由变量会按调用处解析，得到动态作用域；调用处没有那个名字时，则会报未绑定，尽管定义处有。
10. 参数在调用时绑定，不需要从定义环境里取。自由变量不由这次调用的参数决定。两个分支都可能执行，所以两个名字都可能被查找，小环境里必须都有。
11. 那会在运行时反复遍历函数语法，函数大时代价高。预遍在求值开始前对每个函数算一次，把集合存在函数上或侧表里。创建闭包时只做查找和建小表。
12. 因为在 `eval-exp` 被调用之前，Racket 已经把 `andalso` 的结果树建好了，树的根是 `if-then-else`。解释器只处理它认识的构造。这种函数不会给生成的变量改名，也不会按对象语言的定义处作用域处理自由变量，所以不卫生。
