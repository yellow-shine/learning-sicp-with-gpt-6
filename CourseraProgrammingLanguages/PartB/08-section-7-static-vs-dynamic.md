# Section 7 静态检查与动态检查

标注见 `00-course-map.md`。本章覆盖 Section 7 的全部视频，以及 Part B 的 wrap-up。这一周没有编程作业，只有约占课程总分 10% 的 quiz，而且只考本节。

前面两门语言的共同点先放在桌上，免得争论从语法开始。**【课程】** ML 和 Racket 都有高阶函数，都劝你少用 mutation，函数参数都是 eager 的。真正大的差别是：ML 有一套精致的类型系统，在程序开始跑之前拒绝许多程序；Racket 更宽容，把更大的一类错误留到求值过程中。

语法、模式匹配对 struct、几种 `let` 的语义，都是差别，但不是这一节要打的仗。

---

## 两种互相翻译的看法

### 从 Racket 看 ML：ML 是 Racket 的一个子集

**【课程】** 一个自然的看法是：ML 不是另一种计算，而是 Racket 程序的一个子集。类型系统把许多程序扔掉，剩下的才像 ML。

扔掉的里面有真 bug，所以这个子集让人高兴。

```racket
(define (g x) (+ x x))          ; 没问题，留在子集里

(define (f y) (+ y (car y)))    ; 任何调用都会错：y 不能既是数又是 pair
                                ; 不必写测试也知道。ML 会拒绝对应程序

(define (h z) (g (cons z 2)))   ; 看起来合理，但 g 要的是能相加的值
                                ; cons 的结果做不到。类型系统能看见
```

留在子集里的程序，每个地方的类型都已知。于是不需要 `number?` 这种运行时问题。静态上已经知道。

子集也会扔掉没有 bug 的程序。Racket 程序员会觉得委屈：

```racket
(define (f x)
  (if x #t (list 1 2)))         ; 有时返回布尔，有时返回 list。Racket 合法，ML 不行

(define xs (list 1 #t "hi"))    ; 一个 list 里多种数据。不能直接写成 ML 的 int list

(f xs)                          ; Racket 里能跑，得到真。ML 不接受这整段
```

**【讲解】** “子集”是视角，不是字面的语法包含。ML 的语法不是 Racket 的语法。讲师说的是：把构造翻译过去之后，ML 接受的行为是 Racket 接受的行为的一部分，而且这一部分把一些必错的程序排除了，也把一些不会错的程序排除了。后面的 soundness 就是在把这句话说精确。

### 从 ML 看 Racket：不是没有类型，是只有一个类型

另一种看法不是“Racket 是超集”这么简单。**【课程】** 可以把每个 Racket 值想成同一个 datatype 的一个构造：

```sml
datatype theType =
    Int of int
  | String of string
  | Pair of theType * theType
  | Fun of theType list -> theType
  (* 以及 bool、symbol、procedure……每种内置数据一个构造器 *)
```

你写 `42`，实现就像自动写了 `Int 42`。每个传来传去的值都有类型 `theType`，上面永远有一个标签。`car` 和 `pair?` 是你看不见的模式匹配：

```text
car(v) = case v of
           Pair(a, _) => a
         | _ => raise ...

pair?(v) = case v of
             Pair _ => true
           | _ => false

plus(a, b) =
    取出两边的 Int，否则异常
    把两个 int 相加
    再用 Int 把结果包回去，让程序其余部分继续带着标签跑
```

所以 “Racket 没有类型” 是错的。在这个 ML 中心的看法里，它有一个类型。函数接收 `theType` 的列表（因为真有多参数），返回 `theType`。

这个看法覆盖不了 struct。**【课程】** `struct` 是在程序运行期间，往 `theType` 里动态增加一种新构造器。这说得通。ML 不愿意这么做，因为穷尽性检查会被弄乱：你永远不能确定 case 已经写全。ML 的异常类型 `exn` 有一点这个味道，但是冷僻，而且通常不拿来当一般的编程模型。

**【讲解】** 上一章你写的解释器，就是在用宿主语言的谓词做 `car` 那种模式匹配。对象语言没有静态类型时，每次 `add` 都要看标签。ML 的类型检查器试图证明：某些标签检查永远不会失败，于是实现可以不做它们，程序员也可以不写 `number?`。

## 静态检查是什么

先定义，再争论。**【课程】** 不理解要争论的东西就争论它好不好，是最令人沮丧的讨论。

静态检查：程序已经成功解析，得到了抽象语法，但是在开始运行之前，仍被拒绝。拒绝哪些程序、接受哪些程序，是语言定义的一部分。人们靠它知道什么是合法程序。

语言定义之外，也可以有工具在旁边找 bug、给警告。这很好，而且已经很流行。讲师赞成。本节说的静态检查，是语言定义里的那一种，不是外挂的 linter。

最常见的做法是类型系统。要分开两件事：

| | 问的是什么 |
| --- | --- |
| 做法（approach） | 每个变量有一个类型，用它检查每个表达式，函数有类型签名，有的程序通过，有的不通过 |
| 目的（purpose） | 这个类型系统想阻止哪一种运行时行为 |

目的可以是：不要把字符串传给除法；不要打破模块的抽象；不要在运行时还要做 `number?` 那种检查；不要使用未定义的变量。一个类型系统不必同时以全部这些为目的。某种语言阻止的事，另一种语言的类型系统可以不阻止。

**【课程】** 动态类型语言，就是不做这种静态检查的语言。界线不是绝对的。Racket 在你点 Run 时，不允许未定义的变量。它静态检查的东西很少，所以仍叫动态类型语言。

### ML 的类型系统保证什么，不保证什么

若 ML 程序能跑，下面这些不会发生：

- 原语用在错误种类的值上。例如 `e1 e2` 里 `e1` 求值结果不是闭包；`if` 的测试不是布尔。
- 使用一个环境里没有的变量。解释器去查找时一定找得到。
- 冗余的模式。以及其他类型系统写明要防的事。

每个类型系统的清单都是语言定义的一部分。没有类型系统什么都防。

ML 不防这些：

- 对空列表取 `hd`。
- 数组越界。ML 有数组。它保证下标是 `int`，不保证这个 `int` 落在数组长度里。
- 除以零。
- 以及一切“你的程序想做什么”的问题。

**【课程】** 除非静态检查器拿到了程序对全部输入应有的完整规格，它不可能读心。`then` 和 `else` 写反了，两边类型却一样，检查器无从知道。两个函数都是 `int -> int`，你调用了 `f` 而本意是 `g`，这也不是类型系统要防的。类型系统和静态检查器不是测试的替代品。

所以语言设计有两个问题：目的是什么；怎样强制执行，并仍然好用、灵活。难的是让“怎样做”真正达成“要防什么”，而不是只写出一个会终止的递归检查。下一节的正确性就是这个“达成”。

### 不是两个点，是一条轴

**【课程】** 静态或动态，不是仅有的选择。尽早抓住问题，和“这个情况也许永远不会发生，程序员不必现在知道”，之间有固有的张力。

用一个故意陌生的例子：防止除以零。

```text
更早 ←──────────────────────────────────────────────→ 更晚

键入每个字符之前就分析，
当前程序若会除以零，字符甚至不出现在屏幕上

每个文件可以先通过，
但在带着具体 main 和参数真正运行之前再查一次，
觉得可能除以零就拒绝运行

运行到 3/0 那一行，像 REPL 里那样报错
（这是大家熟悉的“动态”）

不报错，返回一个表示“除过零”的结果，让调用者处理
```

最后一档听起来违法，因为学校里不能除以零。浮点却正是这么做的：除以 `0.0` 得到无穷，调用者也许根本不会用到这个结果，它可能在别处被消掉，或者被一个条件跳过。做科学计算的人认为这有用。整数除以零也可以定义成这样。语言没有这么做，是设计选择，不是数学逼的。

经验上，编译时和运行时是这条轴上最常用来报错的两个点。它们不是轴的两端。

## Soundness 与 Completeness

类型系统要阻止某件事，叫它 X。X 可以是“把字符串传给加法”，也可以是“查找未定义变量”，也可以是一组这样的事。不先说 X，就无法说这个类型系统对不对。

**【课程】** 相对这个 X：

| 术语 | 定义 | 医学类比 |
| --- | --- | --- |
| Sound（可靠） | 从不接受一个程序，使得存在某组输入，运行时会做 X | 没有假阴性。检查器说“不会做 X”（阴性），就真的不会 |
| Complete（完备） | 从不拒绝一个其实不会做 X 的程序 | 没有假阳性。检查器说“有这个病”，病人就真有 |

假阴性：检查是测试，程序是病人，检测的是“会不会做 X”。检查器说不会，其实会。Sound 就是没有这种假阴性。

假阳性：检查器说会做 X，其实不会。Complete 就是没有这种假阳性。

**【课程】** 我们实际设计的类型系统以 sound 为目标。设计者和理论工作者花很多时间证明它们确实 sound，以便你相信：通过了检查，就不会得它声称要防的那种病。更花哨的特性，例如 generics，常常是为了减少假阳性。类型系统确实有假阳性：它拒绝一些并不会做 X 的程序。把系统设计得更花哨，是为了让程序员能避开更多假阳性。

### ML 的假阳性，针对“数除以字符串”

ML 对这件事是 sound 的：没有假阴性。下面都是假阳性，程序不会真的把数除以字符串，却被拒绝。

| 函数 | 为什么其实不会做 X | 为什么检查器仍拒绝 |
| --- | --- | --- |
| `f1` | 这个函数从未被调用。里面的除法不会发生 | 检查器把“程序里有这个函数”就当成程序有病 |
| `f2` | 除法在 `if true` 的 else 里，永远走不到 | 它不做“常量 true 的死代码”这种推理，至少课程里的 ML 不为此放行 |
| `f3` | else 可能走到，但若程序只拿 `true` 调用它，就不会 | 检查器按函数的所有合法参数考虑，不按“这个程序里实际的调用”考虑 |
| `f4` | 和 `f2` 一样，永远走真分支，因为 `x <= abs x` 对 int 成立 | 我们并不指望类型检查器懂这个算术事实 |
| `f5` | 实参是 `if true then 1 else "hi"`，分母永远是数 | 要同时推理调用处的死分支和函数体，检查器不做 |

**【课程】** 实用上我们接受这些假阳性。理论上还有更深的原因：几乎任何你想静态阻止的非平凡性质 X，都做不到一个检查器同时：

1. 总是终止；
2. sound；
3. complete。

这是不可判定性。程序员希望类型检查会结束。于是若要终止，就必须有假阳性，或假阴性，或两者都有。常见设计是：不要假阴性，接受一些假阳性，换取总是终止。

这对很多 X 都成立：函数是否终止、把字符串当函数、除以零。课程不证明这条定理。讲师的判断是：静态检查必然近似，并且我们选择把误差放在假阳性一侧，这是该定理对日常软件开发最重要的后果。定理本身不会改变。

**【扩展】** 这条定理在理论课里常和 Rice 定理连在一起。课程没有使用这个名字。不要把“Rice”写进 quiz 答案，除非题目自己用了。课程要的是：非平凡性质上，终止、sound、complete 三者不能兼得；语言选择 sound 加终止，于是不 complete。

### 若类型系统不 sound

检查器接受了程序，运行时 X 仍可能发生。**【课程】** 语言可以怎么办：

1. 承认设计错了，把类型系统收紧，多拒绝一些程序，直到假阴性消失。
2. 即使号称“通常能防住 X”，仍保留动态检查当退路。Racket 那种运行时检查，可以和一套不 sound 的静态检查并存：静态检查少找一些，动态检查补上它没找到的。
3. 允许 X 发生，并规定一个默认结果，例如找不到变量就当 0。脚本语言倾向于这么做。Ruby 通常不走到这么远，但这类选择存在。
4. 最坏：X 真的发生时，程序可以变成任何程序。可以删光你的文件，可以在网上发出病毒。C 和 C++ 的类型系统就是这条路。下一节专门说它。

## Weak typing 不是 dynamic typing

**【课程】** Weak typing 常和静态/动态搞混，所以放在这里，把定义摆正。它最著名的例子是 C 和 C++。

定义：存在一些程序，按语言定义必须通过静态检查；运行之后，它们可以做绝对任何事。讲师的说法是：允许把计算机点着。意思是可以崩溃、可以破坏数据、可以成为病毒、可以删除所有文件。

这些程序执行了没有意义的操作。能在闯祸之前抓住它们的动态检查，是可选的；C 和 C++ 的实际实现不做。

若你只写过 Racket、Python、ML、Java，这看起来很疯。为什么允许实现不做这些检查？

| 理由 | 课程的说法 |
| --- | --- |
| 实现容易移植 | 检查留给程序员。讲师宁愿实现更难、编程更容易，但别人不总是这么权衡 |
| 性能 | 省下检查的时间，也省下为了检查而保存的标签、长度等空间 |
| 更低层 | 程序员要控制数据表示。动态检查需要额外字段，程序员就控制不了那些字段 |

Weak 这个名字不好。它不太是关于类型系统的。它是关于：有一个想阻止的坏性质 X，既不静态查，也不动态查，并且规定若 X 发生，计算机可以着火。

数组越界是 C/C++ 程序做出无法解释的行为的最大原因之一。多数人不把数组边界想成这些语言的类型系统。这就说明问题不在 “static” 这个词上。

几十年前有人赞成 weak typing，口号是 “strong types for weak minds”。意思是：只有认为计算机比人聪明，才想要 strong typing。静态检查永不完美，所以聪明人必须能关掉检查，说“相信我”；若我错了，你可以做任何事。语言不该挡住人。

**【课程】** 主流看法已经变了。人很不擅长避免 bug，能自动检查就该分工：写检查器的人把检查写对，写应用的人依靠检查，专注应用逻辑。类型系统也确实变好了：多态、子类型，使强类型不再那么挡路。

操作系统里有三千万到五千万行 C。两百到一千行，讲师还能同情“人盯着能把 bug 看完，类型系统不该自称更懂”。三千万行里任意一行都能让整个应用做出任意行为，再期待人保证某些错误不可能发生，是荒谬的。讲师的玩笑是：和 C 的 weak typing 有关的重要 bug，就发生在本周；他不必去查，因为总有网站在登记，每周都有。

### Racket 不是 weakly typed

**【课程】** 这只是定义问题。Racket 是动态类型。它在运行时检查很多事，例如不要把数当过程调用。语言定义说：这些错误会在特定时刻被发现，并变成异常或错误。

实现可以去掉某些检查，但只有当分析能证明它们永不失败。定义要求：若检查会失败，程序必须表现出错误。这和“着火语义”不同。着火语义是：检查可以不在，失败了也可以不做任何指示。

### 另一件常被叫成“更动态”的事：原语的求值规则

**【课程】** 这也不是 weak typing，也不是动态类型。

有的语言里，`+` 作用于字符串是错误：ML 是类型错误，Racket 是运行时错误。有的语言里 `+` 就是字符串连接。还有的语言会把数转成字符串，`"foo" + 3` 得到四个字符的 `"foo3"`。

访问只有五个元素的数组的第十个元素，可以是错误，也可以规定返回空。给数组赋值超出末尾，可以是错误，也可以把数组变大。函数参数个数不对，Racket 是错误；另一种语言可以丢掉多余参数，或者给缺少的参数填 79。

这些选择让更多程序合法，往往更晚才发现程序员大概不是这个意思，或者永远只是静静地继续。静态检查早发现、动态检查晚发现，这条权衡在这里仍然适用，而且这是比运行时异常更晚的一档：连“出错了”都可以不宣布。

技术上，这不是静态检查，也不是动态检查。你只是改了某个原语的求值规则，扩大了合法程序的集合。人们有时把更宽容的原语叫成更动态。那是口语，不是本节的定义。

## 七组对照：不是判决

**【课程】** 大多数语言有的事静态查，有的事动态查。问题不是“全部静态还是全部动态”，而是对每一件要查的事，何时查有什么好处。下面七组都有两边的理由。讲师认为它们都成立，差别是你更看重哪边。他拒绝给出总冠军。

### 1. 方便：异构数据，还是“参数已经是对的”

动态这边：list 里放不同种类的数据，函数返回不同种类的值，直接写。

```racket
(define (f y)
  (if y (+ y y) "hi"))
```

ML 要先声明 datatype，自己引入 `Int` 和 `String` 标签，还要记得在哪一支用哪个构造器。使用结果时，Racket 有现成的 `number?`；ML 要用你声明的那个类型做模式匹配。更笨拙。

静态这边：方便也可以是“调用者传来的已经是对的类型”。立方：

```sml
fun cube x = x * x * x   (* 每个调用处都只能传 int。体内不用检查 *)
```

Racket 里谁都能传任何参数。若函数可能被外部使用，你也许得自己查是不是数。Racket 有一套 contract 系统，课程没展示，用来把这种检查写得更统一、更好文档化。不方便的不仅是要写检查，而且误用要到运行时才失败。

### 2. 静态检查总会拒绝有用的程序；标签由谁来打

**【课程】** ML 拒绝这段，尽管它说得通。Racket 接受。

```racket
(define (f g)
  (cons (g 7) (g #t)))

(f (lambda (x) (cons x x)))
; 得到 ((7 . 7) . (#t . #t)) 这种 pair 的 pair
```

对应的 ML 写不出来：类型推导不允许同一个 `g` 既用于 `int` 又用于 `bool`。这不是程序没意义，是类型系统不够强。

静态这边的回答：Racket 能这么做，是因为所有数据都带着标签，每次运算前都检查。ML 里你也可以自己声明 datatype、自己打标签、自己模式匹配。极端情形就是前面的 `theType`：完全按 Racket 的方式在 ML 里编程。差别是，Racket 强迫所有程序始终带标签、始终检查；ML 让程序员决定哪里打标签、哪里可能失败、哪里做动态检查。可能没 Racket 方便，但控制在程序员手里。

### 3. 谁更早抓住 bug，以及它抓得住哪些

`pow1` 本应柯里化，递归调用却按 pair 传了两个参数。ML 在使用这个文件时就报错。Racket 的对应代码能通过 Run，直到调用 `(pow1 3 4)`，或直到递归调用那一层，才发现参数个数不对。自动系统抓住了盯着代码不容易看见的简单 bug。

动态这边：它抓的常常是测试反正会抓到的容易的 bug。不要说有了静态类型就不用测试。把 `pow1` 注释掉，看 `pow2`：类型通过，`(pow2 3 4)` 得到 13，不是 \(3^4\)。原因是把 `*` 写成了 `+`。没有任何类型系统会抓这个，因为加法和乘法的参数类型相同。Racket 里同样的错误，同样靠测试看到 13。既然反正要测，Racket 的那次运行时错误就没有那么可怕。

### 4. 性能

静态：不只省下“加法前检查参数是不是数”的时间。数据上可以没有标签。ML 传给加法的可以是真正的数。Racket 要传一个带着“这是数”的字段、再加上真正的数的值。代码里也不用写 `number?`。类型系统保证某个位置就是某种数据。

动态：语言定义要求这些检查，但实现不必每次都做。通常只有一小部分程序影响性能。内层循环里，编译器常常能删检查。

```racket
(+ x x)
(* x 4)
```

定义上，`+` 要检查两个参数。更聪明的实现看见同一个 `x` 用了两次，可以只查一次。乘 4 时，4 已知是数，不必查；若加法已经成功，`x` 也一定是数，不必再查。理论上大约四次检查，实践中可以收成一次。

另外，你不用为了绕过类型系统而写多余的构造器和重复代码。想做什么就写什么。

### 5. 代码重用

动态：没有类型系统限制，同一个函数能被更多地方调用。一批处理 cons cell 的库函数，可以用于任何数据：内容类型是否相同、是 list 还是别的 tuple，都可以。静态语言里，树、list、数组、哈希表即便很基本，也要复杂的静态类型才能重用，而且有时仍不能覆盖你想要的全部重用。

静态：今天的类型系统已经足够写 list、set、树、表的可重用库。类型可能复杂，使用不该复杂，库只写一次。若什么都用 cons cell，逻辑上不同的东西会很难分辨；以错误顺序传给函数时，你得到的是奇怪的运行时错误，而不是运行前的类型错误。好的类型错误反而使重用库更容易：它指出你用错的地方。

### 6. 原型：规格还在变的时候

真实软件不是作业。早期往往连规格都不清楚，在试数据该怎么表示、one-of 类型还要不要加构造器。这叫 prototyping。

动态：静态类型不让你跑，除非所有 case 都写好，所有人同意，否则全是类型错误。动态类型让你跑已经写好的那部分，知道其余的以后再补。为了能跑，静态世界里你得过早承诺，写出一批稍后会扔掉的代码。

静态：原型阶段反而最需要类型系统。想法在变，数据类型在变，这正是你会把字符串当成 int 传的时候。类型既是文档，又有东西在检查文档。还没实现的函数，让它抛异常即可；ML 里总是抛异常的函数可以有任何类型。Datatype 的 case 没写全，加一个通配支、在里面抛异常。这容易出错，但不会比动态检查替你隐式这么做更糟。

### 7. 维护：软件已经发出去之后

动态更方便的一个例子：函数原来总是 `int -> int`。新版本仍对数字加倍，但若得到字符串，就把字符串和自己拼接。

```racket
; v1
(define (f x) (+ x x))
; v2
(define (f x)
  (if (number? x) (+ x x) (string-append x x)))
```

旧的调用者没有被破坏。这是向后兼容的改变。ML 里，`int -> int` 必须变成某个 one-of 类型到同一 one-of 类型。所有旧调用都要改成加上构造器，对结果做模式匹配。不向后兼容。

静态这边：改类型时，检查器告诉你所有不再通过的地方，像一份待办清单。上一张幻灯片的例子确实烦人，但它把每个调用 `f` 的位置都印出来，你改完，程序再次通过，就知道没有遗漏。

只改返回类型时，对比更鲜明。Racket 继续能“编译”。你必须有足够的测试，才能找到所有仍按旧结果使用的地方，并在运行时错误里把它们抓出来。ML 的检查器直接给你待办。

给 datatype 加一个新构造器时，若你到处用模式匹配，而且最后一支不用通配符，不穷尽的匹配会在正好需要修改的地方报警。你不必担心忘了某一处。

动态的反驳：这份待办清单虽然友好，但是强制的。你不能做完一半、跑一些测试、再做另一半。ML 要求整个程序通过类型检查。至少它把清单给了你。

### 结论：问题问得太粗

**【课程】** 七组都给过了。说静态总是更好，或动态总是更好，太粗。更好的问题是：对正在写的这个软件，哪些事我愿意静态查，并接受必然的假阳性；哪些事我不静态查，愿意靠测试和实际运行来发现。

这里有正当的权衡。两段视频试图给的是基于概念的理由和例子，不是没有技术内容的意见。

若两边都有道理，理想也许是语言两边都支持，不必在 ML 和 Racket 之间选。Racket 在用 Typed Racket 试：有的文件带类型，有的不带。讲师认为，提供两个世界的最好部分，在许多方面仍是开放的研究问题，语言设计上有不容易的事。即便两边都有，问题也不显然变得更容易：写库或用库的人仍要决定，这里要不要类型检查器陪着走、早一点报错，还是把检查推迟。谁来做这个决定、用什么设计标准，并不清楚。

所以静态对动态仍是一个经典问题，配一套经典权衡。你该受过足够的教育，以便在每个具体情形里做尽量好的决定。

### 权衡表

下表是七段视频的压缩，不是新的论点。

| 维度 | 静态检查更强的一边 | 动态检查更强的一边 |
| --- | --- | --- |
| 异构数据 / 返回多种结果 | 调用点已经保证种类，体内可少写检查 | 不用先声明标签和构造器 |
| 有用但被拒绝的程序 | 标签打在你选择的位置，不是处处强制 | 同一个函数可以用于 int 和 bool，不必等类型系统变强 |
| 错误发现 | 参数个数、种类不配，使用文件时就报 | 容易的 bug 测试也会遇到；`+` 写成 `*` 两边都要测 |
| 性能 | 可以不带标签、不做检查 | 定义要求检查，实现可以在能证明安全时删掉；不用为类型写重复构造 |
| 重用 | 库的类型复杂但使用应简单；用错有运行前的消息 | cons 库天然适用于任何数据；有些重用静态类型表达不了 |
| 原型 | 类型在规格变化时充当被检查的文档；异常桩可以有任何类型 | 没写完的 case 不阻止你跑已经写完的部分 |
| 演化 | 改类型或加构造器，得到必须完成的待办，漏改会留下来 | 扩大可接受的参数可以保持旧调用者不变；待办不是强制的，所以可以改一半就测 |
| 文档 | 类型是机器检查的文档 | 文档靠名字、测试、注释、contract；contract 课程只点名 |
| 运行时检查 | 能证明的那类错误不必再查 | 查发生在值真正流到原语的时候 |

最后一行不是视频的独立论点，是第 1、4 组的推论，标成讲解。

## 可选：`eval` 与 `quote`

**【课程】** 有 `eval` 的语言——通常就叫这个名字——允许程序在运行时造出一些数据，再把这些数据当成程序去跑。

Racket 里，这份数据是 list：数、符号，以及嵌套的 list。这和给解释器写 AST 是同一件事。那时用的是自己语言的构造器；这里用 list 和符号，而且这棵树不是另一门语言的程序，就是 Racket 程序。正在运行的 Racket 程序造出另一段 Racket 语法，`eval` 去跑它。

因为开始运行时不知道会造出什么，运行时必须还带着一整份 Racket 实现。若 Racket 是用解释器实现的，`eval` 这个原语调用那个解释器即可。若是编译器，就要在可能用到 `eval` 的程序旁边带上足够做编译的东西，再运行编译结果。不是不可能。

人们因此常认为有 `eval` 的语言必须用解释器实现，并称之为解释型语言。这个直觉有一点道理，技术上不对。Racket 有时被这么叫，是因为它有 `eval`。你可以不用这个特性；即使用，也不必用解释器实现它。这就是上一章那句老话的收尾。

`eval` 常被过度使用。多数时候不合适。也有很强的用途。DrRacket 的 REPL 是用 Racket 写的，实现里几乎可以肯定用了 `eval`。REPL 的 E 就是 evaluate：read、evaluate、print、loop。课程不用它做有用的事，只为了让它不神秘。

```racket
(define (make-some-code1 y)
  (if y
      (list 'begin (list 'print "hi") (list '+ 4 2))
      (list '+ 3 4)))
```

`(make-some-code1 #t)` 得到一个 list。REPL 打印时不再给内部符号加引号，因为外层已经在引号语境里。它仍是数据：`(car (cdr foo))` 是 `(print "hi")`，再 `car` 得到符号 `print`。`(eval foo)` 把这份数据当代码跑：打印 `hi`，结果是 6。`(eval (car (cdr foo)))` 只跑打印。`(eval (car foo))` 把符号 `begin` 交给 `eval`，不是合法程序，报错。

手写 `list` 和 `quote` 很烦。`quote` 是特殊形式：它下面的东西都变成嵌套 list 和符号，不当成要现在求值的表达式。

```racket
'(begin (print "hi") (+ 4 2))
; 不是 begin 表达式。是 list：符号 begin，一个 list，再一个三元素 list
; 那个三元素 list 是符号 +、数 4、数 2。加号不会现在执行
```

**【课程】** `quote` 和 `eval` 在数学意义上互为逆。`quote` 下面不能做计算：你想算出来再放进程序的那一部分，也会变成程序文本。`quasiquote` 配 `unquote` 可以标记“这一段现在就算，把结果放进正在建造的语法”。课程让你自己查。

脚本语言常常把字符串交给 `eval`。那是具体语法，`eval` 得先解析再跑。打字也许更方便，把几段程序组合起来则更痛。那些语言也常有“字符串里嵌一段现在就求值”的东西，名字各异。Lisp、Scheme、Racket 几十年来叫 quasiquote 和 unquote。同一想法出现在不同语言里。

**【课程】** 这是最后一次强调：Racket 的具体语法和抽象语法如此接近——那些括号——对 `eval` 很方便。它可以接收 list，而不是字符串。

## 逐讲笔记

### 01 ML versus Racket

1. **问题：** 两门语言的最大差别是什么？怎样从每一边理解另一边？
2. **动机：** 现在两边都写过，可以比较。若从语法比，会错过类型系统这件真正不同的事。
3. **概念：** 子集看法；一个大 datatype 的看法；struct 是运行中新增构造器。
4. **机制：** ML 丢掉必错的程序，也丢掉能跑的异构程序。Racket 的原语是对标签做模式匹配，再把结果重新包上标签。
5. **代码：** `g` / `f` / `h`；返回布尔或 list 的 `f`；`theType` 的草图。
6. **执行：** 没有新的求值。这是翻译，不是新语义。
7. **PL：** 动态类型不是没有类型。至少可以把它看成“所有值同一个类型，运算前拆标签，运算后贴标签”。
8. **误区：** Racket 是 ML 的超集，所以只是少了检查。Struct 也能用 `Int` / `Pair` 那一套穷尽地说明。
9. **联系：** Section 5 的 `number?`。Section 6 的解释器在做显式的标签检查。Part A 的 datatype 是这幅图的来源。
10. **一句：** ML 少接受一些程序；Racket 可以看成每个值都带着构造器的一种 ML 风格。

### 02 What Is Static Checking?

1. **问题：** 静态检查在语言定义里到底拒绝什么？
2. **动机：** 下一节要比较优劣。还没定义对象就开始比较，讨论没有主体。
3. **概念：** 解析之后、运行之前的拒绝；目的对做法；ML 防什么、不防什么；检查时机是一条轴。
4. **机制：** 类型系统给变量类型、检查表达式，是做法。阻止哪类运行时行为，是目的。除以零可以从“键入之前”一直排到“返回无穷”。
5. **代码：** 无新程序。`hd` 空列表、数组越界、除以零是 ML 不防的例子。
6. **执行：** 浮点除以 `0.0` 得到无穷，调用者可能不用这个结果。这是比异常更晚的一档。
7. **PL：** 合法程序的集合是语言定义的一部分。外挂警告不是这个集合。检查器不知道你的规格，就不能抓住写反的分支。
8. **误区：** 静态检查就是编译器查类型。动态类型语言完全不做静态检查。运行时异常是能多晚就多晚的报错。
9. **联系：** 你的解释器在运行时拒绝坏值。类型检查器试图在运行前证明某些拒绝不会发生。
10. **一句：** 静态检查是运行前按程序结构拒绝一些已经能解析的程序；它的目的是一类运行时行为不会发生。

### 03 Soundness and Completeness

1. **问题：** “类型系统是对的”怎样说才不依赖感觉？
2. **动机：** 假阳性看起来像检查器太笨。需要一个词把“禁止假阴性”和“允许假阳性”分开，并说明为什么不能两个都不要。
3. **概念：** 相对于 X 的 sound / complete；假阴性 / 假阳性；不可判定性；不 sound 时的四条路。
4. **机制：** 通过检查则不会做 X，是 sound。不会做 X 的程序都不被拒绝，是 complete。终止、sound、complete 不能三者兼得，于是选择前两个。
5. **代码：** `f1` 到 `f5`，都是“不会除以字符串”却被拒绝。
6. **执行：** 这些函数若按它们实际会被调用的方式跑，不会做 X。检查器仍然拒绝整个程序。
7. **PL：** 不可判定性在软件开发里的日常形式，就是类型检查器必须近似，而且近似通常偏向多拒绝，而不是少拒绝后让坏行为发生。
8. **误区：** Sound 意味着拒绝所有有 bug 的程序。Complete 意味着能找出所有 bug。假阳性是实现没写好，理论上可以消除而不引入假阴性、也不让检查器不终止。
9. **联系：** 上一讲的目的 X。C/C++ 是“不 sound，而且没有动态退路，失败了可以做任何事”。
10. **一句：** 相对它声称要防的 X，好的类型系统宁可错杀，不可放过；而且它无法既不错杀、也不放过、还保证检查结束。

### 04 Weak Typing

1. **问题：** Weak typing 和动态类型是不是一回事？
2. **动机：** 口号把它们混在一起。不分开，就会把 Racket 的运行时检查说成 C 的着火语义。
3. **概念：** 通过静态检查仍可做任何事；标签和检查的空间时间；“strong types for weak minds”；实现可以删永不失败的检查。
4. **机制：** C/C++ 的数组越界不必在运行时被定义成错误。Racket 的定义要求：若检查会失败，必须表现为错误。
5. **代码：** 无。原语规则的例子是字符串加数、数组越界、缺参数填 79。
6. **执行：** Weak 语言里，无意义操作发生后，实现不必报错。改原语规则的语言里，操作有定义，只是定义可能静静地给一个程序员没想要的值。
7. **PL：** 静/动是“何时检查”。强/弱在本课的用法里是“没检查到的坏行为是否仍被定义成必须失败”。原语是否接受更多种类的值，是第三条轴：求值规则。
8. **误区：** 动态 = weak，静态 = strong。数组越界是类型系统的事，所以 weak typing 就是类型太弱。Racket 实现若删掉一次证明不会失败的检查，就变成了 C。
9. **联系：** Soundness 那一讲的第四条路就是这里的着火语义。Java、ML 是静态且会在剩余的动态错误上失败；Racket 是动态且会失败。
10. **一句：** Weak 是“既不静态拦，也不动态拦，失败了可以做任何事”；Racket 是动态的，不是 weak 的。

### 05 Static versus Dynamic, Part 1

1. **问题：** 方便、表达力、早发现 bug，两边各有什么成立的理由？
2. **动机：** 人们通常只背自己喜欢的那一边。课程要把对应的反驳也放在同一张桌子上。
3. **概念：** 异构返回值；contract 被点名但未演示；`f` 不能对 `g` 既传 int 又传 bool；`pow1` 的参数形式；`pow2` 的 `+` 与 `*`。
4. **机制：** 见上文第 1 到第 3 组。
5. **代码：** `f` 与 `(lambda (x) (cons x x))`；两个 `pow`。
6. **执行：** Racket 的 `f` 得到两个 pair 组成的 pair。`pow2` 两边都给出 13，而不是 81。
7. **PL：** 标签可以在语言里强制处处存在，也可以由程序员用 datatype 选择性地加。早发现的错误和测试才能发现的错误不是同一类。
8. **误区：** 静态类型所以不用测试。动态类型所以不能写立方而不担心参数。ML 拒绝的程序都是没意义的。
9. **联系：** `theType` 是第 2 组里静态这边的极端。Section 5 的运行时错误是第 3 组里动态这边付出的时间。
10. **一句：** 方便、表达力和早报错都有对偶的论点；`+` 写成 `*` 提醒你类型不是规格。

### 06 Static versus Dynamic, Part 2

1. **问题：** 性能、重用、原型和长期修改，是否改变第 5 讲的平衡？
2. **动机：** 作业式的“写完、测过、就完成”不是大多数软件的生命周期。权衡要在规格还在变、以及版本已经发出去之后再看一次。
3. **概念：** 标签的空间；编译器删除重复检查；向后兼容；待办清单；Typed Racket 仍是研究问题。
4. **机制：** 见上文第 4 到第 7 组。
5. **代码：** `(+ x x)` 然后 `(* x 4)`；`f` 从加倍扩成也能拼接字符串。
6. **执行：** 定义上有多次检查的片段，实现可以只做一次。改 ML 函数的类型会让旧调用不再通过；改 Racket 的可接受参数可以让旧调用照旧成功。
7. **PL：** “何时检查”是每个软件、甚至每个库都要做的工程选择。一种语言两边都支持，并不自动替你做这个选择。
8. **误区：** 动态语言的每次加法都必然在发布的实现里检查两次。静态类型使演化总是更难，或总是更容易。选了 Typed Racket 就不再有权衡。
9. **联系：** 浮点无穷是更晚的一档；第 7 组是软件已经存在之后的同一条轴。Soundness 解释了为什么静态这边必然有你不想要的拒绝。
10. **一句：** 没有总冠军。问的是：这件事我要在运行前证明，还是留到测试和运行。

### 07 Optional: eval and quote

1. **问题：** 运行中的程序怎样构造并执行另一段同一语言的程序？
2. **动机：** 解释器那一讲留下了“有 `eval` 是否等于解释型语言”。这里把特性本身看清楚。
3. **概念：** 运行时的 list 当 Racket 程序；实现必须仍在场；`quote`；quasiquote 只被点名；字符串 `eval` 是具体语法。
4. **机制：** `eval` 接收已经是树的数据。`quote` 阻止它下面的表达式被现在求值，把它变成树。两者互逆。
5. **代码：** `make-some-code1`；`'(begin (print "hi") (+ 4 2))`。
6. **执行：** `eval` 打印 `hi` 并得到 6。只 `eval` 打印那一段就只打印。`eval` 符号 `begin` 报错。
7. **PL：** `eval` 是语言里的解释器挂钩。它要求运行时有实现，不要求该实现是解释器。括号使具体语法和抽象语法接近，所以 `eval` 可以吃 list 而不是字符串。
8. **误区：** 有 `eval` 的语言就是解释型语言。`quote` 下面的 `(+ 4 2)` 会先算成 6 再放进 list。`eval` 是写程序的常规工具。
9. **联系：** Section 6：程序员用构造器写 AST，解释器跑树。这里树是 list，语言是 Racket 自己。REPL 是 `eval` 的一个真客户。
10. **一句：** `eval` 跑的是运行时造出来的语法树；`quote` 是把语法冻成那棵树的特殊形式。

### Wrap-up

1. **问题：** Part B 结束时，手上有了什么，Part C 为什么还要继续？
2. **动机：** 否则面向对象会看起来像另一门课，而不是同一套定义方法的下一半。
3. **概念：** 动态类型的函数式；延迟求值；自己实现的闭包；静/动权衡。Part C：对象、相反的分解、更灵活的类型。
4. **机制：** 无新机制。视频是地图。
5. **代码：** 无。几何解释器是 Part C 的作业，不是这里的代码。
6. **执行：** 无。
7. **PL：** 方法查找会被定义成比闭包更复杂的规则。解释器可以解释几何对象的相交，不必解释又一门通用语言。
8. **误区：** Part B 已经把语言讲完了。Part C 因为你写过类，所以没有新的语义。课程反面向对象。
9. **联系：** 闭包的实现是方法查找的对照物。`'a` 是 generics 那一讲的对照物。
10. **一句：** Part B 让你能实现一门有闭包的语言，并说清类型检查保证什么；Part C 用对象把分解问题的另一种方式放到旁边。

## Section 7 Summary

### 这一 Section 的核心问题

把“是否有类型”换成三个更小的问题：检查发生在运行前还是碰到值的时候；检查若失败，语言是否必须表现成错误；检查为了终止和 sound，必须多拒绝哪些其实安全的程序。

### 知识地图

```text
何时发现 X
    键入前 … 编译时 … 运行到那一行 … 返回一个表示失败的值
         │
         ├── 静态检查：解析后、运行前拒绝。是语言定义的一部分
         │       目的：某类行为不会发生
         │       做法：给表达式定类型的递归检查，只是做法之一
         │
         ├── Sound：没有假阴性。通过则不会做 X
         ├── Complete：没有假阳性。不会做 X 的都不拒绝
         └── 终止 + sound ⇒ 一般不能 complete
                  │
                  ▼
         不检查、失败了可以做任何事 = weak
         不是“动态”的同义词

Racket：动态，不是 weak。值有标签。可以看成一个大 datatype
ML：静态，sound 于它列出的那些 X，不防 hd []、越界、除零、写反的分支
```

### 最重要的概念

1. 静态检查是语言定义里的拒绝，不是外挂警告。
2. 目的和做法分开。类型规则是做法，要防的行为是目的。
3. Sound / complete 都相对于一个 X。
4. 假阳性是 sound 加终止的代价，不是偶然的实现缺陷。
5. Weak typing 是着火语义。Racket 不是。
6. 原语接受更多值，是求值规则变了，不是检查变晚了。
7. 七组权衡都成立。Typed Racket 不取消选择。
8. `eval` 不把语言定义成解释型的。

### 最重要的代码模式

本节几乎没有新模式。要记住的是判断模式：

```text
程序通过了检查，是否意味着 X 不会发生？     → 在问 sound
程序被拒绝，是否可能其实不会做 X？           → 在问 complete
X 发生时，语言要求报错，还是允许任意行为？   → 在问 weak
```

### 容易混淆

| 混淆 | 分辨 |
| --- | --- |
| 动态类型 = 没有类型 | 值有标签。可以看成只有 `theType` |
| 静态 = 强，动态 = 弱 | 静/动是何时查。Weak 是查失败了也不必表现为错误 |
| Sound = 没有 bug | Sound 只针对声明的 X。写反的 `then` 不是 X |
| Complete = 理想且可达到 | 和非平凡 X、终止、sound 冲突 |
| 假阴性 | 接受了会做 X 的程序。课程把“说不会，其实会”叫假阴性 |
| `eval` = 解释型语言 | 只说明运行时要有实现 |

### 和上一 Section 的关系

你写的解释器是动态检查的样本：合法树上的坏值必须在递归返回后被拒绝。类型检查器想在任何输入跑起来之前证明某些这种拒绝不会发生。它做不到又终止、又 sound、又 complete，所以 ML 会拒绝 `f2` 那种死代码里的坏运算。C 则连运行时的拒绝都不保证。

Struct 作为“运行中新增构造器”，说明 Racket 的一个大类型并不是在程序开始前就封闭的。这是 ML 的穷尽性不愿付出的代价。

### 为 Part C 准备了什么

比较静态和动态之后，还有一种组织程序的方式没进这套笔记：对象、类、方法查找。Part C 承诺用同样的定义风格处理它，并回到类型变量、generics 和子类型。Part B 的 quiz 不考那一部分。Part C 末的考试会把两边放在一起。

## Engineering Connection

**【课程】** 浮点无穷是“比异常更晚”的真实设计。C 的着火语义是系统软件里每周都能找到的事故来源，不是历史趣闻。Typed Racket 是“一个项目里两种检查”的真实尝试，也是未完成的研究。REPL 是 `eval` 的正当客户；多数其他 `eval` 使用是过度使用。

**【扩展】**

- 生产系统里的静态分析工具，就是课程说的“语言定义之外的检查”。它们可以不 sound，因为它们不定义合法程序的集合。不要把警告器的漏报说成语言不 sound。
- Rust 的安全子集试图对更多的 X（例如数据竞争、悬垂引用）做 sound 的静态检查，并用更复杂的类型减少假阳性。课程没讲 Rust。它是“sound、终止、于是不 complete”这条设计的又一个点，不是反例。
- 渐进类型（gradual typing）是 Typed Racket 所在的研究区。边界上的契约检查、谁为失败负责，比“文件可选类型”这句口号多得多。课程只说到开放问题。

## 检查题

1. 为什么“ML 是 Racket 的子集”既解释了类型系统的好处，也解释了它的代价？各举一个课程里的程序。
2. 用 `theType` 说明：动态类型是否意味着没有类型？`pair?` 在这幅图里是什么？
3. `struct` 为什么破坏了“一个封闭的 datatype”这幅图？这和 ML 的穷尽性有什么关系？
4. 静态检查的定义里，哪三件事必须已经发生或尚未发生？外挂的 bug 警告算不算？
5. ML 保证查找变量一定成功。它不保证哪三件人们可能以为类型系统会管的事？
6. 除以零的四档检查时机里，哪一档是浮点实际采用的？为什么那不算“非法操作必须报错”？
7. 相对于 X，sound 和 complete 各禁止哪种错误判断？医学类比里，假阴性是检查器说了什么？
8. `f2` 和 `f4` 为什么是假阳性？为什么不能指望把所有这种假阳性都去掉，同时保持 sound 和终止？
9. 类型系统不 sound 时，四条路分别是什么？哪一条是 C/C++？
10. 为什么 Racket 实现删掉一次证明不会失败的 `number?`，仍然不是 weak typing？
11. `"foo" + 3` 得到 `"foo3"`，这是动态检查晚了一点，还是求值规则变了？
12. `pow1` 和 `pow2` 各支持哪一边的论点？为什么两边合在一起仍得不出“不必测试”？
13. 把 `int -> int` 扩成也能接受字符串，为什么 Racket 可以不破坏旧调用者，ML 不行？静态这边如何把这种痛苦说成好处？
14. 讲师为什么说“静态还是动态”问得太粗？Typed Racket 解决了这个粗问题吗？
15. 为什么有 `eval` 不推出“必须用解释器实现”？`quote` 和字符串版 `eval` 的输入有何不同？

## Answers

1. 子集把必错的程序扔掉，例如把 `y` 同时送给 `+` 和 `car` 的 `f`，以及把 `cons` 结果送给只做加法的 `g` 的 `h`。它也扔掉能跑的程序，例如有时返回布尔、有时返回 list 的函数，以及混合 list。好处是不必运行就知道某些调用必错；代价是有意义的程序进不了语言。
2. 不是。每个值都是 `theType` 的一个构造，标签总在。`pair?` 是对这个 datatype 的模式匹配：是 `Pair` 就真，否则假。`car` 是同一匹配，匹配失败就异常。
3. 因为 `struct` 在运行中增加一种新构造器。若类型在程序开始前就封闭，穷尽的 case 可以检查；若运行中还能加构造器，你不能再证明 case 已经写全。这是 ML 不把一般 datatype 做成可扩展的原因。`exn` 是一个有限的例外。
4. 解析已经成功，运行尚未开始，程序被拒绝。拒绝规则属于语言定义。外挂警告不改变合法程序的集合，所以不是这个定义里的静态检查，尽管它有用。
5. `hd` 空列表、数组下标越界（只保证下标是 int）、除以零。另外它也不保证你没把 `then` 和 `else` 写反，因为那需要规格。
6. 返回无穷，让调用者决定用不用。语言可以规定除以零有一个值，而不是规定它必须失败。整数通常选择失败，是设计，不是这条轴上唯一说得通的点。
7. Sound 禁止接受会做 X 的程序，即假阴性。Complete 禁止拒绝不会做 X 的程序，即假阳性。假阴性是检查器说“不会做 X”，病人其实会。
8. `f2` 的坏除法在 `if true` 的死分支里。`f4` 的条件对所有 int 都走安全分支，因为 `x <= abs x`，但检查器不懂这个事实。非平凡性质上，总是终止、sound、complete 不能同时成立。要终止又 sound，就必须留下一些假阳性。
9. 收紧类型系统直到没有假阴性；保留动态检查当退路；给 X 一个默认结果，例如 0；让程序在 X 发生时可以做任何事。最后一条是 C 和 C++。
10. 因为语言定义仍说：若那次检查会失败，就必须表现为错误。实现只在能证明不会失败时删检查。Weak 是失败了也不必有定义的错误行为。
11. 求值规则变了。加法被定义成会转换并连接，这个程序是合法的，不是“晚一点才发现的类型错误”。它扩大了合法程序，并可能静静地做出程序员没想要的字符串。
12. `pow1` 支持静态：错误的调用形式在运行前被拒绝，Racket 要到调用或递归调用才发现。`pow2` 支持动态这边的反驳：类型通过仍得到 13，因为 `+` 和 `*` 类型相同，两边都要靠测试。所以静态检查没有取消测试。
13. Racket 的新函数对旧的数字参数行为不变，旧调用仍合法。ML 的类型从 `int -> int` 变成 one-of，旧调用的类型对不上，还要加构造器和匹配。静态的好处是：检查器列出每一个被破坏的调用，改完并通过之后，你知道没有遗漏。动态这边则要靠测试去找仍假设旧返回值的地方。
14. 因为每种要防的事都可以单独选择何时查，软件的原型阶段和维护阶段答案还可能不同。Typed Racket 让不同文件走不同选择，但谁来选、按什么标准选，仍是开放问题。它没有取消权衡。
15. `eval` 只要求运行时还有能力执行新造出来的程序。那个能力可以是编译器：译完再跑。`quote` / `eval` 的输入是已经接近 AST 的 list。字符串版 `eval` 的输入是具体语法，里面还要做一次解析。
