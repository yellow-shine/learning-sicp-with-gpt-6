# Section 6.2 解释器：用一种语言执行另一种语言

标注见 `00-course-map.md`。本章覆盖 Section 6 的第四、五讲：语言如何被实现，以及解释器可以假设什么、必须检查什么。变量、环境和闭包在 `07`。公式汇总在 `09`。

上一章的 `eval-exp` 已经在执行一门只有常数、取负、加法和乘法的语言。这一章把这件事放回“实现一门编程语言”的地图里，并划出一条作业必须遵守的错误边界。

## 从字符串到值

```text
Programming Language
        │
        ▼
Concrete Syntax          程序员写下的字符串
        │
        ▼
Parser                   语法错误在这里：括号位置、关键字位置
        │
        ▼
Abstract Syntax Tree     仍是语法，但是树：哪种构造，子树是什么
        │
        ▼
（可选）Type Checker     又一批错误。作业不做这一步
        │
        ▼
Interpreter 或 Compiler  真正跑起来，或翻译成能跑的另一种程序
        │
        ▼
Value / 行为
```

**【课程】** 典型流程从一段字符串开始，叫具体语法（concrete syntax）。Parser 的工作包括给出语法错误。没有语法错误时，输出是抽象语法树（AST）：一棵说明用了哪些构造、构造如何嵌套的树。

幻灯片上的例子，口头描述是一次函数调用。树的形状是：

```text
        Call
       /    \
 Function    Const 4
 arg: x
 body:        （若要负四，这里可以是 Negate，而不是直接 Const）
   Add
  /   \
 Var x  Var x
```

字幕里有一处先说了 negation、又改口说示例应是 const。可靠的结论是：树的节点是语言构造，叶子是常数或变量，而不是“源码第几列的字符”。

然后才可能有类型检查器，沿着这棵树再报错。例如传给函数的不是数而是另一个函数：能解析，能建成 AST，但类型错误。没有这类错误，AST 才交给“其余的实现”，由它运行并给出答案。

**【讲解】** 所以 parser 不是解释器。Parser 回答“这段文本是不是一棵合法的树，树长什么样”。解释器回答“这棵树按语义跑出来是什么”。把二者并成一个词，后面会分不清错误该由谁负责。

## 两种基本实现，以及为什么没有“解释型语言”

**【课程】** 要在语言 A 里实现语言 B，有两条基本路。

```text
解释器（interpreter）
  用 A 写一个程序
  它接收 B 的语法树
  算出 B 程序的答案
  更好的名字也许是 evaluator 或 executor
  大家叫了几十年 interpreter，课程沿用

编译器（compiler）
  也用 A 写成
  它把 B 的程序翻译成语言 C 的程序
  再靠 C 已有的实现去跑
  更好的名字是 translator
  若 C 是硬件能直接跑的二进制，硬件就是 C 的实现
```

A 有时叫元语言（metalanguage）。本节和作业里，必须在脑子里分开：哪一段是用来实现语言的 A，哪一段是被实现的 B。

现实比二选一复杂。**【课程】** 现代实现常常把两种想法叠在一起。Java 多数实现先编译到字节码（bytecode，字幕写成 bite code），再有一个字节码解释器；解释器里还可以再编译到硬件。x86 芯片甚至会在程序运行时把指令再翻译成更小的内部指令，然后解释那些。Racket 的实现也是类似的混合，不是 Java 特有。概念上仍是那两块：解释，或编译。

语言由书面的语义规则定义。用解释器、编译器还是二者的混合，是实现细节。

> 因此不存在“编译型语言”或“解释型语言”这种说法。存在的是：某个实现使用了解释器，或某个实现使用了编译器。

**【课程】** “C 比 Lisp 快，因为 C 是编译型语言而 Lisp 是解释型语言”这种老话，按定义就不成立，也不怎么有意义。讲师会礼貌地纠正。本节末尾他补了一个使老话似乎有点道理的特征：有的语言有 `eval`。程序运行时可能还要执行同一种语言的另一段程序，于是实现必须在运行时仍在场。但这不要求 `eval` 本身用解释器实现；它同样可以是一个编译器。可选讲在 Section 7，见 `08`。

**【讲解】** 速度差异若存在，来自具体实现做了什么检查、生成了什么代码、能否去掉标签，不来自语言身份证上的“编译”或“解释”二字。Section 7 谈性能时会回到标签和检查，仍不把语言分成这两类。

## 作业的捷径：不写 parser，让程序员直接写 AST

**【课程】** Homework 5 不写 parser，也不写类型检查器，只写解释器。若设置得当，parser 可以省掉。

办法：语言 B 的程序员不写字符串，直接用语言 A 的构造器把 AST 写出来。A 是 Racket，B 的构造器是 struct。写出来的 Racket 数据就是 B 的程序。

```racket
(call (function (list "x")
                (add (var "x") (var "x")))
      (const 4))
```

把这行横过来读，就是上面那棵树。`call` 有两棵子树，`function` 有参数列表和函数体，函数体是 `add`。想要负四，就在常数外包 `negate`。这不是新主意：上一章用 `const`、`negate`、`add`、`multiply` 搭起来的东西，已经是一门小语言。课程叫它算术语言。

| 角色 | 在算术语言这个例子里是什么 |
| --- | --- |
| 元语言 A，宿主语言（host language） | Racket |
| 被实现的语言 B，对象语言（object language） | 算术语言。课程后来说作业语言叫 MUPL |
| 程序 | 一棵 Racket struct 树 |
| 实现 | `eval-exp`。它就是解释器：吃进树，给出语言里的答案 |

**【课程】** 我们已经实现过一门编程语言。它有常数、取负、加法和乘法。程序是 Racket 数据，同时是那门语言的程序。剩下的只是实现比加减法更有趣的构造。变量和闭包是后面的讲，也是作业的主体。

**【讲解】** “用一种语言实现另一种语言”在这里非常具体：Racket 的函数在求值 Racket 的 struct；那些 struct 的意义是另一门语言的表达式。`(add (const 3) (const 4))` 里的 `add` 是 Racket 函数，调用它立刻得到一棵树，并不做加法。加法发生在 `eval-exp` 看到这棵树的时候。若分不清这两次“调用”，就会把宿主语言的函数当成对象语言的函数。

对象语言（object language）这个词课程用 “language B” 说，不总用 object language。下面为了和宿主语言对照，使用这个标准叫法，并标成讲解用语。

## 合法 AST 与值：两条不能混的错误界

**【课程】** 写语言 B 的解释器时，要分清 B 的程序可能有哪类错，以及解释器是否负责把它们说清楚。这也是宿主语言和对象语言的分界，作业按这个标准给分。

到目前为止的设置：

1. 用 Racket struct 定义 B 的抽象语法。
2. B 的程序员用这些构造器在 Racket 里写程序。
3. 解释器是像 `eval-exp` 这样的递归函数。

然后是这条界：

| | 解释器可以怎样 |
| --- | --- |
| 语法树不合法 | 可以假设不会发生。发生了就崩溃、给出奇怪信息，可以 |
| 递归求值得到的值种类不对 | 必须检查。不能假设。要给出说人话的错误，不要把 `car` 之类的实现细节露出去 |

### 什么叫合法 AST

**【课程】** Struct 是动态类型的。声明

```racket
(struct const (int) #:transparent)
(struct negate (e) #:transparent)
(struct add (e1 e2) #:transparent)
(struct multiply (e1 e2) #:transparent)
```

之后，没有任何东西迫使 `int` 是数、`e` 是合法 AST。合法 AST 是所有 Racket 能造出来的树的一个子集。解释器只承诺处理这个子集。

不合法、因此不必好好处理的例子：

```racket
(multiply (const 1) "hi")          ; 第二个“子表达式”是字符串
(negate -7)                        ; 常见笔误。negate 里面应是表达式
(negate (const -7))                ; 这才合法
(const #t)                         ; const 的字段应是数。课程把这叫 non-test
```

这些不是语言 B 的程序。解释器可以给出 “expected number, given true” 这种来自 Racket 底层的坏消息。

### 什么叫值

**【课程】** 解释器返回的是表达式，但不是任意表达式。任何一次调用，包括递归调用，都应返回一个 value：一种求值到自身的表达式。

在只有算术的语言里，值就是 `const`，例如 `(const 17)`。若解释器返回的仍是 `add`、`negate` 或 `multiply`，解释器有 bug：它还没把那棵树算完。

语言有不止一种值时，事情才真正开始。作业语言里还会有 pair：不是每个 pair 都是值，但两个成分都是值时，这个 pair 是值。还可以有布尔、字符串。闭包是值。作业里会有闭包。

所以递归求值一个子表达式之后，可能得到若干种值中的一种。不能看到“我在做加法”就假定两边都是数。

### 必须检查的那种错

课程把语言扩大成：布尔、数值相等、条件，外加原来的算术。

```racket
(struct bool (b) #:transparent)          ; b 应是 #t 或 #f
(struct eq-num (e1 e2) #:transparent)    ; 两个表达式，求值后应是数，再比是否相等
(struct if-then-else (e1 e2 e3) #:transparent)
```

这些字段若本身是合法 AST，整棵树就是合法程序。运行时仍可能用错值：

```text
(add (const 17) (bool #f))
```

这是合法的树：`add` 的两棵子树都是表达式。解释器必须发现“把布尔拿去加”，并给出适当的说明。不应当说“试图取 car”或“找不到某字段”。那是实现的内部。

另一个合法但会错的程序，课程用来当 `test2`：乘法的一边最终是 `const -4`，另一边是 `if-then-else`。条件的测试不是假，于是走假分支，假分支求值成真。于是解释器最终试图把 `-4` 和真相乘。错误应像“把非数拿去运算”，而不是 Racket 的内部消息。

`test1` 是合法且结果正确的树：`Multiply(Negate(Add(Const 2, Const 2)), Add(... 7 ...))` 一类，结果应是 `-28`，并且以对象语言的值返回，即某个 `const`。字幕先说 minus 28，后来的 REPL 描述里出现过 const 28 的口误。算术本身是负二十八；返回形式是 `const` 包着那个整数。以讲师对这棵树的口头计算为准：负四乘七，是负二十八。

### 错的解释器错在哪条假设

**【课程】** 错的版本对 `test1` 完全正确。它的 `cond` 对每种表达式有一支。值，即 `const` 和 `bool`，整棵返回。`negate` 则取出子表达式、递归、用 `const-int` 取出整数、取负、再用 `const` 包起来。

错在 `const-int` 之前没有检查。它假设递归结果一定是 `const`。语言里不只有这一种值。`add`、`multiply`、`eq-num` 同样假设两个递归结果都是 `const`。`if-then-else` 假设测试的结果是 `bool`，然后读 `b` 字段。`eq-num` 用 Racket 的 `equal?` 比较两个数，再必须用 `bool` 构造器把 `#t` / `#f` 包成对象语言的值。解释器不应返回 Racket 的布尔，正如它不应返回裸整数。

对的版本：不需要检查的支路就不检查。`const` 和 `bool` 已经是值，合法 AST 的假设允许直接返回。需要用结果的支路，先把递归结果放进局部变量，再问谓词。

```text
eval(Const _) = 那个 Const 本身

eval(Negate e) =
    let v = eval(e) in
    if v 是 Const then Const( - (取出 v 的整数) )
    else error "negate applied to non-number"

eval(Add e1 e2) =
    let v1 = eval(e1)
        v2 = eval(e2) in
    if 两者都是 Const
    then Const( 整数相加 )
    else error "add applied to non-number"

eval(Multiply e1 e2) = 同 Add，运算改成乘

eval(Bool _) = 那个 Bool 本身

eval(EqNum e1 e2) =
    同 Add 的检查
    然后 Bool( 两个整数是否 equal )

eval(If e1 e2 e3) =
    let v = eval(e1) in
    if v 不是 Bool then error "if test not a bool"
    else if 取出的布尔为真 then eval(e2) else eval(e3)
```

**【课程】** Racket 实现就是这个 `cond`：每种构造一支；需要结果的种类时用 `const?` 或 `bool?`；错误用 `error` 写出对象语言层面的句子。`if` 的两支仍是递归的 `eval`，不要在检查之前就假定测试是布尔。

三条调用的预期：

| 输入 | 对的解释器 | 错的解释器 |
| --- | --- | --- |
| `test1`，合法且种类正确 | `(const -28)` | 同样正确 |
| `test2`，合法 AST，运行时种类错误 | 清楚的对象语言错误 | 坏消息，例如在 `const-int` 内部爆炸 |
| `non-test`，`(const #t)` 这种非法 AST | 可以给出可怕的底层消息 | 同样可以可怕 |

**【讲解】** 这是两条不变量，后面加变量和闭包时仍然有效：

```text
1. 进入 eval 的树若不是合法 AST，解释器没有义务诊断。
2. eval 的每次返回都必须是值。
3. 使用一个值之前，必须确认它是这种构造所要求的那一种值。
```

第 2 条若被违反，第 3 条会在错误的层次上失败：你还没发现“返回了 Add”，就对它取了 `const-int`。第 3 条若被违反，对象语言的类型错误就伪装成宿主语言的字段访问错误。

作业语言把常数写成 `int`，不是这里的 `const`。MUPL 是 Made Up Programming Language。上面的规则是课程讲的语义，不是一份可粘贴的作业解答。作业还有这里没出现的构造；不要把这份算术解释器当成 MUPL 的全部。

## 宿主语言的 `+` 不是对象语言的加法

一次正确的加法里有两次完全不同的“加”：

```text
建树（Racket 在求值构造器调用）
  (add (const 3) (const 4))
  → 一棵 add 树。此时没有做 3+4

解释（eval-exp 看到 add）
  递归得到 (const 3) 和 (const 4)
  确认两者都是 const
  用 Racket 的 + 把 3 和 4 加起来
  用 const 把 7 包回对象语言
  → (const 7)
```

**【课程】** `eq-num` 的字段不是数，甚至不是 `const`。它们是表达式。和 `add` 一样：先求值，再对结果做宿主语言的运算，再把运算结果包回对象语言。

这就是 metalanguage 与 language B 的日常形式。Racket 的 `+`、`equal?`、`if` 是实现工具。对象语言的 `add`、`eq-num`、`if-then-else` 是被实现的构造。用宿主语言的 `if` 去实现对象语言的条件，是允许的，因为你在解释器里；把宿主语言的 `#t` 直接返回给对象语言的调用者，是不允许的，因为那越界了。

## 逐讲笔记

### 04 Implementing Programming Languages

1. **问题：** 一门语言的实现从程序员写下的文本走到答案，中间有哪些阶段？作业为什么可以跳过其中两段？
2. **动机：** 否则 `eval-exp` 只是一个递归函数，看不出它在实现语言，也分不清 A 和 B。
3. **概念：** 具体语法、parser、AST、类型检查器、解释器、编译器、元语言。字节码和硬件翻译是混合实现的例子。
4. **机制：** 字符串到树，树到答案或到另一种语言的程序。作业用构造器直接写树，`eval-exp` 就是解释器。
5. **代码：** `(call (function ...) (const 4))` 这种树的写法。算术语言的 `eval-exp` 在上一章。
6. **执行：** 构造器调用产生树，不产生算术结果。结果要等解释器跑过这棵树。
7. **PL：** 语言由语义定义，不由“它是编译的还是解释的”定义。`eval` 只说明实现在运行时还得在场，不说明必须用解释器。
8. **误区：** 解释器就是 parser。有解释器的语言叫解释型语言，所以更慢。跳过 parser 等于没有 AST。
9. **联系：** Section 5 的括号已经让“文本即树”变得容易。Struct 让树的节点成为新数据。`eval-exp` 是这条链的第一台能跑的机器。
10. **一句：** 解释器是 `eval(树) → 值`；编译器是把树翻译成另一门已有实现的语言。

### 05 What Your Interpreter Can and Cannot Assume

1. **问题：** 解释器要诊断哪些错误，又可以在哪些错误上崩溃？
2. **动机：** 作业若把所有奇怪的 Racket 值都诊断一遍，会把非法语法和对象语言的类型错误混在一起；若什么都不查，合法程序的类型错误会变成 `const-int` 的内部异常。
3. **概念：** 合法 AST；value；一种值与多种值；宿主语言错误与对象语言错误。
4. **机制：** 假设树合法。递归结果先绑定，再用谓词检查，然后才取出字段、做运算、包回构造器。
5. **代码：** `bool`、`eq-num`、`if-then-else`，以及对、错两个 `eval-exp` 的差别。
6. **执行：** `test1` 两边都得到负二十八的 `const`。`test2` 只有检查过的版本给出好消息。`(const #t)` 两边都可以给出坏消息。
7. **PL：** 对象语言的类型规则是解释器的责任，即使对象语言没有静态类型检查器。宿主语言的动态检查会在你忘了检查时“帮忙”崩溃，但那个崩溃不是对象语言的语义。
8. **误区：** 动态类型的对象语言不需要在解释器里检查类型。`(negate -7)` 应该得到 7。返回 Racket 的 `#t` 和返回 `(bool #t)` 一样。解释器返回 `add` 只要最后能印出来就可以。
9. **联系：** 上一章的 `exp -> exp`。Section 5 的 `number?` 就是这种运行时种类检查；现在你在为自己的值种类写同样的检查。闭包成为值之后，调用前要查的就是“是不是闭包”，规则相同。
10. **一句：** 可以假设树长得对；不能假设递归算出来的值是你希望的那一种。

## 本范围小结

### 核心问题

编程语言的实现，是把一种表示（树，或另一种语言的程序）按书面语义变成行为。作业选择的表示是宿主语言里的 struct 树，选择的引擎是递归的 `eval`。

### 知识地图

```text
字符串（具体语法）
    │  parser          作业跳过：人直接写树
    ▼
AST（struct 树）
    │  合法 AST 是子集。子集之外可以崩溃
    ▼
eval
    │  每次返回 value
    │  使用 value 前检查种类
    ▼
对象语言的值（const、bool，以后还有 pair 和 closure）
```

旁边的另一条路是编译：同一棵树翻译到语言 C，再运行 C。混合实现只是把两条路接成管道。

### 最重要的代码模式

```racket
(cond [(const? e) e]
      [(add? e)
       (let ([v1 (eval-exp (add-e1 e))]
             [v2 (eval-exp (add-e2 e))])
         (if (and (const? v1) (const? v2))
             (const (+ (const-int v1) (const-int v2)))
             (error "add applied to non-number")))])
```

宿主语言的 `+` 只出现在确认种类之后，结果立刻包回 `const`。

### 容易混淆

| 混淆 | 分辨 |
| --- | --- |
| Parser 与 interpreter | 前者产树或语法错误。后者消费树，产值或对象语言错误 |
| 编译型语言与有编译器的实现 | 课程否认前一个词。后一个是事实 |
| 宿主语言的值与对象语言的值 | `#t` 不是 `(bool #t)`。`7` 不是 `(const 7)` |
| 非法 AST 与运行时种类错误 | `(negate -7)` 可以乱报。`(add (const 1) (bool #f))` 必须说清楚 |
| 构造器调用与解释 | `(add e1 e2)` 建树。`eval` 才做加法 |

### 和上一范围的关系

Struct 提供了 AST 节点的种类。`pair?` 为假这件事，让解释器不会把一棵 `add` 误当成 Racket 的 list 去 `cdr`。`eval` 返回 `const` 而不是裸整数，是上一章为了多种值所做的选择；这一章说明多种值一旦存在，每次递归之后都必须分支。

### 为下一范围准备了什么

变量求值不是算术。它要在一个“名字到值”的映射里查找。函数也不是值本身：求值一个函数定义，要产生一个带着当时环境的闭包，闭包才是值。下一章把 `eval(e)` 改成 `eval(e, env)`，并说明为什么函数调用不能使用调用者的环境。

## Engineering Connection

**【课程】** 语言实现常常是编译和解释交替：Java 的字节码、JIT、以及芯片内部的再翻译。有 `eval` 的语言必须在运行时带上某种实现，REPL 就是这种客户。几何语言的解释器会在 Part C 出现，说明解释器不等于“又一门通用编程语言”。

**【扩展】**

- SQL 引擎、规则引擎、配置语言、模板引擎，都是“一种小语言 + 一个求值器”。它们的 AST 往往不暴露给用户，前面还有 parser。作业把 parser 拿掉，是为了让你看见求值，不是为了说明生产系统没有 parser。
- 生产解释器里的错误也分成语法错误和运行时类型错误。这条界不是作业的人为规定。
- “没有编译型语言”不否定工程事实：有的实现在运行前生成机器码，有的每次执行都遍历树。课程反对的是把这个实现选择写成语言的本质，并用它解释速度。

## 检查题

1. Parser、类型检查器、解释器、编译器，各自的输入和输出是什么？
2. 为什么“C 是编译型语言所以比 Lisp 快”这句话，按课程的定义不成立？`eval` 使它在哪个很窄的意义上似乎有点道理，又为什么仍然不要求解释器？
3. 作业如何跳过 parser？程序员写下的 Racket 表达式，在哪一次求值里还没有做加法？
4. 用算术语言指出：谁是宿主语言，谁是对象语言，程序是什么，实现是什么。
5. `(negate -7)` 和 `(add (const 1) (bool #f))` 都“会出错”。解释器对它们的义务有何不同？
6. 什么是 value？解释器若返回一个 `add`，违反了哪条约定？
7. 为什么 `eq-num` 的字段不能声明成“两个整数”，而必须是两个表达式？
8. 错的解释器对哪些程序仍然正确？它的错误假设写在哪一次函数调用之前？
9. 为什么对象语言的条件结果不能是 Racket 的 `#t`？宿主语言的 `if` 却可以出现在解释器内部？
10. `test2` 的树是合法 AST。它的错误发生在“建树时”还是“某次递归返回之后”？

## Answers

1. Parser：字符串进，语法错误或 AST 出。类型检查器：AST 进，类型错误或“可以继续”出。解释器：AST 进，值或运行时错误出。编译器：B 的程序进，等价的 C 程序出，然后再运行 C。
2. 语言由语义定义。同一种语义可以有解释实现，也可以有编译实现，所以“是编译型语言”不是语言的属性，不能用来解释速度。`eval` 只要求运行时还拿得到某种实现。那个实现可以是编译器，把当时造出来的程序译完再跑。
3. B 的程序员用 Racket 构造器写出 AST，解释器直接收树。`(add (const 3) (const 4))` 作为 Racket 表达式求值时只调用构造器，得到树；加法要等 `eval-exp`。
4. 宿主语言是 Racket。对象语言是由 `const`、`negate`、`add`、`multiply` 构成的算术语言。程序是这些构造器组成的树。实现是 `eval-exp`。
5. `(negate -7)` 不是合法 AST，`negate` 的字段不是表达式。可以崩溃并给出底层消息。`(add (const 1) (bool #f))` 是合法树，错误是值的种类不对，必须检查并给出对象语言层面的说明，不能暴露 `const-int` 或 `car`。
6. Value 是求值到自身的表达式。算术语言里是 `const`；扩大后还有 `bool`，作业里还有值为值的 pair 和闭包。返回 `add` 说明还有计算没做完，解释器有 bug。
7. 因为相等和加法一样，作用在子表达式的结果上，不是作用在写在源码里的常数上。子表达式可以是任意合法表达式，求值之后才知道是不是数。
8. 对种类始终正确的程序，例如 `test1`，它正确。错误假设是：递归调用一返回就可以 `const-int` 或读布尔字段，而不先看谓词。
9. 对象语言的调用者应只看见对象语言的值。Racket 的 `#t` 是宿主语言的值，类型和打印都越界。解释器内部用 Racket 的 `if` 决定递归哪一支，是实现手段，只要它最后返回的是 `eval` 的结果。
10. 建树时每个字段都是表达式，所以合法。错误发生在条件表达式求值成布尔之后，乘法试图把这个布尔当数用。检查必须放在递归返回之后、做乘法之前。
