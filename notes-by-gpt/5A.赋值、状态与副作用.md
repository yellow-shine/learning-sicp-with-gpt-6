# 1. 这节课到底想解决什么问题？

## 1.1 5A 之前，我们生活在一个几乎“没有时间”的世界

到 Lecture 4B 为止，你已经拥有了非常强的工具：

```text
procedure abstraction
        ↓
higher-order procedures
        ↓
data abstraction
        ↓
symbolic data
        ↓
generic operations
```

你已经可以：

```scheme
(square 5)

(deriv '(+ x 3) 'x)

(add complex-number rational-number)
```

甚至可以构造相当复杂的系统。

但是这些程序有一个非常特殊的性质：

> 一个表达式的值，只取决于表达式本身和变量绑定。

例如：

```scheme
(define (square x)
  (* x x))
```

那么：

```scheme
(square 5)
```

无论今天执行、明天执行、执行第一次还是第 10000 次：

```text
(square 5) = 25
```

程序世界基本上是：

```text
input
  ↓
computation
  ↓
output
```

没有：

```text
before
after
history
```

数学函数就是很好的 mental model：

$$
f(x)=x^2
$$

给定相同的 `x`：

$$
f(x)
$$

永远是同一个结果。

# 2. 但现实世界中的对象不是这样的

考虑一个银行账户。

假设：

```text
Alice Account
balance = 100
```

执行：

```text
withdraw 30
```

以后：

```text
balance = 70
```

然后再次：

```text
withdraw 30
```

变成：

```text
balance = 40
```

这里发生了一件此前 SICP 程序中几乎不存在的事情：

```text
            time →

balance      100
              |
         withdraw 30
              ↓
             70
              |
         withdraw 30
              ↓
             40
```

于是：

```text
(withdraw 30)
```

第一次和第二次执行：

```text
参数完全相同
结果却可能不同
```

为什么？

因为结果还取决于：

```text
history / current state
```

于是计算从：

$$
result=f(input)
$$

变成：

$$
(new\ state,\ result) = F(old\ state,\ input)
$$

这是 Lecture 5A 真正打开的新世界。

# 3. 为什么不能继续使用纯函数？

当然可以。

实际上，任何 stateful computation 原则上都可以显式传递 state。

例如银行账户可以写成：

```scheme
(define (withdraw balance amount)
  (- balance amount))
```

调用：

```scheme
(withdraw 100 30)
=> 70

(withdraw 70 30)
=> 40
```

数学上非常漂亮。

但现在调用者必须记住：

```text
100 → 70 → 40
```

也就是说：

> 状态从对象内部泄漏到了调用者。

复杂一点就更明显。

假设：

```text
random generator
       ↓
Cesaro experiment
       ↓
Monte Carlo
       ↓
estimate-pi
```

random generator 需要一个 seed：

```text
seed₀
  ↓
random
  ↓
random-number + seed₁
```

没有 assignment，你可能需要：

```text
random(seed)
→ value, new-seed
```

于是 Cesaro 必须变成：

```text
cesaro(seed)
→ result, new-seed
```

然后 Monte Carlo：

```text
monte-carlo(trials, seed)
→ result, new-seed
```

最后：

```text
estimate-pi(trials, seed)
```

注意发生了什么：

```text
随机数发生器的内部实现细节
            ↓
         seed
            ↓
泄漏到 Cesaro
            ↓
泄漏到 Monte Carlo
            ↓
泄漏到 estimate-pi
```

Sussman 在 5A 正是用 random number generator / Monte Carlo 说明这个问题：如果不给随机数生成器内部状态，它的 seed 会一路向外传播，使本应独立的程序模块耦合起来。([TAU Open Course Ware](https://ocw.tau.edu.ng/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/5a-assignment-state-and-side-effects/?utm_source=chatgpt.com "5A: Assignment, State, and Side-effects | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

所以 assignment 引入的真正能力不是：

> “终于可以写 `x = x + 1` 了。”

而是：

> **可以让一个模块拥有自己的 local state。**

# 6. 核心机制一：Assignment

先从最小例子开始。

```scheme
(define x 10)

(set! x 20)

x
```

结果：

```scheme
20
```

表面看很简单。

但对于 SICP 来说，这件事是巨大的语义变化。

---

## 6.1 `define` 和 `set!` 不是一回事

首先要严格区分。

```scheme
(define x 10)
```

意味着大致：

```text
在当前 environment 中
建立一个 binding：

x → 10
```

而：

```scheme
(set! x 20)
```

意味着：

```text
寻找已有的 x binding
        ↓
把这个 binding 中保存的值
从 10 改成 20
```

所以：

```text
define
    ↓
建立 binding

set!
    ↓
修改已有 binding
```

这一区别后面理解 environment model 极其重要。

---

# 7. Assignment 引入了“before / after”

以前：

```scheme
(+ 1 2)
```

不存在：

```text
before (+ 1 2)
after  (+ 1 2)
```

两者世界状态完全一样。

但：

```scheme
(set! x 20)
```

存在：

```text
before:

x → 10


(set! x 20)


after:

x → 20
```

第一次出现了真正意义上的：

# **time**

Sussman 在讲座中直接强调，assignment 是第一次产生明显的“before”和“after”的操作。([TAU Open Course Ware](https://ocw.tau.edu.ng/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/5a-assignment-state-and-side-effects/?utm_source=chatgpt.com "5A: Assignment, State, and Side-effects | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

这句话非常值得记。

---

# 8. Side Effect 到底是什么？

考虑：

```scheme
(+ 1 2)
```

evaluation 得到：

```scheme
3
```

除此之外什么都没有改变。

但：

```scheme
(set! x (+ x 1))
```

不只是“算出了某个值”。

更重要的是：

```text
它改变了 environment
```

也就是：

```text
evaluation

不仅产生 value

还产生

change in world
```

这就是：

# side effect

可以把 expression 想象成：

```text
Pure:

Environment E
    │
    │ evaluate expression
    ▼
 value

Environment 仍然是 E
```

而有副作用：

```text
Environment E₀
    │
    │ evaluate expression
    ▼
 value
    +
Environment E₁
```

其中：

```text
E₀ ≠ E₁
```

# 9. 为什么 Substitution Model 开始不够用了？

这是本节最关键的 evaluation-model 转折。

前面 SICP 可以说：

```scheme
(define (square x)
  (* x x))

(square 5)
```

使用 substitution：

```text
(square 5)

→ (* 5 5)

→ 25
```

非常自然。

# 10. 但看看这个程序

```scheme
(define count 0)

(define (next)
  (set! count (+ count 1))
  count)
```

运行：

```scheme
(next)
=> 1

(next)
=> 2

(next)
=> 3
```

注意：

```scheme
(next)
```

这三个 expression：

```text
文本完全相同。
```

如果 substitution model 认为：

```text
一个表达式
        ↓
对应一个固定值
```

就解释不了了。

因为：

```text
(next)
```

可能是：

```text
1
2
3
...
```

答案取决于：

```text
previous history
```

所以现在必须保存：

```text
count 的当前位置
```

于是我们需要：

# Environment Model

# 11. Environment Model 的核心思想

以前你可能把变量理解成：

```text
name → value
```

比如：

```text
x → 10
```

现在需要更精确一些。

可以想象：

```text
        Global Environment
┌───────────────────────┐
│ count → 0             │
│ next  → procedure ────┼───┐
└───────────────────────┘   │
                            │
                 procedure object
               ┌──────────────────┐
               │ parameters: ()   │
               │ body: ...        │
               │ env: ────────────┼──► Global
               └──────────────────┘
```

一个 procedure 不再只是：

```text
代码
```

而是：

```text
procedure
=
code
+
environment pointer
```

这就是 closure 的基础。

---

# 12. Procedure 到底是什么？

这是 5A 以后必须改变的 mental model。

以前你可能想：

```text
procedure = body
```

例如：

```scheme
(lambda (x)
  (+ x 1))
```

但 environment model 中：

```text
procedure
=
┌────────────────────────────┐
│ parameters                 │
│ body                       │
│ defining environment ──────┼────►
└────────────────────────────┘
```

所以同一个 lambda：

```scheme
(lambda () n)
```

如果在两个不同 environment 中求值，可以产生两个不同 procedure。

它们代码一样：

```text
lambda () n
```

但：

```text
environment 不一样
```

所以行为可能不同。

这是后面 closure、object、message passing 的基础。

---

# 13. Procedure application 的新 Evaluation Model

以前：

```text
procedure call
      ↓
substitution
```

现在变成：

```text
evaluate operator
      ↓
得到 procedure object

evaluate operands
      ↓
得到 argument values

create new frame
      ↓
parameter → argument

new frame
      │
      └── enclosing environment
             ↓
    procedure's defining environment

evaluate procedure body
      ↓
in new environment
```

这是你以后应该真正记住的模型。

---

# 14. 一个完整例子

```scheme
(define (square x)
  (* x x))

(square 5)
```

首先 global environment：

```text
G:

┌─────────────────────────┐
│ square → P              │
│ *      → primitive ...  │
└─────────────────────────┘
```

其中：

```text
P:

parameters: (x)

body:
(* x x)

environment:
G
```

调用：

```scheme
(square 5)
```

创建 frame：

```text
E1
┌─────────┐
│ x → 5   │
└─────────┘
     │
     ▼
     G
```

然后 evaluate：

```scheme
(* x x)
```

寻找 `x`：

```text
E1
↓
x → 5
```

寻找 `*`：

```text
E1 没有
↓
G
↓
* → primitive multiplication
```

于是：

```text
(* 5 5)
→ 25
```

这时 environment model 也能解释纯程序。

# 15. 但它还能解释 mutation

假设：

```scheme
(set! x 6)
```

在 E1 中执行。

解释器：

```text
look for x
    ↓
E1 contains x
    ↓
replace binding
```

于是：

```text
Before:

E1
┌─────────┐
│ x → 5   │
└─────────┘


After:

E1
┌─────────┐
│ x → 6   │
└─────────┘
```

substitution model 没有“修改 substitution”这种自然概念。

environment model 有。

# 16. 核心机制二：Local State

现在来到 5A 最漂亮的部分。

定义：

```scheme
(define (make-counter n)
  (lambda ()
    (set! n (+ n 1))
    n))
```

然后：

```scheme
(define c1 (make-counter 0))
```

现在：

```scheme
(c1)
=> 1

(c1)
=> 2

(c1)
=> 3
```

表面上非常神奇：

```scheme
c1
```

是一个：

```text
zero-argument procedure
```

但每次调用结果不同。

它到底把 `n` 放在哪里？

答案就是：

# lexical environment

# 17. 手动展开 `(make-counter 0)`

首先：

```text
Global Environment G
```

有：

```text
make-counter → procedure MC
```

MC：

```text
parameters: n

body:
(lambda ()
  (set! n (+ n 1))
  n)

environment: G
```

调用：

```scheme
(make-counter 0)
```

创建：

```text
E1

┌────────────┐
│ n → 0      │
└────────────┘
       │
       ▼
       G
```

然后在 E1 中 evaluate：

```scheme
(lambda ()
  (set! n (+ n 1))
  n)
```

注意：

> evaluating a lambda 不执行 body。

它创建 procedure。

于是得到：

```text
C1 procedure

parameters: ()

body:
(set! n (+ n 1))
n

environment:
E1
```

然后：

```scheme
(define c1 ...)
```

所以：

```text
G:

c1 ───────────────────┐
                      ▼
                 procedure
               ┌──────────────┐
               │ params: ()   │
               │ body: ...    │
               │ env ─────────┼────► E1
               └──────────────┘

E1:
┌────────────┐
│ n → 0      │
└────────────┘
      │
      ▼
      G
```

这里是关键：

虽然：

```scheme
(make-counter 0)
```

已经返回了，

但：

```text
E1 没有消失
```

为什么？

因为：

```text
c1 → procedure → E1
```

仍然有 procedure 引用它。

这就是：

# closure

# 18. 第一次调用 `(c1)`

调用：

```scheme
(c1)
```

因为它没有参数，会创建调用 frame E2：

```text
E2
┌────────────┐
│            │
└────────────┘
      │
      ▼
E1
┌────────────┐
│ n → 0      │
└────────────┘
      │
      ▼
G
```

执行：

```scheme
(set! n (+ n 1))
```

求 `n`：

```text
E2
没有 n
 ↓
E1
找到 n = 0
```

计算：

```scheme
(+ n 1)

→ (+ 0 1)

→ 1
```

然后：

```scheme
(set! n 1)
```

修改的是：

```text
E1
```

于是：

```text
E1:

n → 1
```

最后：

```scheme
n
```

lookup：

```text
E2 → E1 → n = 1
```

返回：

```text
1
```

# 19. 第二次调用为什么得到 2？

再次调用：

```scheme
(c1)
```

产生新的 call frame：

```text
E3
   │
   ▼
E1
n → 1
```

而不是重新产生：

```text
n → 0
```

因为 c1 保存的 environment 仍然是：

```text
E1
```

执行：

```text
n = n + 1

1 → 2
```

所以：

```text
(c1) => 2
```

这个过程一定要在脑中看见：

```text
procedure call frame
      ↓
persistent lexical frame
      ↓
mutable binding
```

# 21. 两个 counter 会发生什么？

```scheme
(define c1 (make-counter 0))
(define c2 (make-counter 0))
```

关键问题：

```text
c1 和 c2 是不是同一个 counter？
```

不是。

environment：

```text
              G
          /       \
         /         \
        ▼           ▼
       c1           c2
        │            │
        ▼            ▼
   Procedure      Procedure
        │            │
        ▼            ▼
       E1            E2

     n → 0         n → 0
```

调用：

```scheme
(c1)
=> 1

(c1)
=> 2

(c2)
=> 1
```

状态：

```text
c1 state: n = 2

c2 state: n = 1
```

这就是：

# Independent Local State

# 22. Identity 第一次真正成为问题

考虑：

```scheme
(define c1 (make-counter 0))
(define c2 (make-counter 0))
```

此刻两者状态：

```text
c1: n = 0
c2: n = 0
```

从“值”来看完全相同。

但是：

```scheme
(c1)
```

只改变 c1：

```text
c1: n = 1
c2: n = 0
```

所以我们知道：

```text
c1 ≠ c2
```

这里出现一个非常重要的 distinction：

```text
same value
     ≠
same object
```

这就是 object identity。

# 23. SICP 为什么说 mutation 和 identity 关系很深？

如果对象永远不会变化：

```text
object A = 10
object B = 10
```

你其实很难关心：

```text
它们究竟是不是两个东西。
```

因为观察结果完全相同。

但如果可以：

```text
change A
```

然后：

```text
A = 11
B = 10
```

你立刻知道：

```text
它们是两个独立对象。
```

所以：

```text
mutation
   ↓
使 identity 可以被观察
```

反过来：

```text
identity
   ↓
使 mutation 有意义
```

这是 5A 一个非常哲学、同时非常实际的思想。

# 24. Aliasing：状态程序最大的危险之一

再看：

```scheme
(define c1 (make-counter 0))
(define c2 c1)
```

这次不是：

```text
两个 counter
```

而是：

```text
c1 ─────┐
        ▼
     same procedure
        ▲
c2 ─────┘
```

所以：

```scheme
(c1)
=> 1

(c2)
=> 2
```

因为：

```text
c1 和 c2
```

只是两个名字，指向：

```text
同一个 stateful object
```

这就是：

# aliasing

现代语言中的：

```python
a = obj
```

# 28. 但 SICP 为什么对 Assignment 非常警惕？

纯函数：

```scheme

```

永远可替换成：

```scheme
25
```

因此：

```scheme

```

可以安全替换：

```scheme

```

但：

```scheme
(next)
```

不能随便替换。


```scheme

```

于是：

```text

≠
fixed value
```

这叫 referential transparency 被破坏。

# 31. Substitution Model vs Environment Model

这组区别非常重要。

||Substitution Model|Environment Model|
|---|---|---|
|variable|文本替换的占位符|environment 中的 binding|
|procedure|参数 + body|参数 + body + environment|
|call|参数替换|创建新 frame|
|lexical scope|隐含体现|environment chain 明确体现|
|mutation|很难表达|修改 binding|
|closure|不自然|自然表达|
|identity|很难表达|可以表达|
|state|不适合|核心能力|

但是注意：

> Environment Model 不只用于 mutable programs。

没有 mutation 的程序也可以用 environment model。

只是：

```text
mutation 出现后
environment model 从“可选理解方式”
变成“必要模型”
```

# 32. `set!` 改的是 variable 还是 value？

这是非常容易误解的地方。

假设：

```scheme
(define x 10)
(set! x 20)
```

不要想成：

```text
10 被修改成 20
```

数字 `10` 没被修改。

发生的是：

```text
binding

x → 10

变成

x → 20
```

所以 mutation 可能发生在不同层次。

Lecture 5A 主要讨论：

```text
binding mutation
```

Lecture 5B 会进一步讨论：

```text
data mutation
```

例如：

```scheme

set-cdr!
```

区别是：

```text
set!

name ──► old value

变为

name ──► new value
```

而 mutable pair 是：

```text
name ──► pair
          │
          car field changed
```

这两件事一定不要混。

# 35. Hidden State + Closure 是怎么组合出来的？

# 36. Procedure 为什么可以承担 Object 的角色？

这是 SICP 后面的 message-passing object system 的基础。

# 37. 一个更完整的 Account

```scheme
(define (make-account balance)

  (define (withdraw amount)
    (if (>= balance amount)
        (begin
          (set! balance (- balance amount))
          balance)
        "Insufficient funds"))

  (define (deposit amount)
    (set! balance (+ balance amount))
    balance)

  (define (dispatch m)
    (cond ((eq? m 'withdraw) withdraw)
          ((eq? m 'deposit) deposit)
          (else
           (error "Unknown request"))))
```

# 41. Functional vs Imperative Factorial

5A 中一个很有教育意义的对比，是把我们熟悉的 factorial 写成带 assignment 的形式。([TAU Open Course Ware](https://ocw.tau.edu.ng/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/5a-assignment-state-and-side-effects/?utm_source=chatgpt.com "5A: Assignment, State, and Side-effects | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

前面我们写：

```scheme
(define (factorial n)
  (define (iter product counter)
    (if (> counter n)
        product
        (iter (* counter product)
              (+ counter 1))))
  (iter 1 1))
```

状态其实是：

```text
product
counter
```

但不是通过 mutation 表示。

而是：

```text
新的 procedure call
       ↓
新的 parameter values
```

例如：

```text
(product=1, counter=1)
          ↓
(product=1, counter=2)
          ↓
(product=2, counter=3)
          ↓
(product=6, counter=4)
          ↓
(product=24,counter=5)
```

# 42. Imperative version

可以概念上写成：

```scheme
(define (factorial n)
  (let ((product 1)
        (counter 1))

    (define (loop)
      (if (> counter n)
          product
          (begin
            (set! product
                  (* counter product))
            (set! counter
                  (+ counter 1))
            (loop))))

    (loop)))
```

这里：

```text
同一个 frame
```

不断被修改：

```text
product=1 counter=1

        ↓ mutation

product=1 counter=2

        ↓

product=2 counter=3

        ↓

product=6 counter=4

        ↓

product=24 counter=5
```

这两种程序最终都表达：

```text
iterative computation
```

但 representation 不同。

# 43. Recursive Procedure ≠ Recursive Process

这个老知识在 5A 仍然非常重要。

上面的 imperative factorial：

```scheme
(loop)
```

仍然调用自己。

所以：

```text
recursive procedure
```

但 Scheme 有 proper tail recursion 时：

```text

```

处于 tail position。

所以运行过程仍然可以是：

```text
O(1) control stack
```

产生：

```text
iterative process
```

因此：

```text
recursive syntax
       ≠
recursive process
```

与是否有 `set!` 无关。

# 44. Functional iteration vs mutation iteration

两者可以这样看：

### Functional

```text
state = parameters

state₀
  ↓ new procedure call
state₁
  ↓ new procedure call
state₂
```

例如：

```scheme
(iter product counter)
```

---

### Imperative

```text
state = mutable bindings

same frame:

state₀
 ↓ set!
state₁
 ↓ set!
state₂
```

两者表达同一种：

```text
state transition system
```

这是一个很深的统一视角：

$$
S_0 \rightarrow S_1 \rightarrow S_2 \rightarrow \cdots
$$

差别只是：

```text
functional style:
state transition represented by values

imperative style:
state transition represented by mutation
```

# 46. State 不等于 Variable

一个常见误区：

> “有变量就是有 state。”

不是。

例如：

```scheme
(define (square x)
  (* x x))
```

`x` 是 variable。

但是：

```text
没有 mutable state
```

因为调用期间：

```text
x → fixed argument
```

不会变化。

state 更准确地说是：

> **系统中能够随时间变化、并影响未来 computation 的信息。**

所以：

```text
variable
```

只是绑定机制。

```text
mutable variable
```

才可能承载 state。

```text

```

例如：

```text

```

这是：

```text

```

执行：


# 53. 这与现代语言中的 Heap 有什么关系？

概念上可以类比：

```text
SICP environment frame
      ↓
captured by closure
      ↓
outlives function call
```

现代 runtime 通常不能把这些变量简单放在普通 stack frame 上然后丢掉。

因为 closure 仍然引用它们。

因此实现上常常：

```text
captured variables
        ↓
escape analysis
        ↓
heap allocation / closure environment
```

但注意：

> SICP 的 environment model 是**语义模型**，不是要求 runtime 必须 literally 按图实现。

例如 Go：

```go
func Counter() func() int {
    n := 0
    return func() int {
        n++
        return n
    }
}
```

概念与：

```scheme
(make-counter 0)
```

完全对应。

# 58. 为什么 mutable state 会让程序更难推理？

我们可以把纯函数看作：

```text
local reasoning
```

看到：

```scheme
(f 3)
```

只需要知道：

```text
f
3
```

即可。

stateful procedure：

```scheme
(f 3)
```

还需要知道：

```text
current state
previous calls
aliases
evaluation order
possibly concurrent operations
```

所以推理输入变成：

```text
code
+
arguments
+
environment
+
history
+
ordering
```

这就是 complexity cost。

# 59. State 最大的问题不是 `set!` 本身

很多人学到这里会产生：

不是。

SICP 的立场更加细致：

```text
Assignment
       ↓
provides modularity

BUT

Assignment
       ↓
destroys simple substitution reasoning
```

换句话说：

```text
benefit:
localize complexity structurally

cost:
increase semantic complexity
```

这是工程中极其常见的 trade-off。

一定要识别：

```scheme

  (let ((state initial-state))

      ...
      (set! state ...)
      ...)))
```

结构：

```text
make-X
  │
  ▼
fresh environment
  │
  ├── private state
  │
  ▼
return closure
  │
  ▼
future calls
  │
  ▼
read / mutate state
```

看到这种代码立刻想：

```text
constructor + private field + methods
```

# 62. 核心模式二：State Transition

所有 stateful computation 都可以抽象为：

$$
S_{t+1}=F(S_t,input_t)
$$

例如 counter：

```text
S = n

F(n) = n + 1
```

银行：

```text
S = balance

withdraw(amount):

S' = S - amount
```

random generator：

```text
S = seed

new-seed = rand-update(seed)
```

所以：

> assignment 只是实现 state transition 的一种方式。

这是非常重要的 generalization。

# 68. 一个统一的 Evaluation Mental Model

从现在开始，看到：

```scheme
(f (g x))
```

不要只想：

```text
先 g 再 f
```

应该可以在脑中展开：

```text
Global Environment / current environment
                │
                ▼
evaluate operator f
                │
                ▼
procedure object:
(code + environment)

evaluate operand (g x)
                │
                ├─ evaluate g
                │
                ├─ evaluate x
                │
                ▼
apply g
                │
                ▼
create frame Eg
                │
                ├─ bind parameter
                │
                ▼
evaluate g body
                │
                ├─ possibly mutate environment
                │
                ▼
return value v
                │
                ▼
apply f to v
                │
                ▼
create frame Ef
                │
                ├─ bind parameter
                ▼
evaluate f body
```

有 mutation 后还必须加：

```text
at each step:

Environment_before
        ↓
expression
        ↓
Environment_after
```

这就是新的 computation model。

# 72. 常见误区

### 误区一

> `set!` 就是 Scheme 版的 `x = x + 1`，没什么特别。

错。

语法很简单，但它引入：

```text
time
history
identity
side effects
ordering
aliasing
```

它改变的是整个程序语义。

---

### 误区二

> Environment Model 只是另一种画 substitution 的方式。

不够准确。

对于纯程序可以这么理解。

但一旦：

```scheme
set!
```

存在，environment 必须保存可修改 binding。

它已经不只是“替换的可视化”。

---

### 误区三

> Closure 就是匿名函数。

错。

lambda 产生 procedure。

closure 是：

```text
code
+
lexical environment
```

匿名与否不是核心。

---

### 误区四

> `make-counter` 返回以后，它的局部变量 `n` 应该消失。

错误。

因为返回的 closure：

```text
still references that environment
```

所以 environment 必须继续存在。

---

### 误区五

> 两个 counter 的 `n` 都是 0，所以它们是同一个东西。

错误。

```text
same state value
≠
same identity
```

改变一个，另一个不变。

---

### 误区六

> assignment 主要是为了写 loop。

这恰恰不是 Lecture 5A 的重点。

我们之前已经知道：

```text
tail recursion
```

完全可以表达 iteration。

assignment 的关键价值是：

```text
local state
+
modularity
+
objects
```

---

### 误区七

> Mutable state 是坏设计。

也不对。

SICP 的结论更接近：

```text
mutable state
是一种有代价的 abstraction mechanism
```

只有收益值得代价时才使用。

# 76. 你真正应该记住的东西

如果几个月后 Lecture 5A 的细节忘掉了，我希望你至少留下下面这些。

### 5 个核心思想

1. **Assignment 最重要的价值不是 loop，而是 local state 和 modularity。**
    
2. **引入 mutation 就引入了 time、history 和 identity。**
    
3. **procedure 可以携带 environment，因此 closure 可以保存 private state。**
    
4. **state 带来 modularity，同时破坏 referential transparency，使 reasoning 更困难。**
    
5. **Object 的本质不是 class，而是 identity + state + behavior。**
    

### 5 个关键机制

1. `set!` 修改已有 binding。
    
2. procedure = parameters + body + defining environment。
    
3. procedure call 创建新 frame。
    
4. lexical lookup 沿 enclosing-environment chain 查找。
    
5. closure 可以让一个 frame 在创建它的 procedure 返回后继续存在。
    

### 最重要的 3 个 mental models

第一：

```text
Stateful computation

(S_t, input_t)
      ↓
     F
      ↓
(S_t+1, output_t)
```

第二：

```text
Closure

code
+
pointer to lexical environment
```

第三：

```text
Mutation

Environment_before
       ↓
    action
       ↓
Environment_after
```

如果这三个模型非常牢固，Lecture 5A 你实际上已经掌握了大半。
