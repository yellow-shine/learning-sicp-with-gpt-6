# 1. Lecture 2B 到底想解决什么问题？

先不要碰 `cons`。

想象我们正在写 rational number arithmetic。

我们想表示：

```text
1/2
2/3
5/7
```

然后希望写：

```text
(x + y) * (u + v)
```

这是我们脑子里的概念。

但现在 Scheme 给我们的基本数据主要只是：

```scheme
1
2
3
...
```

于是一个 rational number 需要两个数字：

```text
numerator
denominator
```

例如：

```text
1/2 → 1 和 2
3/4 → 3 和 4
```

问题来了。

如果没有 compound data，我们可能写：

```scheme
(add-rat n1 d1 n2 d2)
```

返回什么？

两个值：

```text
new numerator
new denominator
```

然后：

```text
(x + y) * (u + v)
```

很快就会变成：

```text
nx dx ny dy nu du nv dv ...
```

你不是在操作：

```text
x
y
u
v
```

而是在手工维护：

```text
x-numerator
x-denominator

y-numerator
y-denominator

u-numerator
u-denominator

...
```

Lecture 中 Sussman 特意强调：如果有 10 个 rational numbers，你实际上就得追踪 20 个 numerator / denominator，而且还得记住谁和谁属于同一个 conceptual object。

这不是一个 Scheme 小问题。

这是一个非常根本的问题：

> **程序语言里的对象，没有对应到我们思考问题时使用的对象。**

我们脑子里想：

```text
a rational number
```

程序里却只能看到：

```text
two unrelated machine numbers
```

---

## 为什么 procedure abstraction 还不够？

前几节已经教了我们：

```scheme
(define (square x)
  (* x x))
```

之后可以忘掉：

```scheme
(* x x)
```

只想：

```text
square
```

这叫：

```text
implementation
      ↓
 procedure abstraction
      ↓
conceptual operation
```

现在 SICP 想对 **数据** 做完全相同的事情：

```text
numerator + denominator
      ↓
representation
      ↓
rational number
```

于是整个 Lecture 2B 可以看成：

```text
Procedure Abstraction
“隐藏怎么计算”
        ↓

Data Abstraction
“隐藏怎么表示”
```

MIT 讲义明确把这一思想描述为：通过 constructor 和 selector，把数据对象的 **use** 与它的 **representation** 隔离开。

所以这节课最主要属于：

```text
abstraction       ★★★★★
representation    ★★★★★
modularity        ★★★★★
composition       ★★★★
language design   ★★★★
evaluation        ★★★
```

而不是 state。

`state` 要到后面的 assignment / mutation 才真正成为中心问题。

# 3. 第一个核心机制：Wishful Thinking

## ① 直觉

这个词在 SICP 里特别重要。

意思并不是“瞎想”。

而是：

> **先假设我想要的 abstraction 已经存在，在 abstraction level 上完成上层程序；稍后再决定它怎么实现。**

我们需要 rational number。

先别管 rational number 到底是什么。

假装有三个操作：

```scheme
(make-rat n d)

(numer x)

(denom x)
```

它们的意思分别是：

```text
make-rat
    从 n,d 创建一个 rational number

numer
    得到 rational number 的 numerator

denom
    得到 denominator
```

Sussman 在 lecture 中把这个策略直接称为 **wishful thinking**：先假定这种数据对象和这些操作已经存在，再实现 rational arithmetic。

---

## ② 于是加法可以直接写成

```scheme
(define (+rat x y)
  (make-rat
    (+ (* (numer x) (denom y))
       (* (numer y) (denom x)))
    (* (denom x)
       (denom y))))
```

注意这一段代码里没有：

```scheme
cons
car
cdr
```

这是故意的。

它只谈：

```text
rational number
numerator
denominator
```

也就是说：

```text
+rat
```

工作在 **rational-number abstraction level**。

---

## 为什么这种设计重要？

因为 `+rat` 不应该知道：

> rational number 是怎么存的。

这与你工程里非常熟悉的 interface 思想高度相似：

```text
caller
   ↓
interface
   ↓
implementation
```

但 SICP 比“interface”这个术语更进一步。

它是在训练你：

> **程序中每一层应该使用哪一种语言思考。**

上层应该说：

```text
numer(x)
denom(x)
```

而不应该说：

```text
car(x)
cdr(x)
```

因为：

```text
car / cdr
```

属于下一层的 representation language。

# 4. Constructor 和 Selector

这是本节第一个真正需要建立牢固 mental model 的东西。

## Constructor

负责：

> **创造 abstraction 的实例。**

```scheme
(make-rat 1 2)
```

意思不是：

> 创建一个 pair。

它应该被理解成：

> 创建 rational number `1/2`。

---

## Selector

负责：

> **观察 abstraction 的组成部分。**

```scheme
(numer r)
(denom r)
```

于是一个 ADT 可以想成：

```text
               Rational Number

                    r
                 ↙     ↘
            numer       denom


      make-rat
n,d ─────────────→ r
```

# 5. 最重要的变化：Data Abstraction

现在才进入本节真正中心。

假设我们暂时实现：

```scheme
(define (make-rat n d)
  (cons n d))

(define (numer x)
  (car x))

(define (denom x)
  (cdr x))
```

所以：

```scheme
(make-rat 1 2)
```

底层实际上：

```scheme
(cons 1 2)
```

但请马上建立一个非常重要的 mental model：

```text
错误：

rational number = pair
```

更正确的是：

```text
Rational Number
       │
       │ represented using
       ↓
      Pair
```

它们**不是同一个 abstraction level**。

# 6. Abstraction Barrier

这是 Lecture 2B 最重要的图。

```text
      Programs using rational numbers

          +rat
          *rat
          equal-rat?
          print-rat

──────────────────────────────────
       ABSTRACTION BARRIER

          make-rat
          numer
          denom

──────────────────────────────────

       representation of rational

          cons
          car
          cdr

──────────────────────────────────

       primitive implementation
```

MIT lecture 明确把 `make-rat / numer / denom` 这一层称为 abstraction barrier：它把“如何使用 rational number”和“rational number 如何表示”分开。

这个 barrier 有一条非常重要的纪律：

> **上层代码不能偷看 barrier 下方。**

例如这是好的：

```scheme
(define (+rat x y)
  (make-rat
   ...
   (numer x)
   ...
   (denom y)))
```

这是坏的：

```scheme
(define (+rat x y)
  (cons
    (+ (* (car x) (cdr y))
       ...)
    ...))
```

为什么？

因为后者偷偷假设：

```text
rational = cons(numerator, denominator)
```

---

# 7. 为什么 abstraction barrier 真有用？

这里 lecture 给了一个非常漂亮的例子。

假设：

```scheme
(+rat (make-rat 1 2)
      (make-rat 1 4))
```

数学公式会得到：

```text
1*4 + 1*2
───────────
   2*4

= 6/8
```

但我们一般希望输出：

```text
3/4
```

怎么办？

---

## 方案 A：construction 时 normalize

修改：

```scheme
(define (make-rat n d)
  (let ((g (gcd n d)))
    (cons (/ n g)
          (/ d g))))
```

现在：

```scheme
(make-rat 6 8)
```

实际保存：

```text
3,4
```

MIT lecture 就用这个变化展示：`+rat` 根本不用修改，因为规范化可以完全藏在 `make-rat` 后面。

---

## 甚至还有方案 B

完全可以保存：

```text
6,8
```

但是：

```scheme
(numer x)
```

的时候计算 gcd，返回：

```text
3
```

而：

```scheme
(denom x)
```

返回：

```text
4
```

也就是说：

```text
Representation A

stored: 3/4
```

和：

```text
Representation B

stored: 6/8
selectors expose 3/4
```

对于 abstraction 上层来说：

```text
完全可能无法区分
```

# 8. Representation Independence

这就是隐藏在前面例子下面的大思想。

假设上层只有：

```scheme
make-rat
numer
denom
```

那么 representation 可以发生变化：

```text
Representation V1

pair(n, d)
```

↓

```text
Representation V2

pair(reduced-n, reduced-d)
```

↓

甚至：

```text
Representation V3

prime factors
```

只要：

```text
make-rat
numer
denom
```

仍然满足同样的 contract：

```text
上层代码不需要改变
```

这就是：

# representation independence

这比“代码复用”深得多。

它意味着：

> **一个模块依赖的不是另一个模块的数据布局，而是它的行为契约。**

# 9. SICP 开始重新定义“数据是什么”

这里是 Lecture 2B 最哲学、同时也是计算机科学味最浓的一步。

我们通常会说：

> Rational number 到底是什么？

初学者很自然回答：

```text
一个 pair：

(numerator . denominator)
```

SICP 说：

**不对。**

pair 只是其中一个 representation。

那么 rational number “really is” 什么？

Lecture 给出的方向是：

> 一组 constructor / selector，它们满足一定的关系。

例如如果：

```scheme
(define x (make-rat n d))
```

那么：

```text
(numer x)
───────── = n/d
(denom x)
```

也就是说，对 abstraction 而言，我们只关心：

```text
make-rat
numer
denom
```

是否满足 specification。

Sussman 把这直接称作实现者的 **contract**：实现可以不同，只要这些 procedures 满足约定即可。

这其实已经非常接近现代的：

```text
Abstract Data Type
```

定义：

```text
ADT ≠ memory layout

ADT =
    values
  + operations
  + laws / invariants
```

# 10. Pair：`cons`, `car`, `cdr`

现在才轮到 Scheme 语法。

Scheme 给我们：

```scheme
(cons x y)
```

创建一个 pair。

```scheme
(car p)
```

得到第一个部分。

```scheme
(cdr p)
```

得到第二个部分。

满足：

```scheme
(car (cons x y))  => x

(cdr (cons x y))  => y
```

Lecture 强调：从抽象角度看，这两个等式才是你真正需要知道的 pair 行为。

# 11. Box-and-pointer model

例如：

```scheme
(cons 2 3)
```

可以画：

```text
       pair
      ┌───┬───┐
      │ • │ • │
      └─│─┴─│─┘
        │   │
        ↓   ↓
        2   3
```

于是：

```scheme
(car p)
```

沿第一条边。

```scheme
(cdr p)
```

沿第二条边。

但是有一个非常重要的提醒：

> **这张图是一种 representation model，不是 pair 的数学本质。**

后面马上会证明这一点。

# 12. Compound Data 最关键的能力：pair 可以包含 pair

比如：

```scheme
(cons
  (cons 1 2)
  (cons 3 4))
```

结构：

```text
              pair
             /    \
            /      \
         pair      pair
        /   \      /   \
       1     2    3     4
```

这件事情看起来普通，但 Sussman 专门给它一个非常重要的名字：

# Closure Property

Lecture 的定义大意是：

> 某种 combination method 产生的东西，可以继续作为同一种 combination method 的输入。

也就是说：

```text
pair(number, number)
```

之后还可以：

```text
pair(pair, pair)
```

再：

```text
pair(pair(pair,...), pair(...))
```

所以从一个极其简单的 primitive：

```text
pair
```

可以构建：

```text
lists
trees
graphs
symbolic expressions
programs
```

# 13. 一个特别容易混淆的地方：两种 Closure

你之后一定会遇到这个坑。

Lecture 2B 这里讲：

```text
closure under combination
```

指的是数学意义：

```text
combine elements
      ↓
result can itself be combined again
```

例如：

```text
pair + pair → pair-compatible object
```

而现代程序语言经常说：

```text
closure = function + captured environment
```

例如：

```scheme
(lambda (x)
  (+ x a))
```

记住：

```text
SICP 此处的 closure property
         ≠
lexical closure
```

名字相同，概念不同。

有趣的是，这节课最后又真的会碰到第二种 closure 的影子。

# 14. 第二个例子：Point / Vector / Segment

SICP 不想让你误认为：

> Data abstraction 就只是“写一个 Rational class”。

于是继续构建：

```text
number
  ↓
point
  ↓
segment
```

例如 point：

```scheme
(define (make-point x y)
  (cons x y))

(define (x-point p)
  (car p))

(define (y-point p)
  (cdr p))
```

然后 segment：

```scheme
(define (make-segment p q)
  (cons p q))

(define (start-segment s)
  (car s))

(define (end-segment s)
  (cdr s))
```

于是：

```text
                    segment

               start       end
                 │           │
                 ↓           ↓
               point       point
              /    \      /     \
             x      y    x       y
```

Lecture 用这个例子明确展示：

```text
Segment abstraction
────────────────────
make-segment
start-segment
end-segment

        ↓

Point abstraction
────────────────────
make-point
x-point
y-point

        ↓

Pair abstraction
────────────────────
cons
car
cdr

        ↓

primitive system
```

这就是 SICP 一直强调的：

# layered system

# 15. 为什么不能直接在 segment 代码里使用 `car/cdr`？

假设我们写 midpoint：

好的版本：

```scheme
(define (midpoint s)
  (let ((p (start-segment s))
        (q (end-segment s)))
    (make-point
      (/ (+ (x-point p)
            (x-point q))
         2)
      (/ (+ (y-point p)
            (y-point q))
         2))))
```

这里使用的 vocabulary 是：

```text
segment
endpoint
point
coordinate
```

这就是这一层应该思考的语言。

---

坏版本可能是：

```scheme
(define (midpoint s)
  (cons
    (/ (+ (car (car s))
          (car (cdr s)))
       2)
    ...))
```

即使它现在完全正确，也很糟。

因为你已经把：

```text
segment representation
point representation
pair representation
```

全部混在一个 procedure 里。

如果：

```text
point representation
```

稍微改一下：

```text
(x . y)
```

改为：

```text
(y . x)
```

你的大量程序都会坏掉。

# 16. SICP 所谓“控制复杂度”的真正含义

这点对有工程经验的人特别重要。

很多时候我们说 abstraction 是为了：

```text
代码漂亮
少重复
```

SICP 的观点更深：

> **Abstraction 是为了限制你在某个时刻必须同时知道的东西。**

写：

```scheme
(length segment)
```

的时候：

你只需要知道：

```text
segment API
point API
```

不应该同时想着：

```text
cons cell layout
```

再下一层：

实现 point 时：

```text
pair
```

才进入你的认知范围。

所以 abstraction barrier 本质上是在控制：

```text
simultaneously relevant knowledge
```

这和大型 distributed / infrastructure system 是完全一样的。

例如你写：

```text
CreateCluster(spec)
```

上层最好依赖：

```text
Cluster abstraction
```

而不是到处写：

```text
ASG
ENI
IAM
subnet
launch-template
security-group
...
```

否则系统虽然“能工作”，却没有 abstraction boundaries。

# 18. 用 Procedure 实现 Data

定义：

```scheme
(define (my-cons a b)
  (lambda (pick)
    (cond ((= pick 1) a)
          ((= pick 2) b))))
```

然后：

```scheme
(define (my-car x)
  (x 1))

(define (my-cdr x)
  (x 2))
```

这里没有：

```text
pair memory object
struct
record
array
```

`my-cons` 返回的是：

```text
procedure
```

但它表现得跟 pair 一样。

Lecture 正是通过这一实现强调：只要满足 `cons/car/cdr` 的行为关系，这就是一个合法的 pair representation。

现在我们一定要展开 evaluation。

---

# 19. Evaluation：`(my-car (my-cons 37 49))`

先看表达式：

```scheme
(my-car (my-cons 37 49))
```

Applicative-order Scheme：

```text
evaluate operator
        ↓
my-car

evaluate operand
        ↓
(my-cons 37 49)
```

展开：

```scheme
(my-cons 37 49)
```

`my-cons`：

```scheme
(lambda (a b)
  (lambda (pick)
    (cond ((= pick 1) a)
          ((= pick 2) b))))
```

代入：

```text
a = 37
b = 49
```

得到一个 procedure：

```scheme
(lambda (pick)
  (cond ((= pick 1) 37)
        ((= pick 2) 49)))
```

所以原式变成：

```scheme
(my-car
  (lambda (pick)
    (cond ((= pick 1) 37)
          ((= pick 2) 49))))
```

而：

```scheme
(define (my-car x)
  (x 1))
```

所以：

```text
↓
```

```scheme
((lambda (pick)
   (cond ((= pick 1) 37)
         ((= pick 2) 49)))
 1)
```

绑定：

```text
pick = 1
```

执行：

```scheme
(cond ((= 1 1) 37)
      ((= 1 2) 49))
```

得到：

```text
37
```

因此：

```scheme
(my-car (my-cons 37 49))
```

满足：

```text
=> 37
```

同理：

```scheme
(my-cdr (my-cons 37 49))
```

得到：

```text
49
```

这正是 lecture 用 substitution model 验证这一 representation 的方式。

# 21. 如果用后面的 Environment Model 看这一段

这节课本身还主要依靠 substitution model，但这里已经出现了 substitution model 很难自然解释的问题：

```scheme
(define p
  (my-cons 37 49))
```

为什么 `p` 后来还能记住：

```text
37
49
```

？

从后面 SICP 的 environment model 看：

调用：

```scheme
(my-cons 37 49)
```

创建 frame：

```text
E1
┌────────┐
│ a = 37 │
│ b = 49 │
└────────┘
    │
    ↓
Global Environment
```

然后返回：

```scheme
(lambda (pick) ...)
```

但这个 procedure 并不仅仅是代码。

它实际上是：

```text
procedure object
┌─────────────────────────────────┐
│ code: (lambda (pick) ...)       │
│ environment: E1 ──────────────┐ │
└───────────────────────────────│─┘
                                ↓
                          a = 37
                          b = 49
```

之后：

```scheme
(my-car p)
```

调用：

```scheme
(p 1)
```

新建：

```text
E2
┌──────────┐
│ pick = 1 │
└──────────┘
     ↓
E1
┌────────┐
│ a = 37 │
│ b = 49 │
└────────┘
```

所以能访问：

```text
a → 37
b → 49
```

这就是后来所谓 lexical closure 的机制。

Lecture 的现场甚至有人问：

> 多个 `cons` 创建出来以后，它们怎么知道自己的 `a` 和 `b`，为什么不会混？

Sussman 的回答核心就是：你必须认真接受 **procedure 本身也是独立存在的 object**。

这是 Lecture 2A：

```text
procedures are first-class objects
```

与 Lecture 2B：

```text
procedures can represent data
```

之间非常漂亮的连接。

# 23. Procedure Abstraction vs Data Abstraction

这是本节最值得主动比较的一组。

||Procedure abstraction|Data abstraction|
|---|---|---|
|隐藏什么|如何计算|如何表示|
|上层看到|procedure name|constructor/selectors|
|例子|`sqrt`|rational number|
|implementation|iterative-improve 等|pair / procedure|
|barrier|procedure interface|ADT interface|
|允许变化|algorithm|representation|

Procedure abstraction：

```text
How is sqrt computed?

I don't care.

sqrt(9) → 3
```

Data abstraction：

```text
How is rational represented?

I don't care.

numer(make-rat(3,4)) → ...
```

共同思想：

```text
implementation details
        ↓ hide
abstraction boundary
        ↓
conceptual operation/object
```

# 24. Pair vs List

另一个常见混淆。

这节首先讲的是：

```text
pair
```

不是：

```text
list
```

Pair 是：

```scheme
(cons x y)
```

只有：

```text
two slots
```

例如：

```scheme
(cons 1 2)
```

是：

```text
(1 . 2)
```

而 list：

```scheme
(list 1 2 3)
```

本质上是特定形状的 nested pairs：

```text
cons
├── 1
└── cons
    ├── 2
    └── cons
        ├── 3
        └── nil
```

也就是：

```scheme
(cons 1
  (cons 2
    (cons 3 '())))
```

所以：

```text
pair = primitive compound-data building block

list = conventionally structured chain of pairs
```

# 29. 本节的 reusable pattern

# 30. 更深一层的 reusable pattern：Programming by Contract

这节其实还有第二套 pattern：

```text
Don't ask:

"What is X internally?"
```

改问：

```text
"What laws must operations on X satisfy?"
```

对于 pair：

```text
car(cons(a,b)) = a

cdr(cons(a,b)) = b
```

对于 rational：

```text
numer(make-rat(n,d))
─────────────────────  = n/d
denom(make-rat(n,d))
```

于是 implementation：

```text
pair?
closure?
integer encoding?
something else?
```

都可以。

只需要：

```text
satisfy the laws
```

这是 ADT、interface specification、representation invariant 等现代思想的根源之一。

# 35. 这一节真正需要记住的东西

不要记几十个 API。

### 5 个核心思想

**第一：Data abstraction = 把 use 与 representation 分离。**

```text
what it means
      ≠
how it is represented
```

**第二：Constructor / Selector 构成 abstraction boundary。**

```text
make-X
X-part-a
X-part-b
```

不是 convenience functions，而是 abstraction 的语言。

**第三：一个数据对象本质上可以由它的 behavioral contract 定义。**

```text
Don't ask:
"what bits are inside?"

Ask:
"what laws does it satisfy?"
```

**第四：Closure property 让简单的组合机制产生任意复杂结构。**

```text
pair
 ↓
pair of pairs
 ↓
trees / lists / symbolic structures
```

**第五：Procedure 和 Data 的界限并不是绝对的。**

```text
procedure can implement pair
```

这是后面 SICP 大量思想的伏笔。

cons / car / cdr
