# 1. 这节课到底想解决什么问题？

## 1.1 表面的问题：怎么让计算机求一个平方根？

假设我们想求：

$$
\sqrt{2}
$$

数学可以告诉你：

$$
y = \sqrt{x} \iff y \ge 0 \land y^2=x
$$

这是一个 **declarative knowledge（陈述性知识）**：

> 什么是平方根？

但它没有告诉计算机：

> **怎么得到平方根？**

计算机真正需要的是类似：

```text
guess = 1

不断重复：

    如果 guess 足够好：
        返回 guess

    否则：
        guess = average(guess, x / guess)
```

比如求 $\sqrt 2$：

```text
guess = 1

1
↓
(1 + 2/1) / 2
= 1.5

↓
(1.5 + 2/1.5) / 2
≈ 1.41667

↓
(1.41667 + 2/1.41667) / 2
≈ 1.41422

↓
...
```

这就是 **imperative / how-to knowledge**：

> 不只是描述答案是什么，而是描述产生答案的 process。

Lecture 1A 正是从这个区别开始。([MK12](https://mk12.github.io/sicp/lecture/1a.html "SICP Lecture 1A Notes"))

# 2. 真正的问题其实更大：怎么描述“怎么做”？

SICP 在问：

```text
数学
描述：
    what is true?

程序设计
描述：
    how to do it?
```

也就是说：

```text
Declarative Knowledge

sqrt(x) = y
where y² = x

            ↓

How-to Knowledge

make guess
improve guess
test guess
repeat
```

这里就出现了三个东西：

```text
procedure
    ↓
描述规则

process
    ↓
规则执行时产生的计算

language
    ↓
用什么方式描述这些规则
```

这是 SICP 后面极其重要的区分：

> **procedure 是程序文本中的规则；process 是规则执行时产生的动态行为。**

例如：

```scheme
(define (square x)
  (* x x))
```

这是一个 **procedure definition**。

而：

```scheme
(square 5)
```

被 evaluator 执行以后产生的是一个计算 process：

```text
(square 5)
↓
(* 5 5)
↓
25
```

到了下一讲 1B，SICP 会把这个区分进一步发展成：

```text
recursive procedure
        ≠
recursive process
```

所以你现在就可以先埋下这个 mental model。

# 3. 但 SICP 认为最大的敌人不是“不会算平方根”

真正的问题是：

# Complexity

Abelson 在 1A 花相当多时间强调：

> 大系统的问题在于，没有人能够把所有细节同时装在脑子里。

因此程序设计的核心能力不是：

```text
写更多代码
```

而是：

```text
控制你在某一时刻必须思考的东西
```

MIT 的这套讲座把整个课程的复杂度控制方法概括成三个主题：

```text
                    Managing Complexity

                           │
          ┌────────────────┼────────────────┐
          ↓                ↓                ↓
 Black-box          Conventional      Metalinguistic
 Abstraction         Interfaces        Abstraction
          │                │                │
隐藏内部实现          规定连接方式         创造新的语言
          │                │                │
 procedure          generic ops         evaluator
 abstraction        modularity           DSL
 data abstraction   interfaces           interpreter
```

这是整门 SICP 的总地图，而不仅仅是 Lecture 1A。([MK12](https://mk12.github.io/sicp/lecture/1a.html "SICP Lecture 1A Notes"))

其中 1A 最先集中介绍的是：

> **Black-box abstraction。**

# 5. SICP 看一门语言的三个问题

这是 Lecture 1A 最值得长期记住的框架之一。

看到任何语言，不要首先问：

> for 怎么写？class 怎么写？

而应该问：

```text
① Primitive Elements
        原始元素是什么？

② Means of Combination
        怎么把简单东西组合起来？

③ Means of Abstraction
        怎么给组合出来的复杂东西一个名字，
        然后把它当成新的简单东西使用？
```

Lecture 1A 正是用 Lisp 来展示这三件事。([MK12](https://mk12.github.io/sicp/lecture/1a.html "SICP Lecture 1A Notes"))

# 6. Primitive Elements：计算世界的“原子”

最简单的 Scheme 表达式：

```scheme
3
```

evaluation：

```text
expression
   │
   ▼
   3
   │
   ▼
self-evaluating
   │
   ▼
   3
```

数字的特点是：

> 它求值以后就是自己。

再看看：

```scheme
+
```

这里 `+` 不是数字。

它是一个 **name**。

环境里存在某种绑定：

```text
Global Environment

+ ─────→ primitive addition procedure
* ─────→ primitive multiplication procedure
```

所以：

```scheme
+
```

的 evaluation 可以想象成：

```text
expression: +

        ↓ lookup

Global Environment

        ↓

primitive procedure +
```

这已经偷偷引出后面的 environment model 了。

但 1A 暂时不用正式 environment frame 来描述它。

# 7. Means of Combination：Lisp 最重要的第一步

现在：

```scheme
(+ 3 4)
```

它不是“特殊的加法语法”。

它属于更一般的结构：

```scheme
(operator operand operand ...)
```

所以：

```scheme
(+ 3 4)
```

结构其实是：

```text
        +
       / \
      3   4
```

prefix notation 只是把这棵树线性写出来：

```scheme
(+ 3 4)
```

而：

```scheme
(* (+ 2 3)
   (- 10 4))
```

实际上是：

```text
             *
           /   \
          +     -
         / \   / \
        2   3 10  4
```

所以 Lisp 的括号并不是一种奇怪的装饰。

它在直接表达：

> **程序的树结构。**

这是以后理解 Lisp 为什么适合写 interpreter 的第一块拼图。

# 8. Evaluation：到底怎么运行？

考虑：

```scheme
(* (+ 2 3)
   (- 10 4))
```

我们按照 SICP 的 evaluator mental model 看。

```text
expression

(* (+ 2 3) (- 10 4))

        ↓

evaluate operator

*

        ↓

primitive multiplication procedure


evaluate operands
        │
        ├───────────────┐
        ↓               ↓

   (+ 2 3)          (- 10 4)
        ↓               ↓
       5                 6

        └───────┬───────┘

                ↓

     apply multiplication

             (* 5 6)

                ↓

               30
```

因此一般的 procedure application 可以先记成：

```text
(operator operand₁ operand₂ ...)

            ↓

evaluate operator
            ↓
obtain procedure

evaluate operands
            ↓
obtain arguments

            ↓

apply procedure to arguments

            ↓

result
```

这是贯穿整本 SICP 的骨架。

# 9. 一个极其重要的递归结构：Evaluator 本身也是递归的

刚才这个 expression：

```scheme
(* (+ 2 3)
   (- 10 4))
```

为什么 evaluator 能处理？

因为：

```text
evaluate whole expression
        ↓
needs to evaluate operands
        ↓
operands themselves are expressions
        ↓
use SAME evaluator again
```

因此：

```text
eval combination
    ↓
    eval operator
    ↓
    eval operands
          ↓
          eval subexpression
                ↓
                ...
```

这已经体现了一个 SICP 极其典型的思想：

> **语言的语法是递归结构，因此解释这种语言的算法自然也是递归结构。**

现在可能觉得这只是 Lisp 求值规则。

到了 Chapter 4 你会发现：

```text
eval
apply
```

真的可以用 Lisp 写出来。

MIT 在课程总览里明确把 Lisp evaluator 的 `eval/apply` 循环放在后面的 metalinguistic abstraction 主题中。([MK12](https://mk12.github.io/sicp/lecture/1a.html "SICP Lecture 1A Notes"))

# 10. Means of Abstraction：这是 Lecture 1A 真正开始变厉害的地方

假设你经常写：

```scheme
(* 5 5)
(* 10 10)
(* x x)
```

当然可以一直重复写。

但这意味着：

```text
concept: square

没有名字
```

于是：

```scheme
(define (square x)
  (* x x))
```

现在发生的事情不是单纯：

> 定义了一个函数。

而是：

```text
existing primitives

    *

    │

    ↓ combine

(* x x)

    │

    ↓ abstract

square

    │

    ↓

new conceptual primitive
```

原来：

```scheme
(* x x)
```

是一堆 implementation details。

现在我们可以说：

```scheme
(square x)
```

以后就可以暂时忘记 `square` 怎么实现。

---

# 11. 这就是 Black-box Abstraction

假设：

```scheme
(define (square x)
  (* x x))
```

然后：

```scheme
(define (sum-of-squares x y)
  (+ (square x)
     (square y)))
```

站在 `sum-of-squares` 的作者角度：

```text
square
   │
   │ don't care
   ▼
┌───────────────┐
│     square    │
│               │
│ implementation│
│   (* x x)     │
└───────────────┘
```

你只需要知道：

```text
INPUT:
number x

OUTPUT:
x²
```

于是你可以开始构建更高的一层：

```text
primitive
   ↓
*
   ↓
square
   ↓
sum-of-squares
   ↓
larger algorithm
```

这就是 abstraction 最关键的力量：

> **我们不是删除复杂性，而是把复杂性藏在边界后面。**

# 12. 为什么 `define` 如此重要？

考虑：

```scheme
(* 5 5)
```

与：

```scheme
(square 5)
```

结果完全一样。

那为什么还要 `square`？

因为程序设计面对的是两个完全不同的问题：

```text
What computation happens?

vs

What idea does this computation represent?
```

`(* x x)` 描述 mechanics：

```text
multiply x by x
```

`square` 描述 concept：

```text
square a number
```

因此：

```text
abstraction
=
give a name to an idea
while suppressing irrelevant implementation details
```

这件事比“少写代码”重要得多。

# 13. Procedure definition 本身发生了什么？

这段：

```scheme
(define (square x)
  (* x x))
```

在概念上相当于：

```scheme
(define square
  (lambda (x)
    (* x x)))
```

1A 已经指出这种 procedure definition notation 是更方便的表面形式。([MK12](https://mk12.github.io/sicp/lecture/1a.html "SICP Lecture 1A Notes"))

可以想象：

```text
Global Environment

square ──────→ procedure
               ┌────────────────┐
parameter: x   │
body: (* x x)  │
               └────────────────┘
```

现在执行：

```scheme
(square 5)
```

我们先用 **1A → 1B 之间的过渡 mental model**：

```text
(square 5)

     ↓

evaluate operator

square
     ↓
procedure(x) { (* x x) }

     ↓

evaluate operand

5
     ↓
5

     ↓

apply procedure
x = 5

     ↓

evaluate body

(* x x)

     ↓

(* 5 5)

     ↓

25
```

正式的 substitution model 会在 **Lecture 1B** 重点展开，所以现在先掌握这个骨架就够了。OCW 的课程顺序也是 1A 后紧接着 1B 的 substitution model。([MIT OpenCourseWare](https://ocw.mit.edu/courses/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video_galleries/video-lectures/?utm_source=chatgpt.com "Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

# 14. `define` 为什么不是普通 procedure？

考虑：

```scheme
(define x 5)
```

如果完全按照普通 procedure application：

```text
evaluate operator
evaluate every operand
apply procedure
```

那么 evaluator 会先尝试 evaluate：

```scheme
x
```

问题来了：

```text
x 还没有定义
```

所以 `define` 不能按照普通 application rule 工作。

它必须拥有自己的 evaluation rule：

```text
(define x 5)

不要 evaluate x

evaluate 5
     ↓
5

bind name x
     ↓

x ───→ 5
```

因此 `define` 是 **special form**。

这是一个非常重要的语言设计思想：

> 有些语言结构必须改变正常的 evaluation rule。

后面你会遇到很多类似的东西：

```scheme
if
define
lambda
quote
cond
```

---

# 15. 为什么 `if` 也必须是 special form？

考虑：

```scheme
(if (> x 0)
    (/ 10 x)
    0)
```

假设：

```scheme
x = 0
```

正确行为应该是：

```text
evaluate condition

(> 0 0)

↓
false

因此只 evaluate alternative:

0
```

绝不能计算：

```scheme
(/ 10 0)
```

所以 `if` 不能遵循普通 procedure：

```text
evaluate ALL operands
then apply
```

而必须：

```text
evaluate predicate

        ↓

      true?
     /     \
   yes      no
    ↓        ↓
eval then  eval else
only       only
```

这是为什么：

```scheme
(if condition A B)
```

不是：

```scheme
ordinary function(condition, A, B)
```

这种区别以后会直接连接到：

```text
applicative order
normal order
lazy evaluation
short-circuiting
```

# 16. `cond` 是在解决什么问题？

例如绝对值：

```scheme
(define (abs x)
  (cond ((< x 0) (- x))
        ((= x 0) 0)
        ((> x 0) x)))
```

结构是：

```text
           x
           │
           ↓
      case analysis
       /    |    \
      /     |     \
   x < 0   x=0   x>0
     ↓      ↓      ↓
    -x      0      x
```

这里真正的 abstraction 不是：

> Scheme 有个 `cond`。

而是：

> **程序除了组合 computation，还需要选择 computation。**

因此现在我们的计算语言已经拥有：

```text
primitive computation
       +
combination
       +
naming
       +
case analysis
```

而有了这些，再加 recursion，表达能力会突然变得非常强。

# 17. 为什么 Lisp 不需要传统的 loop？

Lecture 1A 接下来非常关键的一步就是：

> 一个 procedure 可以调用自己。

例如：

```scheme
(define (factorial n)
  (if (= n 1)
      1
      (* n (factorial (- n 1)))))
```

我们还没正式学习 process shape。

但先看 computation：

```text
(factorial 4)

↓
(* 4 (factorial 3))

↓
(* 4
   (* 3 (factorial 2)))

↓
(* 4
   (* 3
      (* 2 (factorial 1))))

↓
(* 4
   (* 3
      (* 2 1)))

↓
24
```

为什么 recursion 如此重要？

因为它让我们能够描述：

> **一个问题由更小版本的“同一个问题”构成。**

# 18. Recursion 的真正 abstraction 是什么？

不是：

> 函数调用自己。

而是：

```text
Problem P(n)

       ↓

identify base case
       +
reduce P(n)
to
P(smaller n)

       ↓

trust abstraction P
```

例如 factorial：

```text
factorial(n)

不知道内部过程也没关系。

只要我相信：

factorial(n-1)

能够正确计算 (n-1)!
```

那么：

$$
n! = n \cdot (n-1)!
$$

所以代码：

```scheme
(* n
   (factorial (- n 1)))
```

关键思想其实是：

> **把 recursive call 当作一个 black box。**

这是 abstraction 与 recursion 的第一次融合。

---

# 19. 一个非常重要的误区：不要把 recursion 想成“展开所有代码”

成熟的 recursive reasoning 是：

```text
我正在实现 factorial(n)

我可以假设：

factorial(n - 1)

已经工作。
```

然后只证明：

```text
如果 factorial(n-1) 正确，

那么

n * factorial(n-1)

是否正确？
```

这是一种 inductive reasoning。

所以 recursion 和数学归纳法之间有非常深的联系。

# 20. Square Root：整节课的思想开始组合

现在回到最开始的问题：

$$
\sqrt{x}
$$

我们可以一步步把 how-to knowledge 写成程序。

首先：

```scheme
(define (square x)
  (* x x))
```

然后判断：

```scheme
(define (good-enough? guess x)
  (< (abs (- (square guess) x))
     0.001))
```

然后改进猜测：

```scheme
(define (average x y)
  (/ (+ x y) 2))
```

```scheme
(define (improve guess x)
  (average guess
           (/ x guess)))
```

最后：

```scheme
(define (sqrt-iter guess x)
  (if (good-enough? guess x)
      guess
      (sqrt-iter (improve guess x)
                 x)))
```

入口：

```scheme
(define (sqrt x)
  (sqrt-iter 1.0 x))
```

现在注意。

这段程序最值得看的，不是 Newton method 本身。

而是 abstraction layering：

```text
                  sqrt

                   │
                   ↓

                sqrt-iter

             /       |       \
            /        |        \
 good-enough?     improve     recursion
       │             │
       ↓             ↓
     square        average
       │             │
       ↓             ↓
       *            + /
```

这就是 SICP 想训练你的能力：

> **从 primitive 开始，通过 combination 构建 compound procedure，再把 compound procedure 当作新的 primitive。**

# 21. 真正“看到” `(sqrt 2)` 在运行

假设：

```scheme
(sqrt 2)
```

展开：

```text
sqrt
x = 2

↓

(sqrt-iter 1.0 2)
```

第一轮：

```text
guess = 1.0
x     = 2

↓

(good-enough? 1.0 2)

↓

(square 1.0)

↓

1.0

↓

abs(1.0 - 2)

↓

1.0

不是 < 0.001
```

所以：

```text
(improve 1.0 2)

↓

(average 1.0 (/ 2 1.0))

↓

(average 1.0 2.0)

↓

1.5
```

于是：

```text
(sqrt-iter 1.5 2)
```

下一轮：

```text
guess=1.5

↓

x / guess
= 1.333333...

↓

average(1.5, 1.333333)
≈ 1.416667
```

继续：

```text
1.0
↓
1.5
↓
1.416667
↓
1.414216
↓
1.414214
...
```

直到：

```text
good-enough?
      ↓
true
      ↓
return guess
```

这个动态过程才是：

> **process。**

而 Scheme 中的：

```scheme
sqrt
sqrt-iter
good-enough?
improve
average
```

是描述它的：

> **procedures。**

# 22. Procedure vs Process

这是你现在就应该开始建立的区别。

```text
PROCEDURE
--------------------------------
程序文本中的规则

例如：

(define (sqrt-iter guess x)
  ...)


PROCESS
--------------------------------
执行 procedure 后产生的动态计算

例如：

guess = 1
↓
guess = 1.5
↓
guess = 1.4167
↓
guess = 1.4142
```

因此：

```text
procedure
    │
    │ executed by evaluator
    ▼
process
```

这就像：

```text
recipe
    ↓ cooking
meal preparation process
```

不是同一个东西。

---

# 23. 这一点为什么后来极其重要？

因为下一讲你会看到两个 procedure：

```scheme
(define (factorial n)
  (if (= n 1)
      1
      (* n
         (factorial (- n 1)))))
```

和：

```scheme
(define (fact-iter product counter max-count)
  ...)
```

两段 Scheme 源代码都用了 recursion。

但它们产生完全不同的：

```text
PROCESS SHAPE
```

分别是：

```text
recursive process

6 * (5 * (4 * ...))
```

与：

```text
iterative process

(product, counter)
→
(product', counter')
→
...
```

所以：

> **代码长什么样，与运行中的 process 长什么样，不是同一个问题。**

这是 SICP 全书非常核心的分析方式。

# 24. Block Structure：为什么突然要把 procedure 放进去？

现在我们的 sqrt 可能是：

```scheme
(define (square x) ...)
(define (average x y) ...)
(define (good-enough? guess x) ...)
(define (improve guess x) ...)
(define (sqrt-iter guess x) ...)
(define (sqrt x) ...)
```

问题来了。

对于外部使用者而言，他真的需要知道：

```text
square?
good-enough?
improve?
sqrt-iter?
```

吗？

不需要。

用户只想知道：

```scheme
(sqrt 2)
```

所以可以构造：

```text
PUBLIC

sqrt
 │
 ├──────── abstraction boundary
 │
PRIVATE
 │
 ├── good-enough?
 ├── improve
 └── sqrt-iter
```

这就是 block structure 所解决的问题：

> **抽象不仅意味着给复杂 computation 一个名字，还意味着隐藏不应该泄漏的名字。**

Lecture 1A 把 block structure 明确联系到 black-box abstraction。([MK12](https://mk12.github.io/sicp/lecture/1a.html "SICP Lecture 1A Notes"))

# 26. 为什么 lexical scope 很重要？

假设把 helper procedure 放在 `sqrt` 内部：

```scheme
(define (sqrt x)

  (define (good-enough? guess)
    (< (abs (- (square guess) x))
       0.001))

  (define (improve guess)
    (average guess (/ x guess)))

  (define (sqrt-iter guess)
    (if (good-enough? guess)
        guess
        (sqrt-iter (improve guess))))

  (sqrt-iter 1.0))
```

注意变化。

以前：

```scheme
(good-enough? guess x)
```

现在：

```scheme
(good-enough? guess)
```

为什么不再传 `x`？

因为内部 procedure 可以访问外层的：

```text
x
```

逻辑结构：

```text
sqrt invocation

x = 2
│
├── good-enough?
│       ↑
│       └──── sees x
│
├── improve
│       ↑
│       └──── sees x
│
└── sqrt-iter
```

这已经是后面 environment model / lexical scope / closure 的种子。

1A 不会把 environment frames 正式展开；那属于后面的课程内容。([MIT OpenCourseWare](https://ocw.mit.edu/courses/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video_galleries/video-lectures/?utm_source=chatgpt.com "Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

# 27. 一个重要的 Language Design 思想

Lecture 1A 中有一个非常容易被低估的问题：

# 32. Evaluation model：目前你应该精确掌握到什么程度？

对于普通 application：

```scheme
(f (g x))
```

现阶段可以使用：

```text
(f (g x))

        ↓

evaluate operator f

        ↓

procedure F


evaluate operand (g x)

        ↓

evaluate operator g
        ↓
procedure G

evaluate x
        ↓
value X

apply G to X
        ↓
result R

        ↓

apply F to R

        ↓
result
```

例如：

```scheme
(square (+ 2 3))
```

展开：

```text
(square (+ 2 3))

↓ evaluate operator

square
→ procedure square

↓ evaluate operand

(+ 2 3)

    ↓

    +
    ↓

    primitive addition

    operands:
    2 → 2
    3 → 3

    ↓

    apply +

    ↓

    5

↓

apply square to 5

↓

x = 5

↓

evaluate body:

(* x x)

↓

(* 5 5)

↓

25
```

这就是你现在最重要的 evaluation mental model。

# 33. Applicative order 与 Normal order：现在先知道边界

这里需要稍微克制一点，因为正式讨论属于后面的 1B。

目前我们刚才采用的是：

```text
evaluate arguments first
↓
apply procedure
```

即 **applicative-order evaluation**。

比如：

```scheme
(square (+ 2 3))
```

先：

```text
(+ 2 3)
↓
5
```

再：

```text
(square 5)
```

Normal order 则更像：

```text
先展开
需要的时候再 evaluate operand
```

例如：

```scheme
(square (+ 2 3))

↓ substitute without evaluating operand

(* (+ 2 3)
   (+ 2 3))

↓
(* 5 5)

↓
25
```

注意这里：

```text
(+ 2 3)
```

被计算了两次。

这个差别会在后面变得非常重要：

```text
applicative order
normal order
lazy evaluation
streams
```

但现在的重点是：

> **evaluation strategy 本身是语言语义的一部分。**

# 34. 本节最容易混淆的几个概念

## Procedure vs Process

```text
procedure
=
静态程序规则

process
=
执行规则后产生的动态计算
```

误区：

> 函数代码就是运行过程。

错误。

同一个 procedure 甚至可能因为 input 不同产生非常不同的 process。

---

## Primitive vs Compound Procedure

primitive：

```scheme
+
*
/
```

由语言运行时提供。

compound：

```scheme
(define (square x)
  (* x x))
```

由你通过 abstraction 构造。

但重要的是：

```text
使用方式基本统一
```

都是：

```scheme
(operator operands...)
```

---

## Combination vs Abstraction

Combination：

```scheme
(+ (square x)
   (square y))
```

回答：

> 怎么把东西组合起来？

Abstraction：

```scheme
(define (sum-of-squares x y)
  ...)
```

回答：

> 怎么把整个组合视为一个新的单位？

可以理解为：

```text
combination
     ↓
produces complexity

abstraction
     ↓
compresses complexity
```

这两者永远是一对。
