# 1. 这节课到底想解决什么问题？

## 1.1 7A 给了我们一台“语言机器”

7A 最重要的结果可以压缩成：

```text
程序
 ↓
EVAL
 ↓
识别 expression 类型
 ↓
APPLY procedure
 ↓
environment
 ↓
结果
```

也就是说，我们终于有了一个非常小的 Scheme evaluator。

粗略地：

```scheme
(define (eval exp env)
  (cond
    ((self-evaluating? exp) exp)
    ((variable? exp)
     (lookup-variable-value exp env))
    ((lambda? exp)
     (make-procedure
       (lambda-parameters exp)
       (lambda-body exp)
       env))
    ((application? exp)
     (apply
       (eval (operator exp) env)
       (eval-operands (operands exp) env)))))
```

以前：

> “Scheme 为什么这么运行？”

像是语言规范告诉我们的事实。

现在：

> “Scheme 为什么这么运行？”

答案变成：

```text
因为 evaluator 就是这么写的。
```

于是马上出现一个更有趣的问题：

> **如果我改 evaluator，会发生什么？**

这正是 7B。

Sussman 在这一讲开头强调，metacircular evaluator 很适合拿来实验语言设计：修改少量规则，就可以实际体验一种不同语言的行为。([TAU Open Course Ware](https://ocw.tau.edu.ng/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/7b-metacircular-evaluator-part-2/?utm_source=chatgpt.com "7B: Metacircular Evaluator, Part 2 | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

# 2. 这一讲真正的问题不是 Lazy Evaluation

更准确地说，是：

> **一个 programming language 的语义，到底由哪些设计决策组成？**

7B 故意修改几个地方。

你会看到：

```text
procedure 参数怎么绑定？
        ↓
variable 在哪里找？
        ↓
argument 什么时候求值？
        ↓
什么东西必须 force？
```

每改一个地方，语言就发生变化。

所以这一讲属于：

```text
                         language design ★★★★★
                         evaluation      ★★★★★
                         environment     ★★★★★
                         abstraction     ★★★★★
                         modularity      ★★★★★
                         control flow    ★★★★
                         representation ★★★
                         state           ★★
```

核心不是：

> “学一个 thunk 数据结构。”

而是：

> **evaluation strategy 本身就是语言的一部分。**

# 4. 第一个实验：Variadic Procedure

这是本讲比较容易被忽略的一段，但它非常能体现 SICP 的语言设计观。讲座先讨论了不定数量参数，然后只需改变 evaluator 中参数与实参配对的规则，就能支持这种新语言特性。([TAU Open Course Ware](https://ocw.tau.edu.ng/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/7b-metacircular-evaluator-part-2/?utm_source=chatgpt.com "7B: Metacircular Evaluator, Part 2 | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

假设原来只能：

```scheme
(lambda (x y)
  (+ x y))
```

形式参数：

```text
(x y)
```

必须对应：

```text
arg1 arg2
```

但 `+` 很自然地希望支持：

```scheme
(+ 1 2 3 4 5)
```

怎么办？

一种语法设计是 dotted list：

```scheme
(lambda (x . rest)
  ...)
```

调用：

```scheme
(f 1 2 3 4)
```

得到：

```text
x    = 1
rest = (2 3 4)
```

这件事表面上像一个 Scheme 小语法。

但 SICP 真正要你看到：

```text
syntax
  ↓
formal parameter representation
  ↓
argument-binding semantics
```

语言设计必须同时回答两个问题：

```text
程序员怎么写？
     +
解释器怎么解释？
```

---

# 5. 一个极重要的语言设计原则：Syntax ≠ Semantics

例如：

```scheme
(lambda (x . xs)
  ...)
```

首先只是一种**representation**。

Evaluator 必须决定：

```text
formal: (x . xs)
actual: (10 20 30 40)

         ↓ pair-up

x  → 10
xs → (20 30 40)
```

所以语言 feature 通常都有：

```text
syntax
   ↓
representation
   ↓
recognition
   ↓
semantic action
```

这一模式后面会反复出现。

例如：

```text
if
lambda
define
amb
delay
quote
```

本质上都是：

> 一种 expression representation + evaluator 对它的解释规则。

# 6. 第二个实验：Lexical Binding vs Dynamic Binding

这是 7B 最值得仔细理解的部分之一。

先看这样一个程序：

```scheme
(define n 2)

(define (power x)
  (expt x n))

(define (caller n)
  (power 3))
```

执行：

```scheme
(caller 5)
```

问：

```text
power 中的 n 是谁？
```

---

# 7. Lexical Scoping 的答案

看代码**定义的位置**。

```scheme
(define n 2)

(define (power x)
  (expt x n))
```

定义 `power` 时：

```text
Global Environment
────────────────────
n     → 2
power → closure
```

closure 保存：

```text
procedure
 ├── parameters: (x)
 ├── body: (expt x n)
 └── environment: Global
```

现在执行：

```scheme
(caller 5)
```

environment：

```text
Global
│
├── n = 2
│
├── power = closure(... Global)
│
└── caller = closure(... Global)


调用 caller 5

E1
────────────────
n = 5
parent → Global
```

然后：

```scheme
(power 3)
```

关键来了。

执行 `power` 时不是：

```text
parent → E1
```

而是：

```text
E2
────────────────
x = 3
parent → Global
```

因为 `power` closure 保存的是：

```text
environment of definition
```

于是查找：

```text
x
↓
E2
↓
3

n
↓
E2 没有
↓
Global
↓
2
```

所以：

```scheme
(expt 3 2)
```

得到：

```text
9
```

# 8. Closure 到底是什么？

这一节以后，你应该彻底抛弃这种 mental model：

```text
procedure = code
```

正确的是：

```text
procedure
   =
code
   +
environment
```

或者：

```text
Closure
┌──────────────────────────┐
│ parameters               │
│ body                     │
│ pointer to defining env  │
└──────────────────────────┘
```

这是整个 SICP 的关键模型之一。

# 9. Dynamic Binding 会怎么做？

Dynamic binding 不看：

```text
procedure 在哪里定义
```

而看：

```text
procedure 是谁调用的
```

也就是 free variable 沿着**调用链**寻找。

于是：

```scheme
(caller 5)
```

内部：

```scheme
(power 3)
```

environment 变成：

```text
E2: power
────────────────
x = 3
parent → E1


E1: caller
────────────────
n = 5
parent → Global
```

查：

```text
n
↓
E2 没有
↓
E1
↓
5
```

得到：

```scheme
(expt 3 5)
```

结果：

```text
243
```

Sussman 在讲座里确实把 dynamic binding 作为 evaluator 修改实验，并指出早期 Lisp 之所以出现这种行为，很大程度与简单的实现方式有关；随后重点展示了它带来的 modularity 问题。([TAU Open Course Ware](https://ocw.tau.edu.ng/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/7b-metacircular-evaluator-part-2/?utm_source=chatgpt.com "7B: Metacircular Evaluator, Part 2 | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

# 10. 为什么 Dynamic Binding 看起来一开始很诱人？

假设我想写：

```scheme
(define (nth-power x)
  (expt x n))
```

这里：

```text
n 是 free variable
```

然后：

```scheme
(define (sum-powers a b n)
  (sum nth-power a 1+ b))
```

我们“直觉上”可能希望：

```text
sum-powers 的 n
      ↓
nth-power 中的 n
```

Dynamic binding 正好能做到：

```text
nth-power
   ↓ search caller
sum
   ↓ search caller
sum-powers
   ↓
n
```

这看起来很方便。

但是问题来了。

---

# 11. Dynamic Binding 的 Modularity Crisis

假设库作者写：

```scheme
(define (sum term a next b)
  ...)
```

内部用了名字：

```text
n
```

而你的函数也碰巧依赖调用环境里的：

```text
n
```

那么库作者仅仅把内部变量：

```text
next
```

改名为：

```text
n
```

你的程序可能就坏了。

注意：

> 他没有修改 API。

只是：

```text
local variable rename
```

却改变了外部程序行为。

这非常严重。

---

# 12. Alpha-renaming：一个极深的 modularity invariant

考虑：

```scheme
(lambda (x)
  (+ x 1))
```

把 `x` 改名：

```scheme
(lambda (banana)
  (+ banana 1))
```

程序意义应该完全一样。

这个性质叫：

```text
α-renaming
```

直觉上：

> bound variable 的名字本身不应该有意义。

也就是说：

```text
lambda x
```

某种意义上像数学里的：

$$
\forall x
$$

例如：

$$
\forall x,\; x+1>x
$$

把 `x` 改成：

$$
\forall y,\; y+1>y
$$

意义不会改变。

Lexical scope 保住了这个性质。

Dynamic scope 很容易破坏它。

这也是 Sussman 在这一段想表达的非常深的一点：如果内部名字的改变可以改变其他模块含义，那么语言的 abstraction barrier 会变得非常脆弱。([TAU Open Course Ware](https://ocw.tau.edu.ng/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/7b-metacircular-evaluator-part-2/?utm_source=chatgpt.com "7B: Metacircular Evaluator, Part 2 | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

# 13. SICP 的解决方案：不要 Dynamic Scope，使用 Closure

我们真正想表达的是：

> 给我一个固定了 `n` 的 exponentiation function。

那么直接构造它：

```scheme
(define (pgen n)
  (lambda (x)
    (expt x n)))
```

执行：

```scheme
(pgen 3)
```

发生什么？

---

# 14. Evaluation：`(pgen 3)`

Global：

```text
pgen → closure
```

调用：

```scheme
(pgen 3)
```

创建：

```text
E1
────────────
n = 3
parent → Global
```

执行 body：

```scheme
(lambda (x)
  (expt x n))
```

注意：

`lambda` 不执行 body。

它创建 closure：

```text
Closure C
─────────────────────
parameters: (x)
body: (expt x n)
environment → E1
```

因此：

```scheme
(define cube
  (pgen 3))
```

实际上：

```text
cube
 ↓
Closure C
 ↓
E1
 ↓
n = 3
```

之后：

```scheme
(cube 10)
```

创建：

```text
E2
────────────
x = 10
parent → E1

E1
────────────
n = 3
```

计算：

```scheme
(expt x n)
```

查到：

```text
x = 10
n = 3
```

得到：

```text
1000
```

# 15. 这里为什么“procedure 可以作为返回值”如此重要？

表面：

```scheme
(pgen 3)
```

返回一个函数。

本质：

```text
configuration
     n = 3
        ↓
封装进 environment
        ↓
返回 computation
        ↓
得到 specialization
```

即：

```text
general computation

(expt x n)

       ↓ fix n

specialized computation

cube(x)
```

现代工程里你会到处看到这个思想：

```text
factory
dependency injection
callback factory
middleware generator
configured handler
configured parser
configured retry policy
```

但 SICP 的抽象更基础：

> **一个 computation 可以和它需要的环境一起成为一个值。**

这就是 closure。

# 16. 第三个实验：为什么普通 procedure 无法自己定义 `if`？

现在进入本讲后半段的核心：delayed evaluation。

假设我们想写：

```scheme
(define (unless p c a)
  (if (not p)
      c
      a))
```

希望：

```scheme
(unless #f
        2
        (/ 1 0))
```

结果为：

```text
2
```

从逻辑上看：

```text
p = #f
→ not p = #t
→ choose c
→ 2
```

似乎没问题。

但是 Scheme 不这样执行。

---

# 17. Applicative-order Evaluation

普通 procedure application：

```scheme
(unless #f 2 (/ 1 0))
```

规则：

```text
evaluate operator
       ↓
unless → procedure

evaluate operands
       ↓
#f
2
(/ 1 0)
       ↓
ERROR

apply procedure
```

注意：

```text
APPLY 甚至还没发生。
```

程序就炸了。

因为 Scheme 默认：

```text
evaluate arguments
before
apply procedure
```

也就是 applicative order / eager evaluation。

讲座正是用类似 `unless` 的例子说明：普通 procedure 因为 operands 会先被求值，所以无法直接模拟 `if` 这样的控制结构。([MIT OpenCourseWare](https://ocw.mit.edu/courses/6-001-structure-and-interpretation-of-computer-programs-spring-2005/771092351b136b40083a0f5d147ed2b9_QVEOq5k6Xi0.pdf?utm_source=chatgpt.com "MITOCW | Lecture 7B[MUSIC PLAYING]PROFESSOR: Well, let's see. # 18. 为什么 `if` 能做到？

因为：

```scheme
(if predicate
    consequent
    alternative)
```

不是 ordinary procedure application。

它是 special form。

Evaluator 对它有特殊规则：

```text
evaluate predicate
       ↓
true?
 ↙         ↘
yes         no
 ↓           ↓
evaluate     evaluate
consequent   alternative
```

不会：

```text
evaluate consequent
evaluate alternative
then call if
```

这就是：

> **control flow 本质上是 evaluation policy。**

这是非常重要的一句话。

---

# 19. 问题来了：能不能让普通 procedure 拥有这种能力？

我们希望定义：

```scheme
(unless p c a)
```

但是告诉 evaluator：

```text
p：normal/eager
c：delayed
a：delayed
```

类似讲座中的思路：

```scheme
(define (unless p (name c) (name a))
  ...)
```

其中：

```text
(name c)
```

表达：

> 不要现在 evaluate 这个 operand。

这正是 7B 的 by-name parameter 实验。讲座还特别指出，与前面简单修改参数绑定或 dynamic binding 相比，这次修改更深，因为 evaluator 原来的核心顺序是“先 evaluate 所有 operands，再 apply”；现在必须先知道 procedure 的 parameter policy，才能决定每个 operand 是否求值。([TAU Open Course Ware](https://ocw.tau.edu.ng/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/7b-metacircular-evaluator-part-2/?utm_source=chatgpt.com "7B: Metacircular Evaluator, Part 2 | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

---

# 20. 这为什么不是一个小修改？

原来的 evaluator：

```text
application

      ↓

eval operator
      +
eval every operand
      ↓
argument values
      ↓
apply
```

即：

```scheme
(apply
  (eval operator env)
  (eval-list operands env))
```

但现在不行。

为什么？

因为在 evaluate operands **之前**，我们必须先知道：

```text
parameter 1 是 eager？
parameter 2 是 name？
parameter 3 是 name？
```

于是 control flow 必须变成：

```text
application
    ↓
evaluate operator
    ↓
inspect procedure
    ↓
inspect parameter declarations
    ↓
for each operand:
    eager parameter → evaluate now
    name parameter  → delay
    ↓
bind
    ↓
evaluate body
```

这里直接改变了 evaluator 的 architecture。

我们不能只保存：


所以必须保存：

# 22. 为什么 Thunk 必须保存 Environment？

这是 7B 最容易被低估、但最重要的细节之一。

例如：

```scheme
(let ((x 20))
  (f (+ x 1)))
```

假设 `f` 的参数是 delayed。

创建 thunk 时：

```text
expression:
(+ x 1)

environment:
E1:
x = 20
```

之后可能在完全不同的环境里 force。

但它必须仍然计算成：

```text
21
```

因此：

```text
Thunk
  =
Expression
  +
Environment
```

这和 closure：

```text
Closure
  =
Procedure code
  +
Environment
```

非常相似。

这不是巧合。

# 23. Closure vs Thunk

这是非常值得主动对比的一组。

||Closure|Thunk|
|---|---|---|
|保存什么|procedure body + env|expression + env|
|目的|延迟 procedure body 到调用|延迟 expression evaluation|
|什么时候执行|procedure application|force|
|参数？|有 formal parameters|通常没有|
|本质|packaged computation|packaged computation|

你甚至可以把 thunk 想象成：

```scheme
(lambda ()
  expression)
```

例如：

```scheme
(lambda ()
  (+ x 1))
```

现代语言经常直接用 zero-argument closure 模拟 thunk。

# 24. Force / Undelay 是什么？

假设：

```text
x → thunk
```

当某个地方真正需要值：

```text
force x
```

解释器：

```text
thunk?
 ↓ yes
extract expression
 ↓
extract saved environment
 ↓
eval(expression, saved-env)
 ↓
value
```

伪代码：

```scheme
(define (force value)
  (if (thunk? value)
      (force
        (eval
          (thunk-expression value)
          (thunk-environment value)))
      value))
```

为什么递归 `force`？

因为：

```text
thunk
 ↓ evaluate
another thunk
 ↓ evaluate
...
 ↓
actual value
```

# 25. 完整展开 `unless`

假设：

```scheme
(unless #f
        2
        (/ 1 0))
```

```text
↓
```

```text
↓
```


# 27. 这里最核心的概念：Strictness

并不是所有 operation 都必须马上得到真正的值。

例如：

```scheme

```

```text

```

所以 `+` 是 strict。

类似：

```text

<
pair?

```

都必须观察数据。

因此：

```text

```

但比如某些 data constructor：

```scheme

```

理论上完全可以只是：

```text
保存 x 的 promise
保存 y 的 promise
```

而不用计算。

# 28. Applicative Order vs Normal Order

现在可以正式比较。

## Applicative Order

```scheme
(f (g x))
```

先：

```text
evaluate f
↓
procedure F

evaluate (g x)
↓
evaluate g
↓
evaluate x
↓
apply g
↓
result R

apply F to R
```

即：

```text
arguments first
procedure body later
```

---

## Normal Order / Lazy-style

大致：

```scheme
(f (g x))
```

先：

```text
evaluate f
↓
procedure F

don't evaluate (g x)
↓
make thunk

bind parameter
↓
thunk(g x, environment)

evaluate f body
```

只有真正用到参数：

```text
force
↓
evaluate (g x)
```

# 29. Call-by-value vs Call-by-name vs Call-by-need

这三个一定要分清。

## Call-by-value

```text
argument
 ↓
evaluate once before call
 ↓
value
 ↓
bind parameter
```

Scheme 默认大体属于这一类。

---

## Call-by-name

```text
argument expression
 ↓
delay
 ↓
每次使用 parameter
 ↓
重新 evaluate expression
```

例如：

```scheme
(define (twice x)
  (+ x x))
```

调用：

```scheme
(twice (expensive))
```

可能：

```text
expensive()
↓
first x

expensive()
↓
second x
```

执行两次。

7B 展示的 `thunk + undelay` 设计主要是在说明这种 by-name 风格。讲座自己也把它类比到 ALGOL 的 call-by-name。([MIT OpenCourseWare](https://ocw.mit.edu/courses/6-001-structure-and-interpretation-of-computer-programs-spring-2005/771092351b136b40083a0f5d147ed2b9_QVEOq5k6Xi0.pdf?utm_source=chatgpt.com "MITOCW | Lecture 7B[MUSIC PLAYING]PROFESSOR: Well, let's see. What we did so far was a lot of fun, was it useful for anything? I suppose the answer"))

---

## Call-by-need

改进：

```text
first force
   ↓
evaluate
   ↓
cache value

later force
   ↓
return cached value
```

所以：

```text
(expensive)
```

最多执行一次。

这通常就是今天说的 memoized lazy evaluation。

# 30. 为什么 Call-by-name ≠ Call-by-need？

假设：

```scheme
(define (square x)
  (* x x))
```

调用：

```scheme
(square (expensive-computation))
```

### Eager

```text
expensive
↓ once
R
↓
R * R
```

### Call-by-name

```text
force x
↓ expensive

force x again
↓ expensive again
```

### Call-by-need

```text
force x
↓ expensive
↓ cache R

force x
↓ cache hit
```

这是非常重要的复杂度差异。

# 33. 为什么 `if` 通常是 Special Form？

现在你应该能给出真正的答案，而不是：

> “因为 Scheme 语法规定如此。”

真正原因：

普通 procedure application 的 evaluator rule 是：

```text

↓
apply
```

但 `if` 需要：

```text

↓
select ONE branch
↓
evaluate selected branch only
```

所以它和普通 application 的 evaluation strategy 不一样。

因此必须：

```text
A. 做成 special form

或者

B. 改 procedure parameter semantics
```

# 39. Evaluation Order 为什么会改变程序的“Process Shape”？

这节不主要讨论 recursion，但 evaluation strategy 本身也会改变 process。

例如：

```scheme
(define (first x y)
  x)

(first 1
       (expensive))
```

### Eager

```text
eval 1
↓
1

eval expensive
↓
巨大计算

apply first
↓
1
```

时间：

$$
T = O(T_{\text{expensive}})
$$

---

### Lazy

```text
bind x → thunk(1)
bind y → thunk(expensive)

body = x

force x
↓
1
```

`y` 从未 force。

时间：

$$
T=O(1)
$$

即：

> evaluation strategy 会改变算法实际执行的 computation graph。

# 40. 但是 Lazy 也不是“免费优化”

再看：

```scheme
(define (twice x)
  (+ x x))
```

调用：

```scheme
(twice (expensive n))
```

假设：

$$
T_{\text{expensive}}(n)=O(n)
$$

### eager

一次：

$$
O(n)
$$

### call-by-name

两次：

$$
2O(n)=O(n)
$$

Big-O 没变，但常数翻倍。

如果递归地重复参数，则甚至可能导致非常大的重复计算。

所以才有：

```text
call-by-need
=
lazy
+
memoization
```

# 41. Lazy Evaluation 的 Space Cost

还有一个工程师非常值得关注的问题：

Thunk 持有：

```text
expression
+
environment
```

所以：

```text
environment 不能释放
```

即使我们暂时还不计算它。

可能形成：

```text
thunk
 ↓
environment
 ↓
large data
 ↓
large data
 ↓
large data
```

这就是 lazy language 中典型的：

```text
space leak
```

所以：

```text
less immediate computation
```

不代表：

```text
less memory
```

```text
    Syntax         Binding       Evaluation
       │              │              │
       │        lexical/dynamic   eager/lazy
       │              │              │
       ↓              ↓              ↓
 formal params     Closure          Thunk
       │              │              │
       ↓              ↓              ↓
 argument          saved env       saved env
 pairing              │              │
       └──────────────┼──────────────┘
                      ↓
               APPLY / FORCE
                      │

```

```text

   ↓

   ↓
```

# 57. 真正应该记住的东西

不需要记几十个 evaluator 辅助函数。

### 核心思想

1. **Evaluator 是 executable semantics。** 改 evaluator，就是改语言。
    
2. **Lexical scope 是重要的 modularity mechanism。** free variables 跟 definition environment 走，而不是 caller chain。
    
3. **Closure = code + environment。** 这是 higher-order abstraction 能可靠工作的基础。
    
4. **Evaluation order 是语言设计的一部分。** ordinary procedure、special form、lazy argument 的区别，本质是“什么时候 evaluate”。
    
5. **好的语言设计追求少量可组合机制，而不是不断增加 feature。**
    

### 关键机制

记住：

```text
closure
=
lambda + environment
```

```text
thunk
=
expression + environment
```

```text
eager:
eval operands → apply
```

```text
lazy:
inspect procedure
→ delay some operands
→ apply
→ force when needed
```

```text
lexical:
free variable → definition environment
```

```text
dynamic:
free variable → caller chain
```

### 三个最重要的不变量

我尤其建议记住这三个。

**Invariant 1：**

```text
Lexical closure 中，
procedure 的 free variables
由 procedure 创建时的 environment 决定。
```

**Invariant 2：**

```text
Delayed expression 若以后再求值，
必须携带创建 delay 时的 environment。
```

**Invariant 3：**

```text
Bound variable 改名不应该改变程序意义。
```

第三个其实就是非常深的 modularity test。
