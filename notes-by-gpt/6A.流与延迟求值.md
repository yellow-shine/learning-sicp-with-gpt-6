# Lecture 6A — Streams, Part 1

MIT 的这套经典 6.001 视频里，Lecture 6A 正是 **Streams, Part 1**；它紧接着 5A 的 assignment/state 和 5B 的 computational objects，后面还有 6B 继续把 streams 推向无穷序列和更复杂的计算。MIT OCW 特别说明，这套录像来自 1986 年课程，因此术语和后来第二版 SICP 有少量差异，但整体思想和顺序是一致的。([MIT OpenCourseWare](https://ocw.mit.edu/courses/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video_galleries/video-lectures/?utm_source=chatgpt.com "Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

如果只把这一讲理解成：

> Stream = lazy list

会错过大概 **80% 的价值**。

Lecture 6A 真正讨论的是：

> **我们能否把“计算过程”重新表示成“数据”，从而把程序的逻辑结构与机器真正执行这些计算的时间顺序分离？**

而答案就是：

```text
Streams
+
higher-order procedures
+
delayed evaluation
+
memoization
```

这实际上同时涉及 **abstraction、composition、evaluation、representation、control flow、state 和 language design**。

---

# 1. 这节课到底想解决什么问题？

## 1.1 前两讲刚刚获得了 state，但代价非常大

5A/5B 引入了：

```scheme
set!
state
object identity
message passing
mutation
```

这给程序带来了一个巨大的好处：

> 可以让程序结构模仿现实世界中的对象。

例如一个银行账户：

```text
account
   ↓
balance = 100
   ↓ withdraw
balance = 70
```

或者一个随机数发生器：

```text
random-generator
        │
        ├── internal state
        │
        ↓
      next()
```

这是很自然的模块化方式。

但问题是，一旦有 mutation：

```scheme
(f x)
```

就不再一定是一个只由 `f` 和 `x` 决定的值。

第一次：

```scheme
(f x) → 10
```

第二次：

```scheme
(f x) → 17
```

完全可能。

于是程序的意义开始依赖：

```text
谁先执行？
谁后执行？
变量之前是什么值？
中间谁修改了它？
两个名字是不是指向同一个 object？
```

这就是为什么 substitution model 不够用了。

Lecture 6A 一开头就回顾了这个问题：引入 assignment 后，变量不再只是“代表一个值”，而是指向一个可以改变内容的位置；程序必须开始考虑时间、对象 identity、sharing 和 sequencing。

以前我们可以想：

```text
x = 3

(square x)

→ (* 3 3)
→ 9
```

现在则必须想：

```text
environment
    ↓
x → location L1
         ↓
         3

(set! x 4)

x → location L1
         ↓
         4
```

程序从：

```text
mathematical description
```

变成了某种：

```text
machine history
```

# 2. 那为什么还要 state？

因为 state 解决了一个非常真实的问题：

> **modularity。**

假设我们要模拟数字电路：

```text
input ──▶ gate A ──▶ wire ──▶ gate B ──▶ output
```

最自然的 object-oriented 思维就是：

```text
gate A
  internal state

wire
  current signal

gate B
  internal state
```

然后：

```text
time t0
   ↓
input changes
   ↓
gate A changes
   ↓
wire changes
   ↓
gate B changes
```

程序结构很好地对应现实世界。

但是 SICP 在这里提出了一个非常有意思的问题：

> **也许不是 state 本身有问题，而是“我们怎么看待这个系统”有问题。**

Hal Abelson 在 Lecture 6A 里用 signal processing 做类比：信号处理工程师通常不会把信号理解成“某个对象在 t₀ 是 3、t₁ 变成 5、t₂ 又变成 8”。

更自然的是：

```text
signal =

time:    t0  t1  t2  t3  t4 ...
value:    3   5   8   2   9 ...
```

也就是说：

> 不看“一个值随时间发生变化”，而看“整个时间序列”。

Lecture 直接把这种视角与前面的 object/state 视角进行了对照，并称新的组织方式为 **stream processing**。

这是本讲的第一次巨大 conceptual shift：

```text
Object / State View

variable
   ↓
value changes over time

             ↓ 换视角

Stream View

value-at-t0
value-at-t1
value-at-t2
value-at-t3
...
```

也就是：

```text
state changing through time
```

变成：

```text
a sequence containing all states
```

# 3. 本节真正的问题

所以这节课不是：

> 怎么实现 Stream？

而是：

> **有没有办法既得到 state/object 所追求的 modularity，又尽可能重新得到 functional programming 的清晰性？**

SICP 给出另一种 decomposition：

```text
传统 state/object decomposition

system
 ├── object A + state
 ├── object B + state
 └── messages through time


stream decomposition

source
   ↓
transform
   ↓
filter
   ↓
transform
   ↓
consumer
```

前者关注：

```text
who changes whom, when?
```

后者关注：

```text
what sequence is transformed into what sequence?
```

因此如果必须给 Lecture 6A 的核心问题分类，我会这样看：

```text
最核心：
    modularity
    abstraction
    evaluation
    control flow

非常重要：
    representation
    composition

作为背景/对照：
    state

更深层：
    language design
```

# 5. 第一核心机制：Sequence Processing / Conventional Interfaces

Lecture 先举两个看起来完全不同的问题。

---

## 5.1 问题 A：树中所有奇数的平方之和

假设：

```text
          *
        /   \
       1     *
            / \
           2   3
```

目标：

```text
odd leaves
1,3

square
1,9

sum
10
```

传统递归可能写成：

```scheme
(define (sum-odd-squares tree)
  (cond ((leaf? tree)
         (if (odd? tree)
             (square tree)
             0))
        (else
         (+ (sum-odd-squares (left-branch tree))
            (sum-odd-squares (right-branch tree))))))
```

这代码没错。

但观察一下：

```text
enumeration
filtering
mapping
accumulating
```

全部搅在了一起。

---

# 6. 问题 B：前 n 个 Fibonacci 中所有奇数

传统程序可能是：

```scheme
(define (odd-fibs n)
  (define (iter k)
    (if (> k n)
        '()
        (let ((f (fib k)))
          (if (odd? f)
              (cons f
                    (iter (+ k 1)))
              (iter (+ k 1))))))
  (iter 1))
```

看起来和 `sum-odd-squares` 完全不同。

但从更高层看：

### sum-odd-squares

```text
tree
 ↓
enumerate leaves
 ↓
filter odd
 ↓
map square
 ↓
accumulate +
```

### odd-fibs

```text
1...n
 ↓
enumerate interval
 ↓
map fib
 ↓
filter odd
 ↓
accumulate cons
```

它们实际上是同一种程序。

Lecture 明确指出：原来的递归代码把 enumerator、filter 和 accumulator 的角色分散在 termination test、recursive structure 和 combine operation 中，所以我们“没有名字”来指称这些自然的组件；streams 的一个目的正是建立这样的统一语言。

# 7. 这就是 SICP 所谓 Conventional Interfaces

这是整个 SICP 最值得记住的思想之一：

```text
组件真正容易组合

不是因为组件内部简单

而是因为：

它们共享同一个 interface
```

例如 Unix：

```text
program
  stdin
  stdout
```

所以：

```bash
cat file |
grep error |
sort |
uniq
```

能组合。

而 Streams：

```text
Stream<T>
     ↓
Stream<U>
     ↓
Stream<V>
```

于是：

```text
enumerate
   ↓
filter
   ↓
map
   ↓
filter
   ↓
...
```

任意拼接。

Lecture 把这一点明确称为课程的重要主题之一：`map`、`filter` 等成为可以“粘合”程序的标准组件，因为它们共享 stream 这个统一数据接口。

# 8. Stream 首先是一个 Data Abstraction

先暂时不要考虑 lazy。

概念上，我们定义：

```text
constructor:

cons-stream


selectors:

head
tail
```

满足：

```text
head(cons-stream(x, y)) = x

tail(cons-stream(x, y)) = y
```

看起来是不是很熟悉？

Pair：

```text
cons
car
cdr
```

满足：

```text
car(cons x y) = x

cdr(cons x y) = y
```

所以一开始：

```text
stream ≈ list
```

Lecture 故意先让你这么想，然后再告诉你：

> 它们 interface 相似，但 evaluation semantics 不一样。

这非常 SICP。

因为：

```text
representation
```

不是由表面接口决定的。

# 9. map / filter / accumulate

现在建立统一 vocabulary。

## stream-map

概念代码：

```scheme
(define (stream-map f s)
  (if (empty-stream? s)
      the-empty-stream
      (cons-stream
        (f (head s))
        (stream-map f
                    (tail s)))))
```

不要急着看 recursion。

它描述的是：

```text
s:

x1 x2 x3 x4 ...

        f
        ↓

f(x1) f(x2) f(x3) f(x4) ...
```

---

## stream-filter

```scheme
(define (stream-filter predicate s)
  (cond ((empty-stream? s)
         the-empty-stream)

        ((predicate (head s))
         (cons-stream
           (head s)
           (stream-filter predicate
                          (tail s))))

        (else
         (stream-filter predicate
                        (tail s)))))
```

含义：

```text
1 2 3 4 5 6
       │
       │ odd?
       ▼
1   3   5
```

---

## accumulate

概念上：

```scheme
(define (accumulate op initial s)
  (if (empty-stream? s)
      initial
      (op (head s)
          (accumulate op
                      initial
                      (tail s)))))
```

例如：

```text
1 3 5

↓ accumulate +

1 + (3 + (5 + 0))

= 9
```

Lecture 中正是通过 map/filter/accumulate 把前面两个看似不同的问题重写成了同一种 pipeline。

# 11. `f` 为什么作为 procedure 参数如此重要？

例如：

```scheme
(stream-map square s)
```

重点不是：

> `square` 是函数参数。

真正重要的是：

```text
过去：
数据是可以传递的

3
"hello"
(pair ...)


现在：
computation 本身也可以传递

square
odd?
fib
+
```

也就是说：

```text
data abstraction
+
computation abstraction
```

正在融合。

以前：

```scheme
(square x)
```

表示：

> 执行一个计算。

现在：

```scheme
(stream-map square s)
```

里面的 `square` 本身变成了一个对象：

```text
square
   ↓
passed into another computation
```

所以：

```text
algorithm
```

能够被参数化。

`stream-map` 实际不是“处理某一种数据”的 procedure。

它表达的是：

> 对任何 sequence 应用任何 element-wise transformation。

这就是 reusable abstraction。

# 12. flatmap：把 nested loop 变成 composition

这是本讲另一个重要结构。

假设：

```text
1 → [a b]
2 → [c d]
3 → [e f]
```

普通 map 得：

```text
[[a b]
 [c d]
 [e f]]
```

这是：

```text
stream of streams
```

我们定义：

```text
flatten

[[a b] [c d] [e f]]

↓

[a b c d e f]
```

于是：

```text
flatmap f s
=
flatten(map f s)
```

Lecture 正是这样定义 `flat-map`，并用它表达嵌套枚举。

# 13. 为什么 flatmap 非常重要？

假设：

```scheme
i = 1..n
j = 1..i-1
```

传统语言：

```text
for i in ...
    for j in ...
        ...
```

functional sequence thinking：

```text
for each i
      ↓
generate stream of j
      ↓
produce stream of pairs

stream-of-streams
      ↓
flatten
```

所以：

```text
nested loops
```

可以理解成：

```text
nested flatmaps
```

Lecture 直接指出这一点。

这也是为什么今天这些概念会再次出现于：

```text
Scala flatMap
Java flatMap
Rust flat_map
Python comprehensions
LINQ SelectMany
```

甚至 Monad 里。

# 14. Eight Queens：这里真正改变的是 mental model

传统 backtracking 视角：

```text
try row 1
   ↓ fail
backtrack

try row 2
   ↓
try next queen
   ↓ fail
backtrack

...
```

这是一个 **temporal story**：

```text
first I do X
then Y
if fail go back
then try Z
```

Lecture 认为这是过度关注时间。

换一个视角：

> 假设我已经拥有所有能安全放置前 `k-1` 列皇后的 board。

那么：

```text
solutions(k - 1)
       │
       │ 每个 board
       ▼
try every row
       │
       ▼
all candidate boards
       │
       ▼
filter safe
       │
       ▼
solutions(k)
```

代码开始描述：

```text
set of possibilities
```

而不是：

```text
machine walking around a search tree
```

Lecture 甚至直接说，这种表达之所以更简单，是因为它把“随时间执行的搜索过程”重新看成“一整个解的集合”。

这是一个很深的 abstraction shift：

```text
imperative view:

How do I search?


declarative/stream view:

What is the set of solutions?
```

# 15. 但此时出现一个巨大问题

你应该立即产生怀疑：

> 这样不是巨浪费吗？

例如：

> 找 10,000 到 1,000,000 之间的第二个素数。

如果 stream 就是普通 list：

```scheme
(head
  (tail
    (stream-filter prime?
      (enumerate-interval
        10000
        1000000))))
```

如果 eager：

首先：

```text
enumerate-interval

10000
10001
10002
...
1000000
```

全部生成。

然后：

```text
filter prime?
```

全部检查。

最后：

```text
head(tail(...))
```

我实际上只需要两个 prime！

Lecture 正是在这里指出 contradiction：

```text
modular / compositional program
             vs
efficient computation
```

普通手写 loop 虽然“丑”：

```text
generate
test
generate
test
generate
test
```

但它非常高效。

而 pipeline：

```text
generate everything
      ↓
filter everything
      ↓
take second
```

似乎非常浪费。

# 17. Stream 和 List 真正的区别

普通 list：

```scheme
(cons
  1
  (cons
    2
    (cons
      3
      '())))
```

结构：

```text
+---+---+    +---+---+    +---+---+
| 1 | o----->| 2 | o----->| 3 | / |
+---+---+    +---+---+    +---+---+
```

整个 tail 已经存在。

Stream：

```text
+---+-----------------------+
| 1 | promise to compute... |
+---+-----------------------+
```

也就是：

```text
head = value

tail = computation
```

这是最重要的表示不变量：

> **Stream 的 tail 不是下一段数据，而是“产生下一段数据的 computation”。**

Lecture 将 stream 描述为一种能够 incremental、on-demand 地“计算自身”的数据结构，而且明确把这与 “procedures and data 没有绝对边界” 联系起来。

---

# 18. `cons-stream`

概念上：

```scheme
(cons-stream x y)
```

实现类似：

```scheme
(cons x
      (delay y))
```

注意：

```text
x
```

立即求值。

但：

```text
y
```

不求值。

变成：

```text
promise
```

所以：

```scheme
(cons-stream
  1
  (expensive-computation))
```

真正产生：

```text
pair
 ├── 1
 └── promise:
        "以后需要时再执行
         expensive-computation"
```

---

# 19. `head`

非常简单：

```scheme
(define (head stream)
  (car stream))
```

因为第一项已经计算了。

---

# 20. `tail`

关键：

```scheme
(define (tail stream)
  (force (cdr stream)))
```

因为：

```scheme
(cdr stream)
```

拿到的不是：

```text
next stream
```

而是：

```text
promise of next stream
```

所以：

```text
tail
 ↓
get promise
 ↓
force promise
 ↓
run computation
 ↓
produce next stream cell
```

Lecture 用的就是这个实现模型：`cons-stream` 放入 `(delay y)`，head 相当于 `car`，tail 则要 `force` cdr。

---

# 21. `delay` 到底是什么？

这是这一讲非常漂亮的一步。

问：

> 什么东西可以表示“以后执行一段 computation”？

答案：

procedure。

例如：

```scheme
(+ 1 2)
```

立即执行：

```text
3
```

但是：

```scheme
(lambda ()
  (+ 1 2))
```

现在没有执行 `+`。

我们拥有的是：

```text
procedure
```

以后：

```scheme
((lambda ()
   (+ 1 2)))
```

才执行。

因此概念上：

```scheme
(delay expression)
```

近似：

```scheme
(lambda ()
  expression)
```

---

# 22. `force` 呢？

如果 promise 就是：

```scheme
(lambda ()
  expression)
```

那么：

```scheme
(force promise)
```

概念上就是：

```scheme
(promise)
```

所以：

```text
delay
=
package computation as procedure


force
=
execute packaged computation
```

Lecture 明确展示了这个转换：promise 本质上可以看成 zero-argument procedure，force 就是调用它。

# 23. 一个极重要的 language-design 细节

你可能会写：

```scheme
(define (delay x)
  (lambda () x))
```

但这在 applicative-order Scheme 中 **不对**。

为什么？

调用：

```scheme
(delay (expensive-computation))
```

Scheme 默认先 evaluate argument：

```text
evaluate operator delay

evaluate operand
    ↓
(expensive-computation)
    ↓
already executed!
```

然后才进 `delay`。

那就失去意义了。

所以：

```scheme
delay
```

不能只是普通 procedure。

它必须类似 special form / syntactic transformation：

```text
不要 evaluate argument

而是捕获 expression
```

这一点和：

```scheme
if
lambda
quote
define
```

类似。

# 24. Evaluation Model：普通 procedure call

普通 applicative-order Scheme：

```scheme
(f (g x))
```

过程：

```text
evaluate operator f
        ↓
obtain procedure F

evaluate operand (g x)
        ↓
    evaluate g
        ↓
    evaluate x
        ↓
    apply g
        ↓
    result R

apply F to R
        ↓
evaluate F body
        ↓
result
```

所以 operand：

```scheme
(g x)
```

一定先执行。

---

# 25. Evaluation Model：delay

而：

```scheme
(delay (g x))
```

不是：

```text
evaluate (g x)
```

而是：

```text
expression:

(g x)

      ↓

package as thunk / promise

(lambda ()
  (g x))
```

因此：

```text
g 未调用
x 也不需要现在得到最终计算结果
```

只是保存 computation。

# 26. Environment Model：promise 其实还是 closure

这一步特别重要。

假设：

```scheme
(define (make-stream x)
  (cons-stream
    x
    (make-stream (+ x 1))))
```

调用：

```scheme
(make-stream 1)
```

创建 frame：

```text
Global
  ↑
Frame F1
x = 1
```

尾部大致生成：

```scheme
(lambda ()
  (make-stream (+ x 1)))
```

这个 lambda 是一个 closure：

```text
procedure
    code:
      (make-stream (+ x 1))

    environment:
      F1
```

所以 stream：

```text
+------+--------------------+
|  1   | Promise P1         |
+------+--------------------+
              │
              ▼
        procedure body
        make-stream(x+1)
              │
              ▼
        environment F1
             x=1
```

以后：

```scheme
(tail stream)
```

才：

```text
force P1
   ↓
call closure
   ↓
lookup x in F1
   ↓
1
   ↓
(+ 1 1)
   ↓
2
   ↓
(make-stream 2)
```

于是得到：

```text
+------+--------------------+
|  2   | Promise P2         |
+------+--------------------+
```

这就是为什么：

> **closure 是 lazy computation 的基础机制之一。**

# 28. 第二个 prime 的真实 Evaluation

考虑：

```scheme

  (tail

      prime?
```

先生成：

```text

+

    enumerate 10001..1000000
```

不是百万个数字。

## filter 需要第一个输出

它检查：

```text

```

不是 prime。

所以需要 input 的 tail：

```text

```

得到：

```text

+

```

检查：

```text

```

不是 prime。

继续。

```text

```

是 prime。

此时 filter 输出：

```text

```

但我们要求：

```scheme

```

所以 consumer 又说：

```text

```


# 30. Applicative Order vs Normal Order vs Streams

这是非常容易混淆的地方。

## Applicative Order

Scheme 默认：

```scheme
(f (g x))
```

先：

```text
(g x)
```

再：

```text
f
```

也就是：

```text
evaluate arguments first
```

---

## Normal Order

理论上：

```text
don't evaluate argument
until needed
```

例如：

```scheme
(f (g x))
```

先把：

```scheme
(g x)
```

作为未求值 expression 传进去。

需要的时候再求值。

---

## Streams

Streams **不是把整个 Scheme 变成 normal order**。

而是：

```text
Scheme evaluator:
    applicative order

stream abstraction:
    explicitly delay selected computation
```

典型 stream cell：

```text
head → eager

tail → delayed
```

所以它是一种：

> **局部引入 lazy evaluation。**

这是非常重要的 mental model。

# 31. Delay vs Lambda

二者很像，但不是同一 abstraction。

```text
lambda

表示：
一个 procedure
```

而：

```text
delay

表示：
一个 promise
```

实现上：

```text
promise ≈ zero-argument procedure
```

所以：

```text
abstraction:
promise

possible representation:
closure
```

就像：

```text
abstraction:
rational number

possible representation:
pair(numerator, denominator)
```

不要把 abstraction 和 representation 混为一谈。

```text
(tail s)
```


这不理想。

# Memoization

# 33. Memoization 的直觉

第一次：

```text
force promise

↓
compute result

↓
cache result

↓
return result
```

第二次：

```text
force same promise

↓
already computed?

yes

↓
return cached result
```

---

# 34. `memo-proc`

概念代码大致：

```scheme
(define (memo-proc proc)
  (let ((already-run? #f)
        (result #f))
    (lambda ()
      (if (not already-run?)
          (begin
            (set! result (proc))
            (set! already-run? #t)
            result)
          result))))
```

注意这里出现了：

```scheme
set!
```

很有趣。

我们正在用：

```text
mutation
```

来实现一个表面上 functional 的 abstraction。

---

# 35. Environment Model：memo-proc

调用：

```scheme
(memo-proc P)
```

创建：

```text
Frame M

proc         → P
already-run? → false
result       → ?
```

返回 closure：

```text
+-------------------------+
| lambda ()               |
| if not already-run?...  |
+-------------------------+
             │
             ▼
         Frame M
```

第一次：

```text
closure()
 ↓
already-run? = false
 ↓
(proc)
 ↓
result = value
 ↓
already-run? = true
 ↓
value
```

frame 变成：

```text
already-run? = true
result       = VALUE
```

第二次：

```text
closure()
 ↓
already-run? = true
 ↓
return VALUE
```

因此：

```text
delay + memoization
```

大致给我们：

```text
evaluate at most once
```

Lecture 对这个细节讲得很明确：promise 第一次运行原 procedure 并保存结果，此后直接返回缓存结果，以避免反复重算 tail。

# 36. 这叫 Call-by-Need-like Evaluation

两个概念容易混：

```text
call-by-name
```

大致：

```text
need it?
→ evaluate

need again?
→ evaluate again
```

而：

```text
call-by-need
```

大致：

```text
need it?
→ evaluate
→ remember result

need again?
→ reuse
```

Streams + memoized promises：

```text
≈ call-by-need
```

不过这里只是在 stream tail 上显式构造出来的，并不是整个 Scheme evaluator 都变成 lazy。

# 37. Stream vs List

这是本节最重要的辨析之一。

|---|---|---|

|tail|data structure|promise/computation|

核心区别绝不是：


# 43. Lazy Stream

假设为了找到需要的输出，只检查了前 `k` 个 input：

```text

```

那么大致：

```text

```

不是：


```text
cost =
Σ cost(predicate(x_i))
```

直到找到需要结果。

# 44. Space Complexity 要特别小心

经常有人说：

> lazy stream 是 O(1) space。

不一定。

如果：

```scheme
(define s (integers-from 1))
```

而你始终保留 `s`：

```text
s
↓
1 → 2 → 3 → 4 → ...
```

由于 memoization，已经 force 的 tails 可能保持可达。

于是：

```text
realized prefix
```

可以占：

```text
O(k)
```

空间。

如果旧 prefix 不再有引用，并且 GC 可以回收：

```text
stream processing working space
```

才可能接近常数级。

所以正确 mental model 是：

```text
lazy
≠
zero memory
```

而是：

```text
don't compute / retain what you don't demand
```

具体空间取决于：

```text
retention graph
memoization
consumer behavior
GC
```

# 45. Eight Queens 的复杂度不会 magically 消失

Streams 让：

```text
search program
```

更 declarative。

但不会把 combinatorial search：

```text
exponential
```

变成 polynomial。

仍然大致面对巨大的 search tree。

区别是：

```text
eager representation

可能提前构造很多不需要的候选
```

而 lazy representation：

```text
only explores demanded part
```

如果：

```text
我要所有 solutions
```

最终可能仍要探索大量搜索空间。

如果：

```text
我要第一个 solution
```

lazy search 有机会在找到后停止，而不 materialize 剩余结果。

所以：

```text
abstraction improves organization

laziness avoids unnecessary work

neither changes fundamental combinatorial complexity
```


不对。

在 applicative-order Scheme 里，如果是普通函数：

```scheme

```

所以 `delay` 必须控制 evaluation。

---

## 误解 4

> Stream 就是 normal-order Scheme。

不对。

Scheme evaluator 仍然：

```text

```

只是 stream abstraction 显式 delay tail。

## 误解 5

不对。

```text

```

```text
avoid unnecessary computation
+
preserve modular program structure
```

## 误解 6

> Memoization 和 lazy evaluation 是一回事。

不是。

```text
lazy evaluation:
什么时候算？

memoization:
算过以后要不要保存？
```

可以 lazy 但不 memoize。

---

## 误解 7

> Stream 没有 state。

从 abstraction 层面，你可以以近乎 functional 的方式使用它。

但 memoized promise 的实现通常需要：

```text

```

也就是 state。

所以这里体现了 SICP 非常重要的分层：

```text
interface semantics
≠
implementation mechanism
```

# 47. 更危险的问题：Side Effects + Lazy Evaluation

例如：

```scheme
(define (f x)
  (display x)
  x)
```

然后：

```scheme
(stream-map f s)
```

问题出现：

```text
什么时候 print？
```

不是由代码从上往下出现的位置决定。

而由：

```text
consumer 什么时候 force stream
```

决定。

如果某部分从未 demand：

```text
f
```

可能永远不执行。

如果没有 memoization：

```text
f
```

还可能重复执行。

所以：

```text
side effects
+
lazy evaluation
```

非常危险。

Lecture 的问答也特别提醒：streams 的 substitution-style reasoning 依赖缺少 side effects，而副作用与这种 evaluation strategy 混合时必须非常小心。

正确 mental model：

> Lazy evaluation 让 **evaluation order 成为实现细节**；side effect 却让 **evaluation order 变成 observable behavior**。

两者天然紧张。

# 51. SICP 在这里真正教的不是 Stream API

如果只背：

```scheme
cons-stream
head
tail
delay
force
```

其实几个月后全部忘掉也没关系。

真正应该学会的是设计过程：

```text
1. 发现多个程序结构不同

2. 看出它们其实共享相同 computation stages

3. 给这些 stages 起名字

4. 找一个 conventional interface
   让它们可以组合

5. 写出更 declarative 的程序

6. 发现 abstraction 导致 performance problem

7. 不放弃 abstraction

8. 改变 evaluation strategy

9. 用 delay 把 computation reify 成 data

10. 用 memoization 恢复效率
```

这个过程才是 SICP。

尤其是第 6→8 步：

> **不是为了效率重新把 abstraction 拆掉，而是改变语言机制，让 abstraction 高效运行。**

这是极其重要的 programming-language thinking。

# 52. 本节的三个核心 Pattern

## Pattern A：Sequence Pipeline

```text
source
 ↓
map
 ↓
filter
 ↓
flatmap
 ↓
accumulate
```

看到：

```text
遍历
变换
筛选
组合
```

就应该想到它。

---

## Pattern B：Delayed Data

```text
data =
current value
+
procedure producing rest
```

也就是：

```scheme
(cons value
      (lambda ()
        ...rest...))
```

当你看到：

```text
potentially expensive
potentially infinite
maybe unused
```

就该想到 delayed computation。

---

## Pattern C：Pull Evaluation

```text
consumer requests
      ↓
downstream requests upstream
      ↓
source computes minimum required work
```

也就是：

```text
demand propagates backward

data propagates forward
```

画出来：

```text
demand:

Consumer
   ↑
 Filter
   ↑
  Map
   ↑
Source


data:

Source
   ↓
  Map
   ↓
 Filter
   ↓
Consumer
```

这张图非常值得记住。

# 54. 我建议你真正记住的东西

### 核心思想

**第一，Streams 是另一种 system decomposition。**

不是“特殊 list”，而是：

```text
object/state decomposition

vs

signal/stream decomposition
```

---

**第二，把时间变化重新表示成 sequence。**

```text
x changes:

x0 → x1 → x2 → ...

↓

stream:

[x0 x1 x2 ...]
```

这是这一章哲学上的核心。

---

**第三，Conventional Interface 带来组合能力。**

```text
map
filter
accumulate
flatmap
```

之所以强，不是它们各自复杂，而是：

```text
Stream → Stream
```

允许任意拼装。

---

**第四，程序结构不必等于执行顺序。**

```text
program says:

enumerate
→ filter
→ take

machine does:

enumerate one
→ filter
→ enumerate one
→ filter
→ stop
```

这是 Lecture 6A 最重要的 evaluation insight。

---

**第五，procedure 和 data 的界限可以被打破。**

```text
stream tail

不是 data

也不是单纯 program

而是：

delayed computation represented as data
```

# 55. 关键机制

建议记这五个：

```text
cons-stream

head / tail

delay

force

memoization
```

但要记它们背后的关系：

```text
cons-stream
       │
       └── delays tail
                │
                ▼
            promise
                │
tail ────────── force
                │
                ▼
          compute next cell
                │
                ▼
           memoize result
```

# 56. 三个最重要的不变量

### 不变量 1

```text
Stream cell

=
available head
+
delayed tail
```

---

### 不变量 2

```text
forcing a memoized promise

computes it at most once
```

---

### 不变量 3

```text
demand controls evaluation
```

不是代码的 textual order 控制所有 computation。

# 57. 用一句话总结 Lecture 6A

如果面试式地问：

> Lecture 6A 到底在讲什么？

我建议你回答：

> **SICP 先用 streams 建立 map/filter/accumulate 这样的统一 sequence interface，让程序可以按数据流方式组合；然后通过把 stream 的 tail 表示成 delayed computation，并用 force 和 memoization 按需求值，使程序能够保持 declarative、modular 的结构，同时只执行真正需要的计算。更深层的思想是把随时间发生的 computation 重新表示成 data，并把程序的逻辑结构和机器的实际执行顺序解耦。**

这基本就抓住了整讲。

### 题 3：Side Effect

考虑：

```scheme

  (display x)
  x)

(define x
  (stream-map
    show
    (integers-from 1)))
```

然后依次执行：

```scheme
(head x)

(head (tail x))

(head x)
```

假设 promise 有 memoization。

请预测：

```text
display 的顺序是什么？

哪些数字会被打印？

为什么第三个 expression

```

> 为什么 lazy evaluation 和 side effect 是危险组合？
