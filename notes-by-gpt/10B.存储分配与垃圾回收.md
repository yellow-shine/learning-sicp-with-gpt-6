# 1. 这节课到底想解决什么问题？

## 1.1 前面一直有一个被故意隐藏的问题

从 Lecture 2B 开始，我们大量写：

```scheme
(cons 1 2)

(car p)

(cdr p)
```

我们画：

```text
     +---+---+
p -->| • | • |
     +-|-+-|-+
       |   |
       1   2
```

SICP 前面允许我们假装：

> 世界上天然存在一种叫做 pair 的东西。

调用：

```scheme
(cons x y)
```

就会凭空出现一个新的 box。

这在研究 **data abstraction** 时完全合理。

但是到了 Lecture 9A / 9B / 10A，我们已经不再满足于这种解释了。

我们已经问过：

```text
Scheme
 ↓
Evaluator
 ↓
Register machine
 ↓
instructions
```

那么自然会出现下一个问题：

> register machine 里面的 `cons` 又是谁实现的？

如果我们的答案仍然是：

```text
cons is primitive
```

其实只是把问题往下踢了一层。

Sussman 在这一讲开头直接指出这个“谜”：此前一直在假设总有下一个 `cons` 可用，而 environment 等结构本身最终也需要由这些存储结构实现。

# 2. 真正的问题有两个

假设 Scheme 执行：

```scheme
(define x
  (cons 1
        (cons 2
              (cons 3 '()))))
```

抽象层面你看到：

```text
x
│
▼
+---+---+    +---+---+    +---+---+
| 1 | •----->| 2 | •----->| 3 | / |
+---+---+    +---+---+    +---+---+
```

可是硬件给你的不是这些漂亮的 box。

硬件基本上给你：

```text
Memory

address      value
-------------------
0            ...
1            ...
2            ...
3            ...
4            ...
5            ...
...
```

所以第一个问题是：

```text
Hierarchical Lisp structure
          ↓
How?
          ↓
Flat linear memory
```

这是 **representation problem**。

第二个问题更严重。

程序会不断：

```scheme
(cons ...)
(cons ...)
(cons ...)
(cons ...)
...
```

环境 frame 也要创建，argument list 也要创建，closure 也可能使某些 environment 长期存在。

但是：

```text
physical memory ≠ infinite
```

于是问题变成：

```text
不断创建 object
       ↓
有限 memory
       ↓
最终必然耗尽
```

除非我们发现：

> 很多以前创建的 object 已经永远无法被程序访问了。

然后回收它们。

这就是：

```text
storage allocation
+
garbage collection
```

SICP §5.3 正是用这两个问题——**representation 和 storage management**——来组织这一章。([SICP Source Academy](https://sicp.sourceacademy.org/chapters/5.3.html "5.3  Storage Allocation and Garbage Collection - SICP Comparison Edition"))

所以从你给出的分类看，这一讲主要涉及：

```text
representation    ★★★★★
abstraction       ★★★★★
state             ★★★★
evaluation        ★★★
language/runtime  ★★★★★
resource mgmt     ★★★★★
```

不是 Higher-order Procedure 那种“如何组合 computation”的 abstraction。

而是：

> **如何让一个高级语言抽象在低级机器上真实存在。**

# 4. 核心机制一：Pair 到底是什么？

## 4.1 直觉

这是本讲第一个关键思想：

> **pair 并不是硬件提供的东西。**

`cons` 是 abstraction。

pair 的物理 representation 可以完全不同。

例如理论上甚至可以把：

```scheme
(cons x y)
```

编码成某个整数，比如通过质因数：

```text
2^x × 3^y
```

然后通过分解质因数恢复 `car` 和 `cdr`。

Sussman 开头特意讲 Gödel-style 数字编码，就是为了强调：

> `cons/car/cdr` 描述的是一种抽象接口，而不是某一种物理布局。

只是整数编码效率荒谬，所以实际机器不用它。

这其实是 Lecture 2B 的 **data abstraction** 重新出现了。

以前：

```text
rational number
     ↓
numer / denom
     ↓
cons pair
```

现在：

```text
cons pair
    ↓
memory addresses
    ↓
raw memory
```

抽象层还可以继续往下拆。

---

# 5. Memory as Vectors

实际机器内存更接近：

```text
M[0]
M[1]
M[2]
M[3]
...
```

所以 SICP 用两个 vector 模拟 pair：

```text
the-cars
the-cdrs
```

假设 pair `p3` 放在 index 3：

```text
the-cars[3] = ...
the-cdrs[3] = ...
```

那么：

```scheme
(car p3)
```

在底层就是：

```text
vector-ref(the-cars, 3)
```

而：

```scheme
(cdr p3)
```

就是：

```text
vector-ref(the-cdrs, 3)
```

假设：

```scheme
(cons 1
      (cons 2 '()))
```

被分配到 cell 3 和 cell 7。

可以表示成：

```text
index        CARS         CDRS
--------------------------------
3            N1           P7
7            N2           E
```

这里：

```text
N1 = number 1
N2 = number 2

P7 = pointer to pair #7
E  = empty list
```

于是：

```text
P3
 │
 ▼
CARS[3] = N1

CDRS[3]
 │
 ▼
P7
 │
 ▼
CARS[7] = N2
CDRS[7] = E
```

MIT 讲座就是把 Lisp 的 box-and-pointer 图转换成这种两个线性 vector 的表示，并用 tag 区分 number、pair、empty list 等对象。

注意这里发生了一次非常重要的 abstraction lowering：

```text
Scheme level

(car x)

        ↓ implementation

vector-ref CARS (pointer-index x)
```

这和编译器把：

```c
obj.field
```

降低为：

```text
load [base + offset]
```

本质上是同一类思想。

# 6. 为什么 pointer 如此重要？

以前我们画：

```text
+---+---+
| • | • |
+-|-+-|-+
```

那个箭头其实不是魔法。

箭头最终就是：

```text
address / index
```

例如：

```text
P7
```

> 这里存着整个 pair。

> 去 pair table 的 index 7 找。

于是：

```text
pointer

不是 object 本身

而是
representation-level identity/location
```

现代语言里的：

```java
Object x
```

Python：

```python
x = obj
```

Go：

```go
p := &obj
```

```text
reference
      ↓
object somewhere in memory
```

# 7. Evaluation Model：`cons` 真正发生了什么？

考虑：

```scheme
(define x
  (cons 'a
        (cons 'b '())))
```

在 Scheme evaluator 层看：

```text
evaluate RHS
    ↓
evaluate operator cons
    ↓
evaluate operands
    ↓
inner (cons 'b '())
    ↓
apply cons
    ↓
return pair
    ↓
outer cons receives pair
    ↓
apply cons
    ↓
return new pair
    ↓
bind x
```

以前到这里就停止了。

但 Lecture 10B 要继续向下：

假设 inner pair 分配到 cell 7：

```text
allocate cell 7

CARS[7] = symbol b
CDRS[7] = empty-list

result = P7
```

再创建 outer pair：

```text
allocate cell 3

CARS[3] = symbol a
CDRS[3] = P7

result = P3
```

最后 environment：

```text
Global Environment

x ───────► P3
            │
            ▼
           cell 3
          /      \
        'a        P7
                   │
                   ▼
                  cell 7
                 /      \
               'b        ()
```

这次你已经跨过了三层：

```text
Source expression

(cons ...)

     ↓

Evaluator semantics

apply cons

     ↓

Runtime representation

allocate pair cell

     ↓

Physical-ish representation

write into vectors
```

这就是这一讲真正想让你看到的东西。

# 8. 核心机制二：Storage Allocation

现在出现一个问题：

> cell 3、cell 7 是怎么选出来的？

不能随便挑。

因为有些 memory cell 已经被用了。

---

## 8.1 Free List

一个经典方案：

```text
free
 │
 ▼
cell 6 → cell 8 → cell 3 → cell 0 → cell 15 → ...
```

这些 cell 当前没人用。

把所有 free cell 自己串成一个链表。

Sussman 讲的就是这种方案：取 free list 第一个 cell，把 free 指针推进到下一个 free cell，然后用取出的 cell 构造新的 pair。

所以：

```scheme
(cons B C)
```

底层大概等价：

```text
A ← free

free ← CDRS[A]

CARS[A] ← B
CDRS[A] ← C

A ← pair-pointer(A)
```

假设原来：

```text
free → 6 → 8 → 3 → 0
```

做一次 `cons`：

```text
allocate 6
```

之后：

```text
free → 8 → 3 → 0
```

而 cell 6 变成：

```text
CARS[6] = B
CDRS[6] = C
```

所以：

```text
cons

并不是：

magically create object

而是：

find unused storage
      ↓
write representation
      ↓
return reference
```

根本不用知道：



```text
1000000
↓
999999
↓
999998
...
↓
1
↓
0
```

最后：


Game over。

例如：

```scheme
(define x

```

```text
Global
  │
  x
  │
  ▼
```


# 11. 核心机制三：Reachability

这是整节课我最希望你牢牢记住的概念。

垃圾的定义并不是：

> “这个 object 看起来没用了。”

而是：

> **从程序当前能够访问的 roots 出发，再也到不了这个对象。**

现代术语就是：

```text
roots
  ↓
reachable objects
```

Lecture 中 Sussman 的描述非常漂亮：机器当前的“consciousness”存在于寄存器之中；如果某块 heap memory 无法从这些当前可访问的指针沿合法 selectors 到达，那么它就不可能影响未来计算，可以回收。

例如：

```text
roots
 │
 ▼
 A ─────► B
 │
 ▼
 C ─────► D


 E ─────► F
 ▲        │
 └────────┘
```

从 root 可达：

```text
A
B
C
D
```

不可达：

```text
E
F
```

即使：

```text
E ↔ F
```

彼此还互相引用。

它们仍然是 garbage。

这是非常重要的。

---

# 12. Reachable ≠ 有用

这里非常容易产生一个误解。

假设：

```text
root → A → B
```

而程序以后实际上再也不会读取 B。

B 还是：

```text
reachable
```

所以 tracing GC **不会回收 B**。

因此：

```text
GC 判断的是

reachable / unreachable

不是

will-be-used / will-never-be-used
```

这是故意的。

因为 reachability 是一个局部、机械、可验证的性质：

```text
root
 ↓
follow pointers
 ↓
graph traversal
```

而：

> “这个对象未来究竟会不会再被程序使用？”

是一个关于未来执行行为的问题。

这其实已经悄悄连接到了这堂课最后的 **halting problem**。

这是 Lecture 10B 最漂亮的隐藏联系之一。

# 13. Closure 为什么让 GC 更有意思？

回忆：

```scheme
(define (make-adder x)
  (lambda (y)
    (+ x y)))

(define add5
  (make-adder 5))
```

调用：

```scheme
(make-adder 5)
```

创建 environment：

```text
E1
x = 5
parent = Global
```

然后返回 closure：

```text
add5
  │
  ▼
procedure
  │
  ├── code: (lambda (y) (+ x y))
  │
  └── env ───► E1
```

虽然 `make-adder` 已经 return：

```text
E1 不能被释放
```

因为：

```text
Global
  ↓
add5
  ↓
closure
  ↓
E1
```

它仍然 reachable。

这很好地修正一个常见 mental model：

```text
procedure returned
≠
its frame immediately dies
```

正确的是：

```text
frame lifetime
=
as long as something reachable references it
```

这就是：

```text
lexical scope
+
closure
+
heap allocation
+
GC
```

第一次真正连接起来。

# 14. 核心机制四：Mark-and-Sweep

现在我们知道 garbage 定义了。

问题变成：

> 怎么找到所有 unreachable objects？

答案：

```text
Graph Traversal
```

---

## 14.1 Mark phase

从 roots 开始：

```text
root
 ↓
A
├── B
│   └── D
└── C
    └── D
```

一开始：

```text
A unmarked
B unmarked
C unmarked
D unmarked
E unmarked
```

从 root：

```text
mark A
 ↓
visit B
 ↓
mark B
 ↓
visit D
 ↓
mark D
```

回来：

```text
visit C
 ↓
mark C
 ↓
visit D
```

但：

```text
D already marked
```

停止。

所以结果：

```text
A ✓
B ✓
C ✓
D ✓

E ✗
```

Sussman 正是用这种从 root 递归追踪 car/cdr 引用的方法说明 mark phase。

---

# 15. Mark algorithm 的本质

概念上可以写成：

```scheme
(define (mark x)
  (cond ((not (pair-pointer? x))
         'done)

        ((marked? x)
         'done)

        (else
         (set-mark! x #t)
         (mark (car x))
         (mark (cdr x)))))
```

注意：

```scheme
(marked? x)
```

非常重要。

否则遇到：

```text
A → B
↑   ↓
└───┘
```

就会：

```text
mark A
mark B
mark A
mark B
...
```

无限递归。

所以 mark bit 同时解决：

```text
shared structure
cycles
duplicate traversal
```

---

# 16. Sweep phase

Mark 完：

```text
heap

0  marked
1  marked
2  unmarked
3  marked
4  unmarked
5  unmarked
```

Sweep 扫完整个 heap：

```text
marked?
   │
   ├── yes → keep + clear mark
   │
   └── no  → add to free list
```

最后：

```text
free → 2 → 4 → 5
```

于是垃圾 cell 又能继续：

```scheme
(cons ...)
```

Lecture 对这个过程的描述就是：

```text
mark reachable
      ↓
scan entire memory
      ↓
unmarked → free list
marked   → clear mark
```

---

# 17. Mark-Sweep 的 Process Shape

Mark 本身是：

```text
recursive graph traversal
```

假设结构：

```text
A
↓
B
↓
C
↓
D
```

过程：

```text
mark(A)
 ↓
mark(B)
 ↓
mark(C)
 ↓
mark(D)
```

需要保存返回信息：

```text
mark(A)
 waiting for cdr

mark(B)
 waiting for cdr

mark(C)
 waiting for cdr
...
```

因此朴素 recursive marking：

```text
space = O(max graph depth)
```

Lecture 特别指出，这种 recursive marking 需要辅助 stack，因此极深的数据结构可能产生问题；随后还提到了通过 pointer reversal 消除辅助 stack 的方法。

这个例子又一次说明：

```text
recursive procedure
        ↓
process shape
        ↓
resource consumption
```

Lecture 1B 的东西到了 Lecture 10B 还在用。

---

# 18. Mark-Sweep 的复杂度

令：

```text
H = heap 中所有 cell 数
L = reachable/live cell 数
E = live graph 中 pointer edges 数
```

mark 大约：

```text
O(L + E)
```

sweep：

```text
O(H)
```

所以总体：

```text
O(H + E)
```

对于 pair graph，edge 数量和 object 数量同阶，可以简化理解为：

```text
O(H)
```

辅助空间，朴素递归：

```text
O(graph depth)
```

最坏：

```text
O(L)
```

还有一个实际问题：

```text
free
live
free
live
free
free
live
```

对象不会被移动，因此可能出现 **fragmentation**。

对于固定大小 cons cell 这不是最严重的问题，但对于一般 heap object 会很重要。

# 20. From-space / To-space

把可用内存逻辑上切成两块：

```text
FROM SPACE

live + garbage
────────────────────────────

TO SPACE

empty
────────────────────────────
```

collection 开始：

```text
root
 ↓
object in from-space
```

把 reachable object：

```text
copy
 ↓
to-space
```

最终：

```text
TO SPACE

only live objects
█████████████.............
```

旧 from-space 整块扔掉。

Lecture 用的就是这种 copying collector，并描述为把 useful structure 从 from-space 复制进 to-space。

# 21. Copying GC 最难理解的地方：pointer 怎么办？

假设：

```text
root
 │
 ▼
A@100
 │
 ▼
B@532
```

复制 A：

```text
FROM                    TO

A@100                    A'@0
 │
 ▼
B@532
```

问题：

```text
A'.cdr
```

不能还指向：

```text
B@532
```

因为 from-space 最后整个会被丢弃。

所以：

```text
B@532
 ↓ copy
B'@1
```

然后更新：

```text
A'.cdr → B'@1
```

# 22. 为什么需要 forwarding pointer？

再来一个更有意思的：

```text
       A
      / \
     B   C
      \ /
       D
```

如果你直接复制：

```text
copy B's D
copy C's D
```

D 可能被复制两遍：

```text
D1
D2
```

这样就破坏了：

```text
sharing
```

原来：

```scheme
(eq? (cdr b)
     (cdr c))
```

可能为真。

复制后却变成两个不同对象。

不能这样。

所以第一次复制 D：

```text
FROM

D
│
└── FORWARD → D'
```

Lecture 把这个 forwarding marker 很形象地叫做：

> **broken heart**

即：

```text
这个对象已经搬家了
新地址在这里
```

以后再次遇到旧 D：

```text
see forwarding pointer
        ↓
don't copy again
        ↓
use D'
```

这不是优化而已。

它维护了一个重要语义不变量：

> **对象共享关系必须保持。**

# 23. 一步一步跑 Copying GC

假设：

```text
root → A

A → B
A → C
B → C
```

初始：

```text
FROM

2:A
4:C
9:B

TO

empty
```

两个指针：

```text
scan
free
```

首先 root 指向 A@2。

复制：

```text
TO

0:A'
```

留下：

```text
FROM A@2 → forwarding TO@0
```

现在：

```text
scan = 0
free = 1
```

扫描 A'。

A' 指向 B@9：

```text
B hasn't moved
```

复制：

```text
TO

0:A'
1:B'
```

FROM：

```text
B@9 → forwarding 1
```

然后 A' 指向 C@4：

```text
copy C
```

得到：

```text
TO

0:A'
1:B'
2:C'
```

现在：

```text
free = 3
```

继续扫描 B'。

B' 指向旧：

```text
C@4
```

检查：

```text
C@4 already has forwarding → 2
```

所以：

```text
B'.pointer = 2
```

不再复制。

最终：

```text
scan == free
```

意味着：

```text
所有复制出来的 live objects
都已经扫描过其 pointers
```

GC 完成。

Lecture 也是以 scan pointer 和 free pointer 相遇作为复制完成的条件。

# 24. Copying GC 的三个关键 invariant

这是非常值得记住的。

### Invariant 1

```text
每个 from-space live object
最多被 copy 一次
```

靠：

```text
forwarding pointer
```

保证。

### Invariant 2

当：

```text
object < scan
```

它里面所有 heap pointers：

```text
都已经被修正为 to-space pointers
```

### Invariant 3

当：

```text
scan == free
```

不存在：

```text
copied but not scanned
```

的对象。

因此 collection 完成。

这比背 GC 步骤重要得多。

# 25. Copying GC 的复杂度

如果：

```text
L = live objects
```

GC 工作量基本与：

```text
L
```

相关：

```text
O(L + E_live)
≈ O(L)
```

而不是：

```text
O(heap size)
```

经典 two-space collector 的代价是：

```text
需要额外 semispace
```

大致可以理解成：

```text
只有一半空间用于当前对象
另一半留作 copying destination
```

好处：

```text
allocation 极快
```

因为不需要 free list：

```text
free pointer
     ↓
+--------------------------+
| used used used | free... |
+--------------------------+
                 ↑
               allocate here
```

allocate：

```text
result = free
free += object-size
```

就是：

```text
bump pointer allocation
```

通常 O(1)。

而且 collection 后对象紧密排列：

```text
████████████..............
```

自然完成 compaction。

# 26. Mark-Sweep vs Copying GC

这一组非常值得你辨析：

||Mark-Sweep|Copying|
|---|---|---|
|找 live object|root tracing|root tracing|
|garbage 本身|sweep 时发现|根本不复制|
|是否移动 object|通常不移动|移动|
|allocation|free list 等|bump pointer 很自然|
|fragmentation|可能有|自然 compact|
|collection 成本|与 heap 大小有关|更接近 live size|
|额外空间|较少|semispace 较大|
|pointer update|一般不需要 relocation|必须|
|sharing|mark bit 保证 traversal|forwarding 保证 identity|

最容易理解错的是：

> Copying GC 不是“把垃圾复制走”。

恰恰相反。

它复制：

```text
live objects
```

然后把剩下的整个旧空间当垃圾。

Mental model：

```text
Mark-Sweep

find garbage and reclaim it
```

而：

```text
Copying GC

find survivors and rescue them
```

非常不同。

# 27. Garbage Collection 的真正抽象是什么？

表面上这是：

```text
memory management algorithm
```

但 SICP 真正想训练的是：

```text
finite physical resource

        ↓ abstraction

apparently unlimited resource
```

Sussman 在讲座里直接称这是制造一种 **“illusion of infinity”**：实际 memory 有限，但只要及时回收未来不再可访问的对象，就可以让程序仿佛不断创建新结构。

这和操作系统里的很多思想完全一致：

```text
finite RAM
   ↓
virtual memory
   ↓
large address space illusion
```

以及：

```text
finite CPU
   ↓
scheduler
   ↓
each process appears to run
```

SICP 在教你的一个非常深的系统思想就是：

> 一个 abstraction 不需要在底层真的存在。

只要底层机制能维持它的 observable behavior。

# 28. 一个完整例子：对象是怎样变成垃圾的？

考虑：

```scheme
(define x
  (cons 'a
        (cons 'b '())))

(define y x)

(set! x '())
```

第一次：

```text
Global

x ──► A ──► B
```

然后：

```scheme
(define y x)
```

得到：

```text
Global

x ──┐
    ▼
    A → B
    ▲
y ──┘
```

执行：

```scheme
(set! x '())
```

得到：

```text
x → ()

y → A → B
```

问题：

> A、B 是 garbage 吗？

不是。

因为：

```text
root y
  ↓
A
 ↓
B
```

仍然 reachable。

然后：

```scheme
(set! y '())
```

才变成：

```text
x → ()
y → ()

      A → B
```

现在 A、B：

```text
unreachable
```

GC 才能回收。

所以关键不是：

```text
old variable changed
```

而是：

```text
all paths from roots disappeared
```

# 33. Reachability vs Reference Counting

虽然 Lecture 10B 重点不是 reference counting，但这里值得马上建立区别。

如果：

```text

↑   ↓
└───┘
```

而 root 不再指向 A/B。

它们：

```text
reference count > 0
```

因为互相引用。

reference counting 很难直接发现它们。

Tracing GC：

```text
roots
 ↓
cannot reach A/B
```

直接判定：

```text
garbage
```

所以：

```text

问：
```

```text

```

这是两个完全不同的 mental model。

# 37. 这一讲实际上还有最后一章：Halting Problem

严格说，这部分不是 §5.3 Garbage Collection 的核心内容。

但 Lecture 10B 的视频确实在 GC 后继续讲了它，因为这是整个课程的终章。Sussman 假设存在一个 procedure `safe`，能够判断任意 procedure `p` 在参数 `a` 上是否会正常结束，然后通过让 procedure 对自己运行构造矛盾。

把它简化为 Scheme：

```scheme
(define (diag p)
  (if (safe? p p)
      (loop-forever)
      3))
```

假设：

```scheme
(safe? p x)
```

能够永远正确回答：

```text
#t → p(x) terminates
#f → p(x) does not terminate
```

现在问：

```scheme
(diag diag)
```

---

# 38. 展开这个 evaluation

执行：

```scheme
(diag diag)
```

代入：

```scheme
(if (safe? diag diag)
    (loop-forever)
    3)
```

只有两种情况。

情况 A：

```text
(safe? diag diag) = #t
```

意思：

```text
diag(diag) terminates
```

于是程序进入：

```scheme
(loop-forever)
```

所以：

```text
diag(diag) does NOT terminate
```

矛盾。

情况 B：

```text
(safe? diag diag) = #f
```

意思：

```text
diag(diag) does NOT terminate
```

但是程序走：

```scheme
3
```

于是：

```text
diag(diag) terminates
```

又矛盾。

因此：

```text
safe?
```

不可能存在。

Lecture 就是用这个 contradiction 收尾，并把它称作 halting theorem。

# 39. 为什么 GC 和 Halting Problem 放在同一讲很有味道？

你可以看到一个非常漂亮的联系。

理想 GC 也许想知道：

> “这个 object 从现在开始到底还会不会真正被读取？”

如果能精确知道，就可以更早回收。

例如：

```text
root → A
```

虽然 A reachable，但程序未来可能永远不会再读 A。

可是判断：

```text
will this program ever access A again?
```

本质上是对未来程序行为进行分析。

对于任意程序，这类问题不存在一个万能精确算法。

所以 GC 采用一个非常聪明的保守 abstraction：

```text
unreachable
    ⇒
definitely safe to reclaim
```

但：

```text
reachable
    ⇏
definitely will be used
```

也就是说 GC 不要求解决最难的问题。

它只证明一个更弱、但足够安全的 theorem：

```text
Not reachable from roots
        ↓
cannot affect future execution
        ↓
safe to reclaim
```

这其实是系统设计里非常普遍的思想：

> **不要解决比需求更难的问题。找到一个足够强的不变量。**

# 41. 常见误区

### 误解 1：GC 找的是“以后不会再使用”的对象

错误。

GC 通常找的是：

```text
unreachable
```

正确 mental model：

```text
unreachable ⇒ definitely dead
```

而不是：

```text
reachable ⇒ definitely useful
```

---

### 误解 2：没有变量指向 object，它就是 garbage

不够准确。

可能：

```text
x → A → B
```

没有变量直接指向 B。

但 B 仍然：

```text
reachable through A
```

因此不是 garbage。

---

### 误解 3：循环引用一定无法 GC

对 tracing GC 错。

例如：

```text
A ↔ B
```

只要：

```text
roots cannot reach A/B
```

整个 cycle 都可以回收。

---

### 误解 4：`cons` 就是申请一块新内存

从 abstraction 上不应该这么理解。

正确是：

```text
cons = abstract constructor
```

“申请 heap cell”只是它的一种实现。

---

### 误解 5：Closure 的 environment 在 procedure return 后立即释放

错。

```text
closure → environment
```

只要 closure reachable：

```text
environment reachable
```

必须保留。

---

### 误解 6：Moving GC 会破坏 object identity

只要 runtime 正确更新：

```text
roots
+
internal pointers
```

就不会。

forwarding pointer 的一个核心目的正是保持这种 graph structure / sharing。

---

### 误解 7：Copying GC 是复制垃圾

正好相反：

```text
copy live objects
discard everything else
```

---

### 误解 8：Mark phase 本身只需要 O(1) memory

朴素 recursive marking 不一定。

调用链：

```text
mark A
 → mark B
   → mark C
     → ...
```

需要辅助 stack。

Lecture 特别讨论了这一点。

# 42. Complexity 总结

把本讲几个 process 放在一起：

```text
Free-list allocation

time:
O(1)

space overhead:
one free-list link per free cell
```

Copying collector allocation：

```text
bump-pointer allocation

time:
O(1)
```

Mark：

```text
O(live objects + live edges)
```

Sweep：

```text
O(heap size)
```

所以 Mark-Sweep：

```text
O(heap size)
```

量级。

Copying collection：

```text
O(live objects + live edges)
```

但：

```text
requires extra semispace
```

朴素 recursive marking stack：

```text
O(max graph depth)
```

这就是典型的：

```text
time / space / fragmentation /
allocation-speed
```

trade-off。

```text
roots → objects → objects
```

3. **垃圾的核心定义是 unreachable from roots。**
    
4. **GC 的安全性来自一个不变量：不可达对象无法影响未来计算。**
    
5. **Mark-Sweep 是“标记 survivors，然后扫描 heap 找 garbage”。**
    
6. **Copying GC 是“只搬 survivors”，forwarding pointer 保证一个对象只搬一次并保留 sharing。**
    
7. **Closure 把 environment lifetime 从调用栈 lifetime 中解耦出来，因此 GC 和 environment model 是连在一起的。**
    
8. **高级语言 abstraction 最终必须被 representation、allocation、control 和 storage machinery 实现。**
    

三个最重要的不变量则是：

```text
Invariant 1

Every object reachable from a root
must survive GC.
```

```text
Invariant 2

No reclaimed object may still be reachable.
```

以及 copying collector：

```text
Invariant 3

After relocation,
every live reference must point
to the relocated object,
and sharing must be preserved.
```

如果这三个你真的理解了，这堂课就已经掌握大半。
