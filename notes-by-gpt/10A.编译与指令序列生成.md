# Lecture 10A：Compilation —— 从“解释程序”到“把程序变成机器”

先把这一讲放准位置：MIT 1986 版 6.001 的 **Lecture 10A 主题就是 Compilation**。它紧接 9A Register Machines 和 9B Explicit-Control Evaluator。也就是说，SICP 先让你亲手把 Scheme evaluator 降到 register machine，然后马上追问：

> **既然 evaluator 已经知道如何把 Scheme 的语义落实成寄存器操作，为什么每次运行程序时还要重新解释一遍？能不能提前把这些操作生成出来？**

这就是 10A。MIT 的课程顺序也明确是 `9A Register Machines → 9B Explicit-Control Evaluator → 10A Compilation`。([MIT OpenCourseWare](https://ocw.mit.edu/courses/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video_galleries/video-lectures/?utm_source=chatgpt.com "Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

这一讲表面是 compiler，实际上是 SICP 前面十讲很多思想的一次汇合：

```text
程序也是数据
    +
Evaluator 定义语言语义
    +
Register Machine 定义底层执行模型
    +
静态分析
    +
程序组合
    ↓
Compiler
```

# 1. 这节课到底想解决什么问题？

## 1.1 9B 已经解决了什么？

9B 的 Explicit-Control Evaluator 已经把 Scheme evaluator 变成了一台明确的 register machine。

你可以想象我们输入：

```scheme
(f x)
```

解释器大概会经历：

```text
exp = (f x)
env = current environment

↓ 判断表达式类型

application?

↓ yes

取 operator: f
取 operands: (x)

↓ evaluate f

lookup f in env
proc = ...

↓ evaluate x

lookup x in env
val = ...

↓ build argument list

argl = (...)

↓ apply proc

...
```

问题是：

**每一次执行 `(f x)`，解释器都会重新做这些事情。**

它不仅要完成真正的计算：

```text
lookup f
lookup x
construct argl
call f
```

还要不断做：

```text
这是 self-evaluating expression 吗？
这是 variable 吗？
这是 quoted expression 吗？
这是 assignment 吗？
这是 if 吗？
这是 lambda 吗？
这是 application 吗？
```

换句话说，Interpreter 同时做两种工作：

```text
               Interpreter
                    │
          ┌─────────┴─────────┐
          ↓                   ↓
    分析程序结构          执行程序
    analyze             execute
```

而且：

```text
运行一次 → 分析一次
运行第二次 → 又分析一次
运行第 1,000,000 次 → 又分析一次
```

Lecture 10A 明确把这当作 compilation 可以消除的主要 overhead：interpreter 一边分析表达式是什么、一边执行；compiler 则把分析提前做一次。([MIT OpenCourseWare](https://ocw.mit.edu/courses/6-001-structure-and-interpretation-of-computer-programs-spring-2005/resources/10a-compilation/?utm_source=chatgpt.com "10A: Compilation | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

# 2. Compiler 的核心思想

这里有一个非常漂亮的 SICP 式转变。

9B：

```text
source program
      ↓
 evaluator
      ↓
立即执行 register operations
```

10A：

```text
source program
      ↓
 compiler
      ↓
生成 register operations
      ↓
以后直接执行
```

Sussman 在这一讲里给出了一个非常好的 mental model：

> evaluator 会遍历程序并执行 register operations；compiler 也遍历程序，但是不执行这些 operations，而是把它们记录下来，形成 object code。([MIT OpenCourseWare](https://ocw.mit.edu/courses/6-001-structure-and-interpretation-of-computer-programs-spring-2005/resources/10a-compilation/?utm_source=chatgpt.com "10A: Compilation | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

所以你甚至可以先把 compiler 想成：

```scheme
Evaluator:
    看见 expression
    ↓
    做 machine operation

Compiler:
    看见 expression
    ↓
    输出 machine operation
```

例如：

```scheme
42
```

Evaluator 做：

```text
val ← 42
```

Compiler 则**生成**：

```text
(assign val (const 42))
```

注意两个时间点：

```text
compile time:

42
 ↓
compiler
 ↓
(assign val (const 42))


runtime:

(assign val (const 42))
 ↓
machine executes
 ↓
val = 42
```

这是这一讲最重要的分界。

# 3. Interpreter 与 Compiler 的真正区别

Lecture 10A 一开始用了一个非常 SICP 的视角。

Interpreter 是：

```text
low-level machine
       +
interpreter
       ↓
看起来像一台 high-level-language machine
```

也就是：

> **raise the machine**

Compiler 则反过来：

```text
high-level program
       ↓
compiler
       ↓
low-level machine program
```

也就是：

> **lower the program**

MIT 讲义中的原话思想就是：

```text
Interpretation:
machine ↑ language

Compilation:
program ↓ machine
```

Lecture 10A 明确这样对比两种策略。([MIT OpenCourseWare](https://ocw.mit.edu/courses/6-001-structure-and-interpretation-of-computer-programs-spring-2005/9dfa296596372438318a4315c5a53a0e_TqO6V3qR9Ws.pdf?utm_source=chatgpt.com "MITOCW | Lecture 10A"))

因此不要简单记：

> interpreter 边运行边翻译，compiler 提前翻译。

SICP 要你看到更深的一层：

```text
             High-level Language
                     │
             Scheme semantics
                     │
       ┌─────────────┴──────────────┐
       │                            │
 Interpreter                   Compiler
       │                            │
提升 machine                  降低 program
       │                            │
       └─────────────┬──────────────┘
                     ↓
               Register Machine
```

两者其实都在建立：

> **一个计算模型到另一个计算模型的 correspondence。**

这已经是 language implementation 的核心思想。

> 到底需不需要 `save/restore`？

# 5. 第一核心机制：Compiler ≈ staged evaluator

这是理解 10A 最关键的一步。

## 5.1 先看 evaluator

假设：

```scheme
(+ x 1)
```

Evaluator 不知道 `exp` 是什么，直到 runtime 才拿到它。

因此：

```text
exp = (+ x 1)

↓
self-evaluating?
no

↓
variable?
no

↓
quoted?
no

↓
assignment?
no

...

↓
application?
yes
```

然后：

```text
operator = +
operands = (x 1)
```

这些工作每次执行都要发生。

---

## 5.2 Compiler 已经知道 expression

Compiler 收到：

```scheme
(+ x 1)
```

这时 `(+ x 1)` 本身就是 compiler 正在处理的数据。

所以 compile time 已经知道：

```text
operator = +
operand1 = x
operand2 = 1
```

runtime 根本不需要再问：

```text
(application? exp)
(operator exp)
(operands exp)
```

这些已经在 compile time 完成了。

于是：

```text
Interpreter runtime:

expression
    ↓
classify expression
    ↓
decompose expression
    ↓
execute


Compiler:

compile time:
expression
    ↓
classify
    ↓
decompose
    ↓
generate code

runtime:
execute generated code
```

这就是 **staging**：

```text
能提前做的 computation
        ↓
挪到 compile time
```

现代 compiler/JIT/partial evaluation 都有这个思想。

# 6. 为什么 `exp` 和 `unev` 可以消失？

这是 Lecture 10A 一个非常值得理解的点。

9B evaluator 有：

```text
exp
unev
env
proc
argl
val
continue
```

其中：

```text
exp
```

保存：

> 当前正在 evaluate 的 expression。

`unev` 保存：

> 还没有 evaluate 的 operands / expressions。

但 compiler 看见：

```scheme
(f x)
```

时，`f` 和 `x` 已经直接存在于 compiler 的数据结构中了。

例如 evaluator 可能运行：

```text
assign exp ← operator(exp)
```

因为 runtime evaluator 必须动态保存：

```text
现在应该 evaluate f
```

但是 compiler 可以直接产生：

```text
lookup-variable-value 'f env
```

因为 `'f` 是 compile-time constant。

类似：

```text
x
```

也已经是 compiler 知道的常量。

所以 runtime 不需要：

```text
exp = f
unev = (x)
```

Lecture 中专门指出 `exp` 和 `unev` 是 evaluator 自己为了模拟语言而需要的 bookkeeping；对于 compiled program 来说，这些代码结构已经变成 compile-time constants，因此 generated code 不需要这两个寄存器。([MIT OpenCourseWare](https://ocw.mit.edu/courses/6-001-structure-and-interpretation-of-computer-programs-spring-2005/resources/10a-compilation/?utm_source=chatgpt.com "10A: Compilation | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

这是非常重要的概念：

> **Interpreter 的 internal state 不一定是 object program 真正需要的 state。**

# 7. 一个最小的 compilation 例子

考虑：

```scheme
x
```

解释执行：

```text
exp = x
env = E

↓ variable?

yes

↓ lookup-variable-value

lookup x in E

↓
val = value-of-x
```

Compiler 不需要生成：

```text
variable?
```

也不需要：

```text
exp
```

直接生成：

```scheme
(assign val
        (op lookup-variable-value)
        (const x)
        (reg env))
```

所以：

```text
compile time

x
↓
compiler knows:
  this is a variable
↓
generate:

lookup x using env
put result in val
```

runtime：

```text
env = E

(assign val
        (op lookup-variable-value)
        (const x)
        (reg env))

↓

val = E[x]
```

# 8. `(compile exp target linkage)` 是什么意思？

SICP compiler 的一个非常漂亮的 abstraction 是：

```scheme
(compile exp target linkage)
```

它不只是：

```scheme
compile(exp)
```

而是明确说：

> “请生成一段计算 `exp` 的代码，把结果放到 `target`，完成以后按照 `linkage` 继续。”

这两个参数很重要。

---

## 8.1 target

target 表示：

> expression 计算结果放到哪个 register？

例如：

```scheme
(compile 'x 'val 'next)
```

意思：

```text
evaluate x
↓
result → val
```

而：

```scheme
(compile 'f 'proc 'next)
```

意思：

```text
evaluate f
↓
result → proc
```

为什么需要它？

因为：

```scheme
(f x)
```

最终需要：

```text
proc = value-of-f
argl = (value-of-x)
```

所以 operator 和 operand 的结果不能统统随便放 `val`。

---

# 9. linkage 是什么？

`linkage` 回答：

> **这段代码执行完以后去哪里？**

典型有：

```text
next
return
<label>
```

### `next`

```text
执行完
↓
继续下一条 instruction
```

例如：

```scheme
(compile '5 'val 'next)
```

可能生成：

```scheme
(assign val (const 5))
```

---

### `return`

意味着：

```text
执行完
↓
goto continue
```

例如：

```scheme
(assign val (const 5))
(goto (reg continue))
```

---

### label

例如：

```text
after-call
```

生成：

```scheme
(goto (label after-call))
```

所以：

```text
target  = 数据结果去哪里
linkage = 控制结果去哪里
```

这是一个特别值得记住的二分：

```text
              compilation
             /           \
        data flow       control flow
           │                │
         target           linkage
```

SICP 正文也是这样定义 compiler interface：`target` 指定结果 register，`linkage` 指定完成计算之后的控制去向。([SICP Source Academy](https://sicp.sourceacademy.org/chapters/5.5.1.html?utm_source=chatgpt.com "5.5.1   Structure of the Compiler - SICP Comparison Edition"))

# 10. Conditional 为什么特别？

假设：

```scheme
(if (> x 0)
    (+ x 1)
    (- x 1))
```

Evaluator runtime 时知道 `x`，所以可以：

```text
evaluate predicate
↓
true?
├─ yes → evaluate consequent
└─ no  → evaluate alternative
```

但是 compiler compile time 并不知道：

```text
x > 0 ?
```

因此 compiler 不能只 compile 一个 branch。

它必须生成：

```text
compile predicate

↓ runtime test

branch false → false-branch

true-branch:
    compiled (+ x 1)
    goto after-if

false-branch:
    compiled (- x 1)

after-if:
```

大致：

```text
        predicate code
              │
              ↓
          test val
          /      \
       true      false
        │          │
        ↓          ↓
      code A      code B
        │          │
        └────┬─────┘
             ↓
          linkage
```

Lecture 10A 特别强调：compiler 不知道运行时 conditional 会走哪边，所以必须 compile 两个 branch，并生成运行时 branch instruction。([MIT OpenCourseWare](https://ocw.mit.edu/courses/6-001-structure-and-interpretation-of-computer-programs-spring-2005/resources/10a-compilation/?utm_source=chatgpt.com "10A: Compilation | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

这体现了非常重要的边界：

```text
compile-time-known
vs
runtime-known
```

Compiler 的本质工作之一，就是不断问：

> **哪些事情现在已经知道？哪些事情必须留到运行时？**

# 11. 最关键的例子：`(f x)`

现在进入 Lecture 10A 的核心。

假设：

```scheme
(f x)
```

## Interpreter 的思路

Evaluator 必须非常谨慎。

大致：

```text
save env

evaluate f

restore env

save proc
save argl
save env

evaluate x

restore env
restore argl
restore proc

apply proc
```

为什么这么保守？

因为 evaluator 在递归调用：

```text
eval-dispatch
```

之前，只知道：

> “我要 evaluate 一个 expression。”

但它不知道这个 expression 是：

```scheme
x
```

还是：

```scheme
(really-complicated-function ...)
```

甚至可能：

```scheme
(set! ...)
```

所以 evaluator 必须假设：

```text
recursive evaluation
可能破坏各种 registers
```

Lecture 中把它称为一种 **maximally pessimistic** 的策略。([MIT OpenCourseWare](https://ocw.mit.edu/courses/6-001-structure-and-interpretation-of-computer-programs-spring-2005/resources/10a-compilation/?utm_source=chatgpt.com "10A: Compilation | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

# 12. Compiler 为什么能做得更好？

Compiler 知道正在 compile：

```scheme
x
```

它知道 variable lookup 只需要：

```text
env
```

修改：

```text
val
```

并不会修改：

```text
proc
argl
env
```

所以：

```text
save proc
...
restore proc
```

可能根本没必要。

同样，如果 compile：

```scheme
f
```

只是 variable lookup：

```text
needs: env
modifies: proc
```

它不会破坏 `env`。

于是：

```text
save env
compile f
restore env
```

也没必要。

Lecture 里用 `(f x)` 展示了这一点：原本从 evaluator 直接“照抄”出来可能有大量 machine instructions，而利用 compiler 已知的信息后，很多 register saves/restores 都能消失。([MIT OpenCourseWare](https://ocw.mit.edu/courses/6-001-structure-and-interpretation-of-computer-programs-spring-2005/resources/10a-compilation/?utm_source=chatgpt.com "10A: Compilation | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

这里出现了 compiler 的第一个真正 static analysis：

> **这段代码需要什么？它会破坏什么？**

# 13. `needs` 和 `modifies`

SICP 给每段 instruction sequence 附上 metadata：

```text
Instruction Sequence

┌──────────────────────┐
│ needs                │
│ modifies             │
│ statements           │
└──────────────────────┘
```

例如：

```scheme
(assign r1 (reg r2))
```

显然：

```text
needs:
    r2

modifies:
    r1
```

因为执行之前：

```text
r2 必须已经有值
```

而执行之后：

```text
r1 的旧值已经被覆盖
```

Lecture 10A 明确介绍了这种 representation：一段 code sequence 包含 actual instructions、modified registers 和 needed registers。([MIT OpenCourseWare](https://ocw.mit.edu/courses/6-001-structure-and-interpretation-of-computer-programs-spring-2005/resources/10a-compilation/?utm_source=chatgpt.com "10A: Compilation | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

这是这一讲非常深的地方。

Compiler 不再只处理：

```text
machine instructions
```

而是处理：

```text
machine instructions
+
关于 instructions 的语义信息
```

也就是：

> **代码 + effect summary**

# 14. `preserving`：什么时候才真正 save register？

假设：

```text
seq1
↓
seq2
```

我们想保护 `env`。

并不是无脑：

```text
save env
seq1
restore env
seq2
```

而是问两个问题。

### 问题 1

`seq1` 会修改 `env` 吗？

```text
env ∈ modifies(seq1)?
```

如果不会：

```text
不用保存
```

### 问题 2

`seq2` 真的需要旧的 `env` 吗？

```text
env ∈ needs(seq2)?
```

如果不需要：

```text
即使 seq1 修改了 env
也没关系
```

只有：

```text
seq1 modifies env
        AND
seq2 needs env
```

才需要：

```text
save env
seq1
restore env
seq2
```

所以核心规则是：

```text
need save(r)

iff

r ∈ modifies(seq1)
AND
r ∈ needs(seq2)
```

这就是：

```scheme
(preserving '(env)
            seq1
            seq2)
```

背后的含义。

SICP 正文的 `preserving` 正是这样：只有当前一 sequence 修改某 register，而后一 sequence 又需要它原来的值时，才插入 `save` / `restore`。([SICP Source Academy](https://sicp.sourceacademy.org/split_py/chapters/5.5.1.html?utm_source=chatgpt.com "5.5.1   Structure of the Compiler - SICP Comparison Edition"))

# 15. 为什么这是 Compiler，而不只是“小优化”？

因为这里第一次出现了一种很典型的 compiler 思维：

```text
不要只看 instruction 是什么。

还要知道：

instruction 对 machine state
有什么 requirements 和 effects。
```

也就是：

```text
before:
    what must hold?

instruction sequence

after:
    what may have changed?
```

你作为做基础设施/系统工程的人，可以把它类比成：

```text
Terraform resource

requires:
    VPC
    subnet

modifies:
    route-table
```

如果下一个 operation 需要原 route-table：

```text
就必须 preserve / reconstruct
```

compiler 的数据流分析在做类似的依赖推理，只不过对象是 machine state。

# 16. Instruction Sequence 的组合规则

假设：

```text
S1:
needs    = N1
modifies = M1

S2:
needs    = N2
modifies = M2
```

然后：

```text
S1 ; S2
```

新的 `modifies` 很直接：

$$
M = M_1 \cup M_2
$$

因为任意一段修改过的 register，都应该认为整个组合会修改。

---

新的 `needs` 稍微有意思：

$$
N = N_1 \cup (N_2 - M_1)
$$

为什么？

首先：

```text
S1 运行前需要 N1
```

显然。

S2 需要 N2。

但是假设：

```text
S2 needs r
```

同时：

```text
S1 modifies r
```

这意味着：

```text
S1 已经产生了 S2 要使用的 r
```

因此 `r` 不需要在整个组合开始前已经存在。

例如：

```text
S1:
    assign val 42

needs = {}
modifies = {val}

S2:
    assign x val

needs = {val}
modifies = {x}
```

组合：

```text
assign val 42
assign x val
```

整体根本不需要调用者提前提供 `val`。

因为：

```text
val 是 S1 创建的
```

所以：

```text
needs(combined) = {}
```

这正是 Lecture 10A 在大约 37–40 分钟处详细推导的规则。([MIT OpenCourseWare](https://ocw.mit.edu/courses/6-001-structure-and-interpretation-of-computer-programs-spring-2005/resources/10a-compilation/?utm_source=chatgpt.com "10A: Compilation | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

# 17. 这里隐藏了一个非常重要的 abstraction

注意 compiler 不需要：

```text
重新扫描 seq1 的所有 machine instructions
看看修改了哪些 register
```

因为 `seq1` 本身已经携带：

```text
needs
modifies
```

于是：

```text
primitive sequence
      ↓
有 summary

组合两个 sequence
      ↓
组合 summary

再组合更大的 sequence
      ↓
继续组合 summary
```

形成：

```text
leaf
│
├── instruction
├── needs
└── modifies

       ↓ composition

larger block
│
├── instructions
├── derived needs
└── derived modifies

       ↓

whole program
```

这是一个非常典型的 SICP 思想：

> **不仅设计 primitive，还要设计 closure under combination。**

也就是说：

```text
primitive object
      +
means of combination
      ↓
compound object
```

而 compound object 仍然拥有同样的 interface：

```text
needs
modifies
statements
```

所以它可以继续参与组合。

这和 Lecture 1A 开头讲的：

```text
primitive expressions
means of combination
means of abstraction
```

其实是同一个思想。

# 18. Compiler 的 recursive structure

顶层可以想成：

```scheme
(define (compile exp target linkage)
  (cond ((self-evaluating? exp)
         ...)
        ((quoted? exp)
         ...)
        ((variable? exp)
         ...)
        ((assignment? exp)
         ...)
        ((definition? exp)
         ...)
        ((if? exp)
         ...)
        ((lambda? exp)
         ...)
        ((begin? exp)
         ...)
        ((application? exp)
         ...)))
```

注意它有多眼熟。

Metacircular evaluator 是：

```scheme
(define (eval exp env)
  (cond ((self-evaluating? exp) ...)
        ((variable? exp) ...)
        ((if? exp) ...)
        ((lambda? exp) ...)
        ((application? exp) ...)))
```

Compiler：

```scheme
(define (compile exp ...)
  (cond ((self-evaluating? exp) ...)
        ((variable? exp) ...)
        ((if? exp) ...)
        ((lambda? exp) ...)
        ((application? exp) ...)))
```

两者结构几乎一样。

为什么？

因为：

> **它们都在实现同一门语言的 semantics。**

区别只是：

```text
eval:
    expression → value

compile:
    expression → program that will produce value
```

这是我认为这一讲最值得记住的一句话：

```text
Evaluator:
E → V

Compiler:
E → MachineProgram(E)
         ↓ runtime
         V
```

# 19. Application 是 Compilation 的核心

SICP 直接把 procedure application 称为 compilation 的核心部分。

考虑：

```scheme
(f x)
```

生成代码的逻辑结构：

```text
compile operator f
target = proc
        ↓
proc = procedure for f

compile operand x
target = val
        ↓
val = value of x

construct argl
        ↓
argl = (val)

call proc
        ↓
result → target
        ↓
linkage
```

所以可以理解成：

```text
(application operator operands)

        ↓

compile operator → proc

        ↓

compile operands → argl

        ↓

procedure call

        ↓

target

        ↓

linkage
```

# 20. 一个稍复杂例子：`(f (g x) 1)`

这是特别适合这一讲的例子，Lecture 里也用类似形式展示了 evaluator 会产生多少 save/restore，以及 compiler 为什么能删掉大部分。([MIT OpenCourseWare](https://ocw.mit.edu/courses/6-001-structure-and-interpretation-of-computer-programs-spring-2005/resources/10a-compilation/?utm_source=chatgpt.com "10A: Compilation | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

Source：

```scheme
(f (g x) 1)
```

结构：

```text
application
│
├── operator
│      └── f
│
└── operands
       ├── (g x)
       └── 1
```

compile operator：

```text
lookup f
↓
proc = f-procedure
```

然后 operand `(g x)`：

```text
lookup g
↓
proc temporarily becomes g-procedure

lookup x
↓
val = x-value

argl = (x-value)

call g
↓
val = result-of-g-x
```

问题出现了：

最外层：

```text
proc = f
```

但内层 `(g x)` 也需要：

```text
proc = g
```

因此：

```text
compile (g x)
```

确实会 **modify proc**。

可是后面还需要外层的：

```text
proc = f
```

因此必须保护：

```text
save proc

compile (g x)

restore proc
```

这里保存是有理由的。

相比之下，对：

```scheme
x
```

单纯 variable lookup：

```text
needs env
modifies val
```

它不会 modify `proc`。

所以没必要：

```text
save proc
lookup x
restore proc
```

这就是 compiler 静态分析真正开始发挥作用的地方。

# 21. Interpreter 为什么做不到？

关键不是：

> interpreter 比 compiler 笨。

而是两者拥有的 **information 不同**。

Interpreter 在 runtime 看到：

```text
evaluate SOME-EXPRESSION
```

这个 expression 可能是：

```scheme
x
```

也可能是：

```scheme
(foo (bar (baz ...)))
```

所以必须保守。

Compiler 看到具体 AST：

```scheme
x
```

它知道：

```text
只是 variable lookup
```

因此：

```text
不会 clobber proc
不会 clobber argl
```

所以：

```text
Interpreter:
less knowledge
→ conservative

Compiler:
more static knowledge
→ specialized code
```

这个思想远比“compiler 更快”重要。

# 22. 这其实已经是 Dataflow Analysis 的雏形

现代 compiler 会分析：

```text

def
live-in
live-out
```

SICP 这里：

```text

modifies
```

虽然简单得多，但 mental model 已经非常接近。

例如：

```text

    modifies r

seq2:

```

就表示：

```text
        r's old value
             │
             │ needed later
             ↓
        ┌─────────┐

        └─────────┘
             │
             ↓
        ┌─────────┐
        │  seq2   │ ← needs old r
```

所以需要：


SICP 在这里刻意设计了一个非常小的模型，让核心原理可见。

# 24. Compile time vs Runtime

这是本节必须建立牢固的 mental model。

假设：

```scheme
(+ x 3)
```

### Compile time 已知

```text
这是 application
operator 是 +
有两个 operands
第一个 operand 是 variable x
第二个 operand 是 constant 3
```

### Runtime 才知道

```text
x 当前到底是多少
+ 当前绑定到什么 procedure
执行结果是多少
```

所以 compiler 能把：

```text
"这是 application 吗？"
```

消除。

但不能把：

```text
"x 的 runtime value 是多少？"
```

凭空消除。

这是 compiler design 中非常根本的问题：

```text
Known now?
    │
    ├─ yes → compute / specialize now
    │
    └─ no  → generate runtime code
```

# 25. 为什么 compilation 是一种 abstraction？

很容易把这一讲误认为：

> SICP 最后顺便教一下 compiler。

其实不是。

前面的主题一直是：

```text

```

```text

      ↓

      ↓
```

这里变成：

```text

──────────── language barrier
compiler
────────────
machine representation
```

# 28. 一个非常重要的等式

可以把 interpreter 写成：

$$
Interpreter(P, Input) = Result
$$

其中：

```text
P = program
Input = runtime data
```

如果固定 `P`：

```text
Interpreter(P, ?)
```

Compiler 做的事情可以理解为提前处理 `P`：

$$
Compiler(P)=P'
$$

使得：

$$
P'(Input)=Interpreter(P,Input)
$$

也就是说：

```text
Interpreter
takes:
    program + data

Compiler
takes:
    program

produces:
    specialized program

specialized program
takes:
    data
```

这就是为什么 compilation 和 partial evaluation 有如此深的联系。

# 29. Procedure application 的完整 runtime flow

对于：

```scheme
(f x)
```

compiled code 最终仍然必须实现 Scheme application semantics。

大体：

```text
Global / current environment E

f → closure(...)
x → 10
```

runtime：

```text
lookup f in E
      ↓
proc = closure(f-body, f-env)

lookup x in E
      ↓
val = 10

construct argl
      ↓
argl = (10)

prepare continuation
      ↓
continue = after-call

enter procedure
      ↓
extract procedure environment
      ↓
extend environment:
parameter → argument

      x? / p? → 10

      ↓
evaluate compiled procedure body

      ↓
val = result

      ↓
goto continue
```

也就是说：

> compilation 并没有消灭 environment model。

它只是把：

```text
“如何操作 environment”
```

提前翻译成 machine instructions。

Lexical scope 仍然存在。

Closure 仍然存在。

Environment 仍然存在。

只是不再需要 generic `eval` 每次动态决定下一步是什么。

# 30. Compilation 不会自动改变 Process Shape

这是一个很容易混淆的问题。

假设：

```scheme
(define (factorial n)
  (if (= n 1)
      1
      (* n (factorial (- n 1)))))
```

source-language process：

```text
factorial 5

5 * factorial 4
    ↓
5 * (4 * factorial 3)
        ↓
5 * (4 * (3 * factorial 2))
...
```

这是：

```text
linear recursive process
```

大致：

$$
T(n)=T(n-1)+O(1)=O(n)
$$

stack：

$$
S(n)=O(n)
$$

Compiler 把它变成 machine code，并不意味着：

```text
recursive process → iterative process
```

只是：

```text
同一个 process
用更低层次 representation 实现
```

---

如果 source program 是 tail recursive：

```scheme
(define (fact-iter product counter n)
  (if (> counter n)
      product
      (fact-iter (* counter product)
                 (+ counter 1)
                 n)))
```

Scheme 实现具有 proper tail recursion 时：

```text
(product, counter)
       ↓
(new-product, new-counter)
       ↓
...
```

就是 iterative process。

所以：

```text
recursive procedure
≠
recursive process
```

在 compilation 后依然成立。

# 31. Compilation 改善的是什么复杂度？

对于算法：

```scheme
factorial
```

通常：

```text
interpreter:
O(n)

compiled:
O(n)
```

并不会突然：

```text
O(n) → O(log n)
```

改变的是常数因子以及 interpretive overhead。

Interpreter：

```text
每一步：
syntax dispatch
register bookkeeping
generic evaluator control
actual computation
```

Compiler：

```text
主要：
actual required machine operations
```

因此更像：

$$
T_{\text{interp}} = T_{\text{actual computation}} + T_{\text{interpretation overhead}}
$$

而：

$$
T_{\text{compiled}} \approx T_{\text{actual computation}} + T_{\text{generated-machine overhead}}
$$

所以 compiler optimization 和 algorithmic complexity 是不同层次的问题。

# 32. 几组非常容易混淆的概念

## Interpreter vs Compiler

```text
Interpreter

source
  ↓
analyze + execute
  ↓
value
```

```text
Compiler

source
  ↓
analyze + generate
  ↓
machine program

machine program
  ↓
execute
  ↓
value
```

关键区别不是：

```text
一个“翻译”
一个“不翻译”
```

而是：

```text
什么时候做分析，
分析结果是立即行动还是生成程序。
```

---

## Evaluation vs Compilation

Evaluation：

$$
Expression \to Value
$$

Compilation：

$$
Expression \to Instructions
$$

但生成的 instructions 将来应该满足：

$$
Execute(Compile(E))=Evaluate(E)
$$

这实际上就是 compiler correctness 最核心的 specification。

---

## `target` vs `linkage`

```text
target:
    value 去哪里？

linkage:
    control 去哪里？
```

例如：

```text
target = val
linkage = return
```

表示：

```text
result → val
then
goto continue
```

---

## `needs` vs `modifies`

```text
needs:
执行之前必须正确的 registers

modifies:
执行之后不能保证仍保持原值的 registers
```

它们不是：

```text
read registers
write registers
```

的简单文本统计，而是在组合意义上的 interface。

---

## Compiler optimization vs algorithm optimization

Compiler：

```text
save/restore elimination
constant knowledge
register operations
```

算法：

```text
O(n²) → O(n log n)
```

完全不同层次。

# 33. 为什么 `preserving` 是 SICP 风格的漂亮设计？

你完全可以写每一个 compiler routine 时手动：

```scheme
(save env)
...
(restore env)
```

但是那会导致：

```text
compile-application
懂 register preservation

compile-if
懂 register preservation

compile-assignment
懂 register preservation

compile-lambda
懂 register preservation

...
```

同一套 tricky logic 散落在 compiler 各处。

SICP 反而抽象出：

```scheme
(preserving regs seq1 seq2)
```

意思：

> “我要先做 `seq1` 再做 `seq2`。请确保这些 registers 在必要时得到保护。”

调用者只表达：

```text
semantic requirement
```

而不是：

```text
具体 save/restore mechanism
```

这就是 abstraction。

类似：

```text
I want:
preserve env

not:
emit save env here,
restore it exactly there
```

然后 abstraction 自己判断：

```text
actually necessary?
```

这和现代 optimizer 的理念非常相似：

> 先表达正确性约束，再由 lower layer 选择最便宜的实现。

# 40. 常见误区

### 误区 1：Compiler 就是把 Lisp 换成 Assembly 文本

不够准确。

真正核心是：

```text
source semantics
↓
static analysis
↓
target-machine computation
```

Syntax conversion 只是表面。

---

### 误区 2：Compiler 不需要 evaluator

概念上恰好相反。

你必须先知道：

```text
程序应该是什么意思
```

才能知道：

```text
应该生成什么代码
```

SICP 因此故意：

```text
先 evaluator
再 compiler
```

---

### 误区 3：Compiler 会消灭 environment

不会。

Lexical scope 仍然需要：

```text
environment
closure
bindings
```

只是 generic evaluation dispatch 消失了。

---

### 误区 4：Compile 后算法复杂度就降低了

通常没有。

```text
O(n)
```

还是：

```text
O(n)
```

主要降低 interpretive overhead。

---

### 误区 5：所有 save/restore 都能删掉

错误。

例如：

```scheme
(f (g x))
```

计算 `(g x)` 时会使用 `proc` 保存 `g`。

但外层之后还需要：

```text
proc = f
```

所以确实需要保护 outer `proc`。

正确 mental model 是：

```text
not:
remove saves

but:
save exactly when required
```

---

### 误区 6：`needs` 就是“代码中出现过的所有 registers”

不是。

它表示：

> 在进入这段 code sequence 之前就必须已经有正确值的 registers。

如果某 register 在前半段自己产生：

```text
后半段虽然使用它
```

整个 sequence 也不一定 externally needs 它。

---

### 误区 7：Compiler 与 Interpreter 是两个完全不同的设计

SICP 故意让你看到：

```text
eval dispatch
≈
compile dispatch
```

两者共享同一个 language structure。

# 43. 真正应该记住的 9 个东西

如果几个月以后你只记得这些，就足够了。

### 核心思想

1. **Interpreter 是在 runtime 同时 analyze + execute；compiler 把 analysis 提前。**
    
2. **Compiler 可以理解成 evaluator 的一种 specialization：不是执行 machine operations，而是生成它们。**
    
3. **Compilation 的最大资产是 static knowledge。知道具体程序结构以后，可以消除 interpreter 必须承担的保守 bookkeeping。**
    
4. **Compiler 本身也是 compositional abstraction：小 code fragment 组合成大 code fragment。**
    

### 关键机制

5. `compile(exp, target, linkage)` 中：
    

```text
target = value flow
linkage = control flow
```

6. 每个 instruction sequence 携带：
    

```text
needs
modifies
statements
```

7. preservation 原则：
    

```text
save r
iff
seq1 modifies r
AND
seq2 needs old r
```

8. 顺序组合时：
    

$$
Modifies=M_1\cup M_2 \qquad Needs=N_1\cup(N_2-M_1)
$$

### 最重要的 mental model

```text
Evaluator:
program → actions

Compiler:
program → representation of those actions
```

我认为这就是整节 10A 的灵魂。

### 题 2：手动推演 `needs/modifies`

有：

```text
S1:
    (assign r1 (reg r2))

S2:
    (assign r3 (reg r1))
```

先分别写：

```text
needs(S1)
modifies(S1)

needs(S2)
modifies(S2)
```

然后不用机械套公式，先用直觉推导：

```text
needs(S1 ; S2)
modifies(S1 ; S2)
```

最后再验证：

$$
N=N_1\cup(N_2-M_1)
$$

为什么得到相同结果。
