# 1. 这节课到底想解决什么问题？

先回忆我们前面已经走了多远。

早期 SICP：

```text
Scheme expression
       ↓
substitution model
       ↓
procedure / recursion / higher-order procedure
```

到了 5A/5B：

```text
assignment
   ↓
state
   ↓
environment model
```

到了 7A/7B：

```text
Scheme program
       ↓
eval / apply
       ↓
interpreter
```

于是似乎已经回答了：

> Scheme 程序怎么运行？

例如：

```scheme
(define (fact n)
  (if (= n 1)
      1
      (* n (fact (- n 1)))))
```

我们可以说：

```text
(fact 3)

↓
3 * (fact 2)

↓
3 * (2 * (fact 1))

↓
3 * (2 * 1)

↓
6
```

甚至用 environment model：

```text
Global Env
   |
 fact → procedure
          |
          v

E1: n=3
   |
   +-- evaluate (* n (fact (- n 1)))
                       |
                       v
                  E2: n=2
                       |
                       v
                  E3: n=1
```

但是这里有一个巨大的东西被隐藏了：

> **这些“未完成的计算”到底放在哪里？**

计算 `fact 3` 时：

```text
3 * [something]
```

必须记住这个 `3 * ...`。

进入：

```text
fact 2
```

以后又必须记住：

```text
2 * [something]
```

再进入：

```text
fact 1
```

所以机器实际上必须记住：

```text
等 fact(1) 回来
→ 乘 2

然后
→ 乘 3

然后
→ 回到 fact 的调用者
```

但 Scheme 源代码里没有：

```scheme
push 3
push return-address
goto ...
pop ...
```

这些东西。

## SICP 此时遇到的真正问题

前面的 abstraction 太强大了。

我们写：

```scheme
(fact (- n 1))
```

就像一句魔法：

> “计算一个 factorial，然后回来。”

但是：

```text
“回来”
```

到底是什么意思？

机器怎么知道：

```text
回到哪里？
```

又怎么知道：

```text
之前的 n 是多少？
```

这就是 Lecture 9A 真正要揭开的东西。

# 3. 如果没有 Register Machine 这一层，会缺什么？

例如：

```scheme
(define (gcd a b)
  (if (= b 0)
      a
      (gcd b (remainder a b))))
```

我们知道这是 recursive procedure。

也知道它产生 iterative process。

但是：

```text
为什么 iterative process 可以 constant space？
```

如果只停留在 Scheme 层，很容易回答成：

> “因为 tail recursion。”

这其实还不够。

真正的问题是：

> **为什么 tail recursion 不需要保存旧 computation？**

9A 就会让你亲眼看到：

```text
所有未来计算需要的信息
=
当前 a
+
当前 b
+
controller 当前位置
```

根本没有：

```text
pending computation stack
```

所以才是 constant-space process。

官方讲稿正是从 GCD 开始，并强调这个 recursive procedure 产生 iterative process，因为继续计算所需的信息全部包含在 `a` 和 `b` 这两个状态变量中。

这也是为什么 Lecture 1B 的：

> recursive procedure ≠ recursive process

到 Lecture 9A 才真正“落地成机器”。

# 5. 第一个核心机制：Register Machine

## 5.1 直觉

先把 CPU 想成：

```text
一小堆盒子
+
一些计算器
+
一个决定下一步做什么的控制器
```

盒子就是：

```text
register
```

例如：

```text
a = 30
b = 42
t = ?
```

计算器可以做：

```text
remainder(a, b)
=
(a == 0?)
=
a + b
```

controller 则说：

```text
现在算 remainder

然后把结果放进 t

然后 b → a

然后 t → b

然后检查 b 是否为 0

否则跳回来
```

所以：

```text
Register Machine
=
Data Path
+
Controller
```

官方讲稿在 GCD 的例子里正是以这两个部分来分解机器：datapath 保存/变换数据，而 controller 决定操作顺序和分支。

# 6. Datapath vs Controller

这是第一组一定要分清的概念。

## Datapath

回答：

> **有哪些数据？能对它们做什么？**

例如 GCD：

```text
Registers:

A
B
T
```

Operations：

```text
remainder(A, B)
B == 0
```

数据路径：

```text
A ──────┐
        │
        ▼
    remainder ──→ T
        ▲
        │
B ──────┘


B ─────────────→ A

T ─────────────→ B
```

---

## Controller

回答：

> **什么时候做哪一步？**

大致：

```text
start:
    if B == 0:
        done

    T ← remainder(A, B)
    A ← B
    B ← T

    goto start
```

所以：

```text
Datapath
=
what operations are physically possible

Controller
=
when they happen
```

非常像现代 CPU：

```text
datapath
→ registers
→ ALU
→ buses

controller
→ instruction decode
→ branch logic
→ control signals
```

当然 SICP 的抽象机器比真实 CPU 简化很多。

# 7. GCD：第一次真正把 process 变成 machine

原程序：

```scheme
(define (gcd a b)
  (if (= b 0)
      a
      (gcd b (remainder a b))))
```

注意：

```scheme
(gcd ...)
```

看起来是 recursion。

但运行过程：

```text
gcd(30,42)

(a=30, b=42)
       ↓
(a=42, b=30)
       ↓
(a=30, b=12)
       ↓
(a=12, b=6)
       ↓
(a=6, b=0)
       ↓
6
```

关键是：

```text
每一步完成之后

旧状态
完全可以丢掉
```

例如：

```text
(a=30,b=42)

↓ transition

(a=42,b=30)
```

得到新状态以后：

```text
30,42
```

这个旧状态没有任何未来用途。

于是 process 本质就是：

```text
state₀
  ↓
state₁
  ↓
state₂
  ↓
state₃
  ↓
...
```

# 8. 这其实是一种新的 Evaluation Model

以前我们的 mental model 是：

```text
expression
   ↓
evaluate operator
   ↓
evaluate operands
   ↓
apply procedure
   ↓
extend environment
   ↓
evaluate body
```

到了 Register Machine：

```text
Machine State
    ↓
execute one instruction
    ↓
modify registers / stack
    ↓
update control state
    ↓
Machine State'
```

也就是说：

> **程序执行 = machine state 的连续 transition。**

可以写成数学形式：

$$
S_0 \to S_1 \to S_2 \to \cdots
$$

其中 machine state 大概是：

$$
S = (\text{register contents}, \text{controller position}, \text{stack})
$$

这其实是一个非常重要的 CS mental model。

# 9. 为什么 GCD 需要临时寄存器 `T`？

假设当前：

```text
A = 30
B = 42
```

数学上我们想：

```text
A ← B
B ← remainder(A,B)
```

但如果机器逐条执行：

```text
A ← B
```

那么：

```text
A = 42
B = 42
```

原来的 `A=30` 已经没了。

然后：

```text
B ← remainder(A,B)
```

就变成：

```text
remainder(42,42)
```

错了。

因此：

```text
T ← remainder(A,B)
A ← B
B ← T
```

这背后是一个非常普遍的原则：

> **如果一个值在被覆盖以后仍然需要，就必须先保存。**

请记住这句话。

它马上就会变成 recursive process 的核心问题。

# 10. 从 GCD 到 factorial：真正的大转折

来看：

```scheme
(define (fact n)
  (if (= n 1)
      1
      (* n
         (fact (- n 1)))))
```

这个过程和 GCD 最大的不同不是：

```text
一个用 multiplication
一个用 remainder
```

而是：

```text
GCD:
递归调用回来以后没事干。


factorial:
递归调用回来以后还有事干。
```

具体说：

```text
fact 3

↓
3 * fact 2
```

此时你不能忘记：

```text
n = 3
```

因为等 `fact 2` 得到结果以后：

```text
必须 × 3
```

进入：

```text
fact 2
```

以后：

```text
3 * (
    2 * fact 1
)
```

现在要记：

```text
2
3
```

# 11. recursive process 的本质是什么？

这里我建议你彻底改变一个 mental model。

很多人觉得 recursive process 是：

> “函数调用自己。”

不够准确。

真正更深的定义应该是：

> **当前 computation 必须暂停，并保存一些未来恢复计算所需的信息，然后执行另一个 computation。**

例如：

```text
fact(3)

current work:

3 * [HOLE]
```

`HOLE` 要由：

```text
fact(2)
```

填。

于是：

```text
保存:
    n = 3
    等回来后要做 multiplication
```

进入：

```text
fact(2)
```

又产生：

```text
2 * [HOLE]
```

因此 recursive computation 自然形成：

```text
outer computation
      │
      └── inner computation
                │
                └── inner computation
```

问题来了：

> 一台有限机器怎么模拟任意深的 nested computation？

这是 9A 最漂亮的地方。

---

# 12. 答案：Stack

官方讲稿明确把 stack 引入为一种有限机器模拟任意深递归嵌套的方法：把 inner computation 完成以后恢复 outer computation 所需的信息放到 stack 中，因为这种嵌套天然符合后进先出。

想象：

```text
fact 5
```

逻辑结构像：

```text
machine for fact(5)
    contains
        machine for fact(4)
            contains
                machine for fact(3)
                    ...
```

当然不可能真的造：

```text
无限多台 factorial machine
```

于是我们只造：

```text
一台 machine
+
一块 stack
```

利用 stack 保存：

```text
“外层机器暂停时的关键状态”
```

于是：

```text
many nested machines
```

变成：

```text
one finite controller
+
dynamic stack
```

这是一种非常深的 representation transformation。

# 13. Stack 到底保存什么？

最容易犯的错误是回答：

> 保存局部变量。

不完整。

正确答案：

> **保存当前 computation 被打断以后，将来恢复它所需要的东西。**

factorial 需要至少两个东西。

第一：

```text
旧的 n
```

第二：

```text
回来以后执行哪里
```

第二个就是：

# `continue`

# 14. Continuation：9A 最重要的概念之一

假设：

```scheme
(* n (fact (- n 1)))
```

执行：

```text
fact(n-1)
```

之前，机器必须知道：

```text
等它回来以后
去做 multiplication
```

所以机器保存一个 label：

```text
after-fact
```

可以想象：

```text
continue = after-fact
```

于是：

```text
fact(n-1)
```

计算完成后：

```text
goto continue
```

也就是：

```text
goto after-fact
```

然后：

```text
VAL ← n × VAL
```

# 15. `continue` 到底是什么？

非常值得建立这个对应：

```text
Scheme world

"调用 fact，
 完成以后回这里继续"


        ↓ explicit representation


Machine world

continue = return address
```

现代语言里接近：

```text
CPU return address
```

或者汇编里的：

```text
link register
```

或者 call stack frame 中的：

```text
saved return address
```

在程序语言理论中则开始接近：

```text
continuation
```

即：

> **剩下还要进行的 computation。**

这里的 `continue` 还只是一个低级版本：

```text
label / return address
```

但思想已经非常重要。

# 16. factorial register machine

可以抽象成：

```text
Registers:

n
val
continue
```

外加：

```text
stack
```

机器大致执行：

```text
continue ← done

fact-loop:

    if n == 1:
        goto base-case

    save continue
    save n

    n ← n - 1
    continue ← after-fact

    goto fact-loop


base-case:

    val ← 1
    goto continue


after-fact:

    restore n
    restore continue

    val ← n * val

    goto continue


done:
```

不要把它当 Scheme。

这是：

```text
一种描述 register machine controller 的语言
```

讲稿在 Fibonacci 部分甚至明确提醒，这种括号语法虽然长得像 Lisp，但描述的是另一种语言；之所以采用这种表示，是为了方便用 Lisp 编写 simulator。

# 19. 现在重新理解 recursive process

以前看到：

```text
fact 3
↓
3 * fact 2
↓
3 * (2 * fact 1)
```

我们画的是数学展开。

现在你应该能看到下面这一层：

```text
procedure-level description

3 * (2 * 1)

        ↓ implementation


stack

done
3
after-fact
2


registers

n
val
continue


controller

fact-loop
after-fact
base-case
done
```

所以：

> **调用栈不是 recursion 的定义。**

更准确地说：

```text
recursive process
产生了需要保留的 deferred computation

stack
是实现这些 deferred computations 的一种 representation
```

这一区分很重要。

# 20. 为什么 GCD 不需要 stack？

现在你应该能真正解释 Lecture 1B 的问题了。

GCD：

```scheme
(gcd b (remainder a b))
```

递归调用是整个 procedure 最后一件事情。

没有：

```scheme
(+ ... (gcd ...))
```

也没有：

```scheme
(* ... (gcd ...))
```

所以调用新一轮 GCD 以后：

```text
old computation
没有任何事情需要恢复
```

因此：

```text
不用 save old a
不用 save old b
不用 save return computation
```

机器直接：

```text
overwrite registers
goto beginning
```

即可。

所以：

```text
recursive procedure
```

却是：

```text
iterative process
```

---

# 21. Tail recursion 现在应该这样理解

不要只记：

> tail recursive = recursive call 在最后。

真正意义是：

```text
在递归调用发生以后
没有 pending computation
```

于是机器可以：

```text
reuse current registers
reuse current controller
goto beginning
```

而不需要：

```text
push stack frame
```

因此：

```text
tail recursion
      ↓
no pending continuation
      ↓
no growing control stack
      ↓
constant-space iteration
```

这才是 SICP 对 tail recursion 最深的解释。

# 22. `save` / `restore` 的核心 invariant

看：

```text
save continue
save n
```

stack：

```text
[continue, n]
```

因为 stack 是 LIFO：

```text
restore n
restore continue
```

注意顺序是反过来的：

```text
save A
save B

restore B
restore A
```

这是一个非常重要的 invariant。

# 23. Stack Discipline

Sussman 在 Fibonacci 部分尤其强调：

```text
不要什么都保存。

只保存未来真正需要，
而且即将被覆盖的数据。
```

官方讲稿最后总结的 stack discipline 就包括：只保存以后确实需要的值，并确保 save/restore 正确配对。

这其实已经很像：

```text
compiler register allocation
liveness analysis
calling convention
stack frame design
```

例如：

```text
当前 n

未来不用了
```

那就：

```text
不要 save n
```

如果：

```text
VAL

即将被递归调用覆盖
但以后还要使用
```

那就：

```text
save VAL
```

换句话说：

> **save 的真正判断标准是 liveness。**

这和现代 compiler optimization 已经非常接近。

# 24. 为什么 Fibonacci 比 factorial 更重要？

factorial：

```scheme
(* n
   (fact (- n 1)))
```

只有：

```text
一个 recursive subproblem
```

而 Fibonacci：

```scheme
(+ (fib (- n 1))
   (fib (- n 2)))
```

有两个。

于是机器必须处理：

```text
先计算 fib(n-1)

还要记住：
    原来的 n
    谁等待最终 fib(n)
    fib(n-1) 的结果

然后计算 fib(n-2)

最后：
    result1 + result2
```

这逼迫我们真正搞清楚：

```text
什么必须保存？
何时保存？
何时恢复？
```

# 25. Fibonacci 的 computation shape

Scheme：

```scheme
(define (fib n)
  (if (< n 2)
      n
      (+ (fib (- n 1))
         (fib (- n 2)))))
```

`fib 4`：

```text
                    fib(4)
                   /      \
              fib(3)      fib(2)
              /   \        /   \
         fib(2) fib(1) fib(1) fib(0)
          /  \
     fib(1) fib(0)
```

所以 time：

$$
T(n)=T(n-1)+T(n-2)+O(1)
$$

大约：

$$
O(\varphi^n)
$$

但最大 recursion depth：

```text
fib(n)
→ fib(n-1)
→ fib(n-2)
...
```

只有：

$$
O(n)
$$

所以 stack space：

$$
O(n)
$$

而不是指数空间。

# 26. Factorial / GCD / Fibonacci 的 Process Shape

|Procedure|Process|Time|Growing Stack|
|---|---|--:|--:|
|iterative GCD|iterative|约 `O(log min(a,b))` 次 Euclid steps|`O(1)`|
|recursive factorial|linear recursive|`O(n)`|`O(n)`|
|naive Fibonacci|tree recursive|`O(φ^n)`|`O(n)`|

这里终于能从机器角度理解：

```text
space complexity
≈
同时存在多少尚未完成的 continuation
```

这句话非常值得记。

# 42. Recursive vs Iterative Process：机器级版本

### Iterative

状态可以写成固定大小：

$$
S=(a,b)
$$

每一步：

$$
S_{i+1}=f(S_i)
$$

因此：

```text
fixed number of registers
```

足够。

---

### Recursive

可能需要：

$$
S=(current,\ stack)
$$

stack 深度：

$$
0,1,2,\ldots,n
$$

所以：

```text
所需 state
随问题规模增长
```

这就是 recursive process 的 machine-level meaning。

# 43. Stack vs Environment

还有一组非常容易混。

Stack：

```text
保存动态 execution context
```

Environment：

```text
表示 lexical variable bindings
```

它们在普通 implementation 中可能有关联：

```text
stack frame
```

可以同时包含：

```text
locals
return address
saved registers
```

但概念上千万不要等同。

特别是 closure：

```scheme
(define (make-adder x)
  (lambda (y)
    (+ x y)))
```

其中：

```text
x
```

可能在创建 closure 的 procedure 已经 return 以后仍需存在。

所以它不能简单依赖：

```text
call stack
```

这也是为什么 environment / heap 和 control stack 是不同 abstraction。

# 44. 这一讲真正训练的设计方法

假设让你自己设计 factorial machine。

不要先问：

> 我要哪些指令？

先问：

```text
程序未来需要哪些信息？
```

例如：

```scheme
(* n (fact (- n 1)))
```

当 recursive computation 开始以后：

```text
会被覆盖：
n

以后需要：
n

→ save n
```

同时：

```text
controller 将进入 fact-loop

以后需要知道回哪里

→ save continuation
```

这其实是一套非常系统的设计方法：

```text
1. 找出 computation 的 live state
2. 找出哪些 state 会被 clobber
3. save 它们
4. 执行 subcomputation
5. restore 它们
6. resume continuation
```

这就是一个非常通用的 pattern。

# 45. SICP 的核心模式：Subroutine / Recursive-call Pattern

看到：

```text
调用某个 computation
并且以后还要继续
```

就应该想到：

```text
save values-needed-later
save continuation

setup arguments

continue ← return-label
goto subroutine

return-label:

restore saved-values
restore old-continuation

continue computation
```

这是这一讲最值得识别的 pattern。

# 46. Tail-call Pattern

反过来，如果：

```text
调用 subcomputation
以后什么都不做
```

那么：

```text
不用 save continuation
不用建立新的 dynamic context

setup arguments
goto subroutine
```

这就是：

```text
tail call
```

所以 tail-call optimization 并不是 compiler 的一个“小技巧”。

在 SICP 的视角里：

> **它只是忠实实现 iterative process。**

如果一个 Scheme implementation 对 tail recursion 仍不断增长 stack，它没有正确保留 SICP 所强调的这种 process property。

# 47. Fibonacci 又教了什么额外东西？

factorial 只要求：

```text
save n
save continuation
```

Fibonacci：

```scheme
(+ (fib (- n 1))
   (fib (- n 2)))
```

还产生一个新的问题。

完成：

```text
fib(n-1)
```

以后：

```text
VAL = fib(n-1)
```

但接下来计算：

```text
fib(n-2)
```

也会覆盖：

```text
VAL
```

所以：

```text
fib(n-1)
```

也必须保存。

你应该形成自动反应：

```text
Value needed later
+
will be overwritten
=
SAVE
```

这其实已经是 data-flow reasoning 了。

```text

```

那么 compiler 必须：




的世界。

更准确：


### 误区 3

错误。

> stack 只是存局部变量。

错误。

它真正存的是：

错误。

# 54. 你真正应该记住的 9 个东西

如果几个月以后忘光，只要留下这些就够了。

### 核心思想

**1. 程序执行可以表示为状态转换。**

```text
State → State → State → ...
```

**2. Register machine 把 data state 和 control state 都显式表示出来。**

```text
registers
controller
stack
```

**3. Recursive process 的本质不是“函数调用自己”，而是存在 pending computation。**

**4. Stack 是用有限机器模拟任意深动态嵌套 computation 的 mechanism。**

**5. Continuation 表示：“当前 computation 完成之后做什么”。**

### 关键机制

**6. Datapath 决定能做什么，controller 决定什么时候做。**

**7. 一个值即将被覆盖但以后仍需要时，save 它。**

**8. `save` / `restore` 必须遵守 LIFO 和正确配对。**

### 最重要的不变量

**9. Tail call 后没有 pending computation，因此不需要增长 control stack。**

我尤其建议你把最后一句记牢：

> **Space usage is determined by how much future computation must be remembered.**

这比单纯记：

```text
recursion = stack
```

准确得多。
