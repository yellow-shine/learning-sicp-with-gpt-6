你现在到的 **Lecture 3A: Henderson Escher Example**，可以把它看成 SICP 前几讲的第一次“大合流”。

MIT 官方课程把 3A 标为 **Henderson Escher Example**。这节课表面上是在“用 Lisp 画类似 Escher Square Limit 的递归图案”，但 Abelson 真正想讲的是第三种控制复杂度的方法：**metalinguistic abstraction（元语言抽象）——当已有语言不够适合描述问题时，不只是继续写函数，而是在原语言内部创造一种更适合这个问题的新语言。** ([MIT OpenCourseWare](https://ocw.mit.edu/courses/6-001-structure-and-interpretation-of-computer-programs-spring-2005/resources/lecture-videos/?utm_source=chatgpt.com "Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

如果只记一句：

> **Lecture 2A 教你把 computation 当作对象，2B 教你把 data 组合成复杂对象；3A 则把二者合起来，教你如何构造一种“可组合的语言”。**

# 1. 这节课到底想解决什么问题？

## 1.1 前面已经有 abstraction，为什么还不够？

到 Lecture 3A 之前，你其实已经有了两套非常强的武器。

Lecture 2A：

```text
procedure
   ↓
可以作为参数
   ↓
可以作为返回值
   ↓
higher-order procedure
```

例如：

```scheme
(define (sum term a next b)
  ...)
```

你开始不再抽象“某个计算结果”，而是抽象：

```text
计算过程本身
```

Lecture 2B：

```text
cons / car / cdr
      ↓
compound data
      ↓
data abstraction
      ↓
abstraction barrier
```

并且引入一个非常重要的性质：

```text
closure property
```

例如：

```scheme
(cons 1 2)
```

结果是 pair。

而：

```scheme
(cons (cons 1 2)
      (cons 3 4))
```

仍然可以继续组合。

也就是说：

```text
pair + pair
   ↓
仍然是 pair-like compound data
   ↓
可以继续参与组合
```

Lecture 3A 一开头就在回顾这些内容：上一讲的重要思想之一是把“数据怎么使用”和“数据怎么表示”分离；另一个重要思想则是 pair 的组合具有 closure property。

但现在 SICP 提出一个更大的问题：

> **如果我要描述一个非常复杂、递归、自相似的图案，我应该怎样组织程序？**

# 4. 第一核心机制：什么叫 Picture？

这是这一讲第一次非常容易让人“脑子拧一下”的地方。

你的直觉可能是：

```text
Picture = 一块 bitmap
```

例如：

```text
PNG
JPEG
pixels[]
```

SICP 偏偏不是这样定义。

它说：

> 一个 picture 是一个 **procedure**。

更准确地说：

```text
Picture:

Rectangle → draw something
```

也就是：

```text
picture(rectangle)
```

表示：

> 请把“我代表的图形”画进这个 rectangle。

MIT 讲座明确这样定义 picture：同一个 picture 可以给不同 rectangle，然后自动缩放到对应区域；因此不同大小和形状的 George 在这个语言里仍然是“同一个 picture”。

---

# 5. 为什么 Picture 要设计成 Procedure？

先别看实现。

假设：

```scheme
george
```

不是一张固定尺寸图片，而是：

```scheme
(lambda (rect)
  ;; 在 rect 中画 George
  ...)
```

那么：

```scheme
(george big-rect)
```

画一个大的 George。

```scheme
(george skinny-rect)
```

画一个瘦长的 George。

```scheme
(george tilted-rect)
```

甚至可以画进一个斜着的区域。

于是：

```text
图形本身
```

和：

```text
它最终画在哪里
```

被分离了。

这实际上是一次非常漂亮的 abstraction：

```text
WHAT                      WHERE / HOW LARGE
George                    rectangle

      \                    /
       \                  /
        picture(rectangle)
```

Picture 不保存：

```text
“我的最终坐标”
```

它保存的是：

```text
“如果你给我一个坐标系统，
我知道怎样把自己解释到那个坐标系统中。”
```

这个思想远比“画图”本身重要。

# 6. Rectangle / Frame：把坐标系统变成 Data Abstraction

一个 rectangle 可以用三个向量描述：

```text
             origin + vertical
                    ●
                   /|
                  / |
                 /  |
                /   |
       origin ●─────●
                horizontal
```

更准确地：

```text
origin
horizontal-vector
vertical-vector
```

所以：

```text
Frame = (origin, horizontal, vertical)
```

这甚至不一定非得是轴对齐矩形。

## 6.1 Unit square

先把所有 primitive picture 定义在统一坐标：

```text
(0,1) ───────── (1,1)
  │                │
  │                │
  │                │
(0,0) ───────── (1,0)
```

George 原始线段全部定义在这个：

```text
unit square
```

里面。

然后再做：

```text
unit square
     ↓
coordinate map
     ↓
arbitrary rectangle
```

# 7. Coordinate Map：一个 Frame 产生一个 Procedure

这是 Lecture 3A 一个很漂亮、但很容易被忽略的 higher-order procedure。

假设 frame：

```text
origin = O
horizontal = H
vertical = V
```

unit square 内一点：

$$
(x,y)
$$

映射到实际 frame：

$$
O+xH+yV
$$

也就是：

```text
        x * horizontal
       /
origin + 
       \
        y * vertical
```

Scheme 可以理解成：

```scheme
(define (coordinate-map rect)
  (lambda (point)
    (add-vect
      (origin rect)
      (add-vect
        (scale-vect
          (xcor point)
          (horizontal rect))
        (scale-vect
          (ycor point)
          (vertical rect))))))
```

注意这里最重要的不是线性代数。

真正重要的是：

```text
coordinate-map
```

接收：

```text
rectangle
```

返回：

```text
point → transformed-point
```

也就是说：

```text
Rectangle
    ↓
coordinate-map
    ↓
Procedure
```

MIT 讲座也特别指出，每个 rectangle 都定义了自己的 coordinate-map，而这个 map 本身是作用在 point 上的 procedure。

---

# 8. Evaluation：`coordinate-map` 到底怎么运行？

例如：

```scheme
(define m
  (coordinate-map r))
```

先暂时用 substitution + lexical-scope 的视角。

调用：

```scheme
(coordinate-map r)
```

发生：

```text
evaluate coordinate-map
        ↓
procedure

evaluate r
        ↓
rectangle R

apply
        ↓

rect = R

evaluate body

(lambda (point)
   ... rect ...)
```

结果不是 point。

结果是：

```text
一个 procedure
```

也就是：

```text
m
│
▼
(lambda (point)
   ... R ...)
```

这个 procedure 后面还能“记住” `rect = R`。

严格的 Environment Model 在 SICP 后面才正式展开，但你现在可以先有这个 mental model：

```text
m
│
▼
procedure
   │
   └── carries / closes over R
```

然后：

```scheme
(m '(0.3 0.8))
```

才真正进行：

```text
point = (0.3, 0.8)

O + 0.3H + 0.8V
```

这正是现代意义上的 **closure**。

不过这里必须马上区分两个 closure。

---

# 9. 一个极容易混淆的概念：两种 Closure

## Closure #1：closure property

SICP 前面讲 compound data 时的：

```text
combine A and B
      ↓
result 仍然属于同一种世界
```

比如：

```text
Pair × Pair → Pair
```

这一讲：

```text
Picture × Picture → Picture
```

这是**数学意义/组合意义上的 closure property**。

---

## Closure #2：lexical closure

例如：

```scheme
(define (coordinate-map rect)
  (lambda (point)
    ... rect ...))
```

里面返回的 procedure 记住 `rect`。

这是：

```text
procedure + lexical environment
```

意义上的 **closure**。

两者完全不是一个概念。

只是英文碰巧都叫 closure。

这是学习 SICP 时非常值得提前钉死的区别。

# 10. 从 Segment 构造 primitive picture

现在有：

```text
segment list
```

例如：

```text
segment1
segment2
segment3
...
```

每个端点都在：

```text
unit square
```

中。

那么可以：

```scheme
(define (make-picture segments)
  (lambda (rect)
    (for-each
      (lambda (segment)
        (draw-line
          ((coordinate-map rect)
           (start-segment segment))

          ((coordinate-map rect)
           (end-segment segment))))
      segments)))
```

这段代码值得慢慢看。

---

# 11. `make-picture` 的类型比代码更重要

可以先忽略 Scheme：

```text
make-picture:

List<Segment> → Picture
```

而：

```text
Picture:

Rectangle → Drawing
```

所以：

```text
List<Segment>
      │
      │ make-picture
      ▼
   Procedure
      │
      │ rectangle
      ▼
    drawing
```

MIT 讲座中的 primitive picture 正是这样构造的：给定线段集合，返回一个接受 rectangle 的 procedure；真正调用这个 picture 时，它把每条线段的端点通过 rectangle 的 coordinate map 映射，然后画线。

# 12. 这里出现了一个非常重要的“阶段分离”

假设：

```scheme
(define george
  (make-picture george-segments))
```

执行这句话时：

```text
没有画 George
```

只是：

```text
construct a computation
```

得到了：

```text
george
   ↓
procedure(rect)
```

真正：

```scheme
(george screen-rect)
```

才：

```text
执行 drawing
```

所以程序现在有两个阶段：

```text
Stage 1

构造 picture
construct computation

        ↓

Stage 2

给 picture 一个 frame
execute computation
```

这个 mental model 非常重要。

后面的：

```scheme
(beside ...)
(rotate ...)
(push ...)
```

很多操作其实都没有马上“画”。

而是在：

> **构造以后要怎么画的 computation。**

这已经非常接近现代：

```text
computation graph
query plan
UI tree
parser combinator
workflow DAG
```

的思维了。

# 13. 第二核心机制：Beside

现在假设：

```text
P1 = 一个 picture
P2 = 一个 picture
```

我们希望：

```scheme
(beside p1 p2 0.5)
```

表示：

```text
┌───────────┬───────────┐
│           │           │
│    P1     │    P2     │
│           │           │
└───────────┴───────────┘
```

关键问题：

> `beside` 应该返回什么？

答案：

```text
picture
```

因为我们希望：

```scheme
(rotate90
  (beside p1 p2 0.5))
```

仍然合法。

所以：

```text
beside:

Picture × Picture × Number
            ↓
          Picture
```

MIT 在这里明确把这种能力归结为 closure property：`Beside`、`Rotate`、`Flip` 得到的结果仍然是 picture，因此可以继续作为下一层组合的输入。

---

# 14. `beside` 可以怎样实现？

概念代码：

```scheme
(define (beside p1 p2 a)
  (lambda (rect)

    (define left-rect
      (make-rect
        (origin rect)
        (scale-vect a
                    (horizontal rect))
        (vertical rect)))

    (define right-rect
      (make-rect
        (add-vect
          (origin rect)
          (scale-vect
            a
            (horizontal rect)))
        (scale-vect
          (- 1 a)
          (horizontal rect))
        (vertical rect)))

    (p1 left-rect)
    (p2 right-rect)))
```

不要先陷进 vector 算法。

看结构：

```text
beside(p1, p2, a)
       │
       ▼
returns a procedure
       │
       ▼
lambda(rect)
       │
       ├── split rect
       │
       ├── p1(left-rect)
       │
       └── p2(right-rect)
```

这就是整个 abstraction。

讲座对 `Beside` 的解释也是这个意思：它只需要把传进来的 rectangle 拆成两个 rectangle，然后告诉 `p1`“在这里画自己”、告诉 `p2`“在那里画自己”；它完全不需要知道 `p1` 和 `p2` 内部是什么。

# 15. 这段代码最精彩的地方不是 rectangle

而是这一句：

```scheme
(lambda (rect) ...)
```

为什么？

因为：

```text
beside 返回的东西
```

和：

```text
george
```

具有完全相同的接口：

```text
Rectangle → Drawing
```

因此对于上层来说：

```text
Primitive picture
Combined picture
Recursive picture
```

完全不可区分。

```text
               Picture interface
                      │
      ┌───────────────┼─────────────────┐
      ▼               ▼                 ▼
primitive         beside(...)       push(...)
picture            result            result
```

这就是一个特别漂亮的 abstraction barrier。

# 16. Evaluation：真正展开 `(beside george (rotate90 george) .5)`

这是本讲非常值得手动推一次的表达式。

```scheme
(beside
  george
  (rotate90 george)
  0.5)
```

Scheme 默认是 applicative-order。

所以：

```text
expression

(beside george (rotate90 george) 0.5)

        ↓

evaluate operator

beside
→ procedure BESIDE
```

然后 operands。

```text
george
→ procedure G
```

接下来：

```scheme
(rotate90 george)
```

展开：

```text
evaluate rotate90
→ procedure ROTATE90

evaluate george
→ G

apply ROTATE90 to G
```

结果是什么？

不是 drawing。

而是：

```text
procedure R
```

其中：

```text
R(rect)
=
G(transformed-rect)
```

于是原表达式现在等价于：

```text
(BESIDE G R 0.5)
```

apply：

```text
p1 = G
p2 = R
a  = 0.5
```

`beside` 返回：

```text
procedure B
```

所以：

```scheme
(define picture-x
  (beside
    george
    (rotate90 george)
    0.5))
```

执行完成以后：

```text
仍然什么都没有画。
```

你只是得到：

```text
picture-x
   ↓
B
```

# 17. 真正绘制是在这里

```scheme
(picture-x screen-frame)
```

现在：

```text
B(screen-frame)
        ↓
split screen-frame
        ↓
left-frame      right-frame
    │                │
    ▼                ▼
G(left)          R(right)
                     │
                     ▼
                G(rotated-frame)
```

完整结构：

```text
picture-x(screen)

        │
        ▼

       beside

   ┌───────────┐
   │           │
   ▼           ▼

 george      rotate90
               │
               ▼
             george
```

但执行时不是在“移动 bitmap”。

而是在：

```text
不断变换 coordinate system
```

这是一个非常值得记住的设计技巧。

# 18. Rotate 为什么也很简单？

直觉可能认为旋转图片需要：

```text
拿到所有 pixel
→ 做 rotation matrix
→ 重新生成 pixel
```

SICP 的 picture abstraction 下不需要。

只需要改变：

```text
“我让原 picture 认为自己的 rectangle 是什么”
```

概念上：

```scheme
(define (rotate90 p)
  (lambda (rect)
    (p
      (rotated-version-of rect))))
```

也就是说：

```text
rotate90
不是修改 picture

而是：

change the coordinate system
        ↓
let picture redraw itself
```

这是一种非常强的思维方式：

```text
transform object
```

变成：

```text
transform interpretation context
```

MIT 在实现 `Rotate` 时强调的也正是这一点：不是修改 primitive picture，而是构造一个不同的 rectangle，然后让原 picture 相对于这个新 rectangle 绘制。

# 19. 这里为什么说 “procedure 和 data 的界线开始消失”？

现在看：

```scheme
(define george ...)
```

`george` 是什么？

从执行角度：

```text
procedure
```

因为：

```scheme
(george rect)
```

可以调用。

但我们又写：

```scheme
(beside george george 0.5)
```

这里：

```text
george
```

显然又像 data。

它被：

```text
传递
保存
组合
返回
```

所以：

```text
procedure
   ↕
first-class value
   ↕
data-like object
```

Lecture 3A 特别强调了这个主题：picture 本身就是 procedure，而 procedure 又被拿来当作语言中的对象进行组合，因此“procedure”和“data”的界线开始变得不再重要。

这里不要把结论理解成：

> “内存层面 procedure 和 integer 没区别。”

当然不是。

真正意思是：

> **在 abstraction/composition 层次上，procedure 也可以成为被操作的对象。**

这就是 first-class computation。

# 20. 第三个核心机制：Closure Property 为什么这么重要？

看看这个：

```scheme
(beside george george .5)
```

假设得到：

```text
P1
```

如果：

```text
P1
```

不是 Picture，而是某种特殊：

```text
BesideResult
```

那么：

```scheme
(rotate90 P1)
```

可能就不支持。

你会陷入：

```text
primitive-picture
beside-picture
rotated-picture
above-picture
...
```

每个 combinator 都必须知道几十种类型。

组合复杂度爆炸。

---

而正确设计：

```text
Picture × Picture → Picture
Picture → Picture
Picture × Picture → Picture
```

于是：

```scheme
(beside
  (rotate90 george)
  (above
    george
    (flip george)
    .5)
  .5)
```

完全自然。

结构变成：

```text
           beside
          /      \
     rotate       above
       |         /    \
    george    george   flip
                         |
                      george
```

注意：

> 每个内部节点的结果也仍然是 Picture。

这就是 closure property。

# 21. 这也是为什么复杂性可以快速增长

# 22. Recursive Combination：right-push

现在语言已经有：

```text
beside
above
rotate
flip
```

于是可以进一步定义：

```scheme
(define (right-push p n a)
  (if (= n 0)
      p
      (beside
        p
        (right-push p (- n 1) a)
        a)))
```

假设：

```scheme
(right-push george 2 0.6)
```

展开。

```text
right-push(G,2)

=
beside(
    G,
    right-push(G,1),
    .6)
```

继续：

```text
=
beside(
 G,
 beside(
   G,
   right-push(G,0),
   .6),
 .6)
```

base case：

```text
right-push(G,0)
=
G
```

所以：

```text
beside
├── G
└── beside
    ├── G
    └── G
```

视觉上：

```text
┌────────┬─────┬───┐
│        │     │   │
│ George │ G   │ G │
│        │     │   │
└────────┴─────┴───┘
```

这就是 self-similarity 开始出现的地方。

Lecture 中正是从 `right-push`、`up-push`、更复杂的 corner pattern 一步步得到类似 Square Limit 的递归结构。

# 23. Procedure vs Process：这里也值得分析

代码：

```scheme
(define (right-push p n a)
  (if (= n 0)
      p
      (beside
        p
        (right-push p (- n 1) a)
        a)))
```

它显然是：

```text
recursive procedure
```

而且产生：

```text
recursive process
```

因为必须等：

```text
(right-push ... n-1 ...)
```

先返回 Picture，然后才能调用：

```text
beside
```

展开：

```text
right-push 3
↓
beside P (right-push 2)
              ↓
        beside P (right-push 1)
                         ↓
                   beside P ...
```

存在 deferred operation：

```text
beside
beside
beside
```

所以 construction phase：

```text
time  = O(n)
stack = O(n)
```

构造出来的 picture composition 结构也是：

```text
O(n)
```

# 29. 为什么 procedure 作为参数这么重要？

这正好回答你特别要求关注的：

```scheme

```

因为：

```text

参数化 data
```

例如：

```scheme

```

```text

```


# 30. `push` 真正在抽象什么？

不要回答：

> “它抽象了 `beside` 和 `above`。”

这还太浅。

真正抽象的是：

```text
repeated self-similar composition
```

pattern：

```text
P
↓
combine(P,P)
↓
combine(P,
        combine(P,P))
↓
combine(P,
        combine(P,
                combine(P,P)))
```

所以：

```text
right-push
```

只是：

```text
push + beside
```

```text
up-push
```

只是：

```text
push + above
```

这就是 SICP 一再训练你的能力：

> 不要只找重复代码，要找重复的 computational pattern。

# 32. 这就是 “Embedded Language”

# 39. 为什么 Language Levels 比单纯拆函数强？

假设产品说：

> 不要 horizontally push 了，改成 spiral-like arrangement。

```text

→ task B
→ task C
```

需求改变可能：

```text
整个 decomposition tree
```

都受影响。

但 language-oriented design 中：

```text
low-level picture representation
```

不一定改。

你可能只改：

```text
higher-level combination scheme
```

也就是：

```text
change vocabulary expression
```

```text

```

```text
robustness through abstraction
```

# 44. Process Shape 与复杂度

这节不是 complexity lecture，但仍可以分析。

## right-push

```scheme
(right-push p n a)
```

构造过程：

$$
T(n)=T(n-1)+O(1)
$$

因此：

```text
construction time = O(n)
```

递归调用：

```text
space = O(n)
```

最终 picture 包含大约：

```text
n + 1
```

个 primitive occurrences。

所以一次 render：

```text
O(n × primitive-render-cost)
```

---

复杂的 recursive picture：

```text
corner(n)
↓
corner(n-1)
+
corner(n-1)
+
...
```

如果真的形成多个独立 recursive branches：

$$
T(n)=2T(n-1)+O(1)
$$

就可能出现：

```text
O(2^n)
```

的结构或 rendering work。

这里和 Fibonacci tree recursion 的思想是一样的。

不过 3A 的重点不是优化，而是：

```text
让结构能被清楚表达
```

# 50. 你真正应该记住的东西

如果这节只允许你记住 **8 件事**，我会让你记这些：

1. **Picture 不是 bitmap，而是 `Frame → Drawing` 的 procedure。**
    
2. 好的 representation 会让后面的 operation 变得自然；Picture-as-procedure 是整个设计成功的关键。
    
3. `beside / above / rotate` 返回的仍然是 Picture，这就是 **closure property**。
    
4. 因为结果仍然是 Picture，所以复杂结构可以通过简单组合快速生长。
    
5. Higher-order procedure 的核心不是“函数能传函数”，而是 **computation 本身可以被参数化和抽象**。
    
6. `push` 抽象的不是某幅图，而是 **repeated composition pattern**。
    
7. Picture language 是一个 **embedded language / internal DSL**，它自动继承 Lisp 的 recursion、lambda、procedure composition 等能力。
    
8. SICP 真正希望你形成的设计习惯是：
    

```text
遇到复杂问题
不要只问：

“我要写哪些函数？”

而要进一步问：

“什么 vocabulary
会让这个问题变得容易表达？”
```

其中最重要的三个不变量可以压缩成：

```text
Picture consumes a Frame.

Combinators produce Pictures.

Higher layers manipulate lower-layer abstractions,
not their representations.
```
