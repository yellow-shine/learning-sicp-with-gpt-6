# 1. 这节课到底想解决什么问题？

先抓住 Lecture 1B 最重要的一句话：

> **procedure 是你写下来的规则，而 process 是这些规则执行时产生的动态行为。**

Lecture 1A 之后，你已经会写：

```scheme
(define (square x)
  (* x x))

(define (sum-of-squares x y)
  (+ (square x)
     (square y)))
```

你知道：

```scheme
(sum-of-squares 3 4)
```

得到：

```text
25
```

但这还远远不够。

真正的问题是：

```text
你写下来的程序
        ↓
为什么会产生那个结果？
        ↓
执行过程中机器需要记住什么？
        ↓
计算是线性展开？
还是先展开再收缩？
还是形成一棵树？
        ↓
需要多少时间？
需要多少空间？
```

Sussman 在 Lecture 1B 开头明确说，这一讲就是要建立：

```text
procedures / expressions
          ↓
patterns of execution
          ↓
process behavior
```

之间的联系。为此首先引入一个简单的“机械模型”——**substitution model**。他也特别强调，这不是声称真实计算机真的靠文本替换运行，而是一个足够好的工程模型；后面随着语言模型变复杂，会需要更强的模型。

所以 Lecture 1B 的核心不是：

> 怎么写递归。

而是：

> **看到一段程序时，能不能在脑子里预演它会产生什么形状的计算过程？**

这在工程上其实非常熟悉。

你看到：

```go
for ...
```

会想到：

```text
O(n)
constant state
```

看到：

```go
func f(n int) {
    f(n-1)
    ...
}
```

会想到调用栈。

看到：

```text
f(n-1) + f(n-2)
```

应该马上警觉：

```text
branching
duplicate work
exponential tree
```

SICP 在这里训练的，就是这种能力。

# 3. 第一个核心机制：Substitution Model

## 3.1 直觉

假设：

```scheme
(define (square x)
  (* x x))

(define (sum-of-squares x y)
  (+ (square x)
     (square y)))
```

执行：

```scheme
(sum-of-squares 3 4)
```

最朴素的理解就是：

```text
x ← 3
y ← 4

把 procedure body 中的 x、y
换成对应 arguments
```

得到：

```scheme
(+ (square 3)
   (square 4))
```

然后继续。

这就是 substitution model 的核心。

课堂首先用 `sum-of-squares` 建立这个模型。

# 4. Procedure application 到底怎么 evaluate？

这一条最好背成一个运行模型，而不是 Scheme 语法：

```text
combination

(f a b)
 │
 ▼
evaluate operator f
 │
 ├── 得到 procedure
 │
 ▼
evaluate operands a b
 │
 ├── 得到 argument values
 │
 ▼
apply procedure
 │
 ▼
parameters ← arguments
 │
 ▼
evaluate procedure body
```

例如：

```scheme
(sum-of-squares 3 4)
```

---

## 第一步：evaluate operator

```scheme
sum-of-squares
```

查找到：

```scheme
(lambda (x y)
  (+ (square x)
     (square y)))
```

暂时不用关心 procedure 内部真实如何表示。

---

## 第二步：evaluate operands

```scheme
3 → 3
4 → 4
```

所以：

```text
x = 3
y = 4
```

---

## 第三步：apply

procedure body：

```scheme
(+ (square x)
   (square y))
```

代入：

```scheme
(+ (square 3)
   (square 4))
```

---

## 第四步：继续 evaluate operands

先算：

```scheme
(square 3)
```

因为：

```scheme
(define (square x)
  (* x x))
```

所以：

```text
(square 3)

→ (* 3 3)

→ 9
```

另一边：

```text
(square 4)

→ (* 4 4)

→ 16
```

因此：

```text
(+ (square 3) (square 4))

→ (+ 9 16)

→ 25
```

完整过程：

```text
(sum-of-squares 3 4)

↓ substitute

(+ (square 3)
   (square 4))

↓

(+ (* 3 3)
   (* 4 4))

↓

(+ 9 16)

↓

25
```

课堂中特别有一个很 SICP 的观点：

我们把 `*`、`+` 当作 primitives，不继续往下扒开它们。

为什么？

因为：

```text
abstraction 的能力
    =
知道应该忽略哪些细节
```

课堂也正是在这个例子里强调：理解复杂系统的关键之一，是知道哪些层次此刻不必展开。

这其实就是你做 infra 时每天做的事情：

```text
Kubernetes Service
    ↓

你此刻可能只使用：
"给我一个稳定 service abstraction"

而不是：

立即展开
iptables / IPVS
conntrack
routing
NIC
DMA
driver
```

模型不是假的。

模型是：

> **针对当前问题选择合适的抽象层次。**

# 5. Substitution model 不是“计算机真的复制字符串”

这是很容易误解的一点。

SICP 并不是说：

```text
真实 Scheme interpreter
真的不停复制 source code
然后字符串替换
```

而是说：

```text
我们暂时需要一个模型

它能够预测：

程序应该得到什么结果
以及 computation 如何展开
```

这和：

```text
理想气体模型
电阻 V = IR
数据库 cost model
网络排队模型
```

很像。

模型并不需要包含真实系统的所有细节。

只要它对于当前问题：

```text
足够简单
+
预测正确
```

就有价值。

Lecture 1B 开头对此说得非常明确：substitution model 是此阶段理解 procedure 如何产生 process 的最简单模型，而后续会换成更具体的模型。

# 6. 一个隐藏但极重要的问题：`if` 为什么特殊？

普通 procedure application 是：

```text
evaluate operator
evaluate all operands
apply
```

但是：

```scheme
(if predicate
    consequent
    alternative)
```

不是这样。

它是：

```text
evaluate predicate
        │
     ┌──┴──┐
   true   false
    │       │
    ▼       ▼
evaluate  evaluate
consequent alternative
```

**只 evaluate 一个 branch。**

Lecture 1B 在 substitution model 后专门说明了 predicate、consequent、alternative，以及只执行选中分支的规则。

# 7. 为什么 `if` 不能只是普通 procedure？

这是 language design 问题。

假设：

```scheme
(define (my-if predicate then-clause else-clause)
  ...)
```

然后：

```scheme
(my-if (= x 0)
       y
       (recursive-call ...))
```

按照 applicative-order：

```text
调用 my-if 之前
↓
所有 operands 都必须 evaluate
```

于是：

```text
y
```

会 evaluate，

但是：

```text
(recursive-call ...)
```

也会 evaluate。

即使：

```text
x = 0
```

递归仍然发生。

于是 base case 不能真正停止 computation。

所以 `if` 必须有特殊 evaluation rule。

这是 SICP 很重要的一层：

```text
Language construct
不仅决定“代码长什么样”

还决定：
evaluation happens when?
```

也就是说：

> **控制流，本质上是 evaluation rules。**

# 8. Applicative Order vs Normal Order

Lecture 1B 也提到另一种可能的规则：normal-order evaluation。

## Applicative order

Scheme 默认思路：

```text
先求 arguments
再 apply procedure
```

例如：

```scheme
(square (+ 2 3))
```

变成：

```text
(+ 2 3)
↓
5

(square 5)
↓
(* 5 5)
↓
25
```

---

## Normal order

可以想成：

> 先把表达式代进去，需要的时候再算。

于是：

```scheme
(square (+ 2 3))
```

根据：

```scheme
(square x) = (* x x)
```

先变成：

```scheme
(* (+ 2 3)
   (+ 2 3))
```

然后：

```text
(+ 2 3) → 5
(+ 2 3) → 5

(* 5 5)

→ 25
```

注意重复计算了 `(+ 2 3)`。

# 9. 一个能真正看出区别的例子

经典例子：

```scheme
(define (p)
  (p))

(define (test x y)
  (if (= x 0)
      0
      y))
```

执行：

```scheme
(test 0 (p))
```

### Applicative order

先 evaluate operands：

```text
0 → 0

(p)
↓
(p)
↓
(p)
↓
...
```

永不结束。

---

### Normal order

先代入：

```scheme
(if (= 0 0)
    0
    (p))
```

predicate：

```text
#t
```

所以：

```text
→ 0
```

`(p)` 根本没有 evaluate。

因此：

```text
Applicative order
"evaluate arguments first"

Normal order
"evaluate when needed"
```

后面学 lazy evaluation / streams 时，你会重新看到这个思想。

# 10. Lecture 1B 真正的主菜：Procedure ≠ Process

现在进入这一讲最重要的地方。

考虑两个几乎一样的加法程序。

为了避免重定义 Scheme 的 `+`，我换个名字。

第一种：

```scheme
(define (add-i x y)
  (if (= x 0)
      y
      (add-i (- x 1)
             (+ y 1))))
```

第二种：

```scheme
(define (add-r x y)
  (if (= x 0)
      y
      (+ 1
         (add-r (- x 1) y))))
```

它们看起来非常像。

真正区别只有：

```text
第一种：

(add-i (- x 1)
       (+ y 1))

第二种：

(+ 1
   (add-r (- x 1) y))
```

课堂正是用这两个几乎相同的程序来展示：

> **很小的代码结构差异，可以制造完全不同形状的 process。**

# 11. 第一个过程：Linear Iteration

执行：

```scheme
(add-i 3 4)
```

展开：

```text
(add-i 3 4)

↓
(add-i 2 5)

↓
(add-i 1 6)

↓
(add-i 0 7)

↓
7
```

重点不是结果 7。

重点看 **shape**：

```text
(3,4)
 ↓
(2,5)
 ↓
(1,6)
 ↓
(0,7)
 ↓
  7
```

没有东西先“挂起来”。

每一步：

```text
旧 state
    ↓
计算 next state
    ↓
忘掉旧 state
```

# 12. 什么叫“process state 完全在变量里”？

在：

```scheme
(add-i x y)
```

这个计算的任何时刻，

只要你告诉我：

```text
x = ?
y = ?
```

我就能继续整个 computation。

比如中间状态：

```text
x = 1
y = 6
```

我完全不需要知道：

```text
最开始是不是 (3,4)
```

因为：

```text
(1,6)
```

本身已经编码了继续计算所需的全部信息。

Sussman 在讲座中把这个作为 iteration 的本质：**继续 computation 所需的状态全部显式地保存在程序变量中**。

所以 mental model 是：

```text
Iterative Process

state
(x, y)

 ↓ transition

(x-1, y+1)

 ↓ transition

...

直到 terminal state
```

这其实已经很像：

```text
state machine
```

了。

---

# 13. 注意：这里的“state”还不是 mutable state

这是一个极其重要的 SICP 伏笔。

我们写：

```scheme
(add-i 3 4)
→
(add-i 2 5)
```

并不是：

```scheme
(set! x 2)
(set! y 5)
```

实际上这里仍然可以是纯函数。

每次 recursive call：

```text
产生新的参数绑定
```

而不是修改旧变量。

所以：

```text
Lecture 1B 的 state
=
描述 process 所需的 mathematical state

不是

Lecture 5A 的 mutable state / assignment
```

千万不要把这两种“state”混在一起。

# 14. Linear Iteration 的复杂度

每次：

```text
x → x - 1
```

直到 0。

因此：

```text
T(x) = T(x-1) + Θ(1)

=> T(x) = Θ(x)
```

time：

```text
Θ(x)
```

而 process state 始终只有：

```text
x
y
```

所以 conceptual space：

```text
Θ(1)
```

这就是：

```text
linear iterative process
```

# 15. 第二个过程：Linear Recursion

再看：

```scheme
(define (add-r x y)
  (if (= x 0)
      y
      (+ 1
         (add-r (- x 1) y))))
```

执行：

```scheme
(add-r 3 4)
```

---

## 展开阶段

```text
(add-r 3 4)

↓

(+ 1
   (add-r 2 4))

↓

(+ 1
   (+ 1
      (add-r 1 4)))

↓

(+ 1
   (+ 1
      (+ 1
         (add-r 0 4))))
```

此时：

```scheme
(add-r 0 4)
```

得到：

```text
4
```

---

## 收缩阶段

```text
(+ 1
   (+ 1
      (+ 1 4)))

↓

(+ 1
   (+ 1 5))

↓

(+ 1 6)

↓

7
```

Process shape：

```text
grow

(+ 1 ...)
(+ 1 (+ 1 ...))
(+ 1 (+ 1 (+ 1 ...)))

        ↓

shrink

(+ 1 (+ 1 5))
(+ 1 6)
7
```

Lecture 1B 特别强调这些待做的 increment 是 **deferred operations**：计算机必须记住“回来之后还要 +1”。

# 16. 什么叫 Deferred Operation？

这一点是 recursive process 的灵魂。

当你来到：

```scheme
(add-r 1 4)
```

你不能只说：

```text
当前状态是 (1,4)
```

因为还缺少信息：

```text
外面还有两个 +1 等着做。
```

也就是：

```text
(+ 1
   (+ 1
      [current computation]))
```

这部分信息不在：

```text
x
y
```

里面。

它必须由计算机器替你记住。

概念上就是：

```text
continuation / call stack / pending work
```

所以：

```text
recursive process
=
explicit variables
+
implicit deferred work
```

而：

```text
iterative process
=
state entirely captured explicitly
```

这就是 SICP 对两者最深刻的区分。

---

# 17. Linear Recursion 的复杂度

调用深度：

```text
x
```

每层需要记一个：

```text
+1
```

因此：

```text
time = Θ(x)
space = Θ(x)
```

对比：

||Linear iteration|Linear recursion|
|---|--:|--:|
|Time|Θ(n)|Θ(n)|
|Space|Θ(1)|Θ(n)|
|Deferred operations|无|有|
|State|全在参数里|参数 + 隐式 context|
|Process shape|一条状态链|展开再收缩|

课堂就是通过 process 图的“宽度/未完成工作”来解释 space，以及通过步骤数量理解 time。

# 18. 最大误区：Recursive Procedure ≠ Recursive Process

这是这一讲最值得牢牢记住的一句话。

前面的：

```scheme
(define (add-i x y)
  ...
  (add-i ...))
```

显然它自己调用自己。

所以：

```text
它是 recursive procedure
```

但是它产生的是：

```text
iterative process
```

而：

```scheme
(define (add-r x y)
  ...
  (+ 1 (add-r ...)))
```

也是：

```text
recursive procedure
```

但产生：

```text
recursive process
```

Sussman 在 Lecture 1B 直接强调：两个定义都是 recursive definitions，但它们产生不同 shape 的 process；**定义是递归的，并不意味着 process 就一定是 recursive process。**

所以你应该建立这张表：

```text
Procedure
= source-code structure

Process
= runtime evolution
```

不要把：

```text
“代码里调用自己”
```

和：

```text
“运行时必须保留未完成调用”
```

混在一起。

# 19. 为什么第一种是 Iterative Process？

看：

```scheme
(add-i (- x 1)
       (+ y 1))
```

recursive call 是 procedure 最后需要完成的事情。

调用完成后：

```text
没有额外工作
```

也就是：

```text
return (add-i ...)
```

不需要：

```text
result = add-i(...)
然后再 +1
```

这种位置就是：

```text
tail position
```

所以：

```text
tail-recursive procedure
          ↓
proper tail-call execution
          ↓
iterative process
```

# 20. 这和现代语言有一个巨大差别

在 Scheme 的计算模型里：

```scheme
(define (loop x ...)
  ...
  (loop next-x ...))
```

可以产生 constant-space iterative process。

但是千万不要机械搬到所有语言：

```python
def loop(x):
    return loop(x - 1)
```

Python：

```text
仍然增长 Python stack
```

Go：

```go
func loop(x int) int {
    return loop(x - 1)
}
```

也不能依据 SICP 模型就声称：

```text
O(1) stack
```

Java / C++ / Rust 也没有普遍保证这种尾调用优化。

所以现代语言对应关系应该是：

```text
SICP concept:
iterative process

Scheme:
tail recursion 可以表达

Go / Java / Python:
通常写 loop 更直接
```

注意这进一步说明：

> **procedure syntax 和 process implementation 是两个层次的问题。**

# 21. 两段程序为什么只移动一个 `+1`，process 就彻底变了？

对比：

```scheme
(add-i (- x 1)
       (+ y 1))
```

vs

```scheme
(+ 1
   (add-r (- x 1) y))
```

第一种：

```text
先做 +1
把结果放进下一状态
再递归

当前层没有后续工作
```

第二种：

```text
先递归
然后才能 +1

因此必须记住：
“回来之后我要 +1”
```

于是一个小小的表达式位置变化：

```text
before recursive call

vs

after recursive call
```

改变了：

```text
memory requirement
process shape
control structure
```

这就是 Lecture 1B 想让你形成的“程序视觉”。

看到：

```scheme
(f (recursive-call ...))
```

应该问：

```text
f 能现在执行吗？

不能。

那就意味着：
必须保存 f 作为 deferred work。
```

# 22. 一个特别好用的判断规则

以后看到：

```scheme
(define (foo ...)
  ...
  (foo next-state))
```

如果 recursive call 后面：

```text
nothing remains
```

倾向于：

```text
iterative process
```

如果看到：

```scheme
(combine something
         (foo smaller-problem))
```

那么：

```text
combine 还做不了
↓
必须等 recursive result
↓
形成 deferred operation
↓
recursive process
```

这是一眼看 process shape 的方法。

# 23. Lecture 1B 的第二种 process shape：Tree Recursion

现在看 Fibonacci：

```scheme
(define (fib n)
  (if (< n 2)
      n
      (+ (fib (- n 1))
         (fib (- n 2)))))
```

这是一个非常自然的程序。

因为 Fibonacci 的数学定义就是：

```text
Fib(n)

= n                     n < 2

= Fib(n-1) + Fib(n-2)   otherwise
```

代码几乎就是数学定义。

这说明：

```text
程序可以非常漂亮地表达 specification
```

但是：

> specification 简洁 ≠ process 高效。

这正是 SICP 想展示的。

课堂用 `fib 4` 展开这棵树，并指出其中重复计算会导致指数级时间。

# 24. 手工展开 `(fib 4)`

```text
fib(4)
├── fib(3)
│   ├── fib(2)
│   │   ├── fib(1)
│   │   └── fib(0)
│   └── fib(1)
└── fib(2)
    ├── fib(1)
    └── fib(0)
```

观察：

```text
fib(2)
```

被计算了：

```text
两次
```

当 n 增大：

```text
fib(n-2)
fib(n-3)
fib(n-4)
...
```

都会反复计算。

# 25. 为什么叫 Tree Recursion？

因为每个非 base node：

```text
fib(n)
```

会产生：

```text
two children
```

```text
        fib(n)
        /    \
 fib(n-1)   fib(n-2)
```

而这些 child 又继续展开：

```text
          fib(n)
        /        \
   fib(n-1)     fib(n-2)
    /    \       /    \
   ...   ...    ...   ...
```

所以 process 不是：

```text
line
```

而是：

```text
tree
```

---

# 26. Fibonacci 的 Time Complexity

递推：

$$
T(n)=T(n-1)+T(n-2)+\Theta(1)
$$

增长与 Fibonacci 数列同阶：

$$
T(n)=\Theta(\varphi^n)
$$

其中：

$$
\varphi=\frac{1+\sqrt5}{2}\approx1.618
$$

所以：

```text
time = exponential
```

课堂也是通过 recursion tree 的节点数量说明其指数增长。

---

# 27. 但 Fibonacci 的 Space 为什么不是指数？

这是很容易答错的。

虽然整个树有指数多个节点：

```text
          *
        /   \
       *     *
      / \   / \
```

但程序不是同时保存整棵树。

它大致是 DFS：

```text
沿一个 branch 往下
↓
回来
↓
再走另一个 branch
```

因此同时活跃的调用最多等于：

```text
tree depth
```

而 depth：

```text
≈ n
```

所以：

```text
time  = Θ(φ^n)
space = Θ(n)
```

Lecture 1B 正是用“只需要记住通往 root 的路径”解释 Fibonacci 的 linear space。

---

# 28. 这是分析 recursion 最重要的方法之一

不要问：

> recursion tree 有多少节点，所以 memory 就是多少？

错误。

应该区分：

```text
总共执行多少 node？
        ↓
TIME

同一时刻最大有多少 node 活着？
        ↓
SPACE
```

因此：

```text
Tree size
≈ time

Tree depth
≈ stack space
```

对于这个 DFS 风格的 Fibonacci：

```text
tree size = exponential

tree depth = linear
```

---

# 29. Tree Recursion 暴露出的真正问题：Repeated Work

问题不是：

```text
recursion 本身不好
```

而是：

```text
相同 subproblem
被重复求值
```

例如：

```text
fib(5)

里面计算 fib(3)

fib(4)
里面也计算 fib(3)
```

如果我们：

```text
记住已经算过的 fib(k)
```

就变成：

```text
memoization
```

Lecture 1B 后面的问答也直接提到：缓存已经算出的 Fibonacci 可以避免展开重复的指数树，并进一步指出也存在简单的线性 iterative Fibonacci 方法。

这就是后来的：

```text
Dynamic Programming
Memoization
```

的基本动机。

# 30. 甚至可以把 Fib 改成 Iterative Process

我们维护：

```text
a = Fib(k)

```

不断做状态转换：

```text

   ↓

```

例如：

```text

```

Scheme：

现在：

```text

```

conceptually。

```text
same mathematical function

Fibonacci

↓ can be represented by

```

# 34. Recursive Thinking 的核心：Wishful Thinking

这是 Lecture 1B 一个非常漂亮的思想。

假设：

```text
我已经会解决规模 n-1 的问题。
```

不要问：

> 可是我明明还不会啊？

先相信它。

如果要：

```text
move n disks
A → B
using C
```

那么：

### Step 1

让一个“神奇的 procedure”：

```text
move n-1

A → C

using B
```

结果：

```text
最大盘留在 A
其他盘都到了 C
```

### Step 2

移动最大盘：

```text
A → B
```

### Step 3

再让那个 procedure：

```text
move n-1

C → B

using A
```

完成。

# 35. 为什么这种“假装已经会了”不是循环论证？

因为：

```text
problem size decreases
```

```text
n
↓
n-1
↓
n-2
↓
...
↓
0
```

最终：

```text
n = 0
```

有明确 base case：

```text
什么都不用做
```

因此递归链一定落地。

这就是递归设计的核心证明结构：

```text
Base Case

+
假定 smaller problem 可解

+
证明 current problem
可以由 smaller problem 构造出来
```

非常接近 mathematical induction。

Lecture 1B 甚至把这种递归设计方法直接描述成“wishful thinking”：假设你已经能解决更小的问题，因为规模一直下降，最终会到达 trivial case。

# 36. Hanoi 代码

概念上：

```scheme
(define (move n from to spare)
  (if (= n 0)
      'done
      (begin
        (move (- n 1)
              from spare to)

        (print-move from to)

        (move (- n 1)
              spare to from))))
```

先不要被：

```scheme
begin
print-move
```

吸走注意力。

核心 structure 是：

```text
move(n)

├─ move(n-1)
│
├─ one move
│
└─ move(n-1)
```

---

# 37. Hanoi 的 process shape

递推式：

$$
T(n)=2T(n-1)+1
$$

因为：

```text
一个 n 问题

=
两个 n-1 问题
+
一次 disk move
```

展开：

$$
T(n) =2T(n-1)+1 =2(2T(n-2)+1)+1 =4T(n-2)+3
$$

最终：

$$
T(n)=2^n-1
$$

因此：

```text
time = Θ(2^n)
```

调用深度：

```text
n
```

所以：

```text
recursive stack = Θ(n)
```

而且 Hanoi 和 Fib 还有一个关键区别：

```text
Fib:
指数时间主要来自重复做无用工作
→ 可以优化

Hanoi:
本身就必须输出 2^n - 1 个 moves
→ exponential work 是问题本身要求的
```

课堂也指出 Hanoi 在这些规则下本身需要指数数量的 moves。

# 38. Fibonacci vs Hanoi：非常值得比较

```text
Fibonacci

fib(n)
├─ fib(n-1)
└─ fib(n-2)

看起来 tree recursive
↓
但很多子问题重复
↓
可以 memoize / iterate
↓
O(n)
```

而：

```text
Hanoi

move(n)
├─ move(n-1)
├─ move largest disk
└─ move(n-1)

看起来也是 tree recursive
↓
但这些 moves 都真的需要发生
↓
最少 2^n - 1 moves
```

所以：

> **看到 recursion tree 是第一步；然后还必须判断这些 tree nodes 是必要工作还是重复工作。**

这是很成熟的算法 mental model。

# 39. Procedure vs Process

现在正式把最核心的一对概念拆开。

## Procedure

是：

```text
一组 computation rules
```

例如：

```scheme
(define (fib n)
  ...)
```

它是一个程序对象。

---

## Process

是：

```text
procedure 在某个 input 上运行时
产生的动态 computation
```

例如：

```text
(fib 5)
```

产生：

```text
一棵 computation tree
```

所以：

```text
procedure
   ↓
input
   ↓
evaluation
   ↓
process
```

不要把它理解成：

```text
function = process
```

# 40. Recursive Procedure vs Recursive Process

这是考试级重点。

### Recursive procedure

判断代码：

```text
definition 是否直接/间接调用自身？
```

### Recursive process

判断运行过程：

```text
是否积累 deferred operations？
```

因此：

```scheme
(define (f x state)
  (if ...
      state
      (f (- x 1)
         (next state))))
```

是：

```text
recursive procedure
iterative process
```

而：

```scheme
(define (f x)
  (if ...
      ...
      (combine
        x
        (f (- x 1)))))
```

通常是：

```text
recursive procedure
recursive process
```

# 45. 这一节的几个核心 Pattern

## Pattern 1：State-transition iteration

```scheme
(define (iter state)
  (if (done? state)
      (result state)
      (iter (next-state state))))
```

Mental model：

```text
state₀
↓ next
state₁
↓ next
state₂
↓
...
```

看到这种代码问：

> 当前参数是否包含继续 computation 所需的全部信息？

如果是，很可能是 iterative process。

---

## Pattern 2：Linear recursive decomposition

```scheme
(define (f x)
  (if (base? x)
      base-value
      (combine x
               (f (smaller x)))))
```

Mental model：

```text
f(n)

↓ defer combine

combine(n,
  f(n-1))

↓ defer combine

combine(n,
  combine(n-1,
    f(n-2)))
```

关键词：

```text
deferred computation
```

---

## Pattern 3：Tree recursion

```scheme
(define (f x)
  (if (base? x)
      ...
      (combine
        (f (left x))
        (f (right x)))))
```

Mental model：

```text
              f(x)
            /      \
        f(left)   f(right)
```

看到这种 pattern 马上问：

```text
subproblems 是否 overlap？
```

如果 overlap：

```text
memoization / DP
```

很可能有价值。

---

## Pattern 4：Wishful Thinking

设计 recursive procedure 时：

```text
不要先尝试模拟所有 recursive calls。
```

而是：

```text
假设：

solve(smaller-problem)

已经正确工作

问：

如何利用这个答案
构造 solve(current-problem)？
```

这也是今天写：

```text
DFS
tree algorithms
divide-and-conquer
dynamic programming recurrence
```

最重要的思维方式之一。

# 47. 为什么“递归”是一种 abstraction？

很多人觉得递归只是：

```text

```

这是最低层理解。


例如 Hanoi：


```text

n-2
n-3
...
```

否则你其实破坏了 abstraction。

正确 mental model：

```text
"Assume move works."

Use it as black box.
```

这跟你调用：

```go

```

一样。

你不会为了正确使用它，每次都把：

```text

TCP
TLS

syscall
```

全部展开。

递归调用自己的 procedure，并不意味着你不能把它自己当 abstraction。

# 51. 一组最重要的概念辨析

### Procedure vs Process

```text
Procedure
= rules / source-level abstraction

Process
= execution produced by those rules
```

---

### Recursive procedure vs Recursive process

```text
Recursive procedure
= definition invokes itself

Recursive process
= execution retains deferred work
```

不是同一回事。

---

### Linear recursion vs linear iteration

```text
linear recursion

state:
parameters
+
implicit pending work

space Θ(n)
```

```text
linear iteration

state:
explicit parameters only

space Θ(1)
```

在支持 proper tail calls 的模型下。

---

### Tree recursion vs linear recursion

Linear：

```text
每个问题
产生一个 smaller problem
```

Tree：

```text
每个问题
产生多个 smaller problems
```

---

### Applicative vs normal order

```text
Applicative:
arguments → evaluate → apply

Normal:
substitute first → evaluate when required
```

---

### Process state vs mutable state

```text
Lecture 1B:
state = 描述 computation 的参数

Lecture 5:
state = 可随时间 mutation 的对象状态
```

非常不同。

# 52. 常见误区

### 误区 1

> 只要函数调用自己，就是 recursive process。

错。

```scheme
(add-i ...)
```

调用自身，却产生 iterative process。

判断关键：

```text
有没有 deferred operations？
```

---

### 误区 2

> Tail recursion 只是写法优化。

不只是。

它代表：

```text
整个 future computation
已经被编码进参数
```

这是 process representation 的变化。

---

### 误区 3

> Fibonacci 的 recursion tree 有指数节点，所以 memory 也是指数。

错。

```text
time → tree total nodes
space → longest active path
```

因此 naive Fibonacci：

```text
time exponential
space linear
```

---

### 误区 4

> 递归一定比 iteration 慢。

不成立。

这是两个不同问题：

```text
process structure
```

和：

```text
具体 machine implementation
```

不能混为一谈。

---

### 误区 5

> Recursive Fibonacci 很差，所以 recursion 很差。

错误。

真正的问题是：

```text
overlapping subproblems
```

不是 recursion 本身。

---

### 误区 6

> substitution model 是 Scheme interpreter 的真实实现。

不是。

它是：

```text
reasoning model
```

---

### 误区 7

> `if` 本质就是普通 function。

不是。

它有特殊 evaluation rule：

```text
只 evaluate selected branch
```

这正是它能够表达控制流的重要原因。

---

### 误区 8

> Iterative process 中 x、y 在不断 mutation。

不一定。

在纯 Scheme 里：

```text
每次递归调用产生新的 bindings
```

“process state 更新”不等于语言级 mutation。

# 56. 你真正应该记住的东西

如果整节 Lecture 1B 最终只留下几个东西，我希望是这些。

### 核心思想

1. **Procedure 与 Process 是两个不同层次。**
    

```text
procedure = rule
process = rule running
```

2. **程序员真正控制的是 process，而不只是 source code。**
    
3. **非常相似的 procedure 可以产生完全不同形状的 process。**
    
4. **Recursive reasoning 是 abstraction：假设 smaller problem 已经解决。**
    
5. **Complexity 来自 process shape。**
    

### 关键机制

6. Procedure application：
    

```text
evaluate operator
→ evaluate operands
→ apply
→ evaluate body
```

7. Substitution model 是当前阶段用于 reasoning 的简化计算模型。
    
8. Iterative process：
    

```text
全部 future state
都显式编码在 variables 中
```

9. Recursive process：
    

```text
还有 deferred operations
必须由机器保存
```

10. Tree recursion 要立刻检查：
    

```text
是否有 repeated subproblems？
```

### 最重要的不变量

第一个：

```text
Recursive procedure
≠
Recursive process
```

第二个：

```text
Time ≈ total work

Space ≈ maximum simultaneously-live computation
```

第三个：

```text
如果仅凭当前 parameters
就能完整恢复 computation，

你看到的很可能是 iterative process。
```
