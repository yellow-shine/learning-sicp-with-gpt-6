# Lecture 9B — Explicit-Control Evaluator

这节课可以看成 SICP 整门课里一个非常重要的“**揭底**”时刻。

从 Lecture 1 开始，我们一直在说：

```text
evaluate expression
apply procedure
create environment
return result
```

但直到 9B，SICP 才真正逼你回答：

> **“return” 到底是什么？**
> 
> **递归调用时，到底保存了什么？**
> 
> **解释器怎么知道算完一个子表达式以后该回哪里？**
> 
> **为什么尾递归真的可以 O(1) stack？**
> 
> **eval/apply 如果不允许依赖另一个高级语言的函数调用机制，该怎么实现？**

MIT 官方将 Lecture 9B 明确列为 **Explicit-control Evaluator**；对应 SICP §5.4。这里把之前的 metacircular evaluator 转换成 register machine，使 procedure calling、argument passing、return/control 都落实为寄存器、stack 和 jump。([MIT OpenCourseWare](https://ocw.mit.edu/courses/6-001-structure-and-interpretation-of-computer-programs-spring-2005/resources/9b-explicit-control-evaluator/?utm_source=chatgpt.com "9B: Explicit-control Evaluator | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

# 1. 这节课到底想解决什么问题？

## 1.1 7A/7B 的 `eval/apply` 其实还藏着一只“乌龟”

你在 7A/7B 见过大致这样的 evaluator：

```scheme
(define (eval exp env)
  (cond
    ((self-evaluating? exp) exp)
    ((variable? exp)
     (lookup-variable-value exp env))
    ((if? exp) ...)
    ((lambda? exp) ...)
    ((application? exp)
     (apply
       (eval (operator exp) env)
       (list-of-values (operands exp) env)))))
```

它已经非常漂亮地解释：

```text
Scheme expression
       ↓
classify syntax
       ↓
eval
       ↓
apply
       ↓
environment
```

可是仔细看：

```scheme
(eval ...)
```

里面居然又调用：

```scheme
(eval ...)
```

于是问题来了。

当内部 `eval` 完成以后：

> 它怎么知道回到哪里？

例如：

```scheme
(+ 1 (* 2 3))
```

解释器需要：

```text
evaluate +
evaluate 1
evaluate (* 2 3)
    evaluate *
    evaluate 2
    evaluate 3
    apply *
return
apply +
```

这里有很多：

```text
“先暂停这里”
“去做另一件事情”
“做完回来继续”
```

Metacircular evaluator 的答案实际上是：

> 让底层 Scheme 帮我处理。

宿主 Scheme 帮你维护：

```text
function call
return address
temporary variables
call stack
recursive invocation
```

因此 metacircular evaluator **说明了语言语义，却没有完全说明机器怎样执行这种语义**。

---

# 1.2 9B 要消除这个隐藏层

现在 SICP 问：

> 假设我们没有一个现成的 Scheme procedure-call mechanism 可以依赖呢？

只有 9A 的机器：

```text
registers
stack
assign
test
branch
goto
save
restore
```

能不能实现：

```scheme
(eval exp env)
```

？

答案就是 **Explicit-Control Evaluator**。

这里所谓 explicit control，就是：

以前：

```scheme
(eval operand env)
```

这一行背后的控制流由 Scheme runtime 管。

现在变成：

```text
save what I will need later
put operand in exp
put return address in continue
goto eval-dispatch
```

程序的“下一步去哪里”第一次完全暴露出来。

SICP 对 §5.4 的描述非常直接：显式控制 evaluator 把 underlying procedure-calling 和 argument-passing mechanisms 表示为 registers 与 stack 上的操作。([SICP Source Academy](https://sicp.sourceacademy.org/chapters/5.4.html "5.4  The Explicit-Control Evaluator - SICP Comparison Edition"))

# 3. 先抓住整个 evaluator 最重要的不变量

这一条值得你直接记住。

进入：

```text
eval-dispatch
```

时：

```text
exp      = 我要计算什么 expression
env      = 在哪个 environment 中计算
continue = 算完以后去哪里
```

离开 evaluation 时：

```text
val      = 计算结果
PC       = continue 指定的位置
```

所以可以把整个 evaluator 想象成这个抽象接口：

```text
eval(exp, env, continue)
       ↓
 eventually
       ↓
val = result
goto continue
```

只不过这里已经没有真正的：

```scheme
(eval exp env)
```

procedure call 了。

它变成机器协议：

```text
exp ← ...
env ← ...
continue ← return-label
goto eval-dispatch
```

这是本节最重要的 mental model。

---

# 4. 七个关键寄存器到底在干什么？

经典 Explicit-Control Evaluator 使用这些核心寄存器：`exp env val continue proc argl unev`；`continue` 用来实现递归，而 application 还需要 `proc / argl / unev` 等寄存器。([SICP Source Academy](https://sicp.sourceacademy.org/chapters/5.4.html "5.4  The Explicit-Control Evaluator - SICP Comparison Edition"))

可以把它们理解成：

|Register|含义|类似现代 runtime|
|---|---|---|
|`exp`|当前正在 evaluation 的 expression|AST/current instruction|
|`env`|当前 lexical environment|environment/frame pointer|
|`val`|最近一次 evaluation 的结果|return-value register|
|`continue`|算完后去哪里|return address|
|`proc`|application 中 operator 的值|callee|
|`argl`|已计算好的 arguments|argument array/registers|
|`unev`|尚未 evaluation 的 expressions|pending work|

其中最关键的不是 `exp`。

而是：

```text
continue
```

因为它回答了：

> **“回来”到底是什么？**

---

# 5. `continue`：把函数调用的“返回”变成数据

假设我们需要计算：

```scheme
(* 2 3)
```

高级语言看起来是：

```text
eval operator
eval operands
apply
return
```

但机器没有神奇的“return”。

所以我们做：

```text
continue ← ev-appl-did-operator
goto eval-dispatch
```

含义是：

```text
请 eval-dispatch 去计算 operator。

计算完以后：
    val 放结果
    然后跳到 ev-appl-did-operator
```

于是：

```text
return
```

其实可以重新理解为：

> **jump to saved continuation**。

这件事极其重要。

---

# 6. 但一个 `continue` register 为什么不够？

考虑：

```scheme
(+ 1 (* 2 3))
```

外层可能有：

```text
continue = print-result
```

但开始计算内层 operand：

```scheme
(* 2 3)
```

又需要：

```text
continue = ev-appl-accumulate-arg
```

原来的：

```text
print-result
```

怎么办？

保存到 stack：

```text
save continue
...
continue ← ev-appl-accumulate-arg
goto eval-dispatch
```

回来：

```text
restore continue
```

因此：

```text
continue register
        +
stack
```

共同实现嵌套 procedure invocation。

可以理解成：

```text
continue = 当前 return address

stack = 暂时不用、但以后仍然需要的旧 return addresses
        + environments
        + unevaluated operands
        + accumulated arguments
        + ...
```

这实际上已经非常接近真正机器的 calling convention 了。

# 7. `eval-dispatch`：把 `eval` 从 recursion 变成 state machine

Metacircular evaluator：

```scheme
(define (eval exp env)
  (cond
    ((self-evaluating? exp) ...)
    ((variable? exp) ...)
    ((quoted? exp) ...)
    ((assignment? exp) ...)
    ((definition? exp) ...)
    ((if? exp) ...)
    ((lambda? exp) ...)
    ((application? exp) ...)))
```

Explicit-Control Evaluator 则大致变成：

```text
eval-dispatch

test self-evaluating?
branch ev-self-eval

test variable?
branch ev-variable

test quoted?
branch ev-quoted

test assignment?
branch ev-assignment

test definition?
branch ev-definition

test if?
branch ev-if

test lambda?
branch ev-lambda

test application?
branch ev-application
```

SICP 明确指出，这个 `eval-dispatch` 就对应 metacircular evaluator 的 `eval`。([SICP Source Academy](https://sicp.sourceacademy.org/chapters/5.4.1.html "sicp.sourceacademy.org"))

区别非常值得注意：

```text
Metacircular evaluator

eval(...)
  ↓
cond
  ↓
call eval(...)
```

变成：

```text
Explicit-control evaluator

eval-dispatch:
  ↓
test
  ↓
branch
  ↓
assign registers
  ↓
goto eval-dispatch
```

# 8. 简单 expression 怎么 evaluation？

例如：

```scheme
42
```

进入：

```text
exp = 42
env = E
continue = K
```

`eval-dispatch`：

```text
self-evaluating? → yes
```

然后：

```text
val ← exp
goto continue
```

也就是：

```text
val = 42
goto K
```

变量：

```scheme
x
```

就是：

```text
val ← lookup-variable-value(exp, env)
goto continue
```

lambda：

```scheme
(lambda (x) (* x x))
```

不是执行 body。

而是生成：

```text
procedure =
    parameters: (x)
    body: ((* x x))
    environment: current env
```

然后：

```text
val ← procedure
goto continue
```

因此 Lecture 5/7 里的 closure 在这里仍然存在：

```text
procedure
   =
code/body
+
defining environment
```

# 10. 为什么先 evaluate operator？

application 的语义是：

```text
(operator operand1 operand2 ...)
```

首先必须知道：

```text
operator evaluates to what procedure?
```

所以对于：

```scheme
(square (+ 1 2))
```

先计算：

```scheme
square
```

# 11. 但我们不能忘记 operand

当前：

```text
exp = (square (+ 1 2))
```

马上要覆盖为：

```text
exp = square
```

那么：

```scheme
(+ 1 2)
```

放哪里？

答案：

```text
unev
```

并且之后还要用原 environment。

所以 machine 做：

```text
save continue
save env

unev ← operands(exp)
save unev

exp ← operator(exp)

continue ← ev-appl-did-operator

goto eval-dispatch
```

SICP 的 application controller 正是在这里显式保存 `continue/env/unev`，然后跳回 `eval-dispatch`；这就是原来 metacircular evaluator 中 recursive `eval` call 的机器级展开。([SICP Source Academy](https://sicp.sourceacademy.org/chapters/5.4.1.html "sicp.sourceacademy.org"))

现在：

```text
exp = square
env = GE
continue = ev-appl-did-operator
```

`square` 是 variable：

```text
lookup square in GE
```

得到：

```text
val =
compound procedure
(parameters (x)
 body ((* x x))
 env GE)
```

然后：

```text
goto continue
```

即：

```scheme
(+ 1 2)
```

# 15. `apply-dispatch`：另一半 evaluator

7A/7B 有：

```scheme
eval

```

```text
eval-dispatch

```

`apply-dispatch` 问：

```text
proc 是什么类型？
```

```text

```

SICP 的 `apply-dispatch` 正是按这两个 case 分流。([SICP Source Academy](https://sicp.sourceacademy.org/chapters/5.4.1.html "sicp.sourceacademy.org"))

# 16. Primitive Procedure

比如：

```scheme
(+ 1 2)
```

到这里：

```text
proc = primitive +
argl = (1 2)
```

所以：

```text
val ← apply-primitive-procedure(proc, argl)
```

得到：

```text
val = 3
```

然后：

```text

goto continue
```

---

# 17. Compound Procedure

`square` 则不同。

当前：

```text
proc =
  params: (x)
  body: ((* x x))
  captured-env: GE

argl = (3)
```

要创建：

```text
E1
│
├── x = 3
│
└── parent → GE
```

也就是：

```text
env ← extend-environment(
          parameters(proc),
          argl,
          procedure-environment(proc))
```

然后：

```text
unev ← procedure-body(proc)
goto ev-sequence
```

SICP 特别强调，compound application 使用 **procedure 自己捕获的 environment** 加上 parameter→argument bindings 创建新 environment。([SICP Source Academy](https://sicp.sourceacademy.org/chapters/5.4.1.html "sicp.sourceacademy.org"))

这正是 lexical scope。

# 18. 这里终于能真正看见 lexical scope

很多人背：

> closure = code + environment

9B 让这个东西变得机械化。

```scheme
(define (make-adder x)
  (lambda (y)
    (+ x y)))
```

调用：

```scheme
(define add5 (make-adder 5))
(add5 3)
```

`add5` 内部保存：

```text
procedure
│
├── params: y
├── body: (+ x y)
│
└── env ──→ E1
           x = 5
           parent = GE
```

调用：

```text
(add5 3)
```

不会：

```text
extend current caller environment
```

而是：

```text
extend procedure-environment(add5)
```

形成：

```text
E2
y = 3
parent → E1
         x = 5
```

所以：

```text
(+ x y)
→ (+ 5 3)
→ 8
```

这是 environment model 在机器层面的落实。

## Stack

回答：

> **当前计算暂停以后，我需要回来继续什么？**

保存：


# 20. `if` 为什么不能当普通 procedure？

例如：

```scheme
(if (> x 0)
    (/ 1 x)
    0)
```

如果普通 application 都是：

```text
evaluate all operands
then apply
```

那你会同时 evaluation：

```scheme
(/ 1 x)
```

和：

```scheme
0
```

这显然不对。

所以 `if` 是 special form。

---

# 21. Explicit evaluator 如何实现 `if`

假设：

```text
exp = (if (> x 0) (/ 1 x) 0)
```

需要先记住整个 `if`：

```text
save exp
save env
save continue
```

然后：

```text
exp ← predicate(exp)

continue ← ev-if-decide

goto eval-dispatch
```

得到 predicate value：

```text
val = #t / #f
```

回来：

```text
restore continue
restore env
restore exp
```

然后只选择：

```text
consequent
```

或者：

```text
alternative
```

再次：

```text
goto eval-dispatch
```

这里你开始看到：

> **Language semantics 最终就是 control-flow decisions。**

“`if` 是 special form”不再只是语法规则。

它意味着 machine 在 evaluation strategy 上走不同路径。

# 22. `ev-sequence` 与 procedure body

procedure body 可能是：

```scheme
(lambda (x)
  (display x)
  (+ x 1)
  (* x 2))
```

body 是一个 sequence：

```text
(display x)
(+ x 1)
(* x 2)
```

前两个 expression：

```text
evaluate
discard result
continue next
```

最后一个：

```text
evaluate
its result = whole sequence's result
```

看起来只是一个小细节。

实际上它引出了 9B 最重要的思想之一：

# Tail Recursion

# 23. 为什么最后一个 expression 要特殊处理？

假设 procedure body：

```scheme
(expr1)
(expr2)
(expr3)
```

普通实现可能：

```text
save env
save unev
set continue = sequence-continue
eval expr1
return
restore
...
```

对于最后一个 `expr3`，你也可以这样干：

```text
save ...
continue = sequence-finished
eval expr3
return
sequence-finished:
restore ...
goto original-continuation
```

语义结果完全正确。

但是多了一件没意义的事情：

```text
eval expr3
   ↓
回来
   ↓
只是为了马上再 return
```

为什么不直接让：

```text
expr3
```

使用 caller 原来的 continuation？

也就是：

```text
restore original continue
goto eval-dispatch
```

而不是：

```text
continue ← come-back-here-first
goto eval-dispatch
```

SICP 的 explicit evaluator 正是这么做：对于 sequence 的最后一个 expression，它先恢复原 continuation，再直接跳进 evaluator，因此最后一个 expression 不产生额外待完成的控制工作。([SICP Source Academy](https://sicp.sourceacademy.org/chapters/5.4.2.html "sicp.sourceacademy.org"))

# 24. 这就是 Tail Call

假设：

```scheme
(define (count n)
  (display n)
  (count (+ n 1)))
```

最后：

```scheme
(count (+ n 1))
```

是 procedure body 最后的 expression。

当前 invocation：

```text
count(0)
```

已经没有别的事要干了。

因此：

```text
count(0)
```

没必要说：

```text
“等 count(1) 返回以后请回来告诉我结果”
```

因为它自己唯一要做的事情就是：

```text
把这个结果返回给自己的 caller
```

所以可以直接把 caller 的 continuation 交给：

```text
count(1)
```

# 25. Tail-call 的真正 machine model

普通 recursive call：

```text
A
│
├── call B
│
└── B 返回后：
        还需要做 something
```

所以必须保存：

```text
return-to-A
```

---

Tail call：

```text
A
│
└── return B(...)
```

B 返回以后：

```text
A 已经没有工作
```

所以：

```text
A.continuation
       ↓
直接交给 B
```

于是：

```text
A frame 不需要留下
```

这就是 tail-call optimization 最本质的解释。

不是：

> “编译器发现递归，于是神奇地优化。”

而是：

> **这个 computation 本身不存在 deferred work。**

---

# 26. 回到 Lecture 1B：recursive procedure ≠ recursive process

这就是为什么 SICP 从第一章开始反复强调这件事。

考虑：

```scheme
(define (fact n)
  (if (= n 0)
      1
      (* n (fact (- n 1)))))
```

执行：

```text
fact 5
↓
5 * fact 4
↓
5 * (4 * fact 3)
↓
5 * (4 * (3 * fact 2))
...
```

每次调用之后：

```text
还有 multiplication 等着完成
```

即：

```text
deferred computation
```

所以 stack：

```text
×5
×4
×3
×2
...
```

增长。

Space：

```text
O(n)
```

---

而：

```scheme
(define (fact-iter n product)
  (if (= n 0)
      product
      (fact-iter (- n 1)
                 (* n product))))
```

每次 recursive call：

```text
就是最后一件事情
```

因此：

```text
fact-iter(5,1)
↓
fact-iter(4,5)
↓
fact-iter(3,20)
↓
fact-iter(2,60)
↓
fact-iter(1,120)
↓
fact-iter(0,120)
```

不存在：

```text
“回来之后还要乘”
```

因此一个 tail-recursive evaluator 能让它使用恒定控制栈空间。SICP 明确说明 explicit-control evaluator 正因为最后表达式直接 transfer 到 `eval-dispatch`，所以 tail-recursive；如果最后一个 expression 也额外 save/return，空间就会重新变成与迭代次数成比例。([SICP Source Academy](https://sicp.sourceacademy.org/chapters/5.4.2.html "sicp.sourceacademy.org"))

这就是 Lecture 1B 的理论，到 Lecture 9B 才真正得到机器实现。

# 27. Applicative-order 在这一层是什么？

之前我们说：

```scheme
(f (g x))
```

Scheme 使用 applicative order：

```text
evaluate operator
evaluate operands
apply
```

现在 9B 让这个规则不再只是句英语。

对于：

```scheme
(f (g x))
```

机器真的执行：

```text
exp = (f (g x))
      ↓
eval operator f
      ↓
proc = value-of-f
      ↓
unev = ((g x))
      ↓
eval (g x)
      ↓
    eval g
      ↓
    eval x
      ↓
    apply g
      ↓
    val = g(x)
      ↓
argl = (g(x))
      ↓
apply f
```

而且显式控制 evaluator 的 operand loop 会具体决定 operand evaluation order；SICP 的实现由于按 `first-operand/rest-operands` 顺序处理，因此这里确定为 left-to-right，而 metacircular evaluator 的某些细节会继承宿主 Scheme 的求值顺序。([SICP Source Academy](https://sicp.sourceacademy.org/chapters/5.4.1.html "sicp.sourceacademy.org"))

这非常漂亮：

> evaluation order 最终不是哲学概念，而是 controller 的 instruction ordering。

# 30. Stack 的真正含义：不是“递归专用内存”

这是一个常见误解。

Stack 本质保存：

> **temporarily suspended computation state**

例如 application：

```scheme
(+ (f x) (g y))
```

evaluation `(f x)` 时，你必须记住：

```text
之后还需要：
    evaluate (g y)
    keep +
    keep current environment
    keep accumulated arguments
    finally apply +
```

这些就是：

```text
unfinished work
```

而 stack 正在保存这种 unfinished work。

所以更好的 mental model 不是：

```text
stack = recursion memory
```

而是：

```text
stack
=
suspended continuations
+
temporarily displaced machine state
```

# 31. 为什么不是每次都把所有 register 保存？

最简单的实现当然可以：

```text
save exp
save env
save val
save proc
save argl
save unev
save continue
```

每次“调用”都全存。

这样正确。

但是：

```text
很多值根本不会被覆盖
```

或者：

```text
回来以后根本不需要
```

于是 SICP 有意识地分析：

> 下一步 recursive evaluation 会破坏哪些 register？

以及：

> 回来之后我还需要哪些 register？

只保存两者交集。

例如 operand evaluation：

```text
argl
env
unev
```

回来还要用，因此 save。

这实际上已经是：

```text
liveness analysis
register preservation
calling convention
```

的雏形。

SICP 也指出，全保存虽然能工作，但会产生不必要的 stack 操作，甚至延长无用对象的生命周期、影响 garbage collection。([SICP Source Academy](https://sicp.sourceacademy.org/chapters/5.4.1.html "sicp.sourceacademy.org"))

# 32. 为什么 9B 后面紧接着 Compilation？

```text
      ↓

      ↓
```

假设运行：

```scheme

```

100 万次。

interpreter 每次都需要再次：

```text

```

但 source code 根本没变。

于是下一讲自然出现问题：

> 这些 decision 能不能提前做？

答案：

```text
compiler
```

Interpreter：

```text
source expression
      ↓ runtime
inspect syntax
      ↓
choose machine instructions
      ↓
execute
```

Compiler：

```text
source expression
      ↓ compile time
inspect syntax
      ↓
generate machine instructions

----------------

runtime
↓
execute generated instructions directly
```

所以：

```text
9A Register Machine
      ↓
9B Interpreter on Register Machine
      ↓
10A Compiler generating Register-Machine Code
```

这不是三个分散主题。

是同一条推理链。

SICP §5.5 也正是从“explicit-control evaluator 是一个解释 Scheme 的 register machine”开始，引出如何让 register machine 不再通过解释器 controller 来运行程序，而执行编译出的控制序列。([SICP Source Academy](https://sicp.sourceacademy.org/chapters/5.5.html?utm_source=chatgpt.com "5.5  Compilation - SICP Comparison Edition"))

# 35. 这一节涉及哪些 Complexity？

9B 本身不是主要教 asymptotic complexity，但它终于让 **space complexity 的来源可以被精确解释**。

## Recursive factorial

```scheme
(* n
   (fact (- n 1)))
```

每层都有：

```text
pending multiplication
```

所以：

```text
stack depth ≈ n

space = O(n)
time  = O(n)
```

---

## Iterative factorial

```scheme
(fact-iter (- n 1)
           (* product n))
```

recursive call 是 tail call：

```text
old invocation has no pending work
```

proper tail-recursive evaluator：

```text
stack depth ≈ constant

space = O(1)
time  = O(n)
```

因此第一章所谓：

```text
recursive procedure
```

和：

```text
recursive process
```

的区别现在终于可以翻译成：

```text
调用时有没有必须保留的 continuation state？
```

这是一个非常强的 mental model。

# 38. 几组特别容易混淆的概念

### `eval` vs `apply`

```text
eval
问：
“这个 expression 意味着什么？”

apply
问：
“我已经有 procedure + argument values，
现在怎样调用这个 procedure？”
```

例如：

```scheme
(+ 1 2)
```

先：

```text
eval +
eval 1
eval 2
```

得到：

```text
proc = +
argl = (1 2)
```

然后才：

```text
apply
```

---

### `exp` vs `val`

```text
exp = 尚未求值的 program representation
val = 已经求出的 runtime value
```

例如：

```text
exp = (+ 1 2)

最终：

val = 3
```

---

### `unev` vs `argl`

这是 application 最容易混淆的一组：

```text
unev
=
还没 evaluation 的 operand expressions

argl
=
已经 evaluation 出来的 argument values
```

比如：

```scheme
(f (+ 1 2) (* 3 4))
```

某个中间时刻可能：

```text
unev = ((* 3 4))
argl = (3)
```

注意：

```text
expression ≠ value
```

---

### Environment vs Stack

再强调一次：

```text
env
→ names mean what?

stack
→ after this subcomputation, what must resume?
```

---

### Continuation vs Environment

```text
environment
=
上下文中的变量含义

continuation
=
后面还要做的 computation
```

这两个东西一个描述：

```text
where values come from
```

一个描述：

```text
where control goes
```

### 误区 1：9B 只是把 Scheme 改写成 assembly

不准确。

真正目标是：

```text
把 implicit control
变成
explicit control
```

`goto` 只是手段。

核心问题是：

```text

procedure application
tail calls
```

### 误区 2：stack 保存 local variables

只说这个太窄。

更好的理解：

```text
stack 保存 suspended computation state
```

可能包括：

```text
environment

unevaluated operands

```

### 误区 3：`continue` 就是整个 continuation

严格说不完全是。

当前 `continue` 通常只是：

```text

```

而完整未完成 computation 还依赖：

```text
stack contents
```

所以更准确：

```text
continue + stack
≈ continuation representation
```

### 误区 4：Tail recursion 是语法优化

不是。

本质：

```text

→ caller no longer needs to resume
→ caller continuation can be reused
→ no extra stack frame needed
```

### 误区 5：recursive procedure 一定增加 stack

这正是 SICP 要你摆脱的想法。

如果：


SICP 故意把这两个概念拆开。

Closure 可以引用一个：


而那个 procedure 的创建者 invocation 早就“返回”了。

所以 lexical environment 的生命周期不必和 control stack frame 相同。

# 42. 你真正应该记住的东西

如果几个星期后只记得这节课的一小部分，我建议保留这些：

**核心思想**

1. **Metacircular evaluator 仍然依赖宿主语言隐藏的 procedure-call machinery；9B 把它全部显式化。**
    
2. **Evaluation 可以实现成一个 state machine：registers + stack + labels + jumps。**
    
3. **Continuation 的本质是“当前计算完成以后还要做什么”。**
    
4. **Stack 保存的是 unfinished computation，而不仅仅是“递归变量”。**
    
5. **Tail recursion 的 O(1) space 来自 continuation reuse，而不是“编译器看到递归后做魔法”。**
    

**关键机制**

6. `eval-dispatch`：`expression → appropriate evaluation rule`。
    
7. `apply-dispatch`：`procedure + evaluated arguments → application`。
    
8. `exp/env/continue → val` 是整个 evaluator 最核心的协议。
    
9. Compound procedure application = `captured environment + parameter bindings → new environment`。
    
10. `save → goto evaluator → restore → resume` 是 recursive evaluation 的通用机器模式。
    

最重要的不变量可以压成一句：

```text
At eval-dispatch:

(exp, env, continue)
=
what to compute,
where names mean something,
what to do with the answer.

After evaluation:

val = answer
control → continue
```

如果你真正吃透这一句话，9B 就已经掌握一大半了。
