# Lecture 8A：Logic Programming, Part 1

MIT 的 1986 SICP 视频课程里，Lecture 8A 正式进入 **Logic Programming（逻辑程序设计）**。它紧接 7A/7B 的 Metacircular Evaluator：前两讲让你理解“语言是怎样被解释的”，这一讲马上利用这种能力问一个更激进的问题：

> **我们能不能设计一种语言，让程序员不再告诉计算机“怎么做”，而只告诉它“什么是真的”？**

这其实把 SICP 第一讲提出的 **declarative knowledge vs. imperative/how-to knowledge** 重新捡了回来。Abelson 在 8A 开头明确这样串起课程主线。

---

# 1. 这节课到底想解决什么问题？

## 1.1 之前我们写的程序都有一个隐藏假设

考虑普通 Scheme：

```scheme
(define (sqrt x)
  ...)
```

或者：

```scheme
(define (merge xs ys)
  ...)
```

我们的 mental model 是：

```text
输入
 ↓
procedure
 ↓
执行特定步骤
 ↓
输出
```

比如：

```scheme
(merge '(1 3 7)
       '(2 4 8))
```

得到：

```scheme
'(1 2 3 4 7 8)
```

这是一种非常强的模型，但是有一个隐藏限制：

> **procedure 自带方向。**

`merge` 被设计成：

```text
(xs, ys) → result
```

因此你可以问：

```text
[1 3 7] 和 [2 4 8]
merge 后是什么？
```

但如果我反过来问：

```text
[1 3 7] 和什么
merge 后等于
[1 2 3 4 7 8]？
```

数学关系本身完全有意义。

但 Scheme 的：

```scheme
(merge xs ys)
```

不是为了回答这个问题设计的。

---

# 2. 更深层的问题：procedure 把知识和使用方式绑在一起了

假设有事实：

```text
Adam 的儿子是 Cain
```

数学/逻辑形式可以写成：

```text
son(Adam, Cain)
```

这一个事实同时可以回答：

```text
Adam 的儿子是谁？
→ Cain
```

也可以回答：

```text
Cain 是谁的儿子？
→ Adam
```

甚至：

```text
Adam 和 Cain 之间是什么关系？
→ son
```

也就是说：

```text
一份 knowledge
        ↓
可以支持许多不同方向的问题
```

而传统 procedure 往往提前决定：

```text
什么是 input
什么是 output
```

Lecture 8A 正是在攻击这个限制。

Abelson 用 merge 作为核心例子：普通程序把 `x,y → z` 固定成方向；而逻辑关系 `merge-to-form(x,y,z)` 本身不指定哪一个是输入、哪一个是输出，因此原则上可以从任意已知部分推出未知部分。

---

# 3. 所以这节真正解决的是什么？

如果只能选一个类别，它首先是：

> **language design + abstraction**

但里面同时包含：

```text
language design
    ↓
representation of knowledge
    ↓
evaluation model
    ↓
search
    ↓
abstraction
```

这并不是单纯讲：

> “Prolog 有一种特殊语法。”

真正的问题是：

> **什么样的 programming language，能够把“知识是什么”和“怎样利用知识寻找答案”分离开？**

# 6. 第一核心思想：Function → Relation

这是今天最重要的 mental shift。

## Function

普通编程里：

```text
f : X → Y
```

例如：

```text
square(5) = 25
```

方向非常清楚：

```text
5 → 25
```

Procedure 就像：

```text
┌────────┐
5 ────→ │ square │ ────→ 25
        └────────┘
```

---

## Relation

逻辑编程更喜欢：

```text
square(x, y)
```

表示：

```text
y = x²
```

注意这里没有箭头。

它只是说：

```text
x 和 y 满足某种关系
```

因此理论上可以问：

```text
square(5, ?y)
```

得到：

```text
?y = 25
```

也可以问：

```text
square(?x, 25)
```

寻找：

```text
?x = 5
?x = -5
```

甚至问：

```text
square(?x, ?y)
```

寻找所有满足关系的组合——当然这时搜索空间可能是无限的。

---

# 7. Function 和 Relation 的根本区别

```text
FUNCTION

input
  ↓
procedure
  ↓
output

方向属于程序本身
```

而：

```text
RELATION

        x
       ↙ ↘
 relation
       ↖ ↗
        y
```

relation 只描述：

```text
x 与 y 之间什么成立
```

至于：

```text
已知谁？
未知谁？
```

由 query 决定。

这就是所谓 **relational programming** 的味道。

---

# 8. Lecture 的 merge 例子为什么这么重要？

传统 Scheme：

```scheme
(define (merge x y)
  (cond ((null? x) y)
        ((null? y) x)
        ((< (car x) (car y))
         (cons (car x)
               (merge (cdr x) y)))
        (else
         (cons (car y)
               (merge x (cdr y))))))
```

它编码的是：

```text
HOW TO merge
```

例如：

```text
compare first elements

if 1 < 2
    choose 1
    recursively merge [3 7] [2 4 8]

...
```

计算结构：

```text
merge [1 3 7] [2 4 8]
 ↓
1 :: merge [3 7] [2 4 8]
 ↓
1 :: 2 :: merge [3 7] [4 8]
 ↓
1 :: 2 :: 3 :: ...
```

这里 procedure 决定了控制流程。

---

# 9. 但是把它看作 relation

不用说：

```text
merge(x,y) returns z
```

而说：

```text
merge-to-form(x, y, z)
```

意思只是：

> `x` 与 `y` 合并可以形成 `z`。

例如：

```text
merge-to-form(
    [1 3 7],
    [2 4 8],
    [1 2 3 4 7 8])
```

是 true。

现在可以问：

```text
merge-to-form(
    [1 3 7],
    ?x,
    [1 2 3 4 7 8])
```

系统寻找：

```text
?x = [2 4 8]
```

更厉害：

```text
merge-to-form(
    ?x,
    ?y,
    [1 2 3 4 5])
```

这是在问：

> 哪些两个有序序列可以合并成 `[1 2 3 4 5]`？

lecture 指出，这时有 $2^5=32$ 种分配方式，query system 可以逐个产生答案。

这正好展示：

```text
traditional program
      ↓
usually one direction
      ↓
one result


relation
      ↓
different query directions
      ↓
potentially many results
```

# 10. 这才是 Lecture 8A 的第一次“大跳跃”

你以前理解程序大概是：

```text
Program
=
algorithm
=
steps
```

这里 SICP 说：

> 不一定。

我们可以尝试：

```text
Program

```

然后：

```text
general inference engine
```

负责决定：

```text

```

所以发生了一个非常重要的 separation：

```text
WHAT knowledge
     │
     │ separated from
     ↓
HOW search/inference
```

# 11. 第二核心机制：Fact / Primitive Query

假设数据库包含：

```scheme
(job (Bitdiddle Ben) (computer wizard))

(job (Hacker Alyssa P)
     (computer programmer))

(supervisor (Hacker Alyssa P)
            (Bitdiddle Ben))
```

注意这里本质上只是 data。

例如：

```scheme
(job (Hacker Alyssa P)
     (computer programmer))
```

表示：

```text
relation: job

person = Hacker Alyssa P
job    = computer programmer
```

---

# 12. Query 不是函数调用

查询：

```scheme
(job ?x (computer programmer))
```

不是说：

```scheme
(job x ...)
```

然后执行 `job procedure`。

而是：

> 在已知事实中，寻找一种 `?x` 的绑定，使整个 pattern 成立。

数据库有：

```scheme
(job (Hacker Alyssa P)
     (computer programmer))
```

于是：

```text
query:
(job ?x
     (computer programmer))

fact:
(job (Hacker Alyssa P)
     (computer programmer))
```

匹配：

```text
job       = job                ✓

?x
 ↓
(Hacker Alyssa P)

(computer programmer)
=
(computer programmer)          ✓
```

所以得到 frame：

```text
?x → (Hacker Alyssa P)
```

---

# 13. 这里的 evaluation model 已经变了

以前 Scheme evaluator：

```text
expression
    ↓
evaluate operator
    ↓
evaluate operands
    ↓
apply procedure
    ↓
extend environment
    ↓
evaluate body
```

例如：

```scheme
(square 5)
```

：

```text
evaluate square
    ↓
procedure

evaluate 5
    ↓
5

apply
    ↓
environment:
x → 5

evaluate (* x x)
    ↓
25
```

---

# 14. Query language 完全不是这个模型

现在更像：

```text
query
  ↓
find facts/rules capable of satisfying query
  ↓
match patterns
  ↓
generate variable bindings
  ↓
possibly infer new relationships
  ↓
produce zero / one / many frames
```

因此：

```scheme
(job ?x (computer programmer))
```

不是：

```text
operator = job
operand = ?x
apply job
```

而是：

```text
query pattern
     ↓
search knowledge base
     ↓
try candidate fact
     ↓
pattern match
     ↓
extend frame

?x → Alyssa
```

这是非常重要的 mental shift。

---

# 15. Environment 和 Frame 有一点相似，但不要混为一谈

Scheme evaluator：

```text
Environment

x → 5
y → 10
```

query system：

```text
Frame

?x → Alyssa
?boss → Ben
```

视觉上很像，但语义不同。

Scheme environment 表示：

```text
name 的 lexical binding
```

query frame 表示：

```text
为了让当前 logical statement 成立，
variables 当前必须满足哪些约束
```

所以：

```text
environment
≈ program execution state

frame
≈ partial solution
```

这个区别非常重要。

---

# 16. 一个 query 为什么可能产生多个答案？

假设：

```scheme
(job (Alyssa) (computer programmer))
(job (Lem)    (computer programmer))
(job (Louis)  (computer programmer trainee))
```

问：

```scheme
(job ?x (computer programmer))
```

可能得到：

```text
frame₁:
?x → Alyssa

frame₂:
?x → Lem
```

所以：

```text
query evaluation
```

不是：

```text
query → value
```

而更接近：

```text
query → stream of possible frames
```

即：

```text
Q
 ↓
{F1, F2, F3, ...}
```

这件事下一讲在 evaluator implementation 中会变得极其重要。

# 17. 第三个核心机制：Pattern Matching

你在 Lecture 4A 已经见过类似思想。

query：

```scheme
(job ?x (computer programmer))
```

fact：

```scheme
(job (Hacker Alyssa P)
     (computer programmer))
```

matching 的目标不是：

```text
两个表达式是否完全相等？
```

而是：

> 是否存在变量 binding，使两个结构相等？

例如：

```text
(job ?x (computer ?type))

vs

(job (Hacker Alyssa P)
     (computer programmer))
```

得到：

```text
?x    → (Hacker Alyssa P)
?type → programmer
```

---

# 18. Pattern Matching 在这里不是小技巧

它提供的是：

```text
symbolic structure
       +
variables
       ↓
constraints
       ↓
bindings
```

普通函数参数：

```scheme
(define (foo x)
  ...)
```

是：

```text
argument value
   ↓
bind x
```

而逻辑变量：

```scheme
?x
```

是：

```text
search/inference
      ↓
discover value
      ↓
bind ?x
```

这是两种完全不同的 binding。

---

# 19. 第四个核心机制：Means of Combination = AND

现在开始体现：

```text
simple knowledge
   ↓
compose
   ↓
complex query
```

比如：

```scheme
(and
  (job ?x (computer . ?type))
  (supervisor ?x ?boss))
```

意思：

> 找到一个 `?x`：
> 
> 1. `?x` 在 computer division；
>     
> 2. `?x` 的 supervisor 是 `?boss`。
>     

注意最重要的一件事：

```text
两个 clause 共享 ?x
```

因此它们不是两个独立查询。

---

# 20. 展开 AND 的计算过程

假设：

```text
Alyssa → computer programmer
Ben    → computer wizard
Lem    → computer programmer

Alyssa supervisor → Ben
Lem    supervisor → Ben
Ben    supervisor → Oliver
```

首先：

```scheme
(job ?x (computer . ?type))
```

产生：

```text
F1:
?x    = Alyssa
?type = (programmer)

F2:
?x    = Ben
?type = (wizard)

F3:
?x    = Lem
?type = (programmer)
```

现在第二个 query：

```scheme
(supervisor ?x ?boss)
```

不是从空环境执行。

而是对 **每一个已有 frame** 执行。

---

例如 F1：

```text
?x = Alyssa
```

所以 query 实际变成类似：

```text
(supervisor Alyssa ?boss)
```

匹配：

```text
Alyssa → Ben
```

扩展：

```text
F1':
?x    = Alyssa
?type = programmer
?boss = Ben
```

同理：

```text
F2'
?x    = Ben
?type = wizard
?boss = Oliver
```

等等。

所以 AND 本质上：

```text
frame stream
   ↓
query 1
   ↓
new frame stream
   ↓
query 2
   ↓
new frame stream
```

这其实和数据库 join 极其相似。

# 21. 如果联系你熟悉的数据库思想

可以把：

```scheme
(and
  (job ?x ?job)
  (supervisor ?x ?boss))
```

看成：

```sql
SELECT *
FROM job
JOIN supervisor
ON job.person = supervisor.person;
```

共同变量：

```text
?x
```

相当于 join key。

所以 Logic Programming、Relational Algebra、Datalog 之间天然有亲缘关系。

但是不要把它简单等同 SQL：

```text
SQL
主要是查询 relations

SICP query language
还允许 recursive rules / inference
```

后者更接近 Datalog / Prolog。

# 22. OR 是什么？

逻辑上：

```scheme
(or
  Q1
  Q2)
```

意思：

```text
满足 Q1
或者
满足 Q2
```

evaluation mental model：

```text
input frames
   ├────────→ evaluate Q1 ──→ answers₁
   │
   └────────→ evaluate Q2 ──→ answers₂

answers₁ + answers₂
```

这里会自然引出：

```text
nondeterminism
multiple possibilities
search
streams
```

因此 Lecture 6 的 streams 不是偶然出现的。

Lecture 8A 开头也明确提示，后面会漂亮地使用 streams 来避免传统 backtracking 的一些问题。

# 23. NOT 为什么比你想象的复杂？

你可能第一感觉：

```scheme
(not Q)
```

就是 Boolean：

```scheme
(not #t)
```

不是。

query language 里的 `not` 大概是：

> 在当前 bindings 下，如果找不到任何使 Q 成立的答案，那么这个 frame 才保留下来。

例如：

```scheme
(and
  (job ?x (computer . ?type))
  (not
    (supervisor ?x ?boss)))
```

意思大概是：

```text
computer division 中
没有 supervisor 的人
```

概念过程：

```text
?x = Alice
    ↓
try (supervisor Alice ?boss)
    ↓
found Bob
    ↓
NOT fails

?x = Oliver
    ↓
try (supervisor Oliver ?boss)
    ↓
no answer
    ↓
NOT succeeds
```

这已经暗示了一个危险：

> `not` 的结果可能依赖当前哪些变量已经 bound。

这会在 8B 成为 logic programming limitation 的重要部分。

Lecture 8A 结尾也提前指出：`not` 和 `lisp-value` 会让“无方向性”的理想开始出现限制。

---

# 24. Lisp-value：logic 世界与 Scheme 世界的逃生口

例如想问：

> 工资 > 30000 的人。

可以：

```scheme
(and
  (salary ?person ?amount)
  (lisp-value > ?amount 30000))
```

第一个：

```scheme
(salary ?person ?amount)
```

是逻辑关系。

可能先产生：

```text
?person → Alyssa
?amount → 40000
```

然后：

```scheme
(lisp-value > ?amount 30000)
```

调用 Scheme：

```scheme
(> 40000 30000)
```

得到 true。

lecture 明确把 `lisp-value` 描述成 query language 和底层 Lisp 之间的接口。

---

# 25. 为什么 Lisp-value 会破坏关系式编程的优雅？

考虑：

```scheme
(lisp-value > ?x 10)
```

如果：

```text
?x = 20
```

很好：

```scheme
(> 20 10)
```

可以算。

但如果：

```text
?x 尚未绑定
```

你希望 Lisp：

```scheme
(> ?x 10)
```

自动求出：

```text
11, 12, 13, ...
```

吗？

Scheme 的 `>` 不具备这种能力。

它是：

```text
input × input → boolean
```

而不是关系：

```text
greater-than(x,y)
```

所以：

```text
logic relation
bidirectional-ish

vs

Scheme procedure
directional
```

一旦调用普通 procedure：

```text
方向重新出现
```

这就是 abstraction leakage。

# 26. 第五核心机制：Rule = Means of Abstraction

这是 Lecture 8A 的另一个绝对核心。

普通 Scheme 的 abstraction：

```scheme
(define (square x)
  (* x x))
```

意思：

```text
把一段 computation pattern
起名叫 square
```

Logic language 的 abstraction：

```scheme
(rule
  (big-shot ?person ?division)
  ...)
```

是：

```text
把一段 logical relationship
起名字
```

Lecture 中明确说：

```text
means of abstraction = rules
```

rule 包含：

```text
conclusion
+
body
```

如果 body 成立，就可以推出 conclusion。

---

# 27. 一个最小 rule

例如：

```scheme
(rule
  (grandparent ?x ?z)
  (and
    (parent ?x ?y)
    (parent ?y ?z)))
```

自然语言：

```text
如果：

x 是 y 的父母
AND
y 是 z 的父母

那么：

x 是 z 的祖父母
```

注意：

> 你没有写“怎样找到 grandparent”。

你只描述：

```text
grandparent relation
```

---

# 28. 用它回答 query

事实：

```scheme
(parent Alice Bob)
(parent Bob Charlie)
```

query：

```scheme
(grandparent Alice ?who)
```

系统要证明：

```text
grandparent(Alice, ?who)
```

找到 rule：

```text
grandparent(?x, ?z)
 ←
parent(?x, ?y)
AND
parent(?y, ?z)
```

---

# 29. 展开 inference

第一步，把 query 和 rule conclusion 匹配：

```text
query:
grandparent(Alice, ?who)

rule head:
grandparent(?x, ?z)
```

产生约束：

```text
?x   = Alice
?z   = ?who
```

于是 rule body 变成：

```text
parent(Alice, ?y)
AND
parent(?y, ?who)
```

---

然后：

```text
parent(Alice, ?y)
```

匹配事实：

```text
parent(Alice, Bob)
```

得到：

```text
?y = Bob
```

于是剩下：

```text
parent(Bob, ?who)
```

匹配：

```text
parent(Bob, Charlie)
```

得到：

```text
?who = Charlie
```

最终：

```text
grandparent(Alice, Charlie)
```

成立。

# 30. 这相当于什么 evaluation model？

你可以把逻辑 evaluator 暂时想成：

```text
Goal
 ↓
寻找可以证明 Goal 的 fact / rule
 ↓
如果是 fact
     match
     ↓
     answer frame

如果是 rule
     ↓
match rule conclusion
     ↓
得到 bindings
     ↓
把 Goal 转化为 rule body
     ↓
证明 subgoals
     ↓
得到 answer frames
```

和普通 evaluator 比：

```text
Scheme

expression
 ↓
operator + operands
 ↓
apply
 ↓
body
```

Logic programming：

```text
goal
 ↓
candidate fact/rule
 ↓
match / unify
 ↓
subgoals
 ↓
search
 ↓
answers
```

所以两者都在：

```text
不断把复杂问题
reduce 成更小的问题
```

只是 decomposition rule 不一样。

# 32. Rule vs Procedure

这是本讲一定要分清的一组。

## Procedure

```scheme
(define (grandparent x)
  ...)
```

通常：

```text
x → answer
```

procedure body 指定：

```text
HOW
```

---

## Rule

```scheme
(rule
  (grandparent ?x ?z)
  ...)
```

指定：

```text
WHEN relationship is true
```

它没有显式说：

```text
哪个是 input
哪个是 output
```

所以理论上：

```scheme
(grandparent Alice ?x)
```

和：

```scheme
(grandparent ?x Charlie)
```

都可以使用同一个 rule。

# 33. Procedure abstraction vs Logical abstraction

这是 SICP 的另一个很漂亮的对称。

Procedure：

```scheme
(define (square x)
  (* x x))
```

抽象的是：

```text
computational process
```

Rule：

```scheme
(rule
  (grandparent ?x ?z)
  ...)
```

抽象的是：

```text
logical relationship
```

所以：

```text
Procedure abstraction
=
name a computation


Rule abstraction
=
name a relation / inference pattern
```

# 34. 第六核心思想：Declarative vs Imperative

这个概念值得单独讲。

## Imperative / procedural knowledge

你写：

```scheme
(define (member? x xs)
  (cond ((null? xs) #f)
        ((equal? x (car xs)) #t)
        (else (member? x (cdr xs)))))
```

你告诉机器：

```text
先检查 null
然后比较 car
然后递归 cdr
```

这叫：

```text
how-to knowledge
```

---

## Declarative knowledge

你写：

```text
member(x, [x | tail])

member(x, [head | tail])
    if member(x, tail)
```

核心是：

```text
什么情况下 member 关系成立
```

而不是：

```text
CPU 第一步做什么
第二步做什么
```

---

# 35. 但千万不要产生一个误解

错误 mental model：

> Declarative programming 没有 algorithm。

当然有。

因为真实机器最终必须决定：

```text
先试哪个 rule？
怎样搜索？
什么时候回退？
怎样避免无限循环？
怎样枚举多个答案？
```

区别在于：

```text
application-level program
          ↓
少指定 HOW

language implementation
          ↓
承担更多 HOW
```

也就是说：

> Declarative programming 没有消灭 control，它把更多 control 移进了 language/runtime。

这是非常重要的一句话。

# 41. AND 的本质：Constraint Accumulation

例如：

```scheme
(and
  (job ?x (computer programmer))
  (supervisor ?x ?boss))
```

你可以理解成不断给未知变量加约束：

```text
initial:
?x unconstrained

job clause:
?x ∈ {Alyssa, Lem}

supervisor clause:
?boss must satisfy
supervisor(?x, ?boss)
```

因此 Logic Programming 另一个非常有用的 mental model 是：

> **computation = progressive constraint refinement**

不是：

```text
不断把 value 算出来
```

而是：

```text
不断缩小可能解集合
```

这个思想后来在：

```text
constraint programming
SAT/SMT solving
type inference
Datalog
symbolic execution
```

都会再次出现。

# 42. Query variable 和普通 Scheme variable 不一样

是 caller 给出的。


所以：

```text

        ↓

```

而：

```text

        ↓

```

# 45. 本节的 Process Shape

Lecture 8A 不再主要关心：

```text

tree recursion
iteration
```

而出现一种新的 process shape：

```text
SEARCH TREE
```

例如：

```text
Goal G
  │
  ├── Rule 1
  │     ├── subgoal A
  │     └── subgoal B
  │
  ├── Rule 2
  │     ├── subgoal C
  │     └── subgoal D
  │
  └── Fact 3
```

一条 branch：

```text
成功
```

可能产生一个答案。

```text
失败
```

被丢弃。

```text
多个答案
```

# 46. Complexity 也因此变了

普通 merge：

```text
T(n,m) = O(n+m)
```

因为程序明确知道下一步如何走。

relation 版本如果你问：

```text
?x 和 ?y
merge 成
[1 2 3 4 5]
```

runtime 必须探索许多可能性。

5 个元素每一个可以属于：

```text
x
or
y
```

所以：

$$
2^5 = 32
$$

一般：

$$
2^n
$$

所以 declarative flexibility 不是免费的。

你获得：

```text
direction independence
multiple query modes
```

但付出的可能是：

```text
search complexity
```

Lecture 中的 merge demo 正展示了这个性能代价。

> **把 HOW 从用户程序中移走，并不代表 HOW 消失了。**

```text
     ↓

interpreter
     ↓

```

这也是为什么：

```text
language design
```

本质上就是：

> 决定 programmer 与 runtime 各承担多少复杂性。

# 48. 常见误区一：Logic Programming = Boolean logic

不对。

看到：

```text
AND OR NOT
```

容易觉得只是 Boolean expression。

真正重要的是：

```text
logical variables
+
relations
+
multiple bindings
+
inference
+
search
```

例如：

```scheme
(and
  (parent ?x ?y)
  (parent ?y ?z))
```

不是简单计算：

```text
true AND true
```

而是在寻找：

```text
?x
?y
?z
```

哪些组合使两个 statement 同时成立。

---

# 49. 常见误区二：Query 就是 database lookup

primitive query 确实像：

```sql
SELECT ...
```

但是 rules 让系统可以推导数据库里没有直接存储的事实。

数据库只有：

```text
parent(Alice,Bob)
parent(Bob,Charlie)
```

并没有：

```text
grandparent(Alice,Charlie)
```

但 rule：

```text
parent(x,y)
AND
parent(y,z)
→
grandparent(x,z)
```

可以推导出来。

所以：

```text
retrieval
+
inference
```

才是重点。

---

# 50. 常见误区三：“无方向”意味着任何 query 都一定能有效运行

这是非常危险的理解。

Logical relation：

```text
数学语义上没有方向
```

但 implementation：

```text
必须执行某种 search strategy
```

所以：

```text
semantic symmetry
≠
operational symmetry
```

例如理论上：

```text
x + y = 10
```

可以问很多方向。

但具体实现可能：

```text
solve(3,7)
```

容易，

而：

```text
solve(?x,?y)
```

永远枚举不完。

这是 Logic Programming 最重要的现实限制之一。

---

# 51. 常见误区四：Rule 是 if statement

表面：

```text
if body then conclusion
```

很像：

```scheme
(if ...)
```

但运行语义完全不同。

Scheme：

```scheme
(if predicate
    consequent
    alternative)
```

是：

```text
control flow
```

rule：

```text
Body ⇒ Conclusion
```

是：

```text
logical implication / inference recipe
```

query engine 可以：

```text
为了证明 Conclusion
尝试证明 Body
```

它不是简单“条件成立就执行某段代码”。

---

# 52. 常见误区五：Logic variable 就是 mutable variable

完全不是。

例如：

```text
?x = Bob
```

不是：

```text
给变量 x 赋值 Bob
```

更接近：

```text
当前 hypothesis / solution 中，
?x 必须与 Bob 一致
```

它是：

```text
constraint / binding
```

而不是：

```text
mutable storage cell
```

所以不要把 Lecture 5 的 assignment mental model 带进来。

---

# 53. 常见误区六：Declarative = runtime 不关心执行顺序

不对。

**语义描述** 尽量不依赖执行顺序。

但：

```text
implementation
```

依然必须决定：

```text
rule order
search order
branch scheduling
when to evaluate predicates
```

而这些选择甚至可能决定：

```text
程序 terminate
还是
无限搜索
```

这正是 Logic Programming 的深层 tension：

```text
declarative semantics

        vs

operational behavior
```

# 54. 一个值得记住的模式：Relation Definition Pattern

下一次看到：

```text

成立
如果
B(x,y)
且

```

应该立刻识别成：

```text

  (A ?x ?z)
  (and
    (B ?x ?y)
```

```text
Target relation
       ↑
       │ infer
       │
subrelation₁
   AND
subrelation₂
   AND
...
```

这相当于传统程序里的：

```text
recursive procedure pattern
```

但它抽象的是：

```text
proof / relation structure
```

# 61. 完整 Evaluation Mental Model

把目前所有内容统一起来。

假设：

```scheme
(rule
  (grandparent ?x ?z)
  (and
    (parent ?x ?y)
    (parent ?y ?z)))
```

事实：

```scheme
(parent Alice Bob)
(parent Bob Charlie)
(parent Alice Diana)
(parent Diana Eve)
```

query：

```scheme
(grandparent Alice ?who)
```

运行可以想象为：

```text
QUERY
grandparent(Alice, ?who)

        ↓

look for facts/rules
matching grandparent(...)

        ↓

RULE FOUND

grandparent(?x, ?z)
←
parent(?x, ?y)
AND
parent(?y, ?z)

        ↓

match rule conclusion

?x   → Alice
?z   → ?who

        ↓

new goals

parent(Alice, ?y)
AND
parent(?y, ?who)

        ↓

first goal

parent(Alice, ?y)

       / \
      /   \
 Bob       Diana

 ↓           ↓

frame A    frame B

?y=Bob     ?y=Diana

 ↓           ↓

second goal

parent(Bob, ?who)
             parent(Diana, ?who)

 ↓                   ↓

Charlie              Eve

 ↓                   ↓

ANSWER 1             ANSWER 2

?who=Charlie         ?who=Eve
```

这是 Logic Programming 的基本 process shape。

# 63. “把 computation 当 data”在这里进一步升级了

Higher-order procedure 中：

```scheme
(foo f x)
```

核心思想：

```text
computation itself
can be represented by procedure
and passed around
```

Logic Programming 更进一步：

> **我们甚至不必显式提供 computation。**

我们提供：

```text
logical constraints
```

runtime 根据它们：

```text
constructs / explores computation
```

也就是说：

```text
Higher-order programming

computation
→ first-class object


Logic programming

knowledge
→ executable specification
```

这是一种更激进的 abstraction。

# 64. SICP 这里真正训练你的是什么？

面对问题时，不要立刻问：

> “我要写什么 algorithm？”

可以先问：

```text
问题中真正存在什么关系？

哪些是事实？

哪些是约束？

哪些 inference pattern 可以复用？

HOW 是否必须由 application code 决定？

还是可以让一个更通用的 engine 决定？
```

这其实非常现代。

例如：

```text
SQL optimizer
dependency solver
Kubernetes controller
SAT solver
Terraform desired state
```

都有一点这种味道：

```text
you specify desired relationships/state
        ↓
general mechanism
        ↓
figures out actions/search
```

当然它们不是 Prolog，但 abstraction philosophy 很相似。

# 65. 你尤其可以用 Kubernetes/Terraform 来类比

例如 Terraform：

你更多写：

```text
desired state
```

而不是：

```text
API call 1
wait
API call 2
delete X
create Y
...
```

Terraform runtime 负责推导：

```text
current state
+
desired state
        ↓
plan
        ↓
operations
```

Logic programming 更极端：

```text
facts
+
relations
        ↓
inference/search
```

共同思想都是：

> 把 HOW 从业务描述里抽出去。

这不是说 Terraform 是 logic language，而是二者体现了类似的 declarative abstraction 思想。

# 69. 真正应该记住的 8 个东西

### 核心思想 1：Relation，而不是 Function

```text
function:
inputs → output

relation:
participants satisfying a constraint
```

不要预先固定 input/output。

### 核心思想 2：Declarative Knowledge

```text
describe WHAT is true
```

而尽量把：

```text
HOW to find it
```

交给 inference engine。

### 核心思想 3：Knowledge / Control separation

```text
facts + rules
       ↓
knowledge

search/inference
       ↓
control
```

### 核心思想 4：Rule 是新的 abstraction mechanism

Procedure：

```text
name computation
```

Rule：

```text
name logical relationship
```

---

关键机制则记住：

```text
1. query variable
2. pattern matching / binding
3. AND = constraint refinement
4. rule application = goal reduction
```

最后一个关键 invariant：

> **Query evaluator 的结果不是一个 value，而是一组可能的 variable bindings。**

你可以暂时牢牢记成：

```text
Scheme:
Expression → Value

Logic language:
Query → Stream<Frames>
```

如果这个转换真正进入脑子，Lecture 8A 基本就通了。

# 71. 给你 5 道真正值得推演的题

## 题 1：手动执行 AND

已知：

```scheme
(job Alice programmer)
(job Bob programmer)
(job Charlie manager)

(supervisor Alice Charlie)
(supervisor Bob David)
```

执行：

```scheme
(and
  (job ?x programmer)
  (supervisor ?x ?boss))
```

不要只写最终答案。

请画：

```text
initial frame stream
      ↓
after first query
      ↓
each frame passed to second query
      ↓
final frames
```

重点回答：

> 第二个 query 为什么不能独立执行？

---

## 题 2：Procedure vs Relation

普通 Scheme：

```scheme
(define (append x y)
  (if (null? x)
      y
      (cons (car x)
            (append (cdr x) y))))
```

可以计算：

```scheme
(append '(1 2) '(3 4))
```

现在假设存在：

```text
append-to-form(x,y,z)
```

解释为什么理论上可以问：

```text
append-to-form(?x, ?y, '(1 2 3))
```

并列举所有可能答案。

然后回答：

> 为什么普通 `append` procedure 做不到这一点？

重点不是 Scheme syntax，而是：

```text
function directionality
vs
relation
```

## 题 3：自己设计一个 Rule

事实：

```text
parent(Alice,Bob)
parent(Bob,Charlie)
parent(Charlie,David)
```

设计：

```text
ancestor(x,y)
```

要求支持：

```text
ancestor(Alice, ?who)
```

而不仅仅是 grandparent。

思考：

```text
base rule 是什么？
recursive rule 是什么？
```

然后画：

```text
ancestor(Alice, David)
```

的证明树。

## 题 4：为什么这个 query 有问题？

考虑：

```scheme
(lisp-value > ?x 10)
```

假设 `?x` 尚未绑定。

解释：

> 为什么普通 Scheme 的 `>` 无法像真正 relational `greater-than` 一样反向生成 `?x`？

进一步回答：

```text
为什么 lisp-value
会削弱 relation 的 direction-independence？
```

## 题 5：最重要的一题

比较：

```scheme
(define (grandparent x)
  ...)
```

和：

```scheme
(rule
  (grandparent ?x ?z)
  (and
    (parent ?x ?y)
    (parent ?y ?z)))
```

分别回答：

```text
1. abstraction 的对象是什么？
2. 谁决定 input/output？
3. computation 的 HOW 在哪里？
4. evaluation 返回一个 value 还是多个 bindings？
5. 为什么后一种形式可能需要 search？
```

如果这道题你能够完整解释，说明 Lecture 8A 的核心已经掌握了。
