你这节 **Lecture 4B: Generic Operators**，是 SICP 前半部分非常关键的一次“尺度升级”。

前面我们学的大多是：

> **如何把一个东西抽象好。**

4B 开始问更困难的问题：

> **如果一个大型系统里同时存在很多种表示、很多种数据类型、很多套独立实现，怎样让它们组合起来，而且新类型加入时不需要修改整个系统？**

MIT OCW 的课程顺序里，4B 正是 **Generic Operators**；它接在 4A 的 pattern matching / rule-based substitution 后面，下一讲 5A 就进入 assignment、state 和 side effects。([MIT OpenCourseWare](https://ocw.mit.edu/courses/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video_galleries/video-lectures/?utm_source=chatgpt.com "Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

而 4B 一开头，Sussman 就明确指出：此前的 data abstraction 提供了“horizontal abstraction barrier”，但复杂系统还需要另一种隔离不同实现的“vertical barrier”。

# 1. 这节课到底想解决什么问题？

先忘掉 `put`、`get`、type tag 这些实现细节。

真正的问题是：

> **Data Abstraction 解决了“隐藏一种 representation”，但没有彻底解决“多个 representation 同时存在”。**

## 1.1 前面 Data Abstraction 已经解决了什么？

例如有 rational number：

```scheme
(make-rat 1 2)

(numer x)
(denom x)

(add-rat x y)
```

上层不用知道：

```text
rational
   ↓
到底是不是
(cons numerator denominator)
```

这是：

```text
User
   |
   | make-rat / numer / denom
   |
---------------------- abstraction barrier
   |
   | cons / car / cdr
   |
Representation
```

这是 **horizontal abstraction barrier**：

> 上层不知道下层怎么表示。

很好。

但现在问题来了。

---

## 1.2 如果有两套 representation 怎么办？

Complex number 可以表示为：

```text
Rectangular representation

z = x + iy

(x, y)
```

也可以表示为：

```text
Polar representation

z = r e^(iθ)

(r, θ)
```

例如：

```text
3 + 4i
```

rectangular：

```text
(3, 4)
```

polar：

```text
(5, 0.927...)
```

两个表示都有合理理由。

加法特别适合 rectangular：

```text
(x1 + iy1) + (x2 + iy2)

= (x1+x2) + i(y1+y2)
```

乘法特别适合 polar：

```text
(r1, θ1) × (r2, θ2)

= (r1*r2, θ1+θ2)
```

所以你不能简单地说：

> “选一个最好 representation。”

Lecture 4B 的真正问题恰恰是：

> **如果两种 representation 都有价值怎么办？**

这就是 Sussman 讲 George 和 Martha 的原因：George 用 rectangular，Martha 用 polar，希望两套 incompatible representations 能同时存在。([TAU Open Course Ware](https://ocw.tau.edu.ng/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/4b-generic-operators/ "4B: Generic Operators | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

# 2. 为什么普通 Data Abstraction 不够？

假设底层的数据都只是 pair：

```scheme
(cons 3 4)
```

它是什么意思？

可能是：

```text
rectangular:
real = 3
imag = 4
```

也可能是：

```text
polar:
magnitude = 3
angle = 4
```

同一个：

```scheme
(cons 3 4)
```

已经不能自己说明自己是什么。

比如：

```scheme
(magnitude z)
```

如果：

```text
z = rectangular(3,4)
```

结果应该是：

```text
5
```

但如果：

```text
z = polar(3,4)
```

结果应该是：

```text
3
```

所以：

> representation 本身已经不够了。

必须增加一点信息：

```text
data + representation identity
```

也就是：

# Typed Data

这就是 4B 的第一个关键跳跃。

SICP 第二版也用几乎同样的问题说明 tagged data：如果 pair `(3,4)` 同时可能是 rectangular 或 polar，我们必须有办法区分它们。([SICP Source Academy](https://sicp.sourceacademy.org/chapters/2.4.2.html?utm_source=chatgpt.com "2.4.2   Tagged data - SICP Comparison Edition"))

# 5. 核心机制一：Tagged Data

## ① 直觉

以前一个 object 是：

```text
contents
```

现在变成：

```text
┌────────────────────┐
│ type               │
├────────────────────┤
│ contents           │
└────────────────────┘
```

例如：

```text
rectangular complex

(rectangular
   3
   4)
```

或者：

```text
polar complex

(polar
   5
   0.927)
```

可以写成类似：

```scheme
(define (attach-tag type contents)
  (cons type contents))

(define (type-tag datum)
  (car datum))

(define (contents datum)
  (cdr datum))
```

于是：

```scheme
(type-tag z)
```

可以回答：

```scheme
'rectangular
```

而：

```scheme
(contents z)
```

得到真正给 rectangular package 使用的数据。

# 6. Type Tag 的真正意义

不要把 type tag 理解成：

> Scheme 没有类型，所以手工搞了一个类型系统。

这只理解了一半。

更深的意义是：

> **Data carries information about how it should be interpreted.**

也就是：

```text
raw representation
        ↓
无法解释
        ↓
representation + tag
        ↓
可以选择 interpretation
```

例如：

```text
(3 . 4)
```

本身没有完整语义。

但：

```text
(rectangular . (3 . 4))
```

就告诉系统：

```text
请使用 rectangular interpretation
```

而：

```text
(polar . (3 . 4))
```

则告诉系统：

```text
请使用 polar interpretation
```

所以 type tag 本质上是一种：

> **runtime interpretation metadata**

# 7. 核心机制二：Dispatch on Type

有了 tag，最直接的办法是什么？

写一个 manager：

```scheme
(define (real-part z)
  (cond ((eq? (type-tag z) 'rectangular)
         (rect-real-part (contents z)))
        ((eq? (type-tag z) 'polar)
         (polar-real-part (contents z)))
        (else
         (error "unknown type"))))
```

直觉很简单：

```text
收到 object
   ↓
看 type
   ↓
rectangular?
   ├── yes → George
   │
polar?
   └── yes → Martha
```

这叫：

# dispatch on type

Lecture 中也是这样描述第一版 generic operator 的：manager 检查 type，然后把 contents 交给对应 representation package。([TAU Open Course Ware](https://ocw.tau.edu.ng/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/4b-generic-operators/ "4B: Generic Operators | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

# 8. Evaluation：`(real-part z)` 到底发生什么？

假设：

```scheme
z =
(rectangular 3 . 4)
```

执行：

```scheme
(real-part z)
```

按照 applicative-order evaluation：

```text
(real-part z)
      │
      ├── evaluate operator
      │
      │     real-part
      │       ↓
      │     procedure
      │
      └── evaluate operand
            z
            ↓
      tagged object
```

apply：

```text
real-part procedure
+
tagged object
        ↓
execute body
```

执行：

```scheme
(type-tag z)
```

得到：

```scheme
'rectangular
```

因此选择：

```scheme
(rect-real-part (contents z))
```

然后：

```text
(contents z)
     ↓
  (3 . 4)
```

再：

```scheme
(rect-real-part '(3 . 4))
```

rectangular package 内部知道：

```text
first component = real
```

所以：

```text
(car '(3 . 4))
   ↓
3
```

完整流程：

```text
(real-part z)
     ↓
inspect tag
     ↓
'rectangular
     ↓
strip tag
     ↓
(3 . 4)
     ↓
rect-real-part
     ↓
3
```

特别重要：

> generic layer **不理解 `(3 . 4)`**。

只有 rectangular package 理解。

generic layer只理解：

```text
tag → 找谁处理
```

这是 abstraction barrier 的关键。

# 9. 但 Dispatch on Type 有一个严重问题

假设现在来了 Harry。

Harry 发明第三种 representation：

```text
'awesome-complex
```

怎么办？

你就得改：

```scheme
real-part
imag-part
magnitude
angle
...
```

每一个函数都加入：

```scheme
((eq? type 'awesome)
 ...)
```

于是系统逐渐变成：

```scheme
(cond
  ((rect?) ...)
  ((polar?) ...)
  ((harry?) ...)
  ((alice?) ...)
  ((bob?) ...)

```

问题不是不能工作。

这正是 lecture 对 dispatch-on-type 的批评：George 和 Martha 本身不需要改，但每增加一个新 representation，central manager 就必须修改，因此 manager 成了扩展瓶颈。([TAU Open Course Ware](https://ocw.tau.edu.ng/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/4b-generic-operators/ "4B: Generic Operators | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

```text
                   rectangular       polar

imag-part          rect-imag        polar-imag
magnitude          rect-mag         polar-mag

```

中央 `cond` 本质上其实就在做：

```text

       ↓
```

那为什么还要写很多 `cond`？

直接把这个关系显式表示出来不就行了吗？

于是：

```text

              RECT        POLAR
```

# 11. 核心机制三：Data-Directed Programming

我们假设有：

```scheme
(put type operation procedure)

(get type operation)
```

George 安装自己的 package：

```scheme
(put 'rectangular 'real-part rect-real-part)
```

Martha：

```scheme
(put 'polar 'real-part polar-real-part)
```

```scheme
(put 'harry 'real-part harry-real-part)

```

Lecture 正是在这里把 manager 替换成 table，并让每个 representation provider 自己注册相应的方法。([TAU Open Course Ware](https://ocw.tau.edu.ng/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/4b-generic-operators/ "4B: Generic Operators | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

# 12. Generic `operate` 是整个机制的核心

可以想成：

```scheme
(define (operate op obj)
  (let ((proc
         (get (type-tag obj) op)))
    (if proc
        (proc (contents obj))
        (error "no method"))))
```

然后：

```scheme
(define (real-part z)
  (operate 'real-part z))

(define (magnitude z)
  (operate 'magnitude z))
```

于是 `real-part` 自己已经完全不知道：

```text
rectangular
polar
Harry
Martha
George
```

这些名字。

它只知道：

```text
operation = real-part
object = z
```

# 13. 这里发生了一个非常深的变化

原来 control flow 写在程序里：

```scheme
(cond
  ((rect?) ...)
  ((polar?) ...)
  ...)
```

现在 control flow 写进：

```text
data structure
```

即：

```text
dispatch table
```

换句话说：

> **我们把“程序应该执行哪个 procedure”这个决定本身数据化了。**

以前：

```text
code decides behavior
```

现在：

```text
data
 ↓
lookup
 ↓
select procedure
 ↓
behavior
```

这就是：

# Data-Directed Programming

所以这个名字不能简单理解成：

> 根据数据类型调用函数。

更好的 mental model：

> **系统的控制结构部分由 data 驱动，而不是全部硬编码进 control flow。**

# 14. 这里 Higher-Order Procedure 又回来了

table 中到底存什么？

不是：

```text
"rect-real-part"
```

这个字符串。

也不是 procedure 的名字。

而是：

```text
procedure object
```

也就是：

```text
(type, operation)
      ↓
actual computation
```

例如：

```text
('polar, 'real-part)
          ↓
(lambda (z)
  (* (car z)
     (cos (cdr z))))
```

Lecture 里还专门强调，table 中存的是 procedure 本身，因此甚至可以直接存匿名 lambda，不需要先给 procedure 起名字。([TAU Open Course Ware](https://ocw.tau.edu.ng/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/4b-generic-operators/ "4B: Generic Operators | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

这正是你前面问过的那个问题的一个巨大应用：

> 为什么 computation 要能作为 data？

因为现在我们才能做到：

```text
operation description
       ↓
lookup
       ↓
computation
```

# 15. Evaluation：Data-Directed 版本的 `(real-part z)`

现在假设：

```text
z =
(polar . (1 . 2))
```

执行：

```scheme
(real-part z)
```

### Step 1：evaluate operator

```text
real-part
   ↓
procedure
```

### Step 2：evaluate operand

```text
z
 ↓
(polar . (1 . 2))
```

### Step 3：apply `real-part`

body：

```scheme
(operate 'real-part z)
```

注意：

```scheme
'real-part
```

是一个 **symbol**。

不是 procedure application。

---

### Step 4：进入 `operate`

先算：

```scheme
(type-tag z)
```

得到：

```scheme
'polar
```

然后：

```scheme
(get 'polar 'real-part)
```

得到：

```text
procedure object

polar-real-part
```

---

### Step 5：取 contents

```scheme
(contents z)
```

得到：

```text
(1 . 2)
```

---

### Step 6：动态选择 procedure

现在运行时才决定：

```text
apply

polar-real-part
       │
       ▼
    (1 . 2)
```

于是：

```text
r = 1
θ = 2

real = r cos θ
```

最后：

```text
cos 2
```

整个过程：

```text
(real-part z)
     ↓
(operate 'real-part z)
     ↓
type-tag(z)
     ↓
'polar
     ↓
get('polar, 'real-part)
     ↓
polar-real-part procedure
     ↓
contents(z)
     ↓
(1 . 2)
     ↓
apply procedure
     ↓
(* 1 (cos 2))
```

这其实就是一个非常小型的：

# Dynamic Dispatch Engine

# 17. 容易混淆：Data Abstraction vs Generic Operation

这是本节第一组非常重要的区分。

## Data Abstraction

解决：

```text
How is one abstraction represented?
```

例如：

```text
rational

numer
denom
make-rat
```

把：

```text
use
```

和：

```text
representation
```

分开。

---

## Generic Operation

解决：

```text
Which implementation should handle this object?
```

例如：

```scheme
(real-part z)
```

可能调用：

```text
rect-real-part
```

也可能调用：

```text
polar-real-part
```

所以：

```text
Data abstraction
    ↓
hide representation

Generic operation
    ↓
choose implementation
```

# 18. Horizontal Barrier vs Vertical Barrier

这是这节课特别值得记住的一张图。

```text
                    USER

              add-complex
                   │
───────────────────┼───────────────────
                   │
                real-part
                imag-part
                magnitude
                angle
                   │
          ┌────────┴────────┐
          │                 │
          ▼                 ▼
     RECTANGULAR          POLAR
       package             package
```

horizontal：

```text
────────────
```

表示：

> 上层不关心下面怎么表示。

vertical：

```text
      │
      │
```

表示：

> rectangular implementation 和 polar implementation 可以独立存在。

SICP 2.4 对这个结构的总结也是：horizontal barrier 隔离高层操作与低层 representation，而 vertical barrier 允许不同 representations 独立设计和安装。([SICP Source Academy](https://sicp.sourceacademy.org/chapters/2.4.html?utm_source=chatgpt.com "2.4  Multiple Representations for Abstract Data - SICP Comparison Edition"))

# 19. 下一次升级：Generic Arithmetic

到目前为止 generic 的只是：

```text
real-part
imag-part
magnitude
angle
```

但 Sussman 接下来问：

为什么不让：

```scheme
(add x y)
```

也成为 generic operation？

我们可能有：

```text
ordinary number
rational
complex
```

但用户都写：

```scheme
(add x y)
```

而不是：

```scheme
+
add-rat

```

```text
                  add

                   │
            inspect types
```

这就是 **generic arithmetic system**。SICP 2.5 也正是把普通 arithmetic、rational arithmetic 和 complex arithmetic 放到同一个 generic interface 下。([SICP Source Academy](https://sicp.sourceacademy.org/chapters/2.5.html?utm_source=chatgpt.com "2.5  Systems with Generic Operations - SICP Comparison Edition"))

# 20. 二元 generic operation

概念上：

```scheme
(define (add x y)
  (operate-2 'add x y))
```

`operate-2` 做的事：

```text
type(x)
type(y)
   ↓
find method
   ↓
strip tags
   ↓
apply
```

Lecture 中简化版首先要求：

```text
type(x) == type(y)
```

如果：

```text
rational + rational
```

查：

```text
(rational, add)
```

得到：

```text
add-rat
```

如果：

```text
complex + complex
```

得到：

```text
add-complex
```

---

# 21. 特别注意：`+` 和 `add` 已经不是一回事

这是本节一个很重要的 mental model。

```scheme
(+ x y)
```

意味着：

> 我已经知道 x、y 是 Scheme primitive number。

而：

```scheme
(add x y)
```

意味着：

> 我不知道 x、y 是什么类型，让 generic arithmetic system 决定。

因此：

```text
+       concrete operation

add     abstract / generic operation
```

这件事情马上产生巨大的后果。

# 22. Nested Type Tags：这部分最容易没真正理解

假设 complex number 是 rectangular representation：

```text
3 + 4i
```

内部可能长成：

```text
complex
   │
   ▼
rectangular
   │
   ▼
(3 . 4)
```

或者写：

```text
(complex
   (rectangular
      (3 . 4)))
```

为什么两个 tag？

因为它跨了 **两个 abstraction boundaries**。

第一个：

```text
generic arithmetic
       ↓
     complex
```

回答：

> 这是什么数学对象？

第二个：

```text
complex package
      ↓
rectangular
```

回答：

> complex 内部采用什么 representation？

这两个 type 的语义完全不同。

# 23. Generic multiplication 的完整执行

假设：

```scheme
(mul z1 z2)
```

其中：

```text
z1 =
complex
  ↓
rectangular
  ↓
(3,4)
```

执行过程：

```text
(mul z1 z2)
      ↓
operate-2('mul, z1, z2)
      ↓
type-tag
      ↓
complex
      ↓
lookup:

(complex, mul)
      ↓
mul-complex
```

于是 outer `complex` tag 被剥掉。

进入 complex package：

```text
mul-complex
      ↓
mul-c
```

complex multiplication 更适合 polar：

```text
magnitude(z1) * magnitude(z2)
angle(z1) + angle(z2)
```

于是：

```scheme
(magnitude z1-inner)
```

再次 generic dispatch：

```text
type-tag
    ↓
rectangular
    ↓
lookup
    ↓
rect-magnitude
```

然后：

```text
(3,4)
 ↓
sqrt(3²+4²)
 ↓
5
```

因此：

```text
mul
 ↓
complex dispatch
 ↓
complex multiplication
 ↓
generic magnitude
 ↓
rectangular dispatch
 ↓
representation operation
```

Lecture 把这种现象描述为一条 **chain of types**：每穿越一个有多种 implementation 的 vertical barrier，就由一个 type 告诉系统下一步应该走向哪里。([TAU Open Course Ware](https://ocw.tau.edu.ng/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/4b-generic-operators/ "4B: Generic Operators | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

---

# 24. 这里真正建立的是“分层解释”

可以把它理解为：

```text
Level 1:

"This is a complex number"
        ↓

Level 2:

"This complex number is rectangular"
        ↓

Level 3:

raw pair
```

也就是说：

> 每一层只理解下一层需要暴露给自己的东西。

generic arithmetic 不理解 rectangular。

complex arithmetic 不需要理解 rational。

rectangular package 不需要理解 polynomial。

这才是大型软件能够继续扩展的基础。

# 25. 这节课最精彩的地方：Polynomial

如果前面只是 method dispatch，其实思想还没完全展开。

Sussman 后面引入 polynomial，真正展示 generic operations 为什么强大。([TAU Open Course Ware](https://ocw.tau.edu.ng/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/4b-generic-operators/ "4B: Generic Operators | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

例如：

```text
P(x) = 3x² + 2x + 5
```

可以表示为 term list：

```text
(order=2, coefficient=3)
(order=1, coefficient=2)
(order=0, coefficient=5)
```

假设：

```text
P = 3x² + 2x
Q = 5x² + 7
```

加法类似 merge：

```text
3x²      2x
5x²           7
----------------
8x²      2x   7
```

# 26. `add-terms` 的核心

大致模式：

```scheme
(define (add-terms L1 L2)
  (cond
    ((empty? L1) L2)
    ((empty? L2) L1)
    (else
      ...)))
```

看首项：

```text
order(t1) > order(t2)
order(t1) < order(t2)
order(t1) = order(t2)
```

最关键的是相等情况。

不要写：

```scheme
(+ (coeff t1)
   (coeff t2))
```

而写：

```scheme
(add (coeff t1)
     (coeff t2))
```

只有一个单词的区别：

```text
+     → primitive arithmetic

add   → generic arithmetic
```

但系统能力发生巨大变化。

---

# 27. 为什么这一个 `add` 如此重要？

如果写：

```scheme
+
```

意味着：

```text
coefficient 必须是普通数字
```

而写：

```scheme
add
```

意味着：

```text
coefficient 可以是任何“知道如何 add 的东西”
```

于是 coefficient 可以是：

```text
integer
rational
complex
polynomial
...
```

Lecture 对这一点特别强调：polynomial addition 被归约成 coefficient addition，而 coefficient 用的是 generic `add`，因此 polynomial 自动可以拥有 rational、complex，甚至 polynomial coefficient。([TAU Open Course Ware](https://ocw.tau.edu.ng/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/4b-generic-operators/ "4B: Generic Operators | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

# 28. 举一个很重要的例子

以前：

```text
P(x) = 3x² + 2x + 1
```

现在：

```text
P(x) =
  (2/3)x²
  +
  (3+4i)x
  +
  7/5
```

完全没问题。

为什么？

当 polynomial package 遇到：

```text
coefficient1 + coefficient2
```

它不问：

```text
你们是 rational？
你们是 complex？
```

它只说：

```scheme
(add c1 c2)
```

然后：

```text
generic arithmetic
```

自己决定。

# 29. 甚至 polynomial 的 coefficient 可以还是 polynomial

例如：

```text
P(y) =
     (x² + 1)y²
   + (3x + 2)y
   + (x³ + 7)
```

这里：

```text
P 是 y 的 polynomial
```

但 coefficient：

```text
x² + 1
3x + 2
x³ + 7
```

本身又是：

```text
x polynomial
```

于是：

```text
add polynomial
       ↓
add coefficients
       ↓
coefficient itself is polynomial
       ↓
add polynomial
       ↓
add its coefficients
       ↓
...
```

这不是 hack。

这是：

# Recursive Generic Structure

SICP 把它称作一种 data-directed recursion：当 coefficient 本身是 polynomial 时，generic dispatch 会再次进入 polynomial arithmetic，并可以任意继续下去。([SICP Source Academy](https://sicp.sourceacademy.org/chapters/2.5.3.html?utm_source=chatgpt.com "2.5.3   Example: Symbolic Algebra - SICP Comparison Edition"))

---

# 30. Process Shape：这里发生的是哪种 recursion？

例如：

```text
add-poly
   ↓
add-terms
   ↓
add coefficients
   ↓
generic add
   ↓
add-poly
   ↓
add-terms
   ↓
...
```

这和：

```scheme
(f (- n 1))
```

那种单纯的 recursive procedure 不完全一样。

它是一种：

> **由数据的类型结构驱动的 recursive computation。**

递归深度不是由一个简单的 `n` 决定。

而是由：

```text
data nesting depth
```

决定。

例如：

```text
polynomial
   coefficient →
      polynomial
         coefficient →
            complex
```

generic dispatch 会沿着这个 structure 往下。

---

# 31. 这就是“composition”真正发生的地方

前面的 composition 是：

```scheme
(f (g x))
```

这节课把 composition 提升了一层：

```text
abstraction A
internally uses generic abstraction B
               ↓
B can itself be A
               ↓
recursive composition
```

因此系统不是：

```text
一个大程序
```

而是：

```text
small independent packages
        +
generic interface
        +
recursive composition
```

形成大系统。

# 32. 一个非常重要的 SICP Pattern

以后看到这种代码：

```scheme
(define (foo x y)
  ...
  (generic-operation
     (part x)
     (part y))
  ...)
```

你的第一反应应该是：

> `foo` 的 abstraction 是否正在把自己的问题 reduction 到 constituent parts 的同一个 generic problem？

例如：

```text
Polynomial addition
    ↓
coefficient addition
```

或者：

```text
Matrix addition
    ↓
element addition
```

或者：

```text
Rational arithmetic
    ↓
numerator/denominator arithmetic
```

这种 pattern 可以写成：

```text
Composite abstraction
        ↓
decompose into parts
        ↓
generic operation on parts
        ↓
reassemble
```

这个模式极其重要。

# 33. Rational Numbers 也能被进一步泛化

最开始 rational：

```text
3 / 5
```

似乎 numerator / denominator 必须是 integer。

但 rational formula：

```text
a/b + c/d

= (ad + bc) / bd
```

实际上只要求：

```text
a,b,c,d
```

支持：

```text
add

```

所以为什么一定要 integer？

完全可以：

```text
3x + 7
────────
x² + 1
```

numerator 和 denominator 都是 polynomial。

如果把 rational package 内部 primitive：

```scheme
+

```

替换成：

```scheme
add

```

generic arithmetic 又向外扩展一层。Lecture 也正用这个例子说明，把 lower-level primitive operations 替换成 generic ones 后，更复杂的对象组合可以“自动”获得支持。([TAU Open Course Ware](https://ocw.tau.edu.ng/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/4b-generic-operators/ "4B: Generic Operators | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

# 34. 最深层思想：Closure Property

这其实和前面的 closure property 紧密相连。

当：

```text
operation produces values
that can again participate
in the same operation
```

你就能不断组合。

例如 pair：

```text
pair
 ├─ atom
 └─ pair
      ├─ pair
      └─ atom
```

形成 tree。

现在 generic arithmetic：

```text
polynomial
 ├─ rational
 ├─ complex
 └─ polynomial
      └─ complex
```

形成：

```text
recursive algebraic structure
```

所以这里的 closure 已经不只是“数据能嵌套”。

而是：

> **抽象操作对组合后的数据仍然有效。**

# 35. Data-Directed Programming vs Message Passing

这两个特别容易混。

## Data-directed

object：

```text
type + contents
```

method：

```text
external table
```

调用：

```text
(op, type)
   ↓
method table
   ↓
procedure
```

---

## Message passing

另一种设计是：

```text
object 本身知道如何响应 operation
```

例如概念上：

```scheme
(z 'real-part)
```

对象收到：

```text
'real-part
```

然后自己选择行为。

可以想：

```text
data-directed

      operation
          ↓
      global table
          ↓
        object
```

vs：

```text
message passing

message
  ↓
object
  ↓
object chooses method
```

Lecture 4B 甚至提到：如果不是只把 `'polar` tag 放进 data，而是把 operations 本身放进去，就会走向 message passing。([TAU Open Course Ware](https://ocw.tau.edu.ng/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/4b-generic-operators/ "4B: Generic Operators | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

这正是后面 SICP object-oriented style 的伏笔。

# 36. Generic Operation vs Method Overloading

现代语言里最像的是：

```java
a.add(b)
```

或者：

```rust
a + b
```

trait resolution。

但不能直接画等号。

SICP 的机制更显式：

```text
runtime value
 ↓
type-tag
 ↓
lookup table
 ↓
```

它实际上把：

```text
dynamic dispatch mechanism
```

整个暴露给你看。

现代语言通常由 compiler/runtime 帮你隐藏了。

# 38. 但不要把它简单理解成 OOP

SICP 这里更大的问题是：

> **如何组织一个可扩展的计算系统。**

OOP 只是可能答案之一。

可以把整个 design space 看成：

```text
                 Where is dispatch knowledge?

central code
    │
    ├── cond / switch
    │

    │
    ├── data-directed
    │
object
    │
    ├── message passing / OO
    │
type system
    │
    └── traits / typeclasses / overload resolution
```

> **把 dispatch 本身看成一种可设计的 abstraction。**

# 40. 一个特别重要的不变量

整个系统要正确，有一个 invariant：

```text
tag 与 contents 的 interpretation 必须一致
```

例如：

```text
tag = rectangular
contents = (3 . 4)
```

必须保证：

```text
rectangular package
```

能正确理解 `(3 . 4)`。

generic layer 的承诺是：

```text
我不查看 contents 的内部结构
```

representation package 的承诺是：

```text
收到我的 contents 后，我知道如何解释
```

所以边界是：

```text
Generic layer
    knows tag
    does NOT know representation

Representation package
    knows representation
    does NOT care who called it
```

这是本节最重要的不变量之一。

---

# 41. 第二个重要 invariant：strip before entering package, tag before leaving

可以记成：

```text
            Generic world

tagged object
     │
     │ strip tag
     ▼

---------------- abstraction boundary

      contents
         ↓
 representation-specific procedure
         ↓
      contents

---------------- abstraction boundary

     │ attach tag
     ▼

tagged object
```

也就是：

> **进入 package 前剥掉 package 不需要看的 metadata；离开 package 时重新恢复 abstraction identity。**

# 42. 第三个 invariant：generic code 不应该枚举所有 concrete types

如果你看到：

```scheme
(define (add x y)
  (cond
    ((both-rational?) ...)
    ((both-complex?) ...)
    ((both-polynomial?) ...)
    ...))
```

你的 architecture alarm 应该响。

因为：

```text
generic abstraction
```

已经重新依赖：

```text
all concrete representations
```

扩展性又没了。

data-directed version 应该更像：

```text
type(s)
   ↓
lookup
```

而不是：

```text
if every known type...
```

# 43. 本节的 complexity / process shape

4B 主要不是算法复杂度课，但还是可以分析。

比如两个按 degree 降序排列的 term list：

```text
L1 length = m
L2 length = n
```

`add-terms` 类似 merge。

每一步至少消耗一个 term：

```text
T(m,n)
  ≈ T(m-1,n)
```

或：

```text
T(m,n)
  ≈ T(m,n-1)
```

或：

```text
T(m,n)
  ≈ T(m-1,n-1)
```

所以：

```text
time = O(m+n)
```

构造结果：

```text
O(m+n)
```

如果使用直接递归实现，则未完成的 `adjoin-term` 调用可能导致：

```text
stack = O(m+n)
```

这部分的重点依然不是 complexity，而是：

> coefficient combination 的 cost 被抽象成 generic operation 的 cost。

所以更准确：

```text
Tpoly
≈ O(m+n) dispatch work
 + coefficient operations
```

如果 coefficients 本身是 huge polynomials：

```text
coefficient add
```

就可能再次触发大规模 computation。

# 46. 常见误区一：Type Tag 就是静态类型系统

不完全是。

这里：

```text
tag
```

首先是普通 runtime data。

例如：

```scheme
'polar
```

只是 symbol。

系统：

```text
read symbol
  ↓
lookup procedure
```

它并没有依赖 compiler 做静态证明。

正确 mental model：

```text
type tag
=
runtime dispatch metadata
```

---

# 47. 常见误区二：Generic Operation 就是很多 `if`

功能上可以。

架构上不一样。

```text
central cond
```

的问题是：

```text
new type
 ↓
edit central code
```

而 data-directed：

```text
new type
 ↓
install new methods
```

这个区别是：

> **change locality**

也就是“变化发生在哪里”。

这才是 modularity 的核心。

---

# 48. 常见误区三：table 里放的是函数名

不是。

关键是：

```text
procedure itself
```

例如：

```scheme
(lambda (z) ...)
```

procedure 是 first-class value。

所以：

```text
symbol
   ↓
lookup
   ↓
procedure value
```

才能成立。

这是 Higher-Order Procedure 在大型软件 architecture 中的应用。

---

# 49. 常见误区四：rectangular 和 complex 是同一级 type

不是。

这是非常容易混淆的地方。

```text
complex
```

表示：

> 数学对象属于什么抽象类型。

而：

```text
rectangular
polar
```

表示：

> complex 内部采用什么 representation。

所以：

```text
complex
   ↓
rectangular
```

不是重复。

它是两个 abstraction level。

---

# 50. 常见误区五：generic `add` 只是方便少写几个函数名

完全不是。

如果只是：

```text
+ 换个名字叫 add
```

没什么意义。

真正的力量来自：

```text
high-level abstraction
uses generic operation
on its components
```

# 56. 真正应该记住的东西

如果几周以后你把代码都忘了，我希望你还记得下面这些。

### 核心思想

1. **Data abstraction 隔离 use 和 representation，但多个 representation 共存还需要额外的 dispatch abstraction。**
    
2. **Type tag 让 data 携带“如何解释我”的信息。**
    
3. **Generic operation 把“我要做什么”和“具体怎么做”分开。**
    
4. **Data-directed programming 把 control decision 从中央 `cond` 搬进可扩展的数据结构。**
    
5. **真正强大的地方不是 dispatch 本身，而是 generic operations 可以递归组合。**
    

### 关键机制

1. `type-tag / contents / attach-tag`
    
2. `(type, operation) → procedure`
    
3. `get → procedure → apply`
    
4. outer type 和 representation type 可以形成多层 tag
    
5. composite abstraction 内部使用 generic operations
    

### 三个最重要的不变量

```text
Invariant 1:
tag 必须正确描述 contents 的 interpretation。
```

```text
Invariant 2:
generic layer 不应该理解 concrete representation。
```

```text
Invariant 3:
新增 concrete type 不应该迫使 generic dispatcher 枚举所有类型。
```

而我认为本节最值得长期记住的一句话是：

> **SICP 4B 不是在教你怎么实现“函数重载”；它在教你如何把 variation point 从程序中的硬编码控制逻辑，提升成一个可以组合、扩展和解释的 abstraction。**

这才是 Generic Operators 在整个 SICP 里的真正位置。
