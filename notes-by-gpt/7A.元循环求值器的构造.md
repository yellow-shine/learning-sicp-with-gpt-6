这节 **Lecture 7A: Metacircular Evaluator, Part 1** 是整门 SICP 的一个非常大的转折点。

前面 1A～6B，你一直在学习：

> **如何用一门语言描述计算。**

到了 7A，Sussman 开始反过来问：

> **“语言本身为什么会有这些含义？”**  
> `lambda` 为什么产生 procedure？  
> `(+ x 1)` 为什么先求 `x` 的值？  
> `cond` 为什么只执行一个分支？  
> procedure 调用为什么会产生新的 environment？  
> 到底是谁规定这些事情？

答案就是：**Evaluator。**

MIT 的课程目录明确把 7A 标为 _Metacircular Evaluator, Part 1_；它对应 SICP 第 4 章开头的 **Metalinguistic Abstraction / 4.1 The Metacircular Evaluator**。7B 才继续深入修改 evaluator 和 evaluation strategy。([MIT OpenCourseWare](https://opencw.aprende.org/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/?utm_source=chatgpt.com "Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

而且 1986 年这节课有一个很有意思的特点：Sussman 故意把 evaluator 写成一个非常紧凑、充满 `car` / `cdr` 的版本，让整个 Lisp evaluator 能放在黑板上；为了突出核心，他甚至暂时省略了 `define` 和 assignment。教材版本则重新加入 abstraction barrier，用 `application?`、`lambda-body`、`lookup-variable-value` 等名字把 representation 隔开。([TAU Open Course Ware](https://ocw.tau.edu.ng/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/7a-metacircular-evaluator-part-1/ "7A: Metacircular Evaluator, Part 1 | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

# 1. 这节课到底想解决什么问题？

## 1.1 前面一直有一个“黑盒”

例如你已经知道：

```scheme
((lambda (x)
   (+ x 1))
 5)
```

结果是：

```text
6
```

以前我们的解释可能是：

```text
把 x 替换成 5
↓
(+ 5 1)
↓
6
```

后来有了 environment model：

```text
创建 frame

x → 5

在这个 environment 中
evaluate (+ x 1)
```

这当然比 substitution model 更强。

但是仍然存在一个更深的问题：

> **谁执行这个规则？**

为什么看到：

```scheme
(lambda (x) (+ x 1))
```

不是立即执行 `(+ x 1)`？

为什么看到：

```scheme
(quote (+ 1 2))
```

不会计算出 `3`？

为什么：

```scheme
(if #t
    1
    (/ 1 0))
```

不会计算 `/ 1 0`？

为什么：

```scheme
(+ 1 (* 2 3))
```

必须先把：

```scheme
(* 2 3)
```

变成 `6`？

这些都不是 `+`、`lambda`、`if` 自己“神奇地知道”的。

存在一个东西：

```text
Evaluator
```

它决定：

```text
这种 expression
应该按照什么规则解释
```

```text
Program = Data
   ↓
Expression
   +
Environment
   ↓
        EVAL
         │
         ├── number ─────────────→ value
         │
         ├── variable ───────────→ lookup environment
         │
         ├── quote ──────────────→ quoted data
         │
         ├── lambda ─────────────→ closure
         │                           │
         │                           ├─ parameters
         │                           ├─ body
         │                           └─ environment
         │
         ├── cond ───────────────→ special evaluation
         │
```

```text
        ↓
fixed point
        ↓
Y combinator
```

所以整节课实际上有两个层次：

```text
第一层：

第二层：

```

# 3. 第一个核心思想：Program 也是 Data

这是理解 7A 的第一道门。

以前看到：

```scheme

```

容易把它想成：

> “一条正在运行的命令。”

但对于 evaluator 来说，它首先只是一个 Lisp list：

```scheme

```

也就是大概：

```text
cons
├── +
└── cons
    ├── 1
    └── cons
        ├── 2
        └── ()
```

```scheme

(cdr exp)
```

问：

```text
这是什么类型的 expression？
```

这是 3B quotation 开始埋下的伏笔。

# 4. `eval`：语言语义的总调度器

Sussman 在 lecture 中首先做的事情，其实非常简单：

> 对 expression 分类。

大致可以理解成：

```scheme
(define (eval exp env)
  (cond
    ((number? exp)
     exp)

    ((symbol? exp)
     (lookup exp env))

    ((quoted? exp)
     ...)

    ((lambda? exp)
     ...)

    ((cond? exp)
     ...)

    (else
     ...application...)))
```

lecture 为了能写在黑板上直接使用具体 `car/cdr`；教材版本则把这些判断包装为 abstract syntax predicates。([TAU Open Course Ware](https://ocw.tau.edu.ng/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/7a-metacircular-evaluator-part-1/ "7A: Metacircular Evaluator, Part 1 | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

这里最重要的不是代码。

而是这个思想：

> **一个 programming language 的 semantics，在 operational level 上可以表现成 expression cases。**

# 5. Self-evaluating expression

最简单：

```scheme
42
```

Evaluator：

```text
eval(42, E)
```

发现：

```text
42 是 number
```

于是：

```text
42
↓
42
```

没有 lookup。

没有 procedure invocation。

可以理解成：

```text
meaning(42) = 42
```

# 6. Variable：为什么 environment 是 evaluator 的参数？

考虑：

```scheme
x
```

仅仅看到符号 `x`：

```text
完全不知道它是多少。
```

必须同时知道：

```text
Environment
```

例如：

```text
E2:
y → 4
parent → E1

E1:
x → 3
parent → E0

E0:
+ → primitive-add
* → primitive-mul
...
```

执行：

```text
eval(x, E2)
```

Evaluator：

```text
x is variable
↓
lookup(x, E2)
```

过程：

```text
E2
x? no
↓
E1
x? yes
↓
3
```

所以 evaluator 的真正基本形式不是：

```text
eval(expression)
```

而是：

```text
eval(expression, environment)
```

这非常关键。

因为：

```scheme
(+ x 1)
```

本身没有唯一意义。

在：

```text
E1: x=3
```

它是 `4`。

在：

```text
E2: x=10
```

它是 `11`。

因此：

> **expression 的 meaning 是 environment-relative 的。**

# 7. Lambda：lambda expression ≠ procedure

这是 7A 最重要的地方之一。

看：

```scheme
(lambda (x)
  (+ x y))
```

初学者非常容易认为：

```text
这就是一个 procedure
```

严格来说不是。

它是：

```text
procedure description
```

Evaluator 看到 lambda 时，需要制造一个真正的 runtime object：

```text
Closure

parameters: (x)

body:
    (+ x y)

environment:
    E
```

也就是：

```text
(lambda expression)
        ↓ eval
   procedure object
        ↓
┌──────────────────────┐
│ parameters: (x)      │
│ body: (+ x y)        │
│ environment: E       │
└──────────────────────┘
```

Sussman 在 lecture 中明确强调 procedure object 必须保存定义 lambda 时的 environment，因为自由变量要在那里解释。([TAU Open Course Ware](https://ocw.tau.edu.ng/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/7a-metacircular-evaluator-part-1/?utm_source=chatgpt.com "7A: Metacircular Evaluator, Part 1 | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

# 8. 为什么 closure 必须保存 environment？

例如：

```scheme
((lambda (x)
   (lambda (y)
     (+ x y)))
 3)
```

先处理外层：

```scheme
(lambda (x)
  (lambda (y)
    (+ x y)))
```

产生 closure：

```text
C1

parameters = x
body       = (lambda (y) (+ x y))
env        = E0
```

应用给 `3`：

```text
x → 3
```

生成：

```text
E1:
x → 3
parent → E0
```

然后 evaluate：

```scheme
(lambda (y)
  (+ x y))
```

注意。

这时候生成的 closure 必须是：

```text
C2

parameters = y
body       = (+ x y)
env        = E1
```

为什么？

因为以后：

```text
x
```

要从 `E1` 找到。

即使外层 procedure 已经返回：

```text
x → 3
```

仍然活着。

这就是：

> **lexical closure。**


# 10. Evaluate operator

operator 是：

```scheme
((lambda (x)
   (lambda (y)
     (+ x y)))
 3)
```

这本身又是 application。

因此：

```text
eval lambda
↓
closure C1
```

C1：

```text
params = (x)

body =
(lambda (y)
  (+ x y))

env = E0
```

同时：

```text
eval 3
↓
3
```

所以：

```text
apply(C1, [3])
```

# 11. APPLY compound procedure

这就是另一个核心 procedure：

```text
APPLY
```

概念上：

```scheme
(apply procedure arguments)
```

如果是 primitive：

```text
直接执行 primitive
```

如果是 compound procedure：

```text
取：
parameters
body
saved environment

        ↓

parameters ↔ arguments

        ↓

extend environment

        ↓

evaluate body
```

SICP 对 compound procedure application 的核心规则正是：在 procedure 保存的 environment 上扩展一个 frame，把 formal parameters 绑定到 actual arguments，再在那里 evaluate procedure body。([SICP Source Academy](https://sicp.sourceacademy.org/chapters/4.1.html?utm_source=chatgpt.com "4.1  The Metacircular Evaluator - SICP Comparison Edition"))

所以：

```text
C1
params: x
args:   3
```

产生：

```text
E1
─────────────
x → 3
─────────────
parent → E0
```

# 12. Evaluate C1 body

现在：

```scheme
(lambda (y)
  (+ x y))
```

在：

```text
E1
```

中 evaluate。

lambda 不执行 body。

而是创建：

```text
C2
────────────────────
params: (y)
body:   (+ x y)
env:    E1
────────────────────
```

于是原来的 operator：

```scheme
((lambda (x) ...)
 3)
```

最终变成了：

```text
C2
```

operand：

```text
4
```

这是 application。

Evaluator：

operand 2：

# 15. `eval` 和 `apply` 到底有什么区别？

这是本节第一大混淆点。

可以记成：

```text
EVAL
输入：
    expression
    environment

问题：
    "这个 expression 意味着什么？"

输出：
    value
```

而：

```text
APPLY
输入：
    procedure
    argument values

问题：
    "把这个 procedure 用在这些 values 上会发生什么？"

输出：
    value
```

换句话说：

```text
EVAL:
syntax → value

APPLY:
procedure + values → value
```

它们组成循环：

```text
                expression
                    │
                    ▼
                  EVAL
                    │
          procedure + values
                    │
                    ▼
                  APPLY
                    │
       expression + environment
                    │
                    └──────────→ EVAL
```

这就是为什么教材把它称为 evaluator 的核心 cycle。([SICP Source Academy](https://sicp.sourceacademy.org/chapters/4.1.1.html?utm_source=chatgpt.com "4.1.1   The Core of the Evaluator - SICP Comparison Edition"))

# 16. 为什么 `apply` 又会回到 `eval`？

假设：

```scheme
(square 5)
```

`eval` 最终得到：

```text
procedure:
    params: x
    body: (* x x)
    env: E0

arguments:
    [5]
```

此时 `apply` 并不知道：

```text
(* x x)
```

是多少。

它只能：

```text
创建：
x → 5

然后：

eval((* x x), new-env)
```

所以：

```text
eval → apply → eval
```

不是偶然实现细节。

这是：

> **procedure application 的定义本身。**

# 17. Primitive procedure vs compound procedure

这里一定要分清。

### Primitive

比如：

```scheme
+
car
cdr
cons
=
```

Evaluator 最终把它交给底层 Scheme：

```text
apply primitive-add [3,4]
↓
host Scheme / machine operation
↓
7
```

---

### Compound procedure

比如：

```scheme
(lambda (x)
  (* x x))
```

它的实现不是 machine primitive。

而是：

```text
parameters
+
body
+
environment
```

所以 apply：

```text
bind arguments
↓
new environment
↓
eval body
```

---

## 一个非常深的点

那么 evaluator 自己没有实现加法？

基本可以这么理解。

它假设存在一些 primitive。

SICP 指出 evaluator 真正负责的是把 primitives 连成一门语言的 **glue**：

```text
nested expressions
variables
procedure abstraction
procedure application
special forms
```

例如 primitive `+` 本身根本不知道：

```scheme
(+ x (* 2 3))
```

是什么意思。

Evaluator 必须先把：

```scheme
(* 2 3)
```

变成：

```text
6
```

把：

```scheme
x
```

lookup 成某个 value，然后 primitive `+` 才能工作。([SICP Source Academy](https://sicp.sourceacademy.org/chapters/4.1.html?utm_source=chatgpt.com "4.1  The Metacircular Evaluator - SICP Comparison Edition"))

这正是语言 runtime 的本质之一：

> primitives 并不构成 language；  
> **composition rules + abstraction rules + evaluation rules** 才构成 language。

# 18. Special Form 为什么不能全部做成普通 procedure？

这是 7A 非常重要的 language-design insight。

例如：

```scheme
(cond
  ((= x 0) 1)
  (else (/ 1 x)))
```

为什么不能简单：

```text
evaluate operator
evaluate every operand
apply
```

因为这样会：

```text
evaluate 所有 branch
```

但 conditional 的意义是：

```text
evaluate predicate
↓
只 evaluate 被选择的 expression
```

因此：

```text
COND / IF
```

必须控制：

> **哪些 expression 被 evaluate，以及什么时候 evaluate。**

普通 procedure 收到的是：

```text
already evaluated arguments
```

special form 收到的是：

```text
syntax / unevaluated expressions
```

这是关键区别。

# 19. `quote` 更明显

```scheme
(quote (+ 1 2))
```

如果它是 ordinary application：

```text
evaluate (+ 1 2)
↓
3
```

就太晚了。

`quote` 的语义恰恰是：

```text
DO NOT EVALUATE
```

因此 evaluator 必须特别识别：

```text
quote
```

然后直接返回里面的 data。

---

# 20. `lambda` 也是 Special Form

这个经常被忽略。

如果：

```scheme
(lambda (x)
  (+ x 1))
```

像普通 procedure call 一样 evaluate operands：

那么：

```scheme
(x)
```

和：

```scheme
(+ x 1)
```

都可能提前 evaluation。

这完全不对。

lambda 的语义是：

```text
Don't evaluate body now.

package:

parameters
body
current environment

into a closure
```

因此：

```text
lambda expression
      ↓
   closure
```

# 21. `EVLIST`：Applicative-order evaluation 藏在哪里？

Lecture 版本中还有一个：

```text
EVLIST
```

它做的事情非常简单：

```text
operands

(e1 e2 e3)

↓

(eval e1 env)
(eval e2 env)
(eval e3 env)

↓

(v1 v2 v3)
```

之后：

```text
apply(proc, [v1,v2,v3])
```

所以这个 evaluator 是：

> **applicative-order / eager evaluation**

也就是：

```text
先 evaluate operands
↓
再 apply procedure
```

这对应你在 1B 学过的：

```text
Applicative-order Evaluation
```

# 22. 这时候终于能看到 applicative order 在哪里实现了

以前这似乎只是一个“规则”：

```text
evaluate arguments first
```

现在你会发现：

> 它就是 evaluator 中的一段程序。

例如：

```scheme
(apply
  (eval operator env)
  (evlist operands env))
```

如果我把 `EVLIST` 改掉：

```text
不要立即 eval operand
```

而是把它包装起来：

```text
thunk
```

那么语言就可能变成 lazy language。

# 26. 一个非常重要的设计思想：Syntax 和 Semantics 分开

# 27. 到这里整个 evaluator 可以压缩成两个 procedure

教材更清楚地写成：

```text
EVAL(exp, env)

case exp:

literal
    → literal

variable
    → lookup

quote
    → quoted value

lambda
    → closure(params, body, env)

if
    → evaluate selected branch

begin
    → evaluate sequence

application
    → APPLY(
          EVAL(operator, env),
          EVAL-OPERANDS(operands, env)

```

然后：

```text
APPLY(proc, args)

    → primitive operation

if compound

          EXTEND(
              params(proc),
              args,
              environment(proc)
          )
```

# 33. 把 recursion 看成 equation

Sussman 的关键转变是：

不要只把：

```scheme

```

```text

```

```scheme
F(g)
```

意思：


```scheme
F =
λg.
  λ(x,n).
```


```text

```

> EXPT 是 F 的 **fixed point**。

# 34. Fixed Point 是什么？

如果：

```text
F(x) = x
```

那么：

```text
x
```

就是：

```text
F 的 fixed point
```

最熟悉的 SICP 例子其实早就出现过：

```text
cos(x) = x
```

不断：

```text
x
↓
cos x
↓
cos(cos x)
↓
...
```

可能趋向一个 fixed point。

现在把：

```text
number
```

换成：

```text
procedure
```

而已。

以前：

```text
F : number → number
```

现在：

```text
F : procedure → procedure
```

# 35. `F` 如何逐渐构造 exponentiation？

假设：

```text
E0 = completely useless procedure
```

例如任何输入都 error。

然后：

```text
E1 = F(E0)
```

E1 至少知道：

```text
x^0 = 1
```

但：

```text
x^1
```

可能失败。

再：

```text
E2 = F(E1)
```

因为 E1 会算：

```text
x^0
```

所以 E2 能算：

```text
x^1
```

再：

```text
E3 = F(E2)
```

能算：

```text
x^2
```

于是：

```text
E0
↓ F
E1
↓ F
E2
↓ F
E3
↓
...
```

直觉上：

```text
limit → EXPT
```

Lecture 用这个近似序列来说明递归方程的 fixed-point 意义，同时也提醒这种 limit argument 需要数学条件，不能随便对所有无限结构做代数操作。([TAU Open Course Ware](https://ocw.tau.edu.ng/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/7a-metacircular-evaluator-part-1/ "7A: Metacircular Evaluator, Part 1 | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

# 37. Y 的真正意义不是“炫技”

# 38. 一个重要警告：Y combinator 与 Scheme 的 eager evaluation

这里我要额外帮你避开一个非常常见的坑。

经典 lambda calculus 中：

```text

```

很好。

但是 Scheme 是：

```text
applicative-order
```

如果你直接把经典 Y combinator 原样放进严格 Scheme：

```text

必须先算 Y F

为了算 Y F
又必须先算 Y F

...
```

很容易立即无限展开。

所以：

```text
classical Y combinator
```

更自然地对应 normal-order lambda calculus。

严格语言中通常需要：

```text
delay / thunk
```

或 η-expansion，得到类似 strict fixed-point combinator / Z combinator 的形式。

这和前面的 evaluator 主题其实恰好连起来：

```text
fixed-point expression 是否能运行
        ↓
依赖 evaluation strategy
```

这也再次证明：

> evaluation order 不是无关紧要的实现细节。

# 41. `eval` 本身是递归 procedure，那它产生什么 process？

注意不要混两层。

Evaluator：

```text
eval ↔ apply
```

当然是 mutual recursion。

但：

```text
object program 是否产生 recursive process
```

仍然由 object program 决定。

例如：

```scheme
(define (fact n)
  (if (= n 0)
      1
      (* n (fact (- n 1)))))
```

仍然产生：

```text
fact 5
↓
5 * fact 4
↓
5 * (4 * fact 3)
...
```

需要 deferred multiplication：

```text
space O(n)
```

而：

```scheme
(define (fact-iter product n)
  (if (= n 0)
      product
      (fact-iter (* product n)
                 (- n 1))))
```

产生：

```text
(product=1,n=5)
↓
(product=5,n=4)
↓
(product=20,n=3)
↓
...
```

是 iterative process。

如果 host Scheme 实现 proper tail calls，并且 evaluator 在 tail positions 中继续 tail-call `eval`/`apply`，metacircular evaluator 可以保留这种 tail-recursive 行为。

所以：

> **eval/apply 本身用了 recursion，不意味着所有被解释程序都消耗线性 stack。**

Scheme 中没有：

```text
[x]
```

这种 capture list。

Evaluator 根据 lexical scoping 自然决定：

```text
free variable x
从 closure saved environment 找
```

# 50. 这一节的几个关键 Concept Distinctions

## Expression vs Value

```scheme
(lambda (x) (+ x 1))
```

是 expression。

evaluate 后：

```text
closure(...)
```

是 value。

类似：

```scheme
(+ 1 2)
```

是 expression。

```text
3
```

是 result value。

---

## Lambda expression vs Closure

```text
lambda expression
=
syntax

closure
=
runtime value
```

即：

```text
(lambda (x) (+ x y))
        ↓ EVAL
closure {
    params: x
    body: (+ x y)
    env: E
}
```

---

## Eval vs Apply

```text
eval:
expression + environment → value

apply:
procedure + values → value
```

---

## Special form vs Procedure

Procedure：

```text
arguments evaluated first
```

Special form：

```text
controls evaluation of its subexpressions
```

---

## Lexical Environment vs Dynamic Caller

Closure 使用：

```text
environment where procedure was CREATED
```

不是：

```text
environment where procedure was CALLED
```

这是 lexical scope 的核心。

---

## Metacircular vs Circular reasoning

Metacircular：

```text
implementation language
=
implemented language
```

不意味着逻辑错误。

实际底层仍然有一个：

```text
host implementation
```

提供 primitive execution。
