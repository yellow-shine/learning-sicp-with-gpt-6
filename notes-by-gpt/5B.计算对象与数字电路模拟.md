# 1. 这节课到底想解决什么问题？

## 1.1 从纯函数世界到“对象世界”

在 5A 之前，我们擅长的是：

```text
input
 ↓
procedure
 ↓
output
```

例如：

```scheme
(define (square x)
  (* x x))
```

`square` 没有历史。

```scheme
(square 5)
```

无论你昨天调用过多少次，结果还是 `25`。

这是一个接近数学函数的世界：

$$
f(x)=y
$$

---

5A 加入：

```scheme
set!
```

于是我们可以有：

```scheme
(define balance 100)

(define (withdraw amount)
  (set! balance (- balance amount))
  balance)
```

现在：

```scheme
(withdraw 20) ; 80
(withdraw 20) ; 60
```

第二次 `(withdraw 20)` 的意义取决于**过去发生过什么**。

程序中出现：

```text
identity
state
time
history
```

而 substitution model 已经不足以完整解释它了。

---

## 1.2 但只有一个 mutable variable 还远远不够

真正的问题不是：

> 怎么修改一个变量？

而是：

> 怎么构造很多**独立拥有状态的东西**？

例如现实中的银行系统：

```text
account A
    balance = 100

account B
    balance = 200
```

或者数字电路：

```text
wire A --\
          AND ---- wire C ---- NOT ---- wire D
wire B --/
```

这里：

- A 有自己的 signal
    
- B 有自己的 signal
    
- C 有自己的 signal
    
- 每根 wire 还需要知道“我的值变化以后通知谁”
    
- gate 需要记住自己连接到哪些 wire
    
- signal 变化会触发其他 computation
    
- 变化不是瞬间传播，还存在 delay
    

于是程序不能再只是：

```text
function composition
```

而开始变成：

```text
object
 ├── local state
 ├── operations
 ├── connections
 └── interactions
```

Sussman 在这一讲一开始几乎就明确提出了这个目标：

> 给现实世界中的每个对象一个 computational object，并让现实对象之间的关系对应到计算机对象之间的关系。

这样做的收益是 **modularity**。([TAU Open Course Ware](https://ocw.tau.edu.ng/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/5b-computational-objects/?utm_source=chatgpt.com "5B: Computational Objects | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

# 4. 第一核心思想：Computational Object

## 4.1 直觉

一个 computational object 是：

> 一个有身份、有自己的状态，并且允许外界通过某些操作与它交互的计算实体。

SICP 并没有首先引入：

```scheme
class Wire ...
```

因为 Scheme 根本不需要 `class` 才能构造对象。

它用：

```text
closure + local state + message dispatch
```

直接把 object 从更基础的语言机制里“造出来”。

---

# 5. 从最小对象开始：counter

暂时不要上数字电路。

先写：

```scheme
(define (make-counter)
  (let ((count 0))
    (lambda ()
      (set! count (+ count 1))
      count)))
```

然后：

```scheme
(define c1 (make-counter))
(define c2 (make-counter))
```

运行：

```scheme
(c1) ; 1
(c1) ; 2
(c2) ; 1
```

关键问题：

> 为什么 `c1` 和 `c2` 不共享 `count`？

答案不能用 substitution model 很漂亮地说明。

必须用 **environment model**。

---

# 6. `make-counter` 的 Environment Model

执行：

```scheme
(define c1 (make-counter))
```

首先调用 `make-counter`。

产生一个 frame：

```text
Global Environment
│
├── make-counter → procedure
│
└── c1 → ?
     ↑
     │
     E1
     ├── count = 0
     │
     └── returned procedure
            |
            +---- environment pointer → E1
```

真正返回的不是单纯：

```scheme
(lambda ()
  ...)
```

而是一个 **procedure object**：

```text
procedure object
├── code:
│     (lambda ()
│       (set! count ...)
│       count)
│
└── environment → E1
```

因此它记住了：

```text
count lives in E1
```

调用：

```scheme
(c1)
```

会建立：

```text
E2
(empty parameter frame)
  ↓ enclosing
E1
count = 0
```

寻找 `count`：

```text
E2: 没有
 ↓
E1: count = 0
```

执行：

```scheme
(set! count 1)
```

不是创造新的变量。

而是修改 E1：

```text
E1
count: 0 → 1
```

下一次 `(c1)` 仍然捕获同一个 E1。

于是：

```text
count = 1 → 2
```

---

# 7. 为什么这就是 object？

因为 `c1` 具有：

```text
identity
   +
private state
   +
behavior
```

再创建：

```scheme
(define c2 (make-counter))
```

产生另一个 environment：

```text
c1
 ↓
procedure
 ↓
E1
count = 2


c2
 ↓
procedure
 ↓
E3
count = 0
```

所以：

```text
c1 ≠ c2
```

即使它们来自完全相同的代码。

这是 assignment 带来的一个巨大变化：

> **identity 开始具有意义。**

纯函数世界里：

```scheme
(list 1 2)
(list 1 2)
```

只要值一样，通常可以互换。

mutable object 世界里：

```text
两个内容一样的对象
```

不一定等价，因为未来其中一个可以变化而另一个不变。

# 8. 第二核心机制：Message Passing

只有：

```scheme
(lambda ()
  ...)
```

能力太弱。

我们希望对象支持多个操作。

例如：

```text
wire:
    get-signal
    set-signal!
    add-action!
```

于是使用 dispatch procedure。

一个简化版本：

```scheme
(define (make-cell)
  (let ((value 0))

    (define (set-value! new-value)
      (set! value new-value))

    (define (dispatch message)
      (cond ((eq? message 'get) value)
            ((eq? message 'set) set-value!)
            (else
             (error "Unknown message"))))

    dispatch))
```

使用：

```scheme
(define x (make-cell))

(x 'get)
```

得到：

```text
0
```

而：

```scheme
((x 'set) 10)
```

先：

```scheme
(x 'set)
```

得到 procedure：

```scheme
set-value!
```

然后：

```scheme
(set-value! 10)
```

---

# 9. 展开 `((x 'set) 10)`

这一行非常值得展开。

```scheme
((x 'set) 10)
```

AST 大致是：

```text
application
├── operator: (x 'set)
└── operand: 10
```

Applicative-order：

```text
evaluate operator
        ↓
evaluate (x 'set)
        ↓
x → dispatch procedure
'set → symbol set
        ↓
apply dispatch
        ↓
message = 'set
        ↓
return set-value! procedure
```

现在原表达式变成：

```text
(set-value! 10)
```

再次：

```text
evaluate operator
    ↓
set-value! → procedure

evaluate operand
    ↓
10

apply procedure
    ↓
new-value = 10
    ↓
(set! value 10)
```

关键点：

> **message 返回的甚至可以是一个 procedure。**

所以对象实际上在说：

```text
“你问我要 set operation？
这是执行这个 operation 的能力。”
```

# 12. 为什么数字电路不是写成一个大函数？

例如你当然可以写：

```scheme
(define (circuit a b)
  (not (and a b)))
```

逻辑值是对的。

但这遗漏了非常重要的信息：

```text
wire state
gate delay
signal propagation
fan-out
history
events
```

真实数字电路并不是数学函数：

$$
D=\neg(A\land B)
$$

这么简单。

更准确是：

```text
A changes
    ↓
AND gate notices
    ↓
wait AND-DELAY
    ↓
C changes
    ↓
inverter notices
    ↓
wait INVERTER-DELAY
    ↓
D changes
```

所以我们需要模拟：

> **process evolving through time**

而不仅是计算最终数学结果。

# 15. Half Adder：为什么这个例子如此重要

视频中的结构近似：

```scheme
(define (half-adder a b s c)
  (let ((d (make-wire))
        (e (make-wire)))
    (or-gate a b d)
    (and-gate a b c)
    (inverter c e)
    (and-gate d e s)
    'ok))
```

对应：

```text
              +------+
A ---+------->| OR   |---- D ----+
     |        +------+           |
     |                           AND ---- S
     |        +------+           |
B ---+------->| AND  |---- C --> NOT -- E
              +------+
                         |
                         +------------ CARRY
```

注意 `d` 和 `e`：

```scheme
(let ((d ...)
      (e ...))
 ...
)
```

它们是**internal wires**。

外界只看到：

```text
a
b
s
c
```

这就是 abstraction boundary。

```text
           HALF ADDER
      +-----------------+
 A -->|                 |--> S
 B -->|   d/e hidden    |--> C
      +-----------------+
```

# 17. 第四个核心机制：Wire 是一个真正的 stateful object

Lecture 5B 中最值得吃透的是 `make-wire`。

简化后的原始结构：

```scheme
(define (make-wire)
  (let ((signal 0)
        (action-procs '()))

    (define (set-my-signal! new)
      (if (= signal new)
          'done
          (begin
            (set! signal new)
            (call-each action-procs))))

    (define (accept-action-proc proc)
      (set! action-procs
            (cons proc action-procs))
      (proc))

    (define (dispatch m)
      (cond ((eq? m 'get-signal)
             signal)
            ((eq? m 'set-signal!)
             set-my-signal!)
            ((eq? m 'add-action!)
             accept-action-proc)
            (else
             (error "Bad message"))))

    dispatch))
```

这基本就是整讲的浓缩。视频确实用 `signal` 与 `action-procs` 作为 wire 的 local state，再通过 dispatch 接受消息。([TAU Open Course Ware](https://ocw.tau.edu.ng/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/5b-computational-objects/?utm_source=chatgpt.com "5B: Computational Objects | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

# 20. `make-wire` 的 Environment Model

执行：

```scheme
(define a (make-wire))
```

产生：

```text
Global Environment
│
├── make-wire → procedure
│
└── a
     ↓
 dispatch procedure
     │
     └──────────────→ E1
                      │
                      ├── signal = 0
                      │
                      ├── action-procs = ()
                      │
                      ├── set-my-signal! → proc ─┐
                      ├── accept-action-proc →   │
                      └── dispatch →             │
                                                │
                        all closures capture E1 ─┘
```

这里要建立一个非常重要的 mental model：

> **一个 object 的多个 methods，可以通过闭包共享同一个 environment。**

因此：

```text
get
set
add-action
```

不是彼此独立的函数。

它们共享：

```text
signal
action-procs
```

这就是对象的内部状态。

# 21. `set-signal!` 为什么需要 side effect？

外层 API：

```scheme
(define (set-signal! wire new-value)
  ((wire 'set-signal!) new-value))
```

展开：

```scheme
(set-signal! a 1)
```

第一步：

```text
wire = a
new-value = 1
```

计算：

```scheme
(a 'set-signal!)
```

a 是 `dispatch`：

```text
dispatch('set-signal!)
        ↓
return set-my-signal!
```

然后：

```scheme
(set-my-signal! 1)
```

进入 wire 自己的 environment：

```text
E1:
signal = 0
actions = (...)
```

判断：

```scheme
(= signal new)
```

即：

```text
0 == 1 ?
```

false。

所以：

```scheme
(set! signal 1)
```

环境发生变化：

```text
signal
0
↓
1
```

然后：

```scheme
(call-each action-procs)
```

以前：

```text

    ↓
compute value
```

现在：

```text
mutation
   ↓
notifications
   ↓
procedure calls
   ↓
more mutations
   ↓

```

于是 computation 形状变成：

```text
event
 ↓
state change
 ↓
callback
 ↓
schedule event
 ↓
later state change
 ↓
callback
 ...
```

这是一个完全不同的 computation model。

# 23. 第五核心机制：Gate 不是“计算一次”，而是注册行为

看 inverter：

```scheme
(define (inverter input output)

  (define (invert-input)
    (let ((new-value
           (logical-not
            (get-signal input))))

      (after-delay
       inverter-delay

       (lambda ()
         (set-signal! output
                      new-value)))))

  (add-action! input invert-input))
```

不要把它理解成：

> inverter 接收 input，返回 output。

不是。

它更像：

> inverter 把一段 callback 注册到 input wire 上。

也就是说：

```scheme
(inverter a b)
```

不是：

```text
calculate b now
```

而是建立：

```text
when A changes
    ↓
run invert-input
    ↓
calculate new B
    ↓
schedule B update
```

# 24. 这里 procedure 为什么必须是一等公民？

这里是 higher-order procedure 真正进入“系统编程”的地方。

```scheme
(add-action! input invert-input)
```

传的不是：

```text
数据
```

而是：

```text
未来应该执行的 computation
```

也就是把：

> **行为本身**

变成一个值。

更准确地说：

```text
procedure as value
        ↓
store computation
        ↓
pass computation
        ↓
execute computation later
```

这就是现代：

```text
callback
handler
continuation-like thunk
event listener
task
```

的重要基础思想。

# 25. 为什么 `(lambda () ...)` 没有参数？

你会大量看到：

```scheme
(lambda ()
  (set-signal! output new-value))
```

它不是用来：

```text
接受数据
```

而是用来：

> **包装一个 computation，让它现在先别运行。**

例如：

```scheme
(set-signal! output new-value)
```

会立刻执行。

但是：

```scheme
(lambda ()
  (set-signal! output new-value))
```

得到：

```text
procedure object
```

现在它是一个可以存储的东西。

以后：

```scheme
(action)
```

才执行。

这是一个非常重要的 pattern：

```text
expression
↓ wrap in lambda
thunk
↓ store / pass
execute later
```

后面的：

```text
streams
lazy evaluation
interpreters
```

你还会反复看到它。

# 33. 为什么 Agenda 不是简单 list，而需要时间 segment？

# 34. 为什么相同时间需要 Queue？

假设：

```text
time = 10
```

有：

```text
action A
action B
action C
```

需要保持：

```text
A → B → C
```

即 FIFO。

这不是随便的实现细节。

因为同一逻辑时间内，多个 signal update 的处理顺序可能影响中间状态。

所以一个关键 invariant 是：

```text
earlier scheduled action
        ↓
must execute earlier
```

同一 timestamp：

```text
FIFO
```

保证事件传播符合 simulator 的语义。

# 40. Queue representation

```text
queue
  |
  +---- front-ptr ----+
  |                   v
  |                 +---+---+   +---+---+   +---+---+
  |                 | A | •---->| B | •---->| C | / |
  |                 +---+---+   +---+---+   +---+---+
  |                                             ↑
  +---- rear-ptr -------------------------------+
```

于是 append D：

```text
rear currently C

(set-cdr! C new-node-D)

```

都是：

$$

# 41. `insert-queue!`

核心逻辑：

```scheme
(define (insert-queue! queue item)
  (let ((new-pair
         (cons item '())))

    (if (empty-queue? queue)

        (begin
          (set-front-ptr!
           queue new-pair)

          (set-rear-ptr!
           queue new-pair))

        (begin
          (set-cdr!
           (rear-ptr queue)
           new-pair)

          (set-rear-ptr!
           queue new-pair)))))
```

非空时：

原来：

```text
front
 ↓
A → B → C
        ↑
       rear
```

创建：

```text
D → ()
```

执行：

```scheme
(set-cdr! C D)
```

变成：

```text
A → B → C → D
```

再：

```scheme
(set-rear-ptr! queue D)
```

最终：

```text
front
 ↓
A → B → C → D
            ↑
           rear
```

这就是典型的 mutable data structure update。

# 42. 一个非常重要的 queue invariant

任何时刻：

```text
front-ptr
    ↓
first item
```

以及：

```text
rear-ptr
    ↓
last item
```

并且如果 queue 非空：

```text
rear-ptr.cdr = ()
```

如果为空：

```text
front-ptr = ()
```

rear pointer 的具体残留值有时甚至可以无所谓，只要所有公开操作遵守 abstraction contract。

这也是 SICP 在训练你：

> **representation invariant**

# 45. 最值得区分：Pure function vs Stateful object

### Pure function

```scheme
(define (f x)
  (+ x 1))
```

行为：

```text
input determines output
```

所以：

```text
f(10) always → 11
```

---

### Stateful object

```scheme
(counter)
```

行为由：

```text
input
+
current state
```

共同决定。

即：

$$
Output_t = f(Input_t, State_t)
$$

同时：

$$
State_{t+1}=g(Input_t, State_t)
$$

这是一个更好的数学模型。

所以 object 更像一个：

```text
state machine
```

而不是普通函数。

# 46. Stateful Object 更准确的 mental model

不要想：

```text
object = struct + methods
```

那是某些现代语言的语法表现。

SICP 更基础的模型是：

```text
       incoming message/event
                ↓
        +----------------+
        | local state    |
        |                |
        | behavior       |
        +----------------+
                ↓
           new state
                +
             effects
                ↓
       other objects/events
```

也就是：

$$
(state,\ input) \rightarrow (new\ state,\ output/effects)
$$

# 50. Immediate computation vs deferred computation

这是本节必须掌握的区别。

```scheme
(f x)
```

含义：

```text
现在算
```

而：

```scheme
(lambda ()
  (f x))
```

含义：

```text
构造一个以后能算 (f x) 的 computation
```

例如：

```scheme
(after-delay 5
             (f x))
```

这是错的设计，因为 `(f x)` 会先求值。

正确：

```scheme
(after-delay 5
             (lambda ()
               (f x)))
```

现在 agenda 存的是：

```text

```

而不是执行结果。

# 51. Applicative-order evaluation 在这里非常重要

为什么必须用 lambda 包？

因为 Scheme 使用 applicative-order。

如果：

```scheme
(after-delay 5
             (set-signal! out 1))
```

evaluation：

```text
evaluate operator
after-delay

evaluate operand 1
5

evaluate operand 2
(set-signal! out 1)
        ↓
RUN IT NOW
```

然后把结果传给 `after-delay`。

完全错。

但：

```scheme
(after-delay
 5
 (lambda ()
   (set-signal! out 1)))
```

evaluation：

```text
evaluate lambda
    ↓
create procedure object
    ↓
DON'T execute body
```

于是：

```text
future computation
```

被成功表示出来。

这是 **evaluation model 直接影响 API design** 的绝佳例子。

# 54. Agenda 的复杂度

Lecture 里的 agenda 基本是：

```text
sorted linked list of time segments
```

所以假设当前有 $n$ 个 timestamp segments。

寻找 insertion point：

$$
O(n)
$$

同一 segment 中 enqueue：

$$
O(1)
$$

借助 front/rear pointer 的 queue：

```text
enqueue O(1)
dequeue O(1)
```

现代 simulation engine 往往会用：

```text
priority queue / binary heap
```

让 event insertion：

$$
O(\log n)
$$

但 SICP 的重点不在最佳数据结构，而是：

> 上层 simulator 不应该依赖 agenda 的具体 representation。

# 57. 这一节的几个核心 Pattern

## Pattern 1：Closure Object

```scheme
(define (make-object)
  (let ((state initial-value))

    (define (operation ...)
      ... state ...)

    (define (dispatch message)
      ...)

    dispatch))
```

识别方式：

```text
constructor
 ↓
local state
 ↓
internal procedures
 ↓
returned dispatch closure
```

看到这个结构：

> 这就是 Scheme object。

# 58. Pattern 2：Observer / Reactive propagation

```scheme
state changes
     ↓
call registered procedures
```

模式：

```scheme
(define (set-value! new)
  (if changed?
      (begin
        (set! value new)
        (call-each listeners))))
```

以后看到：

```text
watchers
listeners
subscriptions
callbacks
```

都可以联想到这个 pattern。

# 59. Pattern 3：Deferred Computation

```scheme
(lambda ()
  computation)
```

模式：

```text
computation
    ↓
wrap as procedure
    ↓
pass/store it
    ↓
execute later
```

后面非常重要。

    event = earliest-event

    remove event
```

event loop

task scheduler
```

# 62. 常见误区一：Object 就是 class

**误解：**

> 这一讲是在古早 Scheme 里模拟 class。

不够准确。

真正的 lesson 是：

```text
object-ness
来自：

identity
+
local state
+
behavior
+
message interaction
```

`class` 只是某些语言对这个 pattern 的语法支持。

---

# 63. 常见误区二：Closure 只是“函数引用了外部变量”

这个定义没错，但太浅。

5B 中 closure 实际承担：

```text
private storage
```

它让：

```scheme
dispatch
set-my-signal!
accept-action-proc
```

长期保持对同一个：

```text
signal
action-procs
```

的访问。

所以 closure 可以实现：

```text
encapsulation
object identity
persistent local state
```

---

# 64. 常见误区三：`inverter` 是计算输出的函数

不是：

```text
input → function → output
```

它主要是在建立 connectivity：

```text
input wire
    ↓ register callback
inverter action
    ↓
output wire
```

所以：

```scheme
(inverter a b)
```

更像：

```text
connect(a, inverter, b)
```

而不是：

```text
b = !a
```

---

# 65. 常见误区四：`lambda ()` 只是为了语法好看

完全不是。

它改变了 evaluation timing：

```text
(f)
```

= run computation

而：

```text
(lambda () (f))
```

= construct computation

这是这节课最值得记住的 evaluation insight 之一。

---

# 66. 常见误区五：Agenda 只是一个容器

不对。

Agenda 实际上定义了：

> **这个模拟世界中的时间语义。**

它决定：

```text
哪个事件先发生
logical time 什么时候推进
simultaneous events 如何排序
```

所以 agenda 是 simulator 的一部分 computation model，而不仅是 implementation detail。

---

# 67. 常见误区六：Mutation 只是让代码写起来方便

5B 恰好在展示 mutation 的真正能力：

```text
persistent object identity
dynamic relationships
queues
mutable graph
event systems
local state
```

但 mutation 的代价是：

```text
substitution model gone
aliasing
history dependence
ordering dependence
reasoning becomes harder
```

所以 Chapter 3 不是简单宣传 mutation。

它实际上在研究：

> **state 给我们什么表达能力，又让 reasoning 付出什么代价。**

下一讲 streams 就会提供另一种组织时间的方法。

不要完全等同。

SICP wire：

procedure dispatch convention

并没有天然意味着：

# 69. 最重要的 Evaluation Model 变化

前半本书开始时：

```text
expression
 ↓
substitute parameters
 ↓
simplify expression
 ↓
value
```

现在必须变成：

```text
expression
 ↓
lookup operator in environment
 ↓
evaluate operands
 ↓
apply procedure
 ↓
create frame
 ↓
bind parameters
 ↓
evaluate body
 ↓
possibly mutate an existing frame/object
 ↓
possibly trigger/schedule other procedures
 ↓
future evaluations observe changed state
```

这最后几步是质变。

# 70. 一个完整运行例子

假设：

```text
A ---- inverter ---- B

inverter-delay = 2
```

初始：

```text
time = 0
A = 0
B = 1
```

现在：

```scheme
(set-signal! A 1)
```

### Step 1：修改 A

```text
A.signal:
0 → 1
```

### Step 2：A 通知 listeners

其中有：

```text
invert-input
```

所以执行：

```scheme
(invert-input)
```

### Step 3：读取 A

```scheme
(get-signal A)
→ 1
```

计算：

```text
logical-not(1)
→ 0
```

### Step 4：不是现在修改 B

而是：

```scheme
(after-delay
 2
 (lambda ()
   (set-signal! B 0)))
```

### Step 5：Agenda

```text
time 2:
    set B = 0
```

### Step 6：

运行：

```scheme
(propagate)
```

agenda 取出 event：

```text
advance logical time:
0 → 2
```

执行 thunk：

```scheme
(set-signal! B 0)
```

### Step 7：

B：

```text
1 → 0
```

然后 B 又通知自己的 listeners。

所以完整链路是：

```text
mutation
 ↓
notification
 ↓
computation
 ↓
schedule
 ↓
event loop
 ↓
future mutation
 ↓
notification
 ...
```

这就是 Lecture 5B 的 computational model。

# 75. 你真正需要记住的东西

如果最后只留下 **5 个核心思想**：

### ① Object 可以由 closure + local state 构造

```text
object
≈
private environment
+
procedures that capture it
```

这是这一讲第一重要的 mental model。

### ② Assignment 让 identity、time、history 进入 computation

有 mutation 后：

```text
value alone
```

已经不足以描述程序。

你需要考虑：

```text
which object?
when?
what happened before?
who aliases it?
```

### ③ Procedure 不只是“函数”

procedure 可以表示：

```text
future computation
callback
behavior
event action
```

所以：

```scheme
(lambda () ...)
```

是极其强大的 computation representation。

### ④ 大系统可以建模为 interacting objects

```text
local state
+
interfaces
+
connections
+
events
```

这种结构让程序继承现实系统的 modularity。

### ⑤ 一个好的 abstraction 必须支持 hierarchical composition

```text
primitive
↓
compound
↓
compound can be used like primitive
```

这是 SICP 从 picture language 到 circuit language 一直坚持的原则。

```text
environment + closure
message dispatch
mutable pair
callback registration
agenda + event propagation
```

最后记住 **3 个不变量**：

```text
1. 一个 closure 总是在创建它的 lexical environment 中寻找自由变量。

2. mutation 修改的是现有 location/object，
   不是简单产生一个数学上的新 value。

3. event-driven simulation 的正确性依赖：
   events 按 logical time 顺序执行，

```
