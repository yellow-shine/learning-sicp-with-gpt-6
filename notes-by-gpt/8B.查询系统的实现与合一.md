# Lecture 8B — Logic Programming, Part 2

这一讲是 SICP 里非常重要的一讲，因为它第一次非常直接地让你看到：

> **一种语言表面上的“思维方式”，最终是如何由 evaluator、数据结构和搜索策略实现出来的。**

8A 主要让你体验：

> “我不再写一个 procedure 告诉计算机怎么算，而是描述什么关系成立，让系统替我寻找满足关系的值。”

8B 紧接着追问：

> **那这个看起来会“推理”的系统，底下到底发生了什么？**

讲座本身一开始就是从这个问题进入：前面已经看到 query language 怎么使用，现在开始解释它怎么实现；实现的核心一路经过 pattern matching、frame streams、unification 和 rule application。([OCW ITI](https://ocw.iti.hr/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/8b-logic-programming-part-2/ "8B: Logic Programming, Part 2 | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

而这一讲最后还有一个更深的问题：

> **它真的在做“逻辑”吗？**

答案是：**不完全是。**

这也是 8B 真正值得学的地方。

## 1.1 在 8B 之前，我们已经会什么？

假设数据库里有：

```scheme
(job (Alice) (computer programmer))
(job (Bob)   (computer manager))

(supervisor (Alice) (Bob))
```

8A 让我们可以写：

```scheme
(job ?x (computer programmer))
```

得到：

```text
?x = Alice
```

还可以写：

```scheme
(and
  (job ?x (computer programmer))
  (supervisor ?x ?boss))
```

甚至定义规则：

```scheme
(rule (boss ?person ?division)
      (and
        (job ?employee (?division . ?rest))
        (supervisor ?employee ?person)))
```

表面上看很神奇：

```text
我写关系
    ↓
系统自动找答案
```

但是这个“自动”到底是什么？

# 1.2 普通 Scheme evaluator 为什么不够？

回忆普通 Scheme：

```scheme
(square 5)
```

计算模型是：

```text
(square 5)
    ↓
找到 procedure square
    ↓
绑定 x = 5
    ↓
evaluate (* x x)
    ↓
25
```

它天然是：

```text
input
  ↓
procedure
  ↓
output
```

但是逻辑查询：

```scheme
(supervisor ?x ?y)
```

没有明确 input / output。

它可能产生：

```text
0 个答案
1 个答案
很多答案
无限多个答案
```

甚至：

```scheme
(append-to-form ?x ?y '(a b c))
```

你可能同时求：

```text
?x = ()
?y = (a b c)

?x = (a)
?y = (b c)

?x = (a b)
?y = (c)

?x = (a b c)
?y = ()
```

这已经不是：

```text
f(x) -> y
```

而是：

```text
relation(x, y, z)
    ↓
寻找所有满足关系的变量绑定
```

所以必须换一种 evaluation model。

# 1.3 真正的问题是什么？

8B 实际在回答六个问题：

```text
1. 一个 query 如何产生多个结果？

2. 多个 query 如何组合？

3. 一个 rule 如何被“调用”？

4. query 和 rule 两边都有变量怎么办？

5. recursive rules 怎么搜索？

6. declarative semantics
   和 actual execution strategy
   是否真的一致？
```

其中最后一个尤其重要。

# 3. 第一核心机制：Frame — “可能答案”的表示

## ① 直觉

逻辑编程执行过程中，真正流动的不是普通值：

```text
3
"hello"
(a b c)
```

而是：

> **“到目前为止，我们知道变量必须满足哪些绑定？”**

例如：

```text
?x = Alice
?boss = Bob
```

可以表示成：

```text
Frame F1

?x     → Alice
?boss  → Bob
```

frame 本质上是一个 **partial substitution / dictionary**。

Lecture 里也直接把它称为 dictionary，并指出这些 dictionary 是 matcher 临时创建、向后传递的。([OCW ITI](https://ocw.iti.hr/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/8b-logic-programming-part-2/ "8B: Logic Programming, Part 2 | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

---

## ② 一个非常小的例子

数据库：

```scheme
(job Alice programmer)
(job Bob manager)
(job Carol programmer)
```

query：

```scheme
(job ?x programmer)
```

初始状态不是：

```text
?x = ?
```

而是：

```text
{}
```

即 empty frame：

```text
没有任何约束
```

然后查询数据库。

---

## ③ Evaluation Model

先看第一条：

```scheme
(job Alice programmer)
```

query pattern：

```scheme
(job ?x programmer)
```

matcher：

```text
(job ?x programmer)
(job Alice programmer)

job        = job             ✓
?x         ↔ Alice           bind ?x = Alice
programmer = programmer      ✓
```

得到：

```text
Frame F1

?x → Alice
```

第二条：

```scheme
(job Bob manager)
```

失败：

```text
programmer ≠ manager
```

第三条：

```scheme
(job Carol programmer)
```

得到：

```text
Frame F2

?x → Carol
```

所以整个 query 的结果不是一个 frame：

```text
F1
```

而是：

```text
Stream

F1 = {?x → Alice}
F2 = {?x → Carol}
...
```

---

# 4. Stream of Frames：这是整讲最重要的 abstraction

这里你应该把 query mental model 从：

```text
query -> answer
```

换成：

```text
query:
stream<frame>
      ↓
stream<frame>
```

这是关键。

---

## Primitive query

例如：

```scheme
(job ?x programmer)
```

可以理解成：

```text
                  database
                     │
                     ▼
input frames ──→ [ job query ] ──→ output frames
```

输入：

```text
{}
```

输出：

```text
{?x=Alice}
{?x=Carol}
```

如果输入已经有约束：

```text
{?x=Alice}
```

那么查询：

```scheme
(job ?x programmer)
```

只是在问：

```text
Alice 是 programmer 吗？
```

---

# 5. 为什么要用 stream，而不是 list？

因为逻辑查询天然可能出现：

```text
大量答案

甚至无限答案
```

例如递归规则。

如果要求：

```text
先算出所有答案
然后返回 list
```

那么无限查询永远不会返回第一个答案。

而 stream：

```text
answer1
   ↓ delayed
answer2
   ↓ delayed
answer3
   ↓ ...
```

允许：

> **answer-by-answer 地产生结果。**

这里其实把 Lecture 6A/6B 的 streams 又重新利用起来了。

你现在能看到 SICP 前后的连贯性：

```text
Streams
    ↓
不立即计算完整序列
    ↓
可以表示潜在无限 computation
    ↓
Logic evaluator
    ↓
表示潜在无限的 proof/search results
```

# 6. 第二核心机制：AND 是 query pipeline

假设：

```scheme
(and
  (job ?x programmer)
  (supervisor ?x ?boss))
```

数据库：

```scheme
(job Alice programmer)
(job Carol programmer)

(supervisor Alice Bob)
(supervisor Carol Dave)
```

---

## ① 直觉

AND 的意思不是 evaluator 内部做：

```scheme
(and boolean1 boolean2)
```

而是：

> 第一个 query 产生一些“可能解”，第二个 query 在这些解的基础上继续施加约束。

---

## ② 运行过程

开始：

```text
{}
```

第一阶段：

```scheme
(job ?x programmer)
```

产生：

```text
{?x=Alice}
{?x=Carol}
```

然后每个 frame 流进：

```scheme
(supervisor ?x ?boss)
```

---

### 对第一个 frame

```text
?x = Alice
```

query 变成约束：

```scheme
(supervisor Alice ?boss)
```

匹配：

```scheme
(supervisor Alice Bob)
```

得到：

```text
{?x=Alice,
 ?boss=Bob}
```

---

### 对第二个 frame

```text
?x = Carol
```

得到：

```text
{?x=Carol,
 ?boss=Dave}
```

最后：

```text
{}
 ↓
(job ?x programmer)
 ↓
┌──────────────────┐
│ ?x = Alice       │
│ ?x = Carol       │
└──────────────────┘
 ↓
(supervisor ?x ?boss)
 ↓
┌────────────────────────┐
│ ?x=Alice ?boss=Bob     │
│ ?x=Carol ?boss=Dave    │
└────────────────────────┘
```

Lecture 8B 正是用这种“把两个 query 串起来”的图解释 AND：前一个 query 的 frame 输出成为后一个 query 的输入，因此相同变量自然保持一致。([OCW ITI](https://ocw.iti.hr/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/8b-logic-programming-part-2/ "8B: Logic Programming, Part 2 | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

---

# 7. 为什么这个设计很漂亮？—— Closure

这里是 SICP 非常典型的设计思想。

Primitive query：

```text
stream<frame>
    ↓
QUERY
    ↓
stream<frame>
```

而：

```scheme
(and P Q)
```

也是：

```text
stream<frame>
    ↓
AND(P,Q)
    ↓
stream<frame>
```

因此：

```text
Primitive Query
Compound Query
```

具有同样的 interface。

于是你可以：

```scheme
(and
  P
  (or
    Q
    (and R S)))
```

无限组合。

这就是 SICP 一直强调的：

> **closure property**

Lecture 特别指出，AND / OR / NOT 组合出来以后，外部仍然保持同样的“query box”形状，因此复杂 query 可以继续参与更大的组合；并把这一点和早先 pair、picture language 的 closure 联系起来。([OCW ITI](https://ocw.iti.hr/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/8b-logic-programming-part-2/ "8B: Logic Programming, Part 2 | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

---

# 8. OR：branch + merge

假设：

```scheme
(or
  (job ?x programmer)
  (job ?x manager))
```

可以想成：

```text
                    ┌→ programmer query ─┐
input frames ───────┤                    ├→ merge/interleave
                    └→ manager query ────┘
```

两条 branch 都收到原始 frame。

然后把答案合并。

---

## 为什么这里需要 lazy stream？

因为假设第一支：

```text
产生无限答案
```

第二支：

```text
有一个重要答案
```

如果你做：

```text
先完整跑完 branch 1
再 branch 2
```

branch 2 永远没有机会。

所以逻辑搜索非常依赖：

```text
interleave
fair scheduling
delayed evaluation
```

这也是为什么：

> streams 在这里不是“方便的 sequence API”，而是 **control-flow mechanism**。

# 9. NOT：这里开始出现危险

这是 Lecture 8B 最重要的知识点之一。

---

## ① 直觉

SICP query language 里的：

```scheme
(not Q)
```

不是：

```text
证明 Q 是 false
```

而是：

> **在当前 frame 下，如果 Q 找不到任何解，就保留当前 frame。**

也就是说：

```text
NOT 是 filter
```

Lecture 明确把 NOT 描述成过滤器：如果在当前 frame 下能找到匹配，就丢掉 frame；找不到则让 frame 通过。([OCW ITI](https://ocw.iti.hr/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/8b-logic-programming-part-2/ "8B: Logic Programming, Part 2 | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

---

# 10. 一个极重要的例子

数据库：

```scheme
(person Alice)
(person Bob)

(programmer Alice)
```

查询：

```scheme
(and
  (person ?x)
  (not (programmer ?x)))
```

运行：

```text
{}
 ↓
(person ?x)
 ↓
{x=Alice}
{x=Bob}
 ↓
not programmer
```

Alice：

```text
(programmer Alice)
```

可以证明，所以：

```text
discard
```

Bob：

```text
(programmer Bob)
```

找不到，所以：

```text
keep
```

得到：

```text
?x = Bob
```

这个看起来合理。

---

# 11. 但如果把顺序交换呢？

```scheme
(and
  (not (programmer ?x))
  (person ?x))
```

从：

```text
{}
```

开始。

先执行：

```scheme
(not (programmer ?x))
```

它不是：

```text
生成所有 non-programmers
```

它只能：

```text
过滤已有的 ?x
```

但此时：

```text
?x 尚未绑定
```

系统检查：

```scheme
(programmer ?x)
```

数据库里有：

```scheme
(programmer Alice)
```

所以 query 有解。

于是 empty frame 被丢弃。

结果：

```text
empty stream
```

后面的：

```scheme
(person ?x)
```

根本没机会执行。

所以：

```scheme
(and P Q)
```

与：

```scheme
(and Q P)
```

可能产生不同的 behavior。

这已经说明：

> 表面上的 logical AND，不完全等同于数学逻辑里的 ∧。

# 12. Pattern Matching vs Unification

这是 8B 的技术核心。

---

## Pattern Matching

假设：

```text
pattern:
(job ?x programmer)

data:
(job Alice programmer)
```

右边 data 没变量。

所以：

```text
pattern variable
      ↓
match concrete data
```

得到：

```text
?x = Alice
```

这是 asymmetric：

```text
pattern → data
```

---

# 13. 但是 Rule Application 需要更强的东西

假设规则：

```scheme
(rule
  (boss ?z ?division)
  ...)
```

query：

```scheme
(boss ?who computer)
```

现在两边都有变量：

```text
query:
(boss ?who computer)

rule conclusion:
(boss ?z ?division)
```

pattern matcher 不够。

我们需要：

> **Unification**

---

# 14. Unification 的直觉

unification 问的不是：

> “pattern 能不能 match data？”

而是：

> **能不能给两边的变量添加一些约束，使两个 expression 变成同一个东西？**

例如：

```text
(boss ?who computer)

(boss ?z ?division)
```

可以统一成：

```text
?division = computer
?who      = ?z
```

注意：

```text
?who 还没有具体值
```

但它和：

```text
?z
```

被链接起来了。

---

# 15. 一个更清楚的 Unification 例子

统一：

```scheme
(?x ?x)
```

和：

```scheme
((a ?y c)
 (a b ?z))
```

因为两个 `?x` 必须相同，所以：

```text
(a ?y c)
=
(a b ?z)
```

逐元素比较：

```text
a = a

?y = b

c = ?z
```

得到：

```text
?y = b
?z = c
```

因此：

```text
?x = (a b c)
```

最终 frame：

```text
?x → (a b c)
?y → b
?z → c
```

Lecture 就用类似例子说明：unifier 看起来好像在“推理”，但底层实际上只是递归地传播匹配约束。([OCW ITI](https://ocw.iti.hr/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/8b-logic-programming-part-2/ "8B: Logic Programming, Part 2 | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

---

# 16. Pattern Matching vs Unification

||Pattern Matching|Unification|
|---|---|---|
|两边是否可有变量|通常只有 pattern 有|两边都可以|
|对称性|不对称|基本对称|
|作用|pattern 对 concrete datum|让两个 symbolic terms 一致|
|输出|variable bindings|generalized substitution|
|用途|查 assertion|rule application|
|mental model|“这个数据符合模式吗？”|“怎样约束变量才能让两式相同？”|

一句话记：

```text
Pattern matching
    pattern → data

Unification
    expression ↔ expression
```

---

# 17. Unification 的隐藏问题：Occurs Check

考虑：

```text
?x = (a . ?x)
```

这是什么意思？

展开：

```text
?x
=
(a . ?x)

=
(a a . ?x)

=
(a a a . ?x)

...
```

唯一可能是：

```text
?x = 无限个 a
```

也就是固定点：

```text
x = cons(a, x)
```

如果 unifier 傻傻绑定：

```text
x → (a . x)
```

之后继续 lookup：

```text
x
 ↓
(a . x)
 ↓
(a a . x)
 ↓
...
```

可能无限递归。

---

## SICP 怎么办？

检查：

```text
准备把 ?x 绑定到 expression E

E 是否依赖 ?x？
```

如果：

```text
yes
```

reject。

这就是：

> **occurs check / depends-on?**

SICP 的 `unify-match` 正是 pattern matcher 的对称扩展，并用额外检查拒绝变量依赖自身的情况。([SICP Source Academy](https://sicp.sourceacademy.org/chapters/4.4.4.html?utm_source=chatgpt.com "4.4.4   Implementing the Query System - SICP Comparison Edition"))

# 18. 第三核心机制：Rules 是 Logic Language 的 abstraction

普通 Scheme：

```scheme
(define (square x)
  (* x x))
```

是把 computation：

```text
(* x x)
```

命名为：

```text
square
```

---

Logic language：

```scheme
(rule
  (boss ?z ?division)
  (and
    (job ?x (?division . ?rest))
    (supervisor ?x ?z)))
```

是在把一个 relation：

```text
存在 ?x：

?x 在 division 工作
且
?z 是 ?x 的 supervisor
```

命名为：

```text
boss
```

所以：

```text
procedure abstraction
```

和：

```text
rule abstraction
```

是两个不同世界里的同一个结构思想。

# 19. Rule Application 到底怎么运行？

这是 8B 的高潮之一。

假设 query：

```scheme
(boss ?who computer)
```

rule：

```scheme
(rule
  (boss ?z ?d)
  (and
    (job ?x (?d . ?rest))
    (supervisor ?x ?z)))
```

---

## Step 1：rename rule variables

先不能直接用：

```text
?z
?d
?x
```

因为其他 rule application 里可能也有同名变量。

所以生成 fresh variables：

```text
?z-17
?d-17
?x-17
?rest-17
```

rule 变成：

```scheme
(rule
  (boss ?z-17 ?d-17)
  ...)
```

---

# 20. Step 2：unify query 与 rule conclusion

query：

```scheme
(boss ?who computer)
```

rule head：

```scheme
(boss ?z-17 ?d-17)
```

得到：

```text
?who  ↔ ?z-17
?d-17 → computer
```

frame：

```text
F1

?who  → ?z-17
?d-17 → computer
```

---

# 21. Step 3：evaluate rule body under that frame

rule body：

```scheme
(and
  (job ?x-17 (?d-17 . ?rest-17))
  (supervisor ?x-17 ?z-17))
```

由于：

```text
?d-17 = computer
```

相当于：

```scheme
(and
  (job ?x-17 (computer . ?rest-17))
  (supervisor ?x-17 ?z-17))
```

然后进入普通 query evaluator。

---

# 22. Step 4：first conjunct

假设数据库：

```scheme
(job Alice (computer programmer))
(job Carol (computer researcher))
```

得到：

```text
F2

?x-17 = Alice
?rest-17 = (programmer)
```

以及：

```text
F3

?x-17 = Carol
?rest-17 = (researcher)
```

---

# 23. Step 5：second conjunct

假设：

```scheme
(supervisor Alice Bob)
(supervisor Carol Dave)
```

得到：

```text
F2:
?x-17   = Alice
?z-17   = Bob
?who    = ?z-17
```

所以：

```text
?who = Bob
```

另一个：

```text
?who = Dave
```

最终：

```text
(boss Bob computer)
(boss Dave computer)
```

# 24. 现在把整个 evaluation 展开

```text
query:
(boss ?who computer)

        ↓

find candidate rule

        ↓

rename rule variables

?z → ?z-17
?d → ?d-17
?x → ?x-17

        ↓

unify

(boss ?who computer)
(boss ?z-17 ?d-17)

        ↓

frame

?who   ↔ ?z-17
?d-17  = computer

        ↓

evaluate rule body

(and
 (job ?x-17 (computer . ?rest))
 (supervisor ?x-17 ?z-17))

        ↓

evaluate first query

?x-17 = Alice
?x-17 = Carol

        ↓

evaluate second query

Alice → Bob
Carol → Dave

        ↓

propagate bindings

?who = Bob
?who = Dave

        ↓

instantiate original query

(boss Bob computer)
(boss Dave computer)
```

这就是 logic evaluator。

没有魔法。

# 25. Rule Application vs Procedure Application

这是 Lecture 8B 最值得记住的类比。

普通 procedure：

```text
procedure application

arguments
    ↓
bind parameters
    ↓
create environment
    ↓
evaluate body
```

Logic rule：

```text
rule application

query
    ↓
unify with rule conclusion
    ↓
create/extend frame
    ↓
evaluate rule body
```

并排看：

```text
PROCEDURE                      RULE

parameters                     conclusion variables
    │                               │
arguments                       query
    │                               │
bind                            unify
    │                               │
environment                     frame
    │                               │
evaluate procedure body         evaluate rule body
```

Lecture 特别指出两者具有非常强的形式相似性：

> procedure application 是在参数绑定形成的 environment 下 evaluate body；rule application 是在 query 与 rule conclusion unification 形成的 environment/frame 下 evaluate rule body。

因此依然有某种 **EVAL/APPLY cycle**。([OCW ITI](https://ocw.iti.hr/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/8b-logic-programming-part-2/ "8B: Logic Programming, Part 2 | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

这非常 SICP。

# 26. 为什么 SICP 要强调这个？

因为它真正想让你理解的不是：

```text
Scheme evaluator 是 eval/apply
```

而是：

> **复杂语言通常都会有某种“分解 expression / 建立 context / 再解释 body”的循环结构。**

也就是说：

```text
eval/apply
```

不是 Lisp 的偶然。

而是语言实现中的一种结构模式。

# 28. 为什么每次 Rule Application 都要 rename variables？

假设：

```scheme
(rule
  (ancestor ?x ?y)
  ...)
```

递归过程中同一个 rule 被调用两次。

如果第一次：

```text
?x = Alice
```

第二次：

```text
?x = Bob
```

而两次使用同一个 `?x` binding：

```text
Alice = Bob
```

直接冲突。

但这两个 `?x` 根本不是同一个逻辑变量。

就像：

```scheme
(define (f x) ...)
(define (g x) ...)
```

两个 `x` 不应该冲突。

---

# 29. 解决方法：fresh variables

每次 rule application：

```text
?x
```

变成：

```text
?x-101
```

下一次：

```text
?x-102
```

这就是：

> **alpha-renaming**

Lecture 也明确说实现选择了一种“粗暴但简单”的方法：每次应用 rule 时给所有变量生成新的唯一名字，而不是建立更复杂的 environment structure。([OCW ITI](https://ocw.iti.hr/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/8b-logic-programming-part-2/ "8B: Logic Programming, Part 2 | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

# 31. 现在进入 8B 最深的部分：Declarative vs Operational

逻辑上：

```text
P ∧ Q
```

等价于：

```text
Q ∧ P
```

数学上：

```text
P ∧ Q = Q ∧ P
```

但是 evaluator 里：

```scheme
(and P Q)
```

是：

```text
frames
  ↓
P
  ↓
Q
```

所以 operationally：

```text
P 先运行
Q 后运行
```

于是顺序可能改变：

```text
efficiency
termination
甚至结果
```

这就是：

> **declarative semantics 和 operational semantics 之间的裂缝。**

# 32. Recursive Rule：为什么换一下 AND 顺序就可能死循环？

Lecture 使用 `outranked-by` 演示这个问题。([OCW ITI](https://ocw.iti.hr/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/8b-logic-programming-part-2/ "8B: Logic Programming, Part 2 | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

假设：

```scheme
(rule
  (outranked-by ?staff ?boss)
  (or
    (supervisor ?staff ?boss)

    (and
      (supervisor ?staff ?middle)
      (outranked-by ?middle ?boss))))
```

这是合理的：

```text
staff 被 boss 管理

或者

staff 被 middle 管理
且 middle 被 boss 管理
```

---

# 33. Query

```scheme
(outranked-by ?who Ben)
```

evaluation：

```text
尝试：

(supervisor ?who Ben)

或者：

(supervisor ?who ?middle)
    ↓
先给 ?middle 找到具体值
    ↓
(outranked-by ?middle Ben)
```

递归之前：

```text
?middle 已经缩小了搜索空间
```

所以能工作。

# 34. 把 AND 调换

```scheme
(rule
  (outranked-by ?staff ?boss)
  (or
    (supervisor ?staff ?boss)

    (and
      (outranked-by ?middle ?boss)
      (supervisor ?staff ?middle))))
```

逻辑上仍然：

```text
A ∧ B = B ∧ A
```

但 operationally：

```text
(outranked-by ?middle Ben)
```

此时：

```text
?middle 完全没有约束
```

于是：

```text
outranked-by ?middle Ben
    ↓
outranked-by ?middle2 Ben
    ↓
outranked-by ?middle3 Ben
    ↓
...
```

无限递归。

Lecture 明确用这个例子说明，交换 conjunction 的顺序虽然逻辑上应等价，但在实际实现中一个版本正常产生答案，另一个会进入无限循环。([OCW ITI](https://ocw.iti.hr/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/8b-logic-programming-part-2/ "8B: Logic Programming, Part 2 | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

# 40. Closed World Assumption

```text

```

意味着：

```text

```

## Closed World


# 42. NOT 更准确的名字是什么？

更准确：

> **negation as failure**

```text

```

```text

    ↓

    ↓

```

```text

```

# 43. 为什么这会让 query ordering 影响结果？

因为 NOT 是 filter。

假设：

```scheme
(and
  (address ?x ?addr)
  (not (mortal ?x)))
```

第一步先绑定：

```text
?x
```

然后 NOT 检查每个具体 `?x`。

可以工作。

---

但：

```scheme
(and
  (not (mortal ?x))
  (address ?x ?addr))
```

NOT 先面对：

```text
?x unbound
```

它不能：

```text
枚举所有“不 mortal 的东西”
```

所以行为完全不同。

Lecture 的 “perfect being/address” 示例正是用来展示：仅仅交换 query 的顺序，就可能得到不同结果，而原因不是无限循环，而是 NOT 只是 filter。([OCW ITI](https://ocw.iti.hr/courses/electrical-engineering-and-computer-science/6-001-structure-and-interpretation-of-computer-programs-spring-2005/video-lectures/8b-logic-programming-part-2/ "8B: Logic Programming, Part 2 | Video Lectures | Structure and Interpretation of Computer Programs | Electrical Engineering and Computer Science | MIT OpenCourseWare"))

# 47. 几组最容易混淆的概念

## Pattern Matching vs Unification

```text
pattern matching

(job ?x programmer)
(job Alice programmer)

?x = Alice
```

只有一边主要含变量。

而：

```text
unification

(boss ?who computer)
(boss ?z ?d)

?who = ?z
?d = computer
```

双方都可以有变量。

---

## Rule vs Procedure

procedure：

```text
指定 computation
```

rule：

```text
指定 relation
```

Procedure：

```scheme
(define (append x y) ...)
```

天然方向：

```text
x,y → result
```

Relation：

```scheme
(append-to-form ?x ?y ?z)
```

可以：

```text
x,y → z
x,z → y
z → x,y
```

这就是 logic programming 最大的 conceptual jump：

> computation 从 function 提升为 relation。

---

## Frame vs Environment

```text
environment:
program variable → value

frame:
logic variable → term/substitution
```

结构相似，但语义不同。

---

## Logical NOT vs Query NOT

```text
logical NOT:
证明 ¬P

query NOT:
无法找到 P 的 proof
```

这两个一定不能混。

---

## Declarative Meaning vs Operational Behavior

Declarative：

```text
what is true?
```

Operational：

```text
how evaluator searches?
```

SICP 希望你永远区分这两层。

```text
β = String
```

这和本讲 unification 的 mental model 是一样的：

```text
找 substitution
使两个 symbolic structures 相等
```

# 53. 这一讲最重要的设计模式：Relation Transformer

下一次看到类似代码，尝试识别：

```text
State of partial knowledge
        ↓
computation adds constraints
        ↓
0 / 1 / N new states
```

抽象模板：

```text
Query :
Stream<State>
    →
Stream<State>
```

然后：

```text
AND:
compose transformers

OR:
branch + merge transformers

NOT:
filter states

RULE:
build reusable transformer
```

这是非常通用的 pattern。

现代很多系统都类似：

```text
parser combinator
nondeterministic computation
constraint solver
database execution engine
symbolic execution
search monad
```

# 54. 为什么这和 Parser Combinator 很像？

Parser：

```text
Parser<A> :
Input
→
0 / 1 / many
(value, remaining-input)
```

Logic query：

```text
Query :
Frame
→
0 / 1 / many
extended-frame
```

然后都有：

```text
sequence
choice
failure
```

例如：

```text
AND ≈ sequence

OR ≈ choice

failed match ≈ parser failure
```

背后的抽象结构非常接近。

表面语法：


让你以为：

```text

```

```text
P's frame stream
   ↓
```

于是：

```text
order matters
```

表面：


让你以为：

```text
logical negation
```

# 64. 我建议你真正记住的 9 个东西

## 5 个核心思想

1. **Logic Programming 把 function-oriented computation 提升成 relation-oriented computation。**
    
    ```text
    f(x) → y
    
    变成
    
    relation(x,y)
    ```
    
2. **Query evaluator 操作的基本对象不是 value，而是 frame。**
    
    ```text
    frame = partial variable bindings
    ```
    
3. **每个 query 都可以看成 stream-of-frames transformer。**
    
    ```text
    Stream<Frame>
        →
    Stream<Frame>
    ```
    
4. **Rule application 和 procedure application 有同构结构。**
    
    ```text
    bind params ↔ unify conclusion
    environment ↔ frame
    evaluate body ↔ qeval body
    ```
    
5. **Declarative meaning 与 operational behavior 必须区分。**

## 4 个关键机制

```text
pattern matching

unification

lazy streams

fresh-variable renaming
```

# 65. 三个最重要的不变量 / mental models

## Invariant 1

任何时刻一个 frame 都表示：

> 到目前为止所有已经成立的变量约束。

新增 binding 必须和已有 binding **consistent**。

---

## Invariant 2

每个 query：

```text
不破坏 query interface
```

始终是：

```text
frames in
    ↓
frames out
```

所以才能 closure/composition。

---

## Invariant 3

`not`：

```text
不创造 bindings
```

只：

```text
filter existing frames
```

只要记住这一条，很多 query ordering 问题都会立即看懂。

# 66. 如果你以后看到一段 Logic Programming 代码，怎么读？

不要先问：

> “它输出什么？”

```text
1. 当前有哪些 frames？

2. 当前 query 会：
   generate bindings
   还是 filter bindings？

3. 哪些 variables 已经 bound？

4. pattern match 还是 unification？

5. 是否在 apply rule？

8. search space 会不会无限？

10. 换一下 clause 顺序，behavior 会不会变？
```

如果这十个问题能回答，你基本真正理解 8B 了。

# 67. 给你 5 道真正需要思考的题

先不要看答案，建议你实际拿纸画 frame。

## 题 1：手动推演 Frame Stream

数据库：

```scheme
(job Alice programmer)
(job Bob programmer)
(job Carol manager)

(supervisor Alice Carol)
(supervisor Bob Dave)
```

query：

```scheme
(and
  (job ?x programmer)
  (supervisor ?x ?boss))
```

请画：

```text
{}
 ↓
第一 query 后的 frame stream
 ↓
第二 query 后的 frame stream
```

并说明：

> 为什么第二个 query 里的 `?x` 一定和第一个 query 的 `?x` 是同一个人？

---

## 题 2：Unification

求下面两个 expression 的最一般 unifier：

```scheme
(parent ?x (child ?y ?x))
```

和：

```scheme
(parent Alice (child Bob ?z))
```

请一步一步写：

```text
?x = ?
?y = ?
?z = ?
```

不要直接给最终答案。

---

## 题 3：Occurs Check

尝试 unify：

```scheme
?x
```

和：

```scheme
(a ?x)
```

回答：

> 如果允许这个 binding，`?x` 最终表示什么？

然后解释：

> 为什么 naïve unifier 可能无限递归？

---

## 题 4：Query Order

数据库：

```scheme
(person Alice)
(person Bob)

(programmer Alice)
```

比较：

```scheme
(and
  (person ?x)
  (not (programmer ?x)))
```

与：

```scheme
(and
  (not (programmer ?x))
  (person ?x))
```

请分别手动画 frame。

重点回答：

> 为什么从数学逻辑上似乎相同的两个 query，在这个 evaluator 中表现不同？

---

## 题 5：Rule vs Procedure

考虑：

```scheme
(rule
  (append-to-form () ?y ?y))

(rule
  (append-to-form (?u . ?v) ?y (?u . ?z))
  (append-to-form ?v ?y ?z))
```

不要先跑程序。

解释为什么同一个 relation 有可能支持：

```text
给 x,y 求 z

给 x,z 求 y

给 z 求所有 x,y
```

然后回答：

> 普通 Scheme 的 `append` 为什么通常不能自然地做到这一点？
