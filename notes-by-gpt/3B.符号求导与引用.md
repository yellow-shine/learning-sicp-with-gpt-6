# 1. 这节课到底想解决什么问题？

先暂时忘掉“求导”。

这一讲真正的问题是：

> **如果我不想让计算机立刻计算一个表达式，而是希望把“表达式本身”交给程序处理，该怎么办？**

这是一个非常大的转折。

前几讲你基本上一直在做：

```text
expression
    ↓
evaluate
    ↓
value
```

例如：

```scheme
(+ 1 2)
```

Scheme 看到它以后：

```text
+
↓
找到加法 procedure

1
↓
1

2
↓
2

apply +
↓
3
```

程序关心的是：

```text
(+ 1 2) 的值是什么？
```

但现在考虑另一个问题。

假设我有：

$$
x^2 + 3x + 2
$$

我不想给 `x=10` 然后算出结果。

我想问：

> “这个表达式关于 x 的导数是什么？”

也就是：

```text
x² + 3x + 2
        ↓
程序检查这个表达式的结构
        ↓
发现：
这是一个加法
里面有乘法
里面有变量 x
        ↓
根据求导规则重写
        ↓
2x + 3
```

这里程序处理的对象已经发生变化了。

以前：

```text
data = number
computation = procedure
```

现在：

```text
data = representation of computation / expression
```

也就是说：

> **expression 本身成为 data。**

这就是 Lecture 3B 最关键的一跃。

---

## 为什么前面的机制不够？

因为正常 Scheme evaluation 会自动解释表达式。

假设你写：

```scheme
(+ x 3)
```

Scheme 不会把它理解成：

```text
“一个加法表达式”
```

它会理解成：

```text
evaluate +
evaluate x
evaluate 3
apply +
```

所以假如 `x` 没绑定：

```scheme
(+ x 3)
```

会报错。

可是 symbolic differentiation 希望拿到的是：

```text
(+ x 3)
```

这个**结构本身**。

我们想检查：

```text
operator = +
left operand = x
right operand = 3
```

所以必须拥有一种机制：

> **不要 evaluate 这个 expression，把它作为 data 给我。**

这就是 **quotation**。

# 3. 第一个核心机制：Symbol

## ① 直觉

以前你看到：

```scheme
x
```

含义是：

> 去 environment 里面找变量 `x` 的值。

比如：

```scheme
(define x 10)

(+ x 3)
```

这里：

```text
x
↓
lookup environment
↓
10
```

但有时候我们不想要 `x` 的值。

我们想要：

```text
the symbol x
```

也就是一个名字本身。

于是：

```scheme
'x
```

表示：

```text
symbol x
```

而不是：

```text
变量 x 所绑定的 value
```

这是非常重要的区别。

---

## ② 一个小例子

```scheme
(define x 10)
```

现在：

```scheme
x
```

结果：

```scheme
10
```

但是：

```scheme
'x
```

结果：

```scheme
x
```

注意：

```text
x
```

和

```text
'x
```

不是同一个语义。

前者：

```text
variable reference
↓
environment lookup
```

后者：

```text
symbol literal
```

# 4. Quote：暂停正常 evaluation

Quote 的完整形式是：

```scheme
(quote x)
```

缩写是：

```scheme
'x
```

所以：

```scheme
'x
```

等价于：

```scheme
(quote x)
```

而：

```scheme
'(+ x 3)
```

等价于：

```scheme
(quote (+ x 3))
```

---

## 正常 evaluation

考虑：

```scheme
(+ x 3)
```

Scheme 的 applicative-order evaluation：

```text
expression
(+ x 3)

↓ evaluate operator

+
↓
addition procedure

↓ evaluate operands

x
↓
lookup environment

3
↓
3

↓ apply procedure

+
```

---

## quote evaluation

而：

```scheme
'(+ x 3)
```

也就是：

```scheme
(quote (+ x 3))
```

发生的是：

```text
see special form: quote
        ↓
DO NOT evaluate operand
        ↓
return represented data structure
        ↓
(+ x 3)
```

这一点极其重要：

> **quote 改变了通常的 evaluation rule。**

# 5. 为什么 `quote` 必须是 special form？

这是非常好的 SICP 问题。

为什么不能定义：

```scheme
(define (quote x)
  ...)
```

？

因为普通 procedure application 有一条基本规则：

```text
evaluate operator
evaluate operands
apply procedure
```

所以：

```scheme
(quote (+ x 3))
```

如果 `quote` 是普通 procedure：

```text
先 evaluate (+ x 3)
```

那就已经太晚了。

我们正是想阻止它被 evaluate。

所以 `quote` 必须改变 evaluation rule：

```text
ordinary procedure:

(f arg)
   ↓
evaluate arg
   ↓
call f


quote:

(quote arg)
   ↓
DO NOT evaluate arg
   ↓
return arg as data
```

这也是 SICP 开始让你意识到：

> **语言中的所有东西并不都遵循普通 procedure-call evaluation。**

`if` 也是如此。

```scheme
(if condition
    consequent
    alternative)
```

不能先把两个 branch 全 evaluate。

所以：

```text
if
quote
lambda
define
cond
```

本质上都在触碰：

> **language semantics**

而不仅仅是 library function。

# 6. Quote 开启了一扇非常大的门

有了 quote：

```scheme
'(+ x 3)
```

程序现在得到的不是 `x + 3` 的结果。

它得到：

```text
a representation of:

    +
   / \
  x   3
```

也就是我们今天经常叫：

> **AST — Abstract Syntax Tree**

虽然这一讲未必一直使用 AST 这个现代术语，但 mental model 完全可以这样理解。

# 9. 第二个核心机制：Symbolic Differentiation

现在终于来看求导。

假设我们只支持：

```text
constant
variable
sum
product
```

数学规则非常简单。

---

## Constant Rule

$$
\frac{d c}{dx}=0
$$

例如：

```text
d(5)/dx = 0
```

---

## Variable Rule

$$
\frac{dx}{dx}=1
$$

但：

$$
\frac{dy}{dx}=0
$$

---

## Sum Rule

$$
D(u+v)=D(u)+D(v)
$$

---

## Product Rule

$$
D(uv)=uD(v)+D(u)v
$$

现在关键来了。

这些数学规则几乎可以**直接翻译成程序结构**。

---

# 10. `deriv` 的核心程序

典型 SICP 写法大致是：

```scheme
(define (deriv exp var)
  (cond ((number? exp)
         0)

        ((variable? exp)
         (if (same-variable? exp var)
             1
             0))

        ((sum? exp)
         (make-sum
          (deriv (addend exp) var)
          (deriv (augend exp) var)))

        ((product? exp)
         (make-sum
          (make-product
           (multiplier exp)
           (deriv (multiplicand exp) var))

          (make-product
           (deriv (multiplier exp) var)
           (multiplicand exp))))

        (else
         (error "unknown expression type"))))
```

先不要逐行看。

先看它的**形状**。

```text
deriv(expression)
        ↓
what kind of expression?
        ↓
constant?
variable?
sum?
product?
        ↓
decompose expression
        ↓
recursively derive children
        ↓
construct new expression
```

这其实就是：

```text
recursive tree traversal
+
tree rewriting
```

# 11. 这里真正重要的是 structural recursion

你之前的 recursion 往往是：

```scheme
(f n)
```

然后：

```text
n
↓
n-1
↓
n-2
↓
...
```

例如 factorial：

```text
fact(5)
↓
fact(4)
↓
fact(3)
```

而现在 recursion 的依据不再是数字大小。

而是：

> **数据结构本身。**

比如：

```scheme
'(* (+ x 3) y)
```

树：

```text
        *
       / \
      +   y
     / \
    x   3
```

`deriv` 就沿树下降。

# 12. 手动推演：`d(x + 3)/dx`

调用：

```scheme
(deriv '(+ x 3) 'x)
```

先看最外面的完整 evaluation。

```text
(deriv '(+ x 3) 'x)

↓ evaluate operator

deriv
↓
procedure object

↓ evaluate operand 1

'(+ x 3)
↓
quote suppresses evaluation
↓
list representing (+ x 3)

↓ evaluate operand 2

'x
↓
symbol x

↓ apply deriv

exp = '(+ x 3)
var = 'x
```

进入 body。

---

## Step 1

```scheme
(number? exp)
```

false。

---

## Step 2

```scheme
(variable? exp)
```

false。

因为整个 expression 是一个 list。

---

## Step 3

```scheme
(sum? exp)
```

true。

因此：

```scheme
(make-sum
 (deriv (addend exp) var)
 (deriv (augend exp) var))
```

假设：

```text
addend = x
augend = 3
```

于是：

```text
deriv(x, x)
+
deriv(3, x)
```

---

## 左边

```text
deriv(x, x)
```

`x` 是 variable。

而：

```text
same-variable?(x,x)
= true
```

因此：

```text
1
```

---

## 右边

```text
deriv(3,x)
```

3 是 number。

所以：

```text
0
```

于是：

```text
make-sum(1,0)
```

如果 `make-sum` 会 simplification：

```text
1 + 0
↓
1
```

结果：

```scheme
1
```

# 13. 再看一个真正能体现递归结构的例子

```scheme
(deriv '(* x x) 'x)
```

数学上：

$$
D(x x) = xD(x)+D(x)x
$$

程序执行：

```text
deriv((* x x), x)

↓ product?

yes

↓ product rule

make-sum(
    make-product(
        x,
        deriv(x,x)
    ),

    make-product(
        deriv(x,x),
        x
    )
)
```

然后：

```text
deriv(x,x)
↓
1
```

因此：

```text
make-sum(
    make-product(x,1),
    make-product(1,x)
)
```

如果 constructor 会 simplification：

```text
x * 1
↓
x

1 * x
↓
x
```

得到：

```text
x + x
```

这套简单 constructor 尚未必自动化成 `2*x`。

所以最终可能是：

```scheme
(+ x x)
```

而不是：

```scheme
(* 2 x)
```

这是很重要的。

> **Symbolic differentiation 和 algebraic simplification 是两个不同的问题。**

# 14. 第三个核心机制：Data Abstraction

现在来看这一讲真正漂亮的地方。

你可能觉得：

> “不就是用 car/cdr 拆 list 吗？”

SICP 故意不希望 `deriv` 写成：

```scheme
(car exp)
(cadr exp)
(caddr exp)
```

到处乱飞。

而是希望：

```scheme
(sum? exp)
(addend exp)
(augend exp)

(product? exp)
(multiplier exp)
(multiplicand exp)

(make-sum ...)
(make-product ...)
```

也就是说：

```text
deriv
────────────────────────
abstraction barrier
────────────────────────
representation
car / cdr / list / symbols
```

这是 Lecture 2B 的 data abstraction 在这里的真正应用。

---

# 15. 为什么这件事重要？

假设最开始我们规定：

```scheme
(+ x y)
```

代表 sum。

于是：

```scheme
(define (sum? x)
  (and (pair? x)
       (eq? (car x) '+)))

(define (addend s)
  (cadr s))

(define (augend s)
  (caddr s))
```

但是后来你说：

> 我不喜欢 prefix notation。

我想表示为：

```scheme
(x + y)
```

理论上只要改：

```text
sum?
addend
augend
make-sum
```

`deriv` 就不应该改变。

这就是 representation independence。

# 16. 这里有两个 abstraction layer

这是这一讲必须看清楚的。

```text
                    Algebra
                       │
                       │
                     deriv
                       │
       ┌───────────────┴────────────────┐
       │                                │
    sum?                             product?
 addend/augend              multiplier/multiplicand
 make-sum                        make-product
       │                                │
       └──────── abstraction barrier ───┘
                       │
                 list / pair
                       │

```

`deriv` 所处的世界应该是：

```text

sum
product
```

而不是：

```text
car
cdr
cadr
caddr
```

这是两种不同的语言层次。

# 18. 第四个核心机制：Smart Constructor

最朴素的：

```scheme
(define (make-sum a1 a2)
  (list '+ a1 a2))
```

那么：

```scheme
(deriv '(+ x 3) 'x)
```

会得到：

```scheme
(+ 1 0)
```

这是数学上对的。

但很丑。

于是：

```scheme
(define (make-sum a1 a2)
  (cond ((=number? a1 0) a2)
        ((=number? a2 0) a1)
        ((and (number? a1)
              (number? a2))
         (+ a1 a2))
        (else
         (list '+ a1 a2))))
```

同样：

```scheme
(define (make-product m1 m2)
  (cond ((or (=number? m1 0)
             (=number? m2 0))
         0)

        ((=number? m1 1)
         m2)

        ((=number? m2 1)
         m1)

        ((and (number? m1)
              (number? m2))
         (* m1 m2))

        (else
         (list '* m1 m2))))
```

这里出现了一个非常现代的设计思想：

> **把 representation invariant 放进 constructor。**

---

# 19. 为什么不在 `deriv` 里 simplification？

你当然可以写：

```scheme
(if (= result 0)
    ...
    ...)
```

然后让 `deriv` 到处知道：

```text
0+x=x
1*x=x
0*x=0
```

结果就是：

```text
deriv
├── differentiation logic
├── representation logic
├── simplification logic
├── constant folding logic
└── normalization logic
```

整个 abstraction 会崩掉。

而 smart constructor：

```text
deriv
↓
“我要构造一个 sum”
↓
make-sum
↓
constructor 负责保持 expression 合理
```

于是：

```scheme
(make-sum x 0)
```

保证返回：

```scheme
x
```

而不是：

```scheme
(+ x 0)
```

这就是一个 invariant：

> **经过 constructor 创建的 expression 满足 constructor 所承诺的 canonicalization rules。**

这和你今天看到的：

```text
smart constructor
factory
validated constructor
AST builder
normalization pass
```

完全是一脉相承的。

# 20. 一个特别值得掌握的 evaluation

考虑：

```scheme
(deriv '(* x (+ x 3)) 'x)
```

Expression Tree：

```text
           *
         /   \
        x     +
             / \
            x   3
```

第一步：

```text
deriv(product,x)
```

应用 product rule：

```text
u = x
v = (+ x 3)

D(uv)
=
uD(v) + D(u)v
```

程序结构：

```text
make-sum
├── make-product
│   ├── x
│   └── deriv((+ x 3),x)
│
└── make-product
    ├── deriv(x,x)
    └── (+ x 3)
```

继续展开。

左边：

```text
deriv((+ x 3),x)
↓
make-sum(
    deriv(x,x),
    deriv(3,x)
)
↓
make-sum(1,0)
↓
1
```

右边：

```text
deriv(x,x)
↓
1
```

于是：

```text
make-sum(
  make-product(x,1),
  make-product(1,(+ x 3))
)
```

smart constructors：

```text
make-product(x,1)
↓
x

make-product(1,(+ x 3))
↓
(+ x 3)
```

最终：

```scheme
(+ x (+ x 3))
```

注意它没有自动变成：

```text
2x+3
```

因为：

```text
x + x → 2x
```

属于更高级的 algebraic normalization。

这为下一讲的：

```text
pattern matching
rule-based rewriting
```

埋下了非常明显的伏笔。

# 21. Quote vs List：非常容易混淆

这是我建议你务必弄清楚的一组。

假设：

```scheme
(define x 10)
```

看：

```scheme
'(+ x 3)
```

结果是：

```scheme
(+ x 3)
```

这里 `x` 没有被 evaluation。

而：

```scheme
(list '+ x 3)
```

会发生：

```text
'+
↓
symbol +

x
↓
10

3
↓
3
```

结果：

```scheme
(+ 10 3)
```

注意这个 list 本身仍然不会再次自动 evaluate。

它只是 data：

```text
(+ 10 3)
```

而不是数值：

```text
13
```

这件事非常重要。

---

## 三种东西

```scheme
(+ x 3)
```

表示：

```text
execute addition
```

```scheme
'(+ x 3)
```

表示：

```text
literal data representing (+ x 3)
```

```scheme
(list '+ x 3)
```

表示：

```text
evaluate pieces
then dynamically construct data
```

如果：

```scheme
x = 10
```

那么：

```text

'(+ x 3)        → (+ x 3)

(list '+ x 3)   → (+ 10 3)
```

这是这一讲最值得自己在 REPL 里试一次的例子之一。

# 22. Code vs Data

现在我们接近 Lisp 最著名的思想之一：

```text

↓
represented with lists
↑
data
```


作为 code 时：

```text

```

作为 quoted data 时：



也就是说，同一种 list-like structure 可以处于两个角色：


> Lisp 的程序语法和它天然擅长处理的数据结构高度统一。

# 23. Quote vs Evaluation 的核心 mental model

> **跨过“program → value”这一步，停下来拿到 program representation。**

# 24. Substitution Model 在这里发生了什么？

考虑：

```scheme
(deriv '(* x x) 'x)
```

按照 procedure application：

```text
evaluate deriv
↓
procedure

evaluate '(* x x)
↓
(* x x) as DATA

evaluate 'x
↓
symbol x

apply deriv
```

概念上：

```text
deriv body

exp = representation of (* x x)
var = symbol x
```

于是：

```scheme
(number? exp)
```

检查的是整个 symbolic structure。

不是去 evaluate：

```scheme
(* x x)
```

这是非常关键的。

# 25. Environment Model 在这里该怎么看？

严格来说，此时经典 SICP 录像还没有把 environment model 当作这一讲的核心；处理这里的大部分纯 procedure，用 substitution-style reasoning 已经够了。

不过从你希望建立的长期 mental model 来看，可以提前这样理解：

```text
Global Environment

deriv → procedure
x     → maybe some unrelated value
```

调用：

```scheme
(deriv '(* x x) 'x)
```

建立 procedure application frame：

```text
Frame E1

var → symbol x
parent → Global
```

注意：

```text
exp 里的 symbol x
```

并不会因为 Global Environment 有：

```text

```

就变成 100。

因为它现在是：

```text
data inside exp
```

不是：

```text

```

这是极其重要的区分。

# 30. `deriv` 为什么设计得这么漂亮？

因为 mathematical rule 和 program structure 几乎同构。

数学：

$$
D(u+v)=D(u)+D(v)
$$

Scheme：

```scheme
(make-sum
 (deriv (addend exp) var)
 (deriv (augend exp) var))
```

数学：

$$
D(uv)=uD(v)+D(u)v
$$

Scheme：

```scheme
(make-sum
 (make-product
  (multiplier exp)
  (deriv (multiplicand exp) var))

 (make-product
  (deriv (multiplier exp) var)
  (multiplicand exp)))
```

这体现了 SICP 一个很深的审美：

> **一个好的 representation，可以让 domain rules 直接显现在程序结构中。**

换句话说：

```text
数学结构
≈
数据结构
≈
程序结构
```

当这三者匹配得好时，代码会异常清晰。

# 31. 这其实是“解释器模式”的萌芽

你以后写 evaluator，会看到：

```scheme

```

结构很像：

```scheme

```

`deriv`：

```text

↓
determine its type
↓
recursively process subexpressions
↓
produce result
```

Evaluator：

```text
inspect expression
↓

↓

↓

```

比较：

```text

    ↓

```

而 evaluator：

```text

    ↓
syntax → value
```

这是非常重要的联系。

# 34. 为什么下一讲自然就是 Pattern Matching？

现在我们碰到一个问题。

我们的 differentiator 写成：

```scheme
(cond
  ((number? exp) ...)
  ((variable? exp) ...)
  ((sum? exp) ...)
  ((product? exp) ...))
```

等于手动写：

```text
if expression looks like A
    rewrite into B

if expression looks like C
    rewrite into D
```

这实际上已经是一套：

```text
pattern
↓
match
↓
rewrite
```

例如求导：

```text
Pattern:

D(u + v)

Rewrite:

D(u) + D(v)
```

或者：

```text
Pattern:

D(u * v)

Rewrite:

u * D(v) + D(u) * v
```

于是一个自然的问题出现：

> 我能不能把这些规则本身作为 data？

例如：

```text
(D (? u) + (? v))
   →
(+ (D ?u) (D ?v))
```

这就是下一讲 rule-based system 要走的方向。

因此课程结构不是随机的。

# 35. Process Shape

这节课虽然不是 factorial 那种 recursion lesson，但仍然有非常清楚的 process shape。

`deriv` 是：

> **recursive procedure producing a recursive tree-walking process。**

例如：

```text
             deriv(*)
             /      \
       deriv(+)      deriv(y)
       /    \
 deriv(x)  deriv(3)
```

所以它不是：

```text
linear recursion
```

而是：

```text
structural tree recursion
```

---

## Space

如果 expression tree 的高度是 `h`：

```text
maximum recursion depth ≈ O(h)
```

对于严重倾斜的 expression：

```text
(+ x
   (+ x
      (+ x
         ...)))
```

可以：

```text
h = O(n)
```

对于 balanced tree：

```text
h = O(log n)
```

---

## Time

只考虑“访问输入 expression node”：

```text
O(n)
```

其中 `n` 是 expression tree 中的节点数。

但 symbolic transformation 要注意另一件事：

> **最终成本不仅取决于输入，还取决于生成出的 symbolic expression 大小。**

例如 product rule 会创建新的结构。因此复杂 symbolic rewriting 中，经常真正需要考虑：

```text
input tree size
+
generated tree size
```

而不只是普通的：

```text
n
```

这一讲主要不是复杂度课，所以 mental model 比精确渐进式更重要。

# 36. 这里为什么不是 iterative process？

看 product：

```scheme
(make-sum
 (make-product
  u
  (deriv v x))

 (make-product
  (deriv u x)
  v))
```

调用：

```scheme
(deriv v x)
```

回来以后还要继续：

```text
make-product
make-sum
```

因此 parent operation 尚未完成。

call stack 需要记住：

```text
我现在正在处理 product
等 child derivative 回来以后
还需要组合结果
```

所以它是典型 recursive process。

这和：

```scheme
(fact-iter product counter)
```

完全不同。

# 37. 这节课的重要 Pattern：Structural Recursion

以后你看到：


应该立刻意识到：

> **这是针对 recursive data structure 的 structural recursion。**


# 48. 这一讲真正要记住的 8 件事

### 核心思想

**1. 表达式本身也可以成为数据。**

```text
computation
→
representation of computation
```

---

**2. Quote 的本质是改变 evaluation。**

```text
normal:
expression → value

quote:
expression → representation
```

---

**3. Symbolic computation 本质是 tree transformation。**

```text
syntax tree
↓
recursive traversal
↓
new syntax tree
```

---

**4. Representation 应该藏在 abstraction barrier 后面。**

`deriv` 应该认识：

```text

```

而不是：

```text
car / cdr / list layout
```

---

### 关键机制

**5. Predicate / Selector / Constructor 是数据抽象的三个核心角色。**

```text
what is it?
what is inside?
how do I make one?
```

---

**6. Smart constructor 可以维护 representation invariant。**

例如：

```text
x + 0 → x
x * 1 → x
x * 0 → 0
```

---

**7. `deriv` 是 structural recursion。**

递归规模由：

```text
expression structure
```

决定，而不是某个整数 `n`。

---

**8. Evaluator 和 Transformer 是两种不同操作。**

```text
eval:
syntax → value

deriv/rewrite:
syntax → syntax
```

这一点对后面理解 interpreter 非常重要。

```text
    ↓
program can manipulate program
    ↓
we can build interpreters
    ↓
we can design languages
```
